Tuesday, 08:41

Every night at 02:30 a scheduled query computes each customer’s poor-audio rate over the trailing 7 days; at 08:00 the SLA report emails out. Tuesday’s report told Acme 0.4%. At 08:41 Acme’s IT admin replies: Monday was their worst day in months — a regional network incident — and ClearMeet’s own dashboard agrees, showing 3.1%.
  • Monday’s samples load nightly; Tuesday’s load ran long and committed at 02:47 instead of the usual ~02:10.
  • The 02:30 report query ran on time — against a table whose newest rows were Sunday’s. No error: the table was complete and consistent, it just didn’t include Monday yet.
  • Acme’s trailing-7-day rate without its worst day: 0.4%. With Monday, as the dashboard later showed: 3.1%.
Illustrative measurement.
Nothing failed and no query was wrong. The order — load first, then report — was an assumption, written down nowhere and enforced by nothing.
Speaker notes — Tuesday, 08:41
  • Be precise about the mechanism, because this room knows the architecture module: the load commit is atomic, so the query did not read a half-loaded table. It read a consistent table that simply ended at Sunday. Stale, not corrupt.
  • Monday’s incident is why the delta is big and why Acme noticed. All numbers illustrative and re-derivable: six quiet days at ~0.4% plus one day at ~19% averages to ~3.1%.

Five words, five stages

Five terms carry the rest of this module. They sound interchangeable and are not — they are the successive stages between a file you edit and a job that runs in BigQuery.
TermWhat it isWhen it exists
definition (action)one .sqlx file = one table, view, assertion, or operationyou wrote it
compilation resultthe whole repo turned into SQL, once, with settings frozen incompile time
release configurationa recipe that makes compilation results from a git commitish, on a scheduleyou configured it
workflow configurationa schedule that runs a release configuration’s outputyou configured it
workflow invocationone actual run in BigQueryrun time
A definition compiles into a compilation result; a release configuration decides which code and which settings; a workflow configuration decides when and which actions; a workflow invocation is the run that shows up in your BigQuery job history.
Speaker notes — Five words, five stages
  • Source material uses these terms loosely and it is the most confusing thing in the product. Fixing it here pays for itself in section 4, where the full lifecycle diagram returns to this table.
  • The book analogy if the room wants one: drafts (sqlx) → final manuscript (compilation result) → the print edition with its settings (release config) → the publication schedule (workflow config) → someone actually reading it (invocation). Use it after the table, not instead of it.
  • “Action” and “definition” are used interchangeably by the docs and UI. This deck says action when talking about execution and definition when talking about the file.

Anatomy of a .sqlx file

ClearMeet’s first definition: the cleaned QoS table, clearmeet_silver.qos_events_clean.
qos_events_clean.sqlxconfig {
  type: "table",
  description:
    "QoS samples, device names normalized.",
}

SELECT
  event_time, meeting_id, org_id, region,
  LOWER(device) AS device,
  audio_mos
FROM ${ref("qos_events_raw")}
  • config { } — what to build, plus documentation and tests. type: is one of table, view, incremental, assertion, operations, declaration.
  • SQL body — the only required part; a bare SELECT, no DDL. Dataform adds the CREATE… wrapper at compile time.
  • js { }, pre_operations { }, post_operations { } — optional, covered later.
Comments differ by block: // inside config/js, -- in the SQL body. # does not work anywhere in sqlx, even though BigQuery accepts it.
Speaker notes — Anatomy of a .sqlx file
  • The file name sets the table name; name: in config overrides it. Ask the room to predict the full table name before revealing: defaultDataset + filename → clearmeet_silver.qos_events_clean.
  • The #-comment gotcha costs people ten minutes the first time — worth saying once out loud.
  • The other table types, parked here: type: "view" swaps the wrapper for CREATE OR REPLACE VIEW; materialized: true on a view makes it a BigQuery materialized view with exactly the behavior taught in Storage Optimization — Dataform only issues the DDL. bigquery.additionalOptions covers any option Dataform doesn’t expose directly (expiration_timestamp, max_staleness); quoting rule: numeric_option: "5", string_option: '"text"'.
  • LOWER(device) is a placeholder fix here; section 5 replaces it with the real normalization function, so students see the same file evolve.

Declare what you don’t own

qos_events_raw lives in the raw dataset of the ingestion project, written by the module-3 pipeline. Dataform must read it, and must never build it.
sources/qos_events_raw.sqlxconfig {
  type: "declaration",
  database: "clearmeet-ingest-prod",
  schema: "raw",
  name: "qos_events_raw",
  description: "10-second QoS samples.",
}
  • A declaration is a read-only pointer to a table Dataform did not create.
  • It produces no SQL and modifies nothing — it only gives you a name to ref().
  • Declarations can be a dependency, never a dependent.
  • raw is the bronze layer: rows exactly as ingestion landed them — duplicates, bad device strings and all. Layer-per-dataset (raw → clearmeet_silver → clearmeet_analytics) is formalized in section 5.
Declare every external input. It costs one file and it means the graph shows where your data actually comes from — including the boundary where your ownership starts.
Speaker notes — Declare what you don’t own
  • On naming, real-world practice: most BigQuery shops encode the layer as a dataset per layer (raw/staging/marts, or bronze/silver/gold), because IAM grants, labels, and expiration all attach at dataset level — access control per layer comes free. Filename prefixes (stg_…) are the other convention, and the one the structure-repositories doc shows. This deck uses dataset-per-layer.
  • Common mistake: skipping the declaration and hard-coding the full table name in the FROM clause. It works, and it silently drops the node from the graph — which is exactly Tuesday’s failure mode.
  • database = GCP project, schema = BigQuery dataset. Naming inherited from Dataform’s pre-Google, multi-warehouse life; say it once so it stops being odd.

Speaker notes — ref(): what actually happens at compile time
  • Delivery beat: reveal the substitution (which everyone expects), ask “and what else?”, then reveal the edge.

Incremental tables: the mechanism

qos_events_clean holds 90 days ≈ 450 billion rows. A nightly type: "table" rebuild re-writes all 450 billion — to add the 5 billion that are new.
config {
  type: "incremental",
  bigquery: { partitionBy: "DATE(event_time)" },
}

SELECT event_time, meeting_id, org_id,
       LOWER(device) AS device, audio_mos
FROM ${ref("qos_events_raw")}
${when(incremental(),
  `WHERE event_time > (
     SELECT MAX(event_time) FROM ${self()})`)}
  • First run (no table yet) and full refresh: the when() clause contributes nothing, and the table is built from scratch with CREATE OR REPLACE.
  • Every run after: the same body compiles into an INSERT of only the rows passing the incremental WHERE.
  • ${self()} is this table’s own name: the subquery reads the current high-water mark, so “new” is defined by the data already in the table, not by the clock.
The when(incremental(), …) clause is the whole difference. On an incremental run Dataform applies it; on a full refresh it ignores it and rebuilds with CREATE OR REPLACE.
Speaker notes — Incremental tables: the mechanism
  • Correction to older material (including the Google ILT source deck): it presents CREATE TABLE IF NOT EXISTS AS SELECT as the mapping. That describes only the first build. Current docs: Dataform “builds the incremental table from scratch only for the first time. During subsequent executions, Dataform only inserts or merges new rows.” (Create tables)
  • Every compilation result carries both variants — incremental and full-refresh — and execution selects one. “Run with full refresh” (UI) or --full-refresh (CLI) picks the rebuild path.
  • The when() two-argument form takes a non-incremental branch as its second argument; used here with one argument because there’s no residual filter. Show the two-arg form in the lab.
  • On the byte figures: 170 TB is the 90-day logical size (1.9 TB/day × 90, from Storage Optimization). A rebuild reads only the columns the SELECT touches (columnar), so the read is less than that — but it re-writes the whole table either way. The row count makes the waste plain without byte precision.
  • Partitioning carries over from module 4 and matters more here: the nightly append writes into one partition.

Late data and duplicates: uniqueKey

A participant’s laptop drops off the network mid-meeting. The ClearMeet client buffers unsent samples and re-uploads on reconnect — and when an ack is lost, it re-sends. So qos_events_raw sometimes holds the same sample twice, written minutes apart.
config {
  type: "incremental",
  uniqueKey: ["meeting_id", "event_time"],
}

SELECT …
${when(incremental(),
  `WHERE load_time > (
     SELECT MAX(load_time) FROM ${self()})`)}
Watermark on load_time, not event_time — the reconnect’s rows carry old event times and a strict event-time watermark would drop them.
uniqueKey isn’t a constraint — BigQuery has none. It changes the generated statement from INSERT to MERGE, so a re-delivered row updates in place instead of appending.
Speaker notes — Late data and duplicates: uniqueKey
  • The two-beat story: (1) an event_time watermark silently drops late data, so watermark on load_time; (2) that admits the re-sent duplicate, which is what uniqueKey then kills. Say both out loud — the slide shows the second.
  • Define by mechanism, not synonym: “idempotent” is the word engineers will reach for; make them say what statement is generated instead.
  • Within-batch caveat: MERGE matches source rows against the target, so two copies of the same sample arriving in the same run are not deduplicated by uniqueKey. Dedupe those in the SELECT: QUALIFY ROW_NUMBER() OVER (PARTITION BY meeting_id, event_time ORDER BY load_time) = 1.
  • Cost: MERGE must find matching rows, which on a 450 B-row table means scanning unless bounded. bigquery.updatePartitionFilter restricts which target partitions the merge examines — set it to the recent window late data can realistically fall in.
  • Two properties older material predates: protected: true blocks full refreshes on a table you can never rebuild (source data gone), and onSchemaChange: (IGNORE default / FAIL / EXTEND / SYNCHRONIZE) decides what happens when the SELECT gains a column. SYNCHRONIZE drops removed columns and cannot be undone.

Assertions: four built in

Four checks on qos_events_clean, written in the same config block that defines the table.
config {
  type: "table",
  assertions: {
    nonNull: ["meeting_id", "event_time",
      "org_id"],
    uniqueKey: ["meeting_id"],
    uniqueKeys: [["meeting_id", "event_time"]],
    rowConditions: [
      "audio_mos BETWEEN 1 AND 5",
      "device IN ('macos','windows',"
        "'ios','android','web')",
    ],
  },
}
  • Each entry becomes its own action that runs after the table builds.
  • An assertion is a query that hunts for violating rows; finding any marks it FAILED that night.
  • rowConditions is evaluated per row: every row must satisfy every listed expression.
AssertionFails when
nonNulla listed column is NULL in any row
uniqueKeya single column has a repeated value
uniqueKeysa combination of columns repeats
rowConditionsany row makes an expression false
The second rowConditions entry is the nine-day bug, caught on night one. Assertions are cheapest to write at the moment you learn what “wrong” looks like.
Speaker notes — Assertions: four built in
  • uniqueKeys (plural, list of lists) is missing from older material — it’s the multi-column form, and it’s what you actually want on an event table.
  • Implementation detail that surfaces in the UI: nonNull is implemented as a rowConditions assertion under the hood, so it doesn’t produce a separately-named action. That matters when wiring dependencies by name.
  • These run as BigQuery queries and cost money — full scan per assertion unless the table is partitioned and the condition prunes. Not free; worth budgeting.

What an assertion compiles into

Trace uniqueKey: ["meeting_id"] from config to the thing that actually fails the run.
  • Dataform inverts the rule into a violations view: a query for the rows that break it, materialized in clearmeet_assertions.
  • The assertion action is then a single ASSERT that the view is empty.
When an assertion fails, you don’t reproduce the failure — you SELECT * from the assertion view and look at the exact rows that broke it.
Speaker notes — What an assertion compiles into
  • That persistence is the most practically useful and least advertised thing about Dataform assertions. Lead with it in a demo.
  • Naming pattern: <project>.<assertion_dataset>.<dataset>_<table>_assertions_<condition>_<n>. Ugly, predictable, and greppable.
  • Every assertion is a node in the graph with its own state — which sets up the next slide.

The trap: a failed assertion does not stop anything

The device assertion fails at 02:14. Does the SLA report go out?
  • By default, yes. The assertion is a node beside the table, not between the table and its dependents — sla_by_org depends only on qos_events_clean, which SUCCEEDED.
  • dependOnDependencyAssertions: true rewires this: every assertion of every dependency becomes an additional dependency.
  • Now the failed assertion is on the path, and sla_by_org ends the night SKIPPED.
config {
  type: "table", name: "sla_by_org",
  dependOnDependencyAssertions: true,
}
By default, “the failure of the assertions of action A does not block Dataform from executing action B.” An assertion you don’t wire in is a notification, not a gate.
Speaker notes — The trap: a failed assertion does not stop anything
  • Quote is verbatim from Set dependencies. This is the single most consequential default in the product and most source material buries it.
  • Three ways to wire it: dependOnDependencyAssertions: true (all assertions of all dependencies), includeDependentAssertions per-dependency for exceptions, or naming the assertion action in the dependencies array by hand. The first is the sane default.
  • When both are set, includeDependentAssertions wins — so dependOnDependencyAssertions: true plus {name: "orgs", includeDependentAssertions: false} means “gate on everything except the orgs table’s checks.”
  • SKIPPED is a real terminal state: “Execution of the action was skipped because upstream dependencies did not all complete successfully.”

Manual assertions

Every org_id in qos_events_clean should exist in orgs. No built-in assertion expresses a cross-table check.
definitions/assertions/orgs_fk.sqlxconfig { type: "assertion" }

SELECT org_id, COUNT(*) AS samples
FROM ${ref("qos_events_clean")}
WHERE org_id NOT IN (
  SELECT org_id FROM ${ref("orgs")})
GROUP BY org_id
  • A manual assertion is a query that must return zero rows — any result row is a violation, and the action fails.
  • It is a first-class node: it has dependencies (via ref()), a state, and dependents.
  • Use it for referential integrity, cross-table totals, and business rules.
Built-in assertions check a table against itself. Manual assertions are how you check a table against another table — which is where the interesting bugs live.
Speaker notes — Manual assertions
  • Returning the offending org_ids and a count, rather than SELECT 1, means the failure message points at the culprit. Cheap habit, big payoff.
  • Manual assertions also work against external tables, where built-ins can’t reach.
  • Anti-pattern worth naming: an assertion that’s always slightly failing gets muted, and then all assertions get ignored. Assert things that should be exactly true.

Security: three granularities, one question

A support contractor needs the SLA report for their assigned region. They must not see participant_email, and must not see other regions’ rows.
  • Three controls answer three nested questions, and all three are plain BigQuery:
  • IAM — can you open the dataset or table at all?
  • Policy tags (column-level) — of the columns, which can you read?
  • Row access policies — of the rows, which exist for you?
All three are ordinary BigQuery features. Dataform’s contribution is that they live in the same reviewed file as the table, so the grant cannot drift from the schema.
Speaker notes — Security: three granularities, one question
  • Frame as three questions in order — can you open it, which columns, which rows. Students new to GCP conflate them constantly.
  • Column-level security needs a taxonomy and policy tag to exist first, created outside Dataform.
  • Service limit: “A column can have only one policy tag.” (BQ column-level security)

    bigqueryPolicyTags: [
      "projects/…/taxonomies/8891"
      "/policyTags/4417"],
  },
}
  • The GRANT is plain BigQuery DCL — the same statement you could type in the console. post_operations runs it after every build of this table.
  • ${self()} = this file’s table; ${ref("x")} to grant on another’s. Row access policies go here too.
The Dataform service account needs Fine-Grained Reader on the policy tag, or every assertion on that table fails with a permission error. Same for row access policies: grant the service account a FILTER USING (TRUE) policy, or its assertions silently pass by reading zero rows.
Speaker notes — Writing the grants
  • Dwell on that second failure mode. An assertion that cannot see the bad rows passes. Security misconfiguration turns your data tests into no-ops without any error.
  • Docs suggest removing the GRANT from an incremental table’s definition after the first run, since it re-runs every execution.
  • BigLake caveat: row-level security in post_operations fails on external tables (“Actions may only include post_operations if they create a dataset”) — use a separate type: "operations", hasOutput: false file.

Recap: trust

  • Four built-in assertions; manual assertions for anything cross-table.
  • An assertion compiles to a view of the offending rows plus an ASSERT — the view persists.
  • A failed assertion blocks nothing unless you wire it in (dependOnDependencyAssertions).
  • Three granularities of access, all written next to the table definition.

The code lifecycle

Priya pushes her change at 16:40. It reaches production tables at 02:00. Here is every step in between.
Compilation is separate from execution on purpose: the same compilation result can be run now, re-run after a failure, or run on a schedule — and it produces byte-identical SQL each time.
Speaker notes — The code lifecycle
  • Reinforce the legend from slide 4: this is the picture those five terms describe.
  • Service limits: minimum compilation frequency is 1 hour; workflow invocations expire after 90 days; a workspace’s compilation result expires after 24 hours. (Code lifecycle)
  • You don’t need a release config to run something — a workspace can execute directly. That’s how you develop; it is not how you run production.

Two environments from one repository

The same definitions must build clearmeet_silver_dev from Priya’s branch and clearmeet_silver from main, with a lower threshold in dev.
  • Environments are release configurations over git refs, not copies of the code.
  • projectSuffix / datasetSuffix / namePrefix keep the outputs from colliding.
  • vars overrides let the same SQL behave differently per environment.
One repository, one set of definitions, main is production. Promotion is a merge — which means code review is the deployment gate.
Speaker notes — Two environments from one repository
  • This is the GitOps story most source material never tells. For teams coming from Airflow, the “no separate dev DAG copy” property is the selling point.
  • A separate GCP project per environment (projectSuffix) is stronger isolation than a dataset suffix; pick based on how your org does project boundaries.

Hermetic compilation, and what it costs you

Priya wants the definition to look up today’s active-org list from an internal API at compile time. It cannot.
  • Compilation runs in a sandbox with no internet access and no external calls.
  • The same code plus the same settings always compiles to the same SQL.
  • Anything dynamic must arrive as a compilation variable, or be done in SQL.
This is why a compilation result is reproducible and safe to re-run: it cannot have picked up a different answer from the outside world between two runs.
Speaker notes — Hermetic compilation, and what it costs you
  • Engineers with dbt/Jinja habits reach for a macro that calls something. Head it off.
  • The escape hatch is real: an API caller (Cloud Run function, Composer, Workflows) sets vars when it creates the compilation result. ClearMeet’s version: a backfill job passes vars: {backfill_date: "2026-06-12"} to reprocess the nine bad days.
  • JavaScript in Dataform generates SQL text. It is not a BigQuery UDF and does not run at query time. Common enough confusion to state twice (again in section 5).

The medallion layout

Speaker notes — The medallion layout
  • Terminology discipline: rooms that use medallion language will map it automatically, but the directory names are what the docs and the UI show. Say both once, then use the directory names.
  • The useful boundary rule: bronze is what you didn’t write, silver is one row per real thing with conformed types and values, gold is shaped for a specific consumer.

Reuse: one function, five call sites

The device-name fix is needed in five definitions. Copy-paste is how the customer-tier CASE statement drifted apart.
includes/mappings.jsfunction normalize_device(col) {
  return `CASE
    WHEN LOWER(${col}) IN
      ('macos','mac os x','osx') THEN 'macos'
    WHEN LOWER(${col}) LIKE 'win%' THEN 'windows'
    ELSE LOWER(${col}) END`;
}
module.exports = { normalize_device };
  • At compile time, ${mappings.normalize_device("device")} in a sqlx body calls the function and splices its return string into the SQL.
  • Inside the function, ${col} is ordinary JavaScript interpolation — it inserts the column name, producing CASE WHEN LOWER(device) ….
  • module.exports makes it callable from any definition as filename.functionname.
This JavaScript runs at compile time and produces SQL text. It is not a BigQuery UDF and never executes against a row. Nothing you write here can query data or call an API.
Speaker notes — Reuse: one function, five call sites
  • The warning is the hermetic point restated where people actually trip: they write JS that looks like it should filter rows.
  • includes/ is global — everything in it is available repo-wide via filename.exportname. js { } inside a sqlx file is the file-local version.
  • Also the right place for shared documentation constants and shared column lists.

SCD Type 2: the problem

Support asks: Acme had a bad call on 3 March. Were they on Enterprise then? The orgs table is overwritten nightly. The answer is gone.
  • A daily overwrite answers “what is true now” and destroys “what was true then.”
  • Any question joining an event to an attribute as of the event’s date needs history.
  • Type 1 = overwrite (what they have). Type 2 = keep every version, with validity dates.
This is not a Dataform feature — it is a modeling pattern. Dataform’s contribution is that the incremental table and the history view are two definitions in the same graph, tested and versioned.
Speaker notes — SCD Type 2: the problem
  • Vocabulary beat: Type 1 overwrites, Type 2 adds a row per version with validity dates, Type 3 keeps a “previous value” column. Type 2 is what people mean when they say SCD without qualifying.
  • The join this enables, worth showing verbally: qos_events e JOIN orgs_history h ON e.org_id = h.org_id AND e.event_time >= h.valid_from AND (e.event_time < h.valid_to OR h.valid_to IS NULL).

SCD Type 2: incremental table + LEAD() view

Two definitions. The incremental table keeps every version; the view turns updated_at into validity ranges.
orgs_history.sqlxconfig { type: "view" }

SELECT *,
  updated_at AS valid_from,
  LEAD(updated_at) OVER (
    PARTITION BY org_id
    ORDER BY updated_at) AS valid_to
FROM ${ref("orgs_updates")}
  • orgs_updates only ever appends — every changed version becomes a new row.
  • LEAD looks one row ahead per org: a version’s valid_to is the next version’s valid_from.
  • The newest version has no next row → NULL = current.
History is immutable by construction: the incremental table only appends, so no run can destroy what was true last year.
Speaker notes — SCD Type 2: incremental table + LEAD() view
  • The incremental table is an ordinary type: "incremental" with WHERE updated_at > (SELECT MAX(updated_at) FROM ${self()}) — no uniqueKey, because appending every version is the point.
  • Do not teach the dataform-scd package. It did exactly this, but the repo was archived 19 April 2026 and the Google Cloud doc page for it now 404s. Hand-writing it is ~15 lines and has no dependency risk. If a student has seen it in older material, this slide is the replacement.
  • Caveat: the view can’t be materialized: true — BigQuery rejects analytic functions in incremental materialized views. Build it as a table if read cost matters.
  • Requires a reliable updated_at on the source. No change timestamp → you need a hash-comparison variant, or CDC upstream.

Speaker notes — Caveats, and when not to use Dataform
  • Say the dbt comparison plainly — most experienced data engineers in the room will have used dbt, and pretending otherwise costs credibility. Dataform is narrower, free of infrastructure, and native to GCP IAM; dbt has the larger ecosystem and is portable.
  • The 1-hour minimum compilation frequency is the real freshness floor for scheduled runs; API-triggered invocations can be more frequent, but that’s your scheduler, not Dataform’s.
  • Also missing and worth naming if asked: no built-in data-lineage export beyond the graph, and no non-SQL transform step.
