04CI/CD: continuous integration and continuous delivery

"A software development practice that automates the process of building, testing, and deploying code changes."

The agent's pipeline differs in one step

Example

A pull request changes one sentence of the refund agent's instruction from "offer a refund when appropriate" to "only offer a refund after confirming the order shipped." Unit tests pass (nothing they test changed). The eval step runs the 40-case set; three cases that expect a refund on an unshipped order now fail the tool-trajectory check, and the PR is blocked.

Takeaway: the artifact is code as always; the pipeline differs in one step, an eval run, because unit tests can't check model behavior.

05Continuous integration Correction

"The practice of frequently merging code changes into a central repository." (notes)

CorrectionThat's half the definition; the other half is the automated verification.
Definition (Fowler)Each member of the team merges their changes into the mainline at least daily, and each integration is verified by an automated build (including tests) to detect integration errors as quickly as possible.

"Stable codebase" means

the mainline always builds and passes, so a release can be cut from any commit.

"Integration problems accumulate" means

the cost of reconciling branches grows faster than the time they diverge (Fowler: twice the code, about four times the integration): textual conflicts and behavioral interactions between people's instruction and tool edits.

Work that takes longer than a dayMerge daily anyway and hide the unfinished part (Fowler, "Hide Work-in-Progress"). The agent version of a keystone interface: write and merge the new tool function with its unit tests, but leave it out of the agent's tools=[...] list until it is ready. Unregistered, it cannot change a trajectory, so the eval run stays green while the code lands daily. A config flag that registers the tool only in test environments does the same job.
Example

Priya rewrites the refund instruction to say "call get_order to confirm the order shipped before offering a refund." Marco, in tools.py, renames get_order to lookup_order and updates the old instruction's one reference to it. Each branch passes the 40-case evals. The merge has no textual conflict (instruction file vs. tools file), but the merged instruction names a tool that no longer exists; the model skips the check or calls a tool the runtime rejects, and the shipped-order cases fail. Merged daily, Marco's rename lands on day one and Priya's next eval run fails with a one-line cause. Merged after three weeks, Priya has three weeks of instruction written against the old name to rework, and the failing run contains both people's three weeks of changes to bisect.

Takeaway: integrate at least daily and verify every integration with tests and evals; the cost of reconciling two people's edits grows faster than the time they diverge, so keep each interaction small enough to spot on the day it happens.
Source: martinfowler.com, Continuous Integration (verified 2026-08-25).

06Continuous delivery Correction

"Producing software in short cycles… might mean pushing releases to production several times a day."

Correction"Several times a day" describes continuous deployment. Delivery and deployment are different.
Continuous deliveryContinuous deployment
Meaningany passing commit could be released at any timeevery passing commit is released, automatically
Who decidesthe businessthe pipeline
For agentsthe usual choice, with a canaryrare: the eval set is a sample of the conversations the agent will see
Example

Version 14 of the refund agent passes the eval set. Released as a 5% canary (Cloud Run traffic split, or a second Agent Runtime deployment behind Agent Gateway), its tool-error rate on live traffic is twice version 13's, on request phrasings the eval set does not contain. Traffic goes back to 13; the failing conversations become eval cases.

Takeaway: delivery means every passing commit is releasable; for an agent, release as a canary anyway, because the eval set cannot contain every phrasing.
Source: martinfowler.com, Continuous Delivery (verified 2026-08-25).

What Agent Runtime actually is

The docs' definition: "a fully-managed, opinionated runtime that you can use to deploy, operate, and scale agentic applications" that "abstracts away the underlying infrastructure." Concretely, it is a hosting service for the agent process. The split of work:

You provideThe runtime provides
An agent object (pickled), a source tree, a Dockerfile, or a prebuilt image; plus requirements.txtBuild and serve. Builds the container and runs the HTTP server. A custom image only has to meet the runtime contract: listen on port 8080, answer /api/reasoning_engine (unary) and /api/stream_reasoning_engine (ndjson stream).
Nothing; callers get IAM on the resourceAn endpoint you don't own. The agent is reasoningEngines/NNN, reached via LOCATION-aiplatform.googleapis.com/…/reasoningEngines/NNN/api/run (or api/run_sse) with a Google access token. There is no public URL, no ingress setting, no invoker role to configure separately.
Optional: min_instances, max_instances, cpu, memoryScaling. 1–8 vCPU, 1–32 GiB, min 0–10 and max up to 1000 instances, scale to zero. CPU only (slide 10).
Optional: --agent-identity, or a custom service account emailIdentity. Runs as the Reasoning Engine service agent by default, a service account you name, or an Agent Identity: a per-agent IAM principal tied to the agent's lifecycle (Module 5, slide 37).
Optional: env vars, Secret Manager references, a network attachmentNetworking and secrets. Secrets resolved from Secret Manager (same project); Private Service Connect interface for egress to your VPC or on-prem; VPC Service Controls; CMEK.
GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=trueTelemetry. One env var turns on Cloud Trace spans, Cloud Logging (prompt and response content optional), and Cloud Monitoring metrics for the deployment (Module 3).
Correction: "sessions, memory built in"

Sessions and Memory Bank are Agent Platform services, not runtime features. Their parent resource is a reasoningEngines/NNN instance, and the docs are explicit that the instance can be empty: "You don't need to deploy any code to start using Sessions... creating an Agent Runtime instance only takes a few seconds without code deployment." Memory Bank's setup page has the same path for "a different environment, like Cloud Run or Colab."

So an agent on Cloud Run, GKE, or a laptop uses them by passing that instance id: VertexAiSessionService(project, location, agent_engine_id), same for VertexAiMemoryBankService. Slide 11 already lists managed Sessions as a Cloud Run feature. And neither is required anywhere: ADK's session and memory services are interfaces, with InMemorySessionService and DatabaseSessionService (SQLite, Postgres) as the non-managed implementations.

What deploying to Agent Runtime actually adds here is wiring: an ADK agent deployed there gets Sessions and Memory Bank pointed at its own instance with no configuration.

Example

A two-person team has a Python ADK support agent and no one who runs infrastructure. On Cloud Run they write a Dockerfile, expose a server, set ingress and an invoker role, and choose where sessions live. On Agent Runtime, agents-cli deploy uploads the pickle and requirements; ten minutes later the agent answers at its reasoningEngines endpoint with sessions on its own instance, and one env var gives them traces. Six months on security wants the agent behind the company load balancer with its own domain and a Cloud Armor policy, which needs a URL the team owns; that is the point at which the target changes to Cloud Run or GKE, and the Sessions instance comes along unchanged via agent_engine_id.

Takeaway: Agent Runtime hosts the agent process (build, serve, scale, identity, private network, telemetry); Sessions and Memory Bank are separate services any host can call, so they do not decide the target.

11Cloud Run Correction

"Agent sandbox: isolate untrusted code with GKE Sandbox."

CorrectionGKE Sandbox is a GKE node feature and does not apply to Cloud Run. The sandbox Cloud Run already has (gen1: gVisor; gen2: microVM) is the wrong boundary for this claim: it isolates your container from the host and other tenants, not model-generated code from your agent. Code the agent runs with subprocess inside the container sees the agent's filesystem, environment variables, and the service-account credentials on the metadata server.
What the slide was reaching forCloud Run sandboxes (Preview, July 2026): a second boundary inside the running instance. sandbox do -- python script.py runs with a read-only view of the container filesystem, a write overlay that is discarded afterward, no environment variables, no metadata server, and no egress unless requested. ADK 2.7.1 wires it in as CloudRunSandboxCodeExecutor (google.adk.integrations.cloud_run), network off and a 300 s timeout by default.

Takeaway: GKE is for teams that already run Kubernetes or need custom isolation and networking; Pod Snapshots are about startup time, not memory.

15Artifact Registry Generic

"Fully managed artifact repository… Docker images, binaries, AAR/APK/JAR… vulnerability scanning."

One line, skip the format list.

Addition (not in the deck)Neither the slide nor its notes say how to tag images. The useful specific to add: tag with the commit (agent:$COMMIT_SHA) so the image a deployment is running names the commit it was built from. The deck's slide 29 pipeline pushes an untagged image, so every build overwrites latest.
Example

Priya's instruction edit merges as commit a3f9c1e; the pipeline builds and deploys agent:a3f9c1e. Two days later refunds on unshipped orders start going through. gcloud run revisions list shows the serving revision runs agent:a3f9c1e, so git show a3f9c1e is the one-paragraph instruction diff to read, and gcloud run deploy lab-agent --image ...agent:7c02b4d puts the previous build back while it is fixed. With latest, the revision says agent:latest for every build; finding the commit means matching build timestamps to the git log, and the previous build's image has no name, only a digest to hunt for in the registry.

16Cloud Build

"Executes build steps in response to triggers · serverless · compile, build image, run tests, deploy."

Present as-is. In the agent pipeline the "run tests" step is pytest and adk eval; a non-zero exit from either stops the build before push and deploy (slide 29).

Example

Priya merges a PR to main that changes the refund agent's model id from gemini-2.5-flash to a newer model and rewords two lines of its instruction. A Cloud Build trigger on pushes to main starts the four-step build from slide 29. Step 1 builds the image tagged agent:<commit>. Step 2 runs pytest (green: nothing the unit tests cover changed) and then adk eval against the 40-case set; the new model handles the reworded instruction differently and five cases fall below the tool-trajectory threshold in test_config.json. adk eval exits non-zero, so Cloud Build marks the build Failed at step 2 and never runs step 3 or 4: no image is pushed and the revision serving traffic is the one from the previous commit. The build history entry links to the commit and the step 2 log names the five cases. Priya adjusts the instruction, pushes, and the trigger fires again; this time all four steps pass and the tagged image is deployed.

Two things this step does that a unit-test step does not: it calls the model, so it costs tokens and takes minutes rather than seconds, and it can fail because the model endpoint returned a quota error rather than because the code is wrong. Read the step log before assuming a regression.

18Secret Manager

"Store, manage, and audit credentials · versioning and rotation · never store secrets in source code."

Present as-is. An agent's secrets: credentials for each tool it calls (database password, partner API key), and the model API key only when not using Application Default Credentials.

agents-cli deploy --secrets "API_KEY=my-api-key,DB_PASS=db-password:2"   # secret → env var at deploy time
Example

Priya's refund agent has one tool that calls the payments provider's refund endpoint with an API key. The key is in Secret Manager as payments-api-key; the repository holds only that name. The pipeline deploys with agents-cli deploy --secrets "PAYMENTS_API_KEY=payments-api-key:3" and the tool reads os.environ["PAYMENTS_API_KEY"]. The service account the agent runs as (slide 9) has roles/secretmanager.secretAccessor on that one secret and nothing else. When the provider rotates keys, Priya runs gcloud secrets versions add payments-api-key --data-file=- with the new key, which becomes version 4, redeploys with :4, checks that a test refund goes through, then disables version 3. No commit, no rebuild: the diff is one version number in the deploy command, and the previous version is still there to switch back to if the new key was pasted wrong. When security asks who has read the key in the last 90 days, the Secret Manager audit log lists every AccessSecretVersion call by principal and time (data access logging has to be turned on for that; it is off by default). The same key in a .env file would be in every clone and in the git history from the day it was added, rotating it would mean a commit, a rebuild, and a redeploy, and nothing would record who had read it.

20Source management: repositories

"Versioning is critical for agents · single source of truth · version prompts as artifacts."

Key pointThe instruction, tool definitions, model id, generation config, and eval set are files in the repository, versioned like any code. The slide singles out prompts because a few lines of instruction can change behavior substantially, so instruction diffs get the same review as logic diffs, and the eval score is recorded per commit.
Example

Support reports the agent stopped offering exchanges. git log app/instruction.md shows commit a1b3f ("tighten refund wording") three days ago; that commit's CI record shows tool-call accuracy 0.94 → 0.82. Revert, redeploy the previous image tag. Rollback is the same as for any service: the prior image (Cloud Run revision, or redeploy on Agent Runtime).

Takeaway: version instruction, tools, and eval set with the code and record the eval score per commit, so a behavioral regression is a diff you can find.

21Model governance for agents Compress

"Register custom models in Model Registry · semantic versioning · approval gates · lineage: training data, hyperparameters."

Written for teams that train their own models. For an agent on a foundation model, two rules:

Pin the model id per environment. An alias like gemini-flash-latest resolves to different versions over time and across regions.

Treat a model upgrade as a release: change the id in the repo, run the eval set, compare with baseline, canary. Families retire on a schedule (Gemini 2.5: October 2026).

Example

Staging pins gemini-2.5-flash; production uses gemini-flash-latest. In August the alias moves to a newer version; production's tool-call formatting changes and staging never showed it.

Takeaway: pin the model id, and upgrade it through the pipeline like any other change.

24Tool catalog governance

"Strict schemas · retry policies and circuit breakers · least privilege · log every invocation with agent ID, model version, user context."

Schema and docstring

what the model reads to decide when and how to call the tool; a vague description produces wrong calls; review like code

Least privilege per environment

the dev credential for a tool must not reach production data

Log every invocation

agent id, model version, user id: audit trail, and later the cost-attribution key

Example

issue_refund(order_id, amount) is described as "Refund an order." The model calls it for a customer asking about refund policy. Changing the description to "Issue a refund. Only call after the customer confirms and the order status is delivered" removes the false calls in the eval set. Only the docstring changed.

Takeaway: the tool's description and schema are what the model decides from, so they are reviewed like code; least privilege per tool bounds what a wrong call can do.

29cloudbuild.yaml to deploy an agent to Cloud Run Correction

Build image → push → gcloud run deploy lab-agent … --project ${_PROJECT_ID}.

1
the deploy step uses ${_PROJECT_ID}, an undefined user substitution, while the build step uses the built-in $PROJECT_ID
2
the image has no tag, so every build overwrites latest
3
there is no eval step

Fixed pipeline

substitutions:
  _DEPLOY_PROJECT_ID: "my-deploy-project"
  _REGION: "us-central1"
  _REPO: "my-repo"

steps:
  # 1. build, tagged with the commit
  - name: gcr.io/cloud-builders/docker
    args: ["build","-t","$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA","."]
  # 2. tests and evals; non-zero exit stops the build
  - name: python:3.12
    entrypoint: bash
    args:
      - "-c"
      - |
        pip install -q -r requirements.txt google-adk pytest
        pytest tests/unit
        adk eval app/ tests/eval/full.evalset.json --config_file_path tests/eval/test_config.json
  # 3. push the tagged image before deploy
  - name: gcr.io/cloud-builders/docker
    args: ["push","$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA"]
  # 4. deploy to the deploy project, non-interactively
  - name: gcr.io/cloud-builders/gcloud
    args: ["run","deploy","lab-agent",
           "--image","$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA",
           "--region","$_REGION",
           "--project","$_DEPLOY_PROJECT_ID",
           "--quiet"]

# declared so Cloud Build tracks the tagged image as this build's artifact
images:
  - "$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA"

Declare _DEPLOY_PROJECT_ID, _REGION, and _REPO in substitutions with defaults so the deploy target is explicit rather than an undefined variable, and override _DEPLOY_PROJECT_ID per trigger when the build project and deploy project differ. --quiet suppresses the interactive prompt so the deploy step doesn't hang in CI. For Agent Runtime, step 4 is agents-cli deploy (no gcloud deploy command exists for it); thresholds live in test_config.json.

Takeaway: tag the image with the commit, declare substitutions (including the deploy project) explicitly instead of leaving them undefined, run the eval before push and deploy, and deploy with --quiet so the pipeline never waits on a prompt.
Sources: agents-cli deploy · cloudbuild.yaml schema (verified 2026-08-25).
