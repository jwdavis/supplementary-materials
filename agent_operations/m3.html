04The three signals

"Logs explain events. Traces explain performance. Metrics explain trends."

SignalAnswers, for an agentExample
Logswhat was the model asked and what did it replythe exact prompt that produced the wrong delivery date
Traceswhich step of the trajectory took the time or made the wrong callthe execute_tool span for the shipping API at 2.1 s
Metricsare tool error rate, tokens per conversation, and latency within boundstokens per conversation p95 up 40% after Tuesday's release
Takeaway: an agent needs all three because its failures are wrong steps, not crashes: logs show what the model saw, traces which step, metrics whether it is drifting.

13Monitoring

"Cloud Monitoring time series · infrastructure metrics come built in · custom agent metrics must be emitted or derived: token usage, tool frequency, feedback score, cost per session · alerts."

Built in, no setup

request count, latency, CPU, memory, instance count (Cloud Run and Agent Runtime)

Derived by you

tokens per conversation, tool error rate, from ADK's gen_ai.* metrics or the Agent Analytics table

Example alert

Tokens per conversation, p95, computed hourly. Baseline 38,000; alert at 60,000. After a release that changed the instruction, p95 is 71,000: the agent now asks two clarifying questions before its first tool call. The alert points at the release; the eval set gets a case for "act on a complete request without clarifying."

Takeaway: infrastructure metrics are free; tokens per conversation and tool error rate you must derive, and they are the two alerts that catch agent regressions.

18Agent callback logging

"Callbacks are hooks at points in the agent lifecycle · pros: prototyping, conditional logic, can change behavior · cons: siloed per agent, runs in the request thread."

For logging across all agents, the 2.x idiom is one plugin on the App: BasePlugin has 15 hooks including error hooks callbacks lack (on_model_error_callback, on_tool_error_callback); LoggingPlugin is the shipped version. "Runs in the request thread" is only partly a con; callbacks can be async.

Deck (per-agent callbacks)

root_agent = Agent(name="search",
                   before_model_callback=log_query_to_model,
                   after_model_callback=log_model_response)

Current (one plugin for the app)

from google.adk.plugins import LoggingPlugin
app = App(name="support_app", root_agent=root_agent, plugins=[LoggingPlugin()])
Takeaway: plugins and callbacks can change behavior, OpenTelemetry only records; use a plugin for guardrails and cross-agent logging, OpenTelemetry for the trace.
Source: plugins at v2.7.1 (verified 2026-08-25).

19Callback logging: the functions

log_query_to_model(callback_context, llm_request) and log_model_response(callback_context, llm_response); the last line is cut off on the slide.

Signatures verified. Complete version:

import logging
from google.adk.agents.callback_context import CallbackContext
from google.adk.models import LlmRequest, LlmResponse

def log_query_to_model(ctx: CallbackContext, req: LlmRequest):
    last = req.contents[-1] if req.contents else None
    if last and last.role == "user":
        for p in last.parts:
            if p.text: logging.info("[query to %s] %s", ctx.agent_name, p.text)

def log_model_response(ctx: CallbackContext, resp: LlmResponse):
    for p in (resp.content.parts if resp.content else []):
        if p.text:            logging.info("[response from %s] %s", ctx.agent_name, p.text)
        elif p.function_call: logging.info("[function call from %s] %s", ctx.agent_name, p.function_call.name)

In ADK 2.x CallbackContext is an alias of Context; the code is unchanged.

24Agent execution telemetry

Diagram: agent (LLM call, DB call, LLM call) → OpenTelemetry → Cloud Trace; Cloud Logging → BigQuery. "Logs and traces correlate via trace_id when trace context is propagated."

Image-only slide, same content as slide 6 at more detail. The new idea is context propagation: ADK stamps its own logs and spans with the same trace_id. If your code starts a thread or calls another service without forwarding the trace context, that work appears as unrelated spans or log lines. With ADK on Cloud Run or Agent Runtime, propagation within the process is handled; you deal with it only in your own threads or outbound HTTP calls.

25Controlling message content logging Correction

"Set OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT = True to capture prompts, system instructions, responses, and tool arguments."

CorrectionTwo switches, and this one is not the one that governs ADK's spans.
VariableDefaultControls
ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANSonprompt, response, and tool arguments on ADK's spans; set false to redact
OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENTNO_CONTENTthe OpenTelemetry GenAI switch: NO_CONTENT, EVENT_ONLY, SPAN_ONLY, SPAN_AND_EVENT; True is treated as EVENT_ONLY (log records, not spans)

Per request: RunConfig.telemetry = TelemetryConfig(capture_message_content=…).

Takeaway: for a no-prompt-text policy set ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false; the OpenTelemetry variable alone does not cover ADK's spans.
Source: telemetry/context.py at v2.7.1 (verified 2026-08-25).
