03Financial governance challenges

"Cost drivers: token usage, model tier, multi-agent orchestration, tool/API cost, session-level cost invisibility. Controls: project isolation, agent tagging, token monitoring, budget alerts, billing export."

The five "drivers" are four different things

Billed units

Token usage (input + output) and tool / API cost: the actual line items on the bill.

The one true multiplier

Model tier scales price per token (slide 5): a Pro-class model costs several times a Flash-class one per token, whatever the token count.

Multi-agent: redistribution, not multiplication

ADK sub-agents share one session; each re-sends that shared history plus its own, usually smaller, instruction and tool subset. It adds routing turns, and multiplies context only in parallel fan-out (deprecated in ADK). A monolith drags its full prompt and tool list through every step, so specialists are often leaner.

Not a cost, a blind spot

Session-level cost invisibility: billing aggregates by project and SKU, not by conversation, so runaway sessions hide. Closed by the highlighted control below, not by billing export alone.

Controls: how you turn each one on

ControlHow you turn it on
Agent / feature taggingGenerateContentConfig(labels={"agent": "refund", "feature": "returns"}) on each model call; labels appear in the billing export
Billing exportCloud Billing export to BigQuery (24–48 h lag); query cost by label
Budget alertsCloud Billing budget per project, email or Pub/Sub notification
Project isolationseparate projects for dev / staging / prod and for AI workloads with their own budget
Model allowlistorg policy vertexai.allowedModels (Model Garden models; explicit deny wins)
Cost per conversationtoken counts from ADK event usage_metadata or the BigQuery Agent Analytics table × list price (slide 15)
CaveatAgent Runtime is billed on vCPU-hours and GiB-hours separately from model tokens; Sessions storage billing changes 2026-09-01.
Takeaway: two are billed units, model tier is the one true multiplier, multi-agent mostly redistributes tokens over a shared session (it multiplies only in parallel fan-out), and session invisibility is a visibility gap closed only by per-event token counts.
Sources: labels · allowedModels (verified 2026-08-25).

05Prompt optimization Correction

"Token count is a linear cost multiplier; model tier selection acts as an exponential multiplier on cost."

CorrectionModel tier is a constant multiplier per token (a Pro-class model costs several times a Flash-class model per token), not exponential.
01
shorten the instruction; remove redundant examples
02
trim tool declarations — every tool's full schema (name, description, every parameter) is re-sent on every call, so 30 tools ≈ 2,000+ tokens each turn. Split the toolset across sub-agents so each carries only its own; gate tools per turn in a before_model_callback that strips ones the current state can't use; and tighten each schema (shorter descriptions, drop optional params and inline examples)
03
cap conversation history — ADK context compaction auto-summarizes older events once a token_threshold is crossed, keeping the newest event_retention_size raw
04
limit RAG top-K — documents are split into ~few-hundred-token chunks, embedded, and the top-K most similar are pasted into the prompt; every chunk is input re-sent each turn (K=20 × 500-token chunks ≈ 10k tokens/call before the question). Lower K (3–5), use smaller chunks, or retrieve broadly then rerank and keep only the top few above a relevance-score threshold
05
prefer structured output — a JSON response schema cuts full-price output tokens and avoids a re-parse round-trip
06
then consider a smaller model (slide 9)
Takeaway: trim re-sent input first (tools, history, retrieval), then output — cheapest and reversible. Model tier is a constant multiplier you change last.
Sources: ADK context compaction · ADK sessions (verified 2026-09-09).

06Response caching Correction

"Return a cached response instead of calling the model again… ADK provides Context Caching… zero model cost for those requests." (notes)

CorrectionTwo different mechanisms are merged here. ADK's Context Caching is not response caching.

Response caching

a lookup keyed on the request; on a hit the stored answer is returned and the model is not called. Zero model cost on a hit. Useful for repeated (or paraphrased) prompts. ADK ships no built-in response cache, but documents building one — a before_model_callback short-circuit, or the adk-redis semantic cache (see doc).

Context caching (what ADK provides)

the model runs every turn. The reusable prefix (instruction, tool declarations, prior context) is cached so it is not re-processed; cached input tokens are billed at a discount (90% for Gemini 2.5+); output tokens at full price. Implicit caching is on by default; explicit caching adds a storage charge.

Takeaway: context caching discounts the re-sent prefix; it does not skip the model, and "zero model cost on a hit" is a different mechanism ADK does not provide.
Sources: context caching · ADK (verified 2026-08-25) · how to build a response cache in ADK →

08ADK context caching example Correction

ContextCacheConfig(min_tokens=4096, ttl_seconds=1800, cache_intervals=4) passed to App(…).

CorrectionImport and structure are right. Defaults are min_tokens=0, ttl_seconds=1800, cache_intervals=10. The floor is the model's, not min_tokens: 2,048 tokens for Gemini 2.5, 4,096 for Gemini 3, measured on the whole request; caching begins on turn 2. The API is experimental.

What gets cached is the prefix: static_instruction + tool declarations. Put durable content (persona, schemas, examples) in static_instruction — a types.Content that lands in system_instruction, byte-identical every turn. Put per-turn steering in the dynamic instruction, which is appended to contents and so changes without touching the cached prefix.

Current (ADK 2.7)

from google.adk.agents.llm_agent import Agent
from google.adk.agents.readonly_context import ReadonlyContext
from google.adk.apps.app import App
from google.adk.agents.context_cache_config import ContextCacheConfig
from google.genai import types

# Dynamic instruction: recomputed each turn, appended to CONTENTS (not the prefix).
def steer(ctx: ReadonlyContext) -> str:
    return f"The customer's tier is {ctx.state['tier']}. Be concise."

agent = Agent(
    name="support_agent",
    model="gemini-2.5-flash",
    static_instruction=types.Content(          # cached prefix: durable, byte-identical
        role="user", parts=[types.Part(text=SUPPORT_PERSONA_AND_SCHEMAS)]),
    instruction=steer,                         # dynamic: safe to vary per turn
    tools=[lookup_order, issue_refund],
)

cache = ContextCacheConfig(min_tokens=0, ttl_seconds=1800, cache_intervals=10)  # defaults
app = App(name="support_app", root_agent=agent, context_cache_config=cache)
Payoff

Persona + schemas 3,000 tokens plus two tool declarations ~1,000: a ~4,000-token prefix. Over 8 turns, turns 2–8 bill that prefix at the cached rate (~10% of input price). The model still runs all eight times — caching discounts the prefix, it does not skip the call.

Breaks the cache — silently

A timestamp or state in static_instruction. f"...Today is {date.today()}..." or a fed-in {tier} changes the prefix every turn, so it never matches the previous fingerprint: every turn is a cache miss even though caching is "on." Keep the varying part in the dynamic instruction instead.

Editing the tool set (or its schemas) mid-session. Tools are part of the cached prefix; adding, removing, or renaming a tool re-fingerprints it and the cache resets — the same reason a prefix below the model's token floor (2,048 Gemini 2.5 / 4,096 Gemini 3) never caches at all.

Takeaway: caching keys on a byte-identical prefix (static_instruction + tools). Anything that varies goes in the dynamic instruction; a timestamp or changed tool in the prefix turns every turn into a miss.
Sources: model context caching · static_instruction sample (verified 2026-09-09).

10Fine-tune smaller models

"Replace expensive base models for repetitive tasks · break-even volume = training cost / savings per request."

Example (illustrative)

A classification step runs 200,000 times a month. Tuning costs $400; the tuned small model saves $0.004 per request. Break-even = $400 / $0.004 = 100,000 requests, about two weeks. A task with 5,000 requests a month never pays it back.

CaveatFine-tuning is the heaviest option. Prompt trimming, caching, and right-sizing are reversible and need no training pipeline; do them first.
Takeaway: fine-tuning is a volume decision; compute the break-even before starting a pipeline you then own.

13Dynamic model overrides in code Correction

my_agent = Agent.load("my_agent_dir"); my_agent.run("…", config={"model_name": "gemini-2.5-pro"})

CorrectionNeither Agent.load nor run(prompt, config=…) exists in ADK; the snippet raises AttributeError. The Gemini 2.5 family also retires October 2026.

Current (ADK 2.7): per-request override

def pick_model(ctx, llm_request):
    if needs_long_reasoning(ctx.user_content):
        llm_request.model = PRO_MODEL_ID      # upgrade this call only

agent = LlmAgent(
    name="support",
    model=FLASH_MODEL_ID,                     # default for every call
    before_model_callback=pick_model,
)

Other real options: model= per agent (a model id or a BaseLlm; unset inherits from the parent); the same hook as an app-wide BasePlugin; a router agent (slide 12).

Takeaway: change the model per agent with model=, or per request in a before_model_callback; the deck's API does not exist.
Source: llm_agent.py at v2.7.1 (verified 2026-08-25).

14Batch inference

Use batch for

nightly eval runs, embedding generation for a RAG store, bulk document processing; 50% of the standard token rate

Never for

15Standard FinOps practices on Google Cloud

"Budget alerts · billing export · labels · separate dev/staging/prod · label by model, agent, feature · monitor cost per session · model allowlists."

Mechanics are on slide 3. Spend the time on the query these practices exist to enable:

-- cost per conversation from the BigQuery Agent Analytics table (Module 3); prices as parameters
SELECT session_id,
       SUM(usage_prompt_tokens)                       AS input_tokens,
       SUM(usage_total_tokens - usage_prompt_tokens)  AS output_tokens,
       SUM(usage_prompt_tokens) / 1e6 * @in_price
     + SUM(usage_total_tokens - usage_prompt_tokens) / 1e6 * @out_price AS usd
FROM   agent_events.v_llm_response
WHERE  DATE(timestamp) = CURRENT_DATE()
GROUP BY session_id
ORDER BY usd DESC LIMIT 20;
What the top rows areThe long conversations: from Module 1 slide 9, a 12-turn conversation costs about nine times a 2-turn one. An alert on "tokens per conversation above N" finds the ones that should have gone to a human.
Takeaway: cost per conversation is one query over the Agent Analytics table; the expensive conversations are the long ones.
