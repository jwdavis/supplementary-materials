Response caching in ADK Companion

Response caching = a lookup keyed on the request. On a hit, a stored answer is returned and the model is never called — $0 model cost, near-zero latency. On a miss, the model runs and the answer is stored for next time.

ADK has no out-of-the-box response cache (context caching is a different feature — it discounts the re-sent prefix but still runs the model every turn). What ADK does give you is the callback hook to build one: before_model_callback can return an LlmResponse to short-circuit the call, and after_model_callback fires on the way back to store it.

The mechanism

Example 1 — the roll-your-own pattern everyone starts with

The callbacks page documents the pattern, not a finished cache. Below is the shape everyone writes first: a store keyed on the request, checked in before_model_callback, filled in after_model_callback. Start here to see the mechanism, then read the best-practices section — the naive version has a low hit rate and several sharp edges.

import hashlib
from google.adk.agents import LlmAgent
from google.adk.agents.callback_context import CallbackContext
from google.adk.models import LlmRequest, LlmResponse

# A dict shows the idea; it is in-process and lost on restart. Swap for Redis (Ex. 2).
_CACHE: dict[str, LlmResponse] = {}


def _key(req: LlmRequest) -> str:
    """Build the key from EVERYTHING that changes the answer, not just the text.

    Best practice #3: same question + different model / instruction / tools /
    retrieved docs = a different answer, so all of it belongs in the key.
    """
    text = "".join(p.text or "" for c in req.contents for p in c.parts)
    text = " ".join(text.split()).strip().lower()          # normalize whitespace/case
    parts = [
        text,
        req.model or "",                                    # model id
        req.config.system_instruction or "",               # instruction version
        ",".join(t.name for t in (req.config.tools or [])), # tool list
        # for RAG, also fold in a hash of the retrieved doc IDs
    ]
    return hashlib.sha256("|".join(parts).encode()).hexdigest()


def check_cache(ctx: CallbackContext, req: LlmRequest) -> LlmResponse | None:
    # Returning an LlmResponse short-circuits the model. Stash the key on state so
    # after_model_callback can reuse it (see the ParallelAgent caveat below).
    key = _key(req)
    ctx.state["_cache_key"] = key
    return _CACHE.get(key)


def store_cache(ctx: CallbackContext, resp: LlmResponse) -> None:
    # Reached only on a miss. Don't cache errors/empties (best practice #7).
    if resp.partial or not resp.content:
        return
    _CACHE[ctx.state["_cache_key"]] = resp


agent = LlmAgent(
    model="gemini-flash-latest",
    name="cached_agent",
    instruction="You are a helpful assistant.",
    before_model_callback=check_cache,
    after_model_callback=store_cache,
)

This still only matches exact (normalized) text — "What is Pub/Sub?" hits itself but not "Explain Pub/Sub." Real hit rates come from semantic matching (Example 2). The practices below are what turn this skeleton into something shippable.

No canonical ADK example existsThe ADK repo discussions on this (#4286, #2811) get a "use Plugins with before_model_callback" pointer from maintainers but no worked best-practice implementation — it's a known gap. The only maintained implementation is adk-redis (Example 2).

Best practices for a roll-your-own cache

Framework-agnostic; drawn from GPTCache and the semantic-cache literature.

#PracticeWhy
1Match on meaning, not the raw stringExact match misses every rephrase. Two-stage: normalized exact layer first, then embedding similarity.
2Normalize before keyingLowercase, collapse whitespace, strip trailing punctuation — free hits, no embedding cost.
3Key on all answer-affecting inputsModel + gen params, instruction version, tool list, and for RAG a hash of retrieved doc IDs; add user_id for personalized replies or you leak answers across users.
4Tune the similarity threshold empiricallyGPTCache's default 0.7 is too loose (false hits). Start ~0.92 cosine, watch the false-positive rate ~48 h, adjust in 0.01 steps; optimum depends on the embedding model.
5TTL by volatility~24 h news/live, ~72 h stable facts, ~7 d static FAQ. Vary per category, not one global value.
6Version the cacheFold a version tag into the key/namespace so a prompt/tool/model change doesn't serve pre-change answers.
7Never cache failuresSkip rate-limit, 5xx, timeouts, empty/refusal responses — caching those poisons the cache.
8Bypass when caching is wrongHigh-temperature creative turns, tool-calling turns (the "answer" is an action), anything reading live state.
ADK gotcha · from #4286Under ParallelAgent fan-out, concurrent branches racing on shared state can clobber a stored cache key. Build the key from request content (as _key above does) so it's reproducible, and treat the state["_cache_key"] stash as a convenience, not the source of truth.

Example 2 — the realistic version: adk-redis semantic cache

Rather than hand-code the practices above, ADK's documented integration bakes them in: semantic matching (#1), a shared Redis store, a TTL (#5), and a tunable distance_threshold (#4). You don't write the callbacks — create_llm_cache_callbacks() returns them.

install
pip install 'adk-redis[all]'   # needs Redis 8.4+ with RediSearch for self-hosting
from adk_redis import (
    RedisVLCacheProvider,
    RedisVLCacheProviderConfig,
    LLMResponseCache,
    create_llm_cache_callbacks,
)
from redisvl.utils.vectorize import HFTextVectorizer
from google.adk.agents import Agent

provider = RedisVLCacheProvider(
    config=RedisVLCacheProviderConfig(
        redis_url="redis://localhost:6379",
        ttl=3600,               # answers expire after 1 h
        distance_threshold=0.1, # how close a paraphrase must be to count as a hit
    ),
    vectorizer=HFTextVectorizer(model="redis/langcache-embed-v2"),
)

llm_cache = LLMResponseCache(provider=provider)
before_cb, after_cb = create_llm_cache_callbacks(llm_cache)

agent = Agent(
    model="gemini-flash-latest",
    name="cached_agent",
    instruction="You are a helpful assistant with semantic caching enabled.",
    before_model_callback=before_cb,
    after_model_callback=after_cb,
)

Now "What is Pub/Sub?" and "Explain Pub/Sub" land within distance_threshold of each other and share one cached answer. It's the same two-callback pattern as Example 1 — the provider just supplies a smarter key (an embedding) and a durable store.

Managed alternativeLangCacheProvider does the embedding server-side, so you skip the local vectorizer and Redis-with-RediSearch. Same create_llm_cache_callbacks() wiring.

When to use it (and when not to)

Good fitPoor fit
Repeated / paraphrased FAQ-style promptsEvery prompt unique (no repeats to hit)
Answers stable over the TTL windowAnswers must reflect live data each call
Stateless or safely-shareable responsesPer-user personalized answers (unless key includes user)
Response caching vs. context caching — don't conflate them (the deck's slide 6 correction): response caching skips the model on a hit; context caching still runs the model but discounts the re-sent prefix. They compose — cache the whole answer when you can, discount the prefix when you can't.
