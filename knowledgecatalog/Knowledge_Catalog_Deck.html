A catalog is a queryable map of your data — kept fresh by machines

Knowledge Catalog stores metadata, never the data itself: one searchable entry per asset, across every engine Meridian runs.

  • Governance foundation — technical metadata collected automatically; one zone-level grant propagates IAM to attached storage
  • Context curation — Gemini infers business meaning from schemas, query logs, and usage — accumulating into a context graph
  • Context retrieval — semantic search for people, MCP tools for AI agents: the same map, two kinds of readers
Naming history: Data Catalog → Dataplex Universal Catalog → Knowledge Catalog (April 2026). APIs, gcloud dataplex, and billing SKUs still say dataplex.
The three pillars, straight from the docs: foundation, curation, retrieval.
Speaker notes — What Knowledge Catalog is
  • Be precise about the boundary, because it's the compliance answer too: the catalog holds metadata — names, schemas, descriptions, relationships — never rows. That's why pointing it at everything is safe, and why lineage can be shown to auditors without exposing data.
  • The three pillars come verbatim from the overview doc. Pillar 3 ("retrieval — for agents") is what's genuinely new in 2026 and why Google renamed the product; Section 4 lands it.
  • The naming callout matters practically: students will find blog posts about "Dataplex," "Dataplex Universal Catalog," and "Data Catalog." Same lineage, one current product. Data Catalog itself is deprecated and being transitioned.
  • The three arrow styles are the acquisition story in miniature (Section 2 expands it): Google Cloud analytics sources are automatic; Cloud SQL/AlloyDB are integrated — on by default for instances created after mid-April 2026, one gcloud patch for older ones; Snowflake and other externals arrive by scheduled connector pipeline. Nothing external is collected "automatically."
  • Policy propagation, precisely: for resources attached as assets in a lake/zone, granting a data role (e.g. roles/dataplex.dataReader) makes the service write translated IAM bindings onto the underlying buckets and datasets themselves — the principal really appears in their IAM policies; takes up to 30 minutes. It applies only to attached assets — merely cataloging a table never touches its IAM. The other compliance pattern: require a DataSensitivity aspect via an entry type, then aspect:DataSensitivity.level=PII in search is the "show me every PII asset" audit, on demand.
  • Anticipated question: "is this a data warehouse?" No — nothing moves. The catalog references data where it lives.

Entries hold facts; aspects hold meaning

Before any definitions, look at one: the actual catalog record for Meridian's orders table. All five words, visible at once.

ENTRY  bigquery: meridian-prod.sales.customer_orders
├─ entry group  @bigquery        the drawer it's filed in
├─ entry type   bigquery-table   what kind of card this is
├─ aspects                        forms stapled to the card
│  ├─ schema (system)       24 columns: order_id, email, …
│  ├─ ContactInfo (custom)  owner=sales-eng · #sales-data
│  └─ DataSensitivity       on the email column: level=PII
└─ entry links                    string to other cards
   └─ definition ← glossary term "Net Revenue"
  • Entry — the index card for one asset. Tables, topics, models — but glossary terms and data products are entries too
  • Aspect — a filled-in form stapled to the card or to one column; the aspect type is the blank form
  • Entry type — the checklist: "cards of this kind must carry forms X and Y"
  • Entry group — the drawer of cards, and the IAM boundary
  • Entry link — typed string between two cards: synonym, related, definition, schema-join
Every later feature is these words combined: quality score = an aspect · glossary term = an entry · data product = an entry · lineage = its own graph, not entry links.
Speaker notes — The data model
  • Slow down here — this is the one abstraction slide. Walk the tree on the left top to bottom before touching the definitions: students should see the object first, then hear the word. The metaphor to keep using all deck: entry = index card, aspect = filled-in form stapled to it, aspect type = the blank form, entry type = the checklist of required forms, entry group = the drawer, entry link = string between two cards.
  • Columns are addressable: an aspect can attach to a single column (the DataSensitivity line in the tree), which is how column-level sensitivity tags and glossary links work. Columns come into existence when the schema aspect lands on an entry.
  • The closing callout's last clause is a deliberate landmine-defuser: lineage "links" (Section 3) are observed from job runs and are not entry links. Same word, different mechanism — say it now and again on the lineage slide.
  • For anyone migrating from Data Catalog, the rosetta stone: tag template → aspect type, tag → aspect.
  • Gotcha worth stating: custom aspect types referenced by an entry type must live in the same project and location as that entry type. Plan one governance project rather than scattering types.
  • Reference: metadata management overview.

Speaker notes — Automatic ingestion
  • The moment to land: most students think "set up a catalog" is a project. For the Google Cloud half of the estate it is an API enable — the catalog exists whether or not you look at it. Demo this live if you can: open Search in the console on any project with BigQuery tables.

An engineer runs ALTER TABLE customer_orders DROP COLUMN legacy_sku; the BigQuery integration updates the entry's schema aspect; the feed publishes a message with the entry name, change type, and which aspect changed; a small Cloud Run subscriber checks it against registered data contracts and pages the owning team — before Monday's dashboards break. Scope + filters (entry type, aspect type, CREATE/UPDATE/DELETE) are how you avoid being firehosed.
  • Cloud SQL nuance for older estates: the integration covers the primary instance (not read replicas), and pre–April-2026 instances stay invisible until someone runs the patch command — worth a slide-9 checklist item.

The rest of the estate arrives by pipeline, not by typing

Marcus's problem: Snowflake and the old Postgres schemas aren't Google Cloud. Managed connectivity imports their metadata on a schedule.

A managed connectivity pipeline. Swap the leftmost box for any source you can reach.
  • Prebuilt connectors — Oracle, MySQL, PostgreSQL, SQL Server: configure a connection + schedule on the console's Connectors page, no code; each run fully overwrites the connector's entries
  • Community connectors — Snowflake and others: open source in the cloud-dataplex GitHub repo, not officially supported; they run on the pipeline above
  • Custom connector — anything that can emit ImportItem files can be cataloged; the import job doesn't care who wrote them
Speaker notes — Managed connectivity
  • The design point to emphasize: the import file format is the contract. Google's connectors, community connectors, and your own script are all equal citizens — if it emits ImportItem, the catalog ingests it. That's the extensibility story in one sentence.
  • The two stages are genuinely separate: the connector only extracts and writes files; loading is the metadata import job, a catalog-side service operation (CreateMetadataJob) that the orchestrator invokes as its own step. Worked example: 02:00 Workflows starts the run → Snowflake connector on Managed Spark emits snowflake-metadata-20260805.jsonl to gs://meridian-catalog-imports/ → pipeline calls CreateMetadataJob → the job diffs the file against entry group snowflake_dw → by 02:20 the new finance_mart.q3_revenue table is searchable next to its BigQuery cousins.
  • ImportItem format: newline-delimited JSON, < 1 GiB per file, one item per line: {"entry": {"name", "entryType", "aspects"}, "updateMask", "aspectKeys"}. Sync modes: FULL for entries — anything in scope but missing from the file is deleted; the file is the source of truth — and INCREMENTAL for aspects. Monitor with GetMetadataJob / Cloud Logging.
  • If asked what runs the prebuilt connectors: they're implemented on BigQuery Data Transfer Service — Google reused its mature scheduling/credential machinery to move metadata. Implementation detail, not concept; students may spot BQ DTS transfer configs in the console.
  • Be honest about support tiers: community connectors are public repos, not officially supported by Google. Fine for metadata (worst case: stale entries), but say it.
  • Foreshadow cost: connector runs bill as the services they use — Managed Spark, Cloud Storage, Dataflow — under those SKUs, not Dataplex. Marcus's bill-archaeology thread continues on the cost slide.
  • References: managed connectivity overview, develop a custom connector.

One search box over every entry, aspect, and glossary term — semantic when you type a question, exact when you type an operator.

  • Faceted filters and logical operators for precision when you already know the shape of the answer
  • Search indexes aspects too — enrichment isn't decoration; it's what makes assets findable
  • Programmatic lookup translates a fully qualified SQL name to its catalog entry — tools can resolve sales.customer_orders without screen-scraping

One example, end to end: making Net Revenue mean one thing

Glossary term, entry links, custom aspect — three mechanisms from slide 5's vocabulary, composed to resolve Priya's 14-table search.

  1. Finance writes glossary term Net Revenue — a prose definition with an owner. The term is itself an entry
  2. A definition entry link attaches the term to column fin.revenue_daily.net_revenue — the column is now findable by the business word
  3. A synonym entry link joins Net Sales, the old finance word, to Net Revenue — either vocabulary lands in the same place
  4. Orthogonal to the glossary: a Certification aspect (status=certified) stamped on the table — an attribute of the table, not a definition of a word
The numbers match the steps — walk them in order.
Priya's search works because all four cooperate: her query matches the term (1), links walk to the column (2–3), and the aspect says which of the 14 candidates finance stands behind (4).
Speaker notes — Glossary and enrichment
  • The Socratic move: ask two students to define "active customer." When their answers differ, you've demonstrated the glossary's job better than any slide.
  • Name the primitives as you walk the steps — this slide is slide 5's vocabulary paying off: the term is an entry, both attachments are entry links, certification is an aspect. Nothing new was invented; three existing objects were composed.
  • Column-level term linking is the differentiator over Data Catalog's glossary — a term like Net Revenue points at the exact column, not just the table. That's what step 2's link does.
  • If asked what the Certification aspect type looks like: a small JSON template — status enum (certified/deprecated) plus an owner string — defined once, stamped on every certified asset, searchable forever. Real schema in the catalog docs.
  • The social truth (was on the slide, still true): glossaries succeed socially, not technically — domain owners must write the definitions. A glossary authored by central IT alone is just another wiki. Field experience, not docs; own it as opinion, hold it firmly.

Gemini writes the first draft of your documentation

2,400 tables will never be hand-documented. Curation at that scale is an inference job — and inference is now cheap.

  • Automated metadata generation — Gemini drafts descriptions for tables and columns at scale; stewards review and accept
  • Business intent is inferred from schemas, query logs, and semantic models — how data is used reveals what it means
  • The result accumulates into the context graph: a live map of how assets relate to business concepts
  • Example queries — verified SQL patterns capturing real business logic ("quarterly net revenue, the approved way"), reusable by people and agents alike
Curation as inference: the "Knowledge" in the product name is earned here.
Billing note: Gemini-powered features (data insights, automated metadata) bill through Gemini in BigQuery — not the Dataplex SKUs on the cost slide.
Speaker notes — Gemini curation
  • Set expectations precisely: generated descriptions are drafts for steward review, not truth. The failure mode is auto-accepting plausible-but-wrong descriptions — which poisons search and any agent grounded on the catalog. Human review is the quality gate.
  • "Query logs reveal meaning" deserves a concrete example: if every finance query joins orders to refunds before summing, that join is the de facto definition of net revenue — and it becomes the example query.
  • Example queries reappear on the MCP slide: they're what keeps agent-generated SQL on the approved path. Plant that connection now.
  • Reference: overview — context graph and example queries are named concepts there.

Speaker notes — Lineage: the graph
  • Be precise about direction, because impact analysis reverses it: the auditor walks upstream (where did this come from); the engineer deleting a column walks downstream (who breaks). Same graph, both directions — next slide.
  • The "automatic" claim has a boundary: it covers the listed Google Cloud services. A Python script that rewrites a table via the client library appears as a BigQuery job (captured); movement done entirely outside Google Cloud does not — that's what OpenLineage import is for.
  • Process/run/event mirrors how students already think about Dataflow: pipeline/job/step. Use that analogy. These are the Data Lineage API's official resource names (processes, processes.runs, runs.lineageEvents; searchLinks returns the links).
  • Operational facts for the questions that always come: processing bills as premium DCU-hours (billing label goog-dataplex-workload-type: LINEAGE) and stored lineage counts as metadata storage; reads — console graphs and API — are free. It's opt-in per project because enabling starts metered background collection, and recording who-transforms-what is itself a governance decision (VPC-SC supported; CMEK not). Storage is the lineage service's own Google-managed regional storage — you can't query it directly; for history beyond 30 days, export via the API into your own BigQuery dataset on a schedule.

The catalog is how AI agents learn what your data means

An agent asked "what was net revenue last quarter?" will confidently query the wrong table — unless something tells it which one is right. That something is the catalog.

  • Knowledge Catalog ships an MCP server (local and remote) — Model Context Protocol, the open standard agents use to discover and call tools
  • Agents get the same map people do: search, glossary, lineage, example queries — IAM-filtered, like every other reader
  • The context graph + verified example queries keep generated SQL on approved sources and approved logic — grounding, not vibes
  • Same catalog work, double payoff: everything Meridian curated for Priya now grounds its agents
Grounding an agent = giving it the map, not more confidence.
Speaker notes — Agents and MCP
  • The argument in one line: hallucination in enterprise NL-to-SQL is mostly a context failure, not a model failure — the model never knew which of the 14 revenue tables was real either. The catalog is where that knowledge lives; MCP is the plug.
  • Students who've built agents will recognize MCP immediately; for the rest: an open protocol for exposing tools to any agent framework — not a Google-proprietary interface.
  • Governance point worth pausing on: agents authenticate and get IAM-filtered results like any user. No side door.
  • Demo idea: data insights in BigQuery Studio (Gemini-generated questions/queries about a table) shows catalog-grounded generation without any agent setup.

Speaker notes — Cost
  • The pattern to teach: storage-cheap, processing-metered. Nobody has ever been surprised by a metadata storage bill; plenty have been surprised by an unsampled daily quality scan over five years of history. That was Marcus's bill.
  • DCU-hour is an abstract unit (billed per second, one-minute minimum) — consumption scales with rows, columns, rule complexity, and scan frequency. You can't precompute it exactly; you can bound it with sampling and incremental scans, then read actuals off the billing label.
  • Standard vs premium is a billing split, not a performance one — the tier is decided by which feature family consumed the compute (discovery = standard; lineage, quality, profiling = premium). Nothing runs faster on premium.
  • What lineage does that burns DCUs: every finished job's events get processed — the SQL/job graph parsed into inputs→outputs, up to 1,500 column mappings resolved, process/run/event records written into the graph. It scales with job volume: 50,000 queries a day generates far more lineage processing than 500. No published formula — watch the LINEAGE billing label for a week and extrapolate.
  • Quirk worth naming: a custom execution identity on a scan bills compute to your BigQuery project instead of premium DCUs — changes which budget owns the cost.
  • Free-tier nuance: the 100 DCU-hr/month applies to standard only; premium (lineage, quality) has no free tier — but lineage's premium usage for typical estates is small.
  • Prices drift; SKUs still say "Dataplex." Re-check the pricing page the week you teach this.

Knowledge check

Four questions — answers in the speaker notes.

  1. A steward wants every production table to carry an owner and a sensitivity rating. Which two catalog concepts implement that requirement?
  2. Marcus needs 14 months of provenance for an annual audit. Lineage retention is 30 days — what's the correct design?
  3. Which parts of Meridian's catalog bill are free: auto-ingested BigQuery technical metadata, custom aspects, search API calls, nightly quality scans?
  4. An agent keeps generating SQL against a deprecated revenue table. Name two catalog mechanisms that steer it to the certified one.
If you can answer all four with slide-5 vocabulary — entries, aspects, entry types, links — the model stuck.
Speaker notes — Knowledge check (answers)
  • Q1: an aspect type (defining owner + sensitivity fields) made mandatory by an entry type (e.g. StandardOperationalTable requires it). Bonus credit for noting aspects can also attach per column.
  • Q2: scheduled export of lineage (via the Lineage API) into the team's own storage — e.g. monthly SearchLinks/streaming pulls into BigQuery. The catalog's graph is a 30-day rolling window, not an archive.
  • Q3: free: auto-ingested technical metadata storage and API/search calls. Paid: custom aspect storage (≈$2/GiB-month — tiny) and quality scans (premium DCUs — the one to tune with sampling/incremental).
  • Q4: any two of: certified/deprecated aspects surfaced through search ranking; verified example queries encoding the approved SQL; the context graph relating the business term to the certified asset; glossary term linked to the right table. All reach the agent through the MCP server.
  • Run it as pair discussion, 3–4 minutes, then cold-call. Q2 is the one most groups miss — revisit the retention callout if so.
