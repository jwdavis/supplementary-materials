Speaker notes — Section 1: Partitioning
  • First lever. The mechanism is one sentence given last module’s vocabulary: partitioning makes the commit boundary match the query boundary.

What partitioning physically is

  • A partitioned table routes rows at write time into per-partition storage sets: every storage set belongs to exactly one partition
  • Each partition behaves like a small table: its own metadata, its own lifecycle
  • Pruning = the metadata index returns only matching partitions’ storage sets — before touching data
Speaker notes — What partitioning is
  • In our vocabulary: partition filter → index lookup → storage-set selection, all metadata-level. Bytes billed are computable before running — partitioned tables keep precise upfront estimates (contrast with clustering, later).
  • Streaming caveat inline: rows in the write-optimized buffer aren’t in any partition yet — they sit in __UNPARTITIONED__ (NULL pseudo-columns) until extraction routes them. Source: partitioned-tables doc.
  • “Each partition behaves like a small table” pays rent three times on the ops slide ahead: expiration, per-partition long-term pricing, per-partition DML isolation.

What breaks pruning

Pruning needs a filter the metadata can evaluate: the partition column, isolated, compared to constants.

-- ✓ prunes
WHERE event_time >= TIMESTAMP('2026-07-28')

WHERE DATE(event_time) = '2026-07-28'

WHERE DATE_TRUNC(DATE(event_time), MONTH)
      = '2026-07-01'
-- ⚠ may prevent partition elimination
WHERE TIMESTAMP_ADD(event_time,
  INTERVAL 9 HOUR) >= '2026-07-28'
    -- arithmetic on the column
WHERE event_time >=
  (SELECT MAX(day) FROM control_table)
    -- subquery (verify)
WHERE event_time >= '2026-07-28'
   OR org_id = 'acme'
    -- OR with another column (verify)
The timezone-shift version (top-right) is the one that bites real dashboards. Fix: shift the constant, not the column. Verify the actual estimate with a dry run; supported constant expressions and predicate shape matter.
Speaker notes — What breaks pruning
  • The whitelist of pruning-safe functions (DATE_TRUNC, TIMESTAMP_ADD/SUB/DIFF, EXTRACT, CAST to DATE…) is in the querying-partitioned-tables doc — link it, don’t memorize it. Teach the shape: column alone on one side, constants on the other.
  • This slide exists because the original module never said any of it, and it is the most common real-world partitioning bug.
  • Verification habit: the dry-run byte count tells you immediately whether your filter pruned.

Three ways to partition, four granularities

  • Time-unit column (our case): DATE / TIMESTAMP / DATETIME; hourly, daily, monthly, yearly
  • Ingestion time: no suitable column needed; filter via _PARTITIONTIME / _PARTITIONDATE pseudo-columns
  • Integer range: stable numeric domains (rare)
-- if a day is still too big:
PARTITION BY TIMESTAMP_TRUNC(event_time, HOUR)

-- integer range:
PARTITION BY RANGE_BUCKET(customer_number,
  GENERATE_ARRAY(0, 100, 10))
Selection heuristic, stated plainly: partition by the column every query filters on — in telemetry, almost always the event date/time. Ingestion time only when data has no reliable event timestamp.

  • Out-of-range and NULL partition-column values land in __UNPARTITIONED__ and __NULL__ partitions — worth knowing when byte counts don’t add up.
  • The 17,520 row sets up the next slide’s limit discussion. Source: partitioned-tables doc + quotas.

Limits and the granularity decision

  • 10,000 partitions per table (hard limit); 4,000 modified per job; daily modification quotas
  • Docs guidance: aim for ≥ ~10 GB per partition
  • Partitions too small or too many? Coarser granularity + clustering (next section), or clustering alone
  • Too many partitions = metadata overhead: slower planning, slower full scans, slower commits
Ask the room: daily or hourly for qos_events? (Daily: queries are day-grained, and hourly breaks the limit if retention ever grows to 2 years.)
Speaker notes — Limits and granularity
  • Correction propagated from the fact-check: older material (the original module, the 2019 book) says 4,000 — the current per-table limit is 10,000, and 4,000 survives as the per-job modification limit. Source: docs.cloud.google.com/bigquery/quotas.
  • “Each partition behaves like a table” cuts both ways: per-partition metadata is the power and the overhead. Last module’s fragmentation story (many tiny commits) is the same disease in a different costume.

Partitions as an ops lever

  • Expire old data automatically — deletes are metadata flips, not DML
  • Cheaper archives: partitions untouched 90 days drop to long-term pricing individually
  • DML isolation: mutations touching different partitions don’t conflict; the nightly GDPR delete now rewrites only the partitions holding that participant
  • Surgical backfills: overwrite one day, not the table
ALTER TABLE
  clearmeet_analytics.qos_events_p
SET OPTIONS
  (partition_expiration_days = 90);

# redo one bad day in place:
bq query --destination_table \
'clearmeet_analytics.qos_events_p$20260728' \
  --replace 'SELECT … FROM staging_reload'
Last module’s bad-backfill incident now has a surgical fix ($20260728 overwrite) as well as a time-travel undo.
Speaker notes — Partitions as an ops lever
  • Tie each bullet back to machinery: expiration = storage-set GARBAGE flip; long-term pricing per partition (90 untouched days, ~half price, queries don’t reset the clock); DML conflict scope = partition.
  • The table$YYYYMMDD partition decorator works in bq and load/copy jobs.

Anti-pattern: date-sharded tables

  • The old way: qos_events_20260726, _20260727, … queried with wildcards
  • Costs: per-table metadata and permission checks, schema drift, wildcard quirks — and wildcard-table queries have query-cache limitations: do not assume a cache hit
  • The docs now say it plainly: partitioning performs better — it stays the preferred migration path
-- if you inherit shards, query them…
SELECT * FROM
  `clearmeet_analytics.qos_events_*`
WHERE _TABLE_SUFFIX BETWEEN '20260726'
                   AND '20260728';
-- …then convert them (one time)
Speaker notes — Anti-pattern: sharded tables
  • Frame as inherited legacy, not a choice: students will meet sharded datasets (NOAA GSOD, old exports). Wildcards + _TABLE_SUFFIX are the reading skill; conversion is the fix. Source: partitioned-tables doc, “Partitioning versus sharding.”
  • gcp-demos “Sharded and Wildcard Tables” activity fits here if time allows.

Speaker notes — Section 2: Clustering
  • The scenario beat matters: partitioning solved “which day”; it does nothing for “which customer within the day.”

What clustering physically is

  • CLUSTER BY makes BigQuery sort rows by your columns when writing each partition’s storage set
  • Data lands in storage blocks, adaptively sized — shown here as files for intuition
  • Sorting on write tends to narrow block ranges, so the per-block min/max metadata (which always existed) can exclude blocks
  • Partitioning prunes storage sets; clustering prunes blocks within them
Speaker notes — What clustering is
  • Emphasize what’s new vs partitioning: no new metadata machinery at all — clustering just narrows the ranges the existing per-block metadata already records, so more blocks can be excluded.
  • Current docs say storage blocks, adaptively sized, and describe block pruning; the file drawing is a teaching aid. Don’t promise “one block will be read” — say “fewer blocks,” then measure. Sources: clustered-tables doc; Definitive Guide pp. 222–223 (the older file/binary-search description).
  • Up to 4 clustering columns; STRING uses the first 1,024 characters.

Creating: order matters

CREATE TABLE
  clearmeet_analytics.qos_events_pc
PARTITION BY DATE(event_time)
CLUSTER BY org_id, device_type
AS SELECT * FROM
  clearmeet_analytics.qos_events_p;
  • Up to 4 columns; sort is lexicographic — the leading clustering columns generally provide the strongest pruning, and later columns help most when the leading columns are also constrained
  • Clustering can be added to an existing table; new writes honor it, old data reclusters over time
The phone book rule: sorted by (last, first). Looking up Garcia, Maria — fast. Finding everyone named Maria — much less help from the sort order.

org_id ✓ · org_id, device_type ✓ · device_type alone: little or no pruning
Column choice: most-selective commonly-filtered column first — here org_id (40k values), then device_type (5). High cardinality is good for clustering — the exact opposite of partitioning.
Speaker notes — Creating: order matters
  • That inversion — partitioning wants low cardinality (≤ 10k), clustering wants high — is the fundamental division of labor. Say it twice.
  • ALTER TABLE … SET OPTIONS can add clustering to an existing table; the fake-NULL-date hack from older material (clustering once required partitioning) has been obsolete for years and is gone from this deck.
  • Clusterable types: most scalars (no ARRAY/STRUCT fields). Source: clustered-tables doc.

The payoff, and where it shows up

  • Acme dashboard: 120 GB → ~3 GB in this measured run (only blocks whose org_id range covers acme)
  • Beyond scanning: like keys are pre-colocated — GROUP BY org_id and joins on org_id shuffle less
  • LIMIT on clustered filters can stop early
Real magnitude, public data: Wikipedia pageviews 2.2 TB, CLUSTER BY wiki, title → the same filtered query drops 180 GB → 38.6 GB, 5× faster.
Speaker notes — Clustering payoff
  • The Wikipedia numbers come from the Definitive Guide (p. 285, Felipe Hoffa’s table); rebuild on current public wikipedia pageviews data at demo time and keep the shape (“~5×”), not the exact digits.
  • The shuffle benefit is one sentence here because students know what shuffle costs from the Architecture deck — the original module needed two diagrams for this.
  • 64 MB threshold source: clustered-tables doc (“likely to benefit”).

The estimate caveat (and what to do about it)

  • Partition pruning is priced before the run; cluster pruning happens during it
  • So on clustered tables the validator shows an upper bound; the real (lower) bytes appear in job stats afterward
  • Habit: dry-run for the ceiling, job stats for the floor; cap with maximum_bytes_billed if you need a hard stop
SELECT job_id, total_bytes_processed,
       total_bytes_billed
FROM `region-us`
     .INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE creation_time > TIMESTAMP_SUB(
      CURRENT_TIMESTAMP(), INTERVAL 1 DAY)
ORDER BY creation_time DESC;

Speaker notes — The estimate caveat
  • Mechanism in one sentence from the Architecture model: the estimate is computed from storage-set metadata; block-level min/max elimination happens at execution.
  • The original module stated this caveat twice and never operationalized it — the three-step habit on this slide is the fix.
  • This is also the honest answer to “why does my clustered table say it will cost more than it does?” — a very common student question.

Clustering decays; the optimizer repairs it

  • Streaming keeps appending small storage sets whose blocks overlap the sorted ranges
  • A lookup may now hit multiple sets — “stack depth” > 1
  • Automatic reclustering: the storage optimizer re-sorts in the background — free, no slots consumed, no action required
Same machinery as last module’s compaction — resorted instead of merely merged.
Speaker notes — Clustering decays
  • This is the Architecture deck’s storage-optimizer slide wearing cluster clothes — say exactly that; the reuse is the pedagogy.
  • The original module’s best content (stack depth, overlap) lived in speaker notes under unlabeled diagrams; here it’s the slide face.
  • Practical corollary: freshly streamed data is briefly less-clustered, so heavy readers of the last few minutes get slightly worse pruning. That’s the trade for free background repair. Sources: clustered-tables doc (automatic, free, capacity-neutral); Definitive Guide pp. 223–224.
  • For partitioned tables, clustering is maintained within each partition.

Speaker notes — Partition or cluster?
  • Modeled on the book’s Table 7-1 (p. 287) with current-docs guidance folded in (10 GB/partition aim, 64 MB clustering threshold, “clustering instead of more partitions” from the quotas doc).
  • Decision beat: SDK-rollout monitoring filters WHERE sdk_version = '8.2.1' AND event_time >= …. Extend clustering to (org_id, sdk_version)? Discuss: second position only helps queries that also filter org, so a separate rollup may serve better. There isn’t one right answer — the point is that they can now argue it mechanically.

When clustering alone beats partition + cluster

  • Measured on weather data, same query: clustered-only table 14.7 MB; partitioned and clustered 1.53 GB (one illustrative measurement)
  • Why? Monthly partitions were tiny — each holds one small storage set with too little data to spread across multiple blocks
  • So clustering had nothing to prune, and the query paid per-partition overhead across hundreds of partitions
The pruning unit is the storage block. A partition needs enough data to spread across several blocks before clustering has anything to exclude.
Speaker notes — When clustering alone wins
  • Kept from the original module because it’s memorably counterintuitive — but the mechanism is now stated instead of wondered about (its speaker notes literally asked “is this the correct assumption?”).
  • The original demo dataset (fh-bigquery) is defunct; rebuild on bigquery-public-data.noaa_gsod at demo time and treat the two figures as “expected shape,” not gospel.
  • Second-order effect worth mentioning: a storage block is the unit matched to a slot in stage 1, so over-partitioning also wastes parallelism — lots of slots doing almost nothing.

Schema shapes: skip the join

A relational export just arrived: meetings, participants, orgs. The dashboard now needs poor-audio share by pricing plan — and joins don’t scan more, they shuffle more.

Speaker notes — Section 3: Schema shapes
  • New question shape: not “how much do we scan” but “how much do we shuffle” — the join costs from the Architecture deck come home to roost.
  • The three options are genuinely all valid; the section teaches when each is right, not a single winner.

Option 1: keep it normalized

  • Perfectly valid in BigQuery: storage-efficient, one source of truth, easy to update
  • Cost: every query pays the join
  • Small dims (orgs, 40k rows) broadcast for nearly free
  • Fact-to-fact joins shuffle both sides — billions of rows moving per refresh
Star schema: green joins are cheap, the red one is not.
Speaker notes — Option 1: normalized
  • Docs-aligned guidance: normalized, star, and snowflake schemas all work fine in BigQuery — bring them as-is first (don’t optimize prematurely). The 10 GB heuristic arrives at the end of this section.
  • The red arrow is quantifiable from the Architecture deck: both sides hashed by meeting_id through the shuffle tier, billions of rows per dashboard refresh — and a spill risk.

Option 2: denormalize (flatten)

  • Pre-join into one wide table: no join at query time
  • Columnar storage makes the repeated columns cheap — plan_tier repeated 5B times is a dictionary + RLE dream
  • Costs: storage repetition, update anomalies (a plan rename rewrites everywhere)
  • And grouping on the one-to-many key still shuffles
CREATE TABLE clearmeet_analytics.qos_flat
AS
SELECT q.*, m.started_at,
       m.plan_tier, o.org_name
FROM qos_events q
JOIN meetings m USING (meeting_id)
JOIN orgs o     USING (org_id);
Why repetition is cheaper here than in a row store: the repeated column is its own file, dictionary-encoded and run-length compressed. The real tax is maintenance and consistency, not bytes.
Honest failure mode: per-meeting aggregations on the flat table still shuffle by meeting_id. Flattening removes joins, not grouping.
Speaker notes — Option 2: denormalize
  • Denormalization was devised when storage was expensive and joins were the only alternative; in BigQuery the calculus shifted, but integrity maintenance still costs human time.
  • The “still shuffles” caveat is the pivot into nesting — that’s the failure mode nesting actually fixes.

Option 3: nest the one-to-many

  • One row per meeting; participants as an ARRAY of STRUCTs inside it
  • Parent and children are stored together: no join, and no shuffle to reassemble a meeting
  • Columnar still applies — untouched nested fields aren’t read
CREATE TABLE meetings_n AS
SELECT m.meeting_id, m.plan_tier,
       m.org_id,
  ARRAY_AGG(STRUCT(p.participant_id,
    p.device_type, p.avg_audio_mos))
    AS participants
FROM meetings m
JOIN participant_rollups p
  USING (meeting_id)
GROUP BY 1, 2, 3;
Speaker notes — Option 3: nest

  • Granularity superpower: pick your grain by whether you UNNEST. Aggregates at meeting level need no flattening at all.
  • Physical tie-back: nested/repeated columns are encoded with repetition/definition levels (the Dremel paper scheme Parquet adopted) — the Architecture deck mentioned this in the Capacitor slide.

Working with nested data: the two moves

  • Stay at parent grain — reference or aggregate the array in place
  • Drop to child grain — CROSS JOIN UNNEST(...): the join that never leaves the row
-- child grain: poor-audio share by plan
SELECT m.plan_tier,
  COUNTIF(p.avg_audio_mos < 3.5)
    / COUNT(*) AS poor_share
FROM clearmeet_analytics.meetings_n AS m
CROSS JOIN UNNEST(m.participants) AS p
GROUP BY m.plan_tier;

-- parent grain: no UNNEST needed
SELECT meeting_id,
       ARRAY_LENGTH(participants) AS n_people
FROM clearmeet_analytics.meetings_n;
CROSS JOIN UNNEST is a “correlated flatten,” not a real join. Each row only unnests its own array — no shuffle, no data movement.
The comma shorthand FROM t, UNNEST(t.arr) AS x is everywhere in the wild — same thing. Add WITH OFFSET when you need element order.
Speaker notes — Working with nested data
  • Deliberate compression: the original module spent ~24 slides on ARRAY/STRUCT drills. The deck carries the two moves and the mental model; the lab carries the syntax reps.
  • Array order is preserved within an array (unlike table row order) — OFFSET is 0-based, ORDINAL is 1-based, and out-of-bounds fails the query (failed queries are free).
  • If the room wants more: ARRAY_AGG, ARRAY() subqueries, and WHERE x IN UNNEST(arr) filtering are the next three things to show live.

Choosing a shape: the working rules

  • Dimension < ~10 GB and mutable → keep it a normalized table; joins broadcast, updates stay one-row-one-place (orgs)
  • Big, read-together one-to-many → nest it (participants inside meetings)
  • Denormalize flat when downstream tools can’t handle nesting, or to precompute one hot path
  • Any shape can also be partitioned + clustered — these compose
The 10 GB rule has a mechanism behind it: below broadcast size, a join is nearly free, so normalization costs nothing at read time.
Speaker notes — Choosing a shape

Speaker notes — Section 4: Materialized views
  • The cache exception is the hook: students learned last module that re-running a query is free — except on a streaming table, which is exactly ClearMeet’s case.

Materialized views: fresh results when eligible

  • Stores the result of an aggregation and lets BigQuery maintain it in the background as base tables change
  • When a read is eligible it is current: stored rows plus only the base-table changes since the last refresh
  • When the changes invalidate it, BigQuery reads the base tables instead: correct answer, full price
  • Three things decide what you get: the definition, the refresh settings, and the staleness you allow
CREATE MATERIALIZED VIEW clearmeet_analytics.mv_daily_quality

SELECT DATE(event_time) AS day, org_id, device_type,
       COUNTIF(audio_mos < 3.5) AS poor, COUNT(*) AS total
FROM clearmeet_analytics.qos_events_pc
GROUP BY day, org_id, device_type;

Behavior 1: incremental refresh (the default)

  • Background refresh, best effort: attempted within about 5 minutes of a base-table change if the last one ran more than 30 minutes ago
  • Between refreshes an eligible read is still current, because BigQuery merges stored rows + changes since the last refresh
  • Invalidating changes push the read back to the base tables until the view re-materializes

Speaker notes — Behavior 1: incremental refresh
  • Say the mechanism out loud: the MV is not a cache with a TTL. It is a stored partial result that the engine finishes at query time by reading only what arrived since the last refresh.
  • Docs wording for refresh cadence: cached data is refreshed “within 5 to 30 minutes of a change to the base table,” automatic refresh is “performed on a best-effort basis,” and refresh jobs run as batch-priority jobs under a Google-owned service account — visible in your project’s job history.
  • Manual refresh for the demo: CALL BQ.REFRESH_MATERIALIZED_VIEW('project.dataset.mv_daily_quality'). Don’t run two at once — only the first to finish succeeds.
  • The third row of the table is the honest one, and the reason the next slide exists: not every definition or every mutation can be maintained incrementally.

Behavior 2: when incremental maintenance can’t apply

  • Incremental refresh covers a documented SQL subset. Currently outside it: UNION ALL, outer joins, self-joins, window functions, ARRAY subqueries, non-deterministic functions, UDFs (outer join and UNION ALL support is in preview)
  • Aggregations are a published list, not “anything”: SUM, COUNT, COUNTIF, MIN/MAX, AVG, ARRAY_AGG, APPROX_COUNT_DISTINCT and a few more
  • allow_non_incremental_definition = TRUE buys the wider SQL and changes the deal: it must accompany max_staleness, every refresh reruns the whole query, and smart tuning does not apply

Speaker notes — Behavior 2: non-incremental
  • Order of the diagnosis when a student asks “why is my MV expensive?”: is the definition incremental? is it being refreshed? is a rewrite happening? is max_staleness set? This slide answers the first.
  • Doc anchor: “Non-incremental materialized views support most of the syntaxes that incremental materialized views don’t support,” the option “must be accompanied by the max_staleness option,” and “only incremental materialized views can take advantage of smart tuning.”
  • Full supported-aggregation list (for the inevitable question): ANY_VALUE, APPROX_COUNT_DISTINCT, ARRAY_AGG, AVG, BIT_AND/BIT_OR/BIT_XOR, COUNT, COUNTIF, HLL_COUNT.INIT, LOGICAL_AND/LOGICAL_OR, MAX, MIN, MAX_BY, MIN_BY, SUM.
  • max_staleness is optional on an incremental view and required on a non-incremental one — that pairing is the row cut from the table for space.
  • Worth saying: the preview items (LEFT OUTER JOIN, UNION ALL) inherit incremental limitations — preview is not the same as supported.

The two freshness dials

  • refresh_interval_minutes — how often a refresh may run (cap: 1 minute to 7 days); enable_refresh = FALSE stops it
  • max_staleness — how old a read may be (range: 30 minutes to 3 days)
  • Inside the window: MV only, no base-table read. Outside it: MV plus the changes since the last refresh
  • Size the interval so a refresh finishes inside the window

Speaker notes — The two freshness dials
  • Docs’ own sizing example: a refresh that takes an hour → refresh_interval_minutes = 120 with max_staleness of 4 hours (runtime plus a margin for growth).
  • The counterintuitive bit that students get backwards: max_staleness makes reads cheaper by allowing them to be older. Without it you always get current data and always pay for the delta merge.
  • Doc sentences worth reading aloud: “If the last refresh occurred within the max_staleness interval, then BigQuery returns data directly from the materialized view without reading the base tables,” and if it occurred outside, BigQuery “reads the data from the materialized view, combines it with changes to the base table since the last refresh, and returns the combined result.”
  • ClearMeet decision beat: a 5-minute dashboard refresh over streaming telemetry does not want a 1-hour staleness bound — but the weekly exec rollup happily would. Same view, different consumer, so this is a per-view design choice.
  • The 260M figure is 75 minutes × 3.5M rows/minute — derive it on the board so the cost of letting a refresh fail is visible.

MV rules of thumb (heuristics, not rules)

  • Good fit: aggregate-heavy, small-result, frequently-read queries. Bad fit: one-off analysis
  • Heuristic: put the largest, most-appended table leftmost in a join MV — it is the shape most likely to stay incrementally maintainable, not a guarantee. Read it next to the current incremental-refresh restrictions
  • Heuristic: an MV whose join key is already the cluster key may be buying a join that was already cheap
  • Restrictions exist (the aggregation list, no window functions, no MV-on-MV, outer and self joins) — check the docs, not your memory: limits keep loosening
  • Validate, don’t assume: the view’s refresh status and the query plan tell you whether maintenance is still incremental and whether a rewrite happened
Cost model: you pay MV storage + refresh compute + (much smaller) query compute. For a 288×/day dashboard the trade is overwhelming. For a weekly report it may not be.
Incremental-refresh boundary, stated carefully: appends are the change type incremental refresh handles best; other mutations can invalidate the stored data until the view re-materializes. Confirm with the refresh status and INFORMATION_SCHEMA job history.
Speaker notes — MV rules of thumb
  • Deliberately no hard limit numbers on the slide face: the per-table/per-project/per-org MV caps and the same-dataset smart-tuning restriction were early-2024 facts that have since been relaxed. Verify at docs.cloud.google.com/bigquery/docs/materialized-views-intro when you teach it.
  • In star schemas the leftmost table should be the fact table — that’s the append-heavy one.

Storage housekeeping: stop paying for the past

  • Expiration: dataset default → table → partition; expired data is gone after time travel, automatically, and logged
  • Long-term pricing: any table or partition untouched 90 consecutive days drops to about half price, automatically. Queries don’t reset the clock — writes do
  • Logical vs physical billing: telemetry compresses well, so ClearMeet could be a physical-billing candidate — compare measured active, long-term, time-travel, and fail-safe bytes first

Speaker notes — Storage housekeeping
  • The 90-day clock resets on writes (load, copy-in, query-results-write, DML, streaming) but not on reads, exports, copies-out, or metadata patches. Source: cloud.google.com/bigquery/pricing (storage section).
