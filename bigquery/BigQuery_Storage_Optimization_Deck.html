The problem: a one-day query that reads a year

Cymbal Meet’s ops dashboard asks about yesterday only. telemetry.qos_events holds a year of samples, unpartitioned, and each run of the query reads all of it.

Ops dashboard query

SELECT device_type,
       COUNTIF(audio_mos < 3.5) / COUNT(*) AS poor_share
FROM telemetry.qos_events
WHERE event_time >= TIMESTAMP('2026-07-21')
  AND event_time <  TIMESTAMP('2026-07-22')
GROUP BY device_type;

qos_events keeps everything. One year is ≈1.8 trillion rows, ≈730 TB illustrative. It is unpartitioned and unclustered, as the Architecture module left it.

The query references 3 of 12 columns: 24 B/row × 1.8 trillion rows ≈ 43.8 TB per run illustrative. On an unpartitioned, unclustered table, the WHERE clause doesn’t reduce the bytes billed.

≈$250 per run on demand at $6.25 per TiB illustrative.

Example

Actor: the ops dashboard, refreshing every 5 minutes.

Input: the query above, 288 times a day.

Mechanism: each run reads event_time, device_type, and audio_mos for all 1.8 trillion rows, then keeps the 5B from 2026-07-21.

Result: ≈$72,000 a day to show 5 numbers about one day illustrative.

Takeaway: on an unpartitioned table, a query about one day pays for every day stored.
Sources: BigQuery pricing (verified 2026-09-30).

Partitioning: skip whole days

Store each day in its own storage sets, so a one-day query skips the other 364.
Speaker notes — Section 1: Partitioning
  • An unpartitioned table bills every byte of the columns a query reads. Partitioning is how BigQuery skips data by date.

What a partitioned table stores

A table created with PARTITION BY DATE(event_time) stores each day’s rows in that day’s own storage sets.

At write time, BigQuery routes each row to its day’s partition. A storage set holds rows from exactly one partition.

The metadata records each set’s partition, so a filter on the partition column selects sets before any data is read. This is pruning.

Each partition has its own metadata: you can expire, overwrite, or bill it separately. Page 14 and Section 5 use this.

Example

Actor: a query at 10:05 on 2026-07-22 for the previous day, 3 columns.

Input: event_time on 2026-07-21, against the partitioned table.

Mechanism: metadata returns only the sets tagged partition=20260721; the other 364 days are never opened.

Result: 120 GB read, and the dry-run estimate shows 120 GB before it runs illustrative.

Takeaway: a partitioned table stores each day apart, so the metadata can drop the other days before the query reads anything.
Sources: Partitioned tables, Query partitioned tables, Storage Write API (verified 2026-09-30).
Speaker notes — What a partitioned table stores
  • Partitioned tables: “each partition is stored in physical blocks, each of which holds one partition.” Exact estimate confirmed by T2 (estimate 12,826,583 B = actual).
  • Streaming caveat (Storage Write API, Query partitioned tables): rows just written through the Storage Write API may sit in the __UNPARTITIONED__ partition with NULL pseudo-columns until BigQuery routes them. A query for today can show bytes there.

Partitioned: 43.8 TB becomes 120 GB

Page 3’s one-day query, unchanged, now runs against the partitioned table. The dry-run estimate drops before the query runs.

The query reads 1 of 365 partitions: 120 GB instead of 43.8 TB illustrative.

365× fewer bytes, so 365× lower cost: ≈$250 → ≈$0.68 per run illustrative.

On a partitioned table, the dry-run estimate equals the bytes billed, because pruning happens in metadata before the run.

Rule: bytes read = full-scan bytes × days queried ÷ days stored.

Filters that prune, filters that don’t

Tomás, Americas support lead, wants yesterday in Los Angeles time. His first filter reads the whole year.

Prunes

WHERE event_time >= TIMESTAMP('2026-07-21')
  AND event_time <  TIMESTAMP('2026-07-22')
WHERE DATE(event_time) = '2026-07-21'
WHERE TIMESTAMP_TRUNC(event_time, DAY)
      = TIMESTAMP('2026-07-21')
WHERE DATE(event_time, 'America/Los_Angeles')
      = '2026-07-21'

Reads every partition

WHERE FORMAT_TIMESTAMP('%Y-%m-%d', event_time,
      'America/Los_Angeles') = '2026-07-21'
WHERE UNIX_SECONDS(event_time) >= 1784592000
WHERE event_time >= (SELECT MAX(loaded_at)
                     FROM ops.control)
WHERE event_time >= TIMESTAMP('2026-07-21')
   OR org_id = 'o-0071'

Pruning works when the partition column is compared with constant expressions, alone or inside a supported function (DATE, TIMESTAMP_TRUNC, TIMESTAMP_ADD, EXTRACT, and others the docs list).

It fails when the column is inside an unsupported function, compared with a subquery that reads a table, or OR-ed with another column.

Check with a dry run: the estimate shows whether the filter pruned.

Example

Actor: Tomás.

Input: FORMAT_TIMESTAMP('%Y-%m-%d', event_time, 'America/Los_Angeles') = '2026-07-21'.

Mechanism: the function isn’t one BigQuery can match to partitions, so it keeps all 365.

Result: 43.8 TB. Rewritten as event_time >= TIMESTAMP('2026-07-21', 'America/Los_Angeles') AND event_time < TIMESTAMP('2026-07-22', 'America/Los_Angeles'), it reads 2 UTC partitions: 240 GB illustrative.

Takeaway: keep the partition column bare or inside a supported function such as DATE(event_time, tz), or put the time zone on the constant; confirm with a dry run.
Sources: Query partitioned tables (verified 2026-09-30).
Speaker notes — Filters that prune, filters that don’t
  • Ledger #4 and #18: the old face said TIMESTAMP_ADD “may prevent” pruning. It prunes (Query partitioned tables list; T1: 5.29 GB, 2 partitions). The breaking examples here are tested: T1b (FORMAT_TIMESTAMP with a time zone, UNIX_SECONDS: rejected under require_partition_filter, so no pruning); T1 and T4 (table subquery, OR with another column: billed every partition of the test table). 1784592000 is 2026-07-21 00:00 UTC.
  • DATE(event_time, 'America/Los_Angeles') prunes (T1b, 4.64 GB = 2 partitions on the test table). FORMAT_TIMESTAMP('%Y%m%d', event_time) without a time zone also prunes (QP ledger). The docs list only some forms; that’s why the habit is the dry run, not a memorized list.
  • A constant subquery like (SELECT TIMESTAMP('2026-07-21')) prunes (T1). Only a subquery that reads a table breaks it.
  • Why 2 partitions: LA midnight to midnight is 07:00 UTC to 07:00 UTC, which touches 07-21 and 07-22 UTC. 2 × 120 GB = 240 GB.

Make unpruned queries fail

A query on qos_events without a date filter reads the whole year. A table option makes that query fail instead.

Set once on the table

ALTER TABLE telemetry.qos_events
SET OPTIONS (require_partition_filter = TRUE);

Error without a pruning filter

Cannot query over table 'telemetry.qos_events' without a filter
over column(s) 'event_time' that can be used for partition elimination

With require_partition_filter, a query without a pruning filter on the partition column fails before it runs. Failed queries are free.

“Partition elimination” in the error means pruning.

The filter must prune. The FORMAT_TIMESTAMP filter from page 10 fails the same way.

Example

Result: the error above and 0 bytes billed, instead of ≈29 TB, ≈$170 illustrative.

qos_events is partitioned by DATE(event_time) because most of its queries filter on event time. BigQuery offers two other partitioning types and four granularities.

Work on one day at a time

A bad SDK build wrote invalid audio_mos values on 2026-07-21. An engineer reloads that day without touching the other 364.

Overwrite one partition

$ bq query --use_legacy_sql=false \
    --destination_table 'telemetry.qos_events$20260721' \
    --replace \
    'SELECT * FROM telemetry.qos_reload
     WHERE DATE(event_time) = "2026-07-21"'

A partition decorator (table$YYYYMMDD) targets one partition in a query, load, or copy job. --replace overwrites only that day.

Rows from another day fail the job, so a wrong source can’t spill into other partitions.

DML on different partitions doesn’t conflict. An UPDATE on 07-21 and a DELETE on 07-19 can run at the same time.

Partitions can also expire one at a time (Section 5).

Example

Actor: the engineer.

Input: corrected rows for 2026-07-21 in telemetry.qos_reload.

Mechanism: the job writes a new storage set for partition 20260721 and replaces the old one in one commit.

Result: one day rewritten (~2 TB); the other 364 partitions are unchanged illustrative.

Takeaway: fix, reload, or delete data one day at a time with partition decorators.
Sources: Partitioned tables, Data manipulation language (verified 2026-09-30).

Date-sharded tables: convert them

A new hire finds an old export: telemetry.qos_events_20260720, _20260721, … one table per day. Queries read them with a wildcard.

Reading shards you inherit

SELECT device_type, COUNT(*) AS samples
FROM `telemetry.qos_events_*`
WHERE _TABLE_SUFFIX BETWEEN '20260720' AND '20260726'
GROUP BY device_type;

Each shard is a separate table with its own schema, metadata, and permissions. Schemas can drift apart.

Wildcard queries over several tables don’t use the query cache.

The docs recommend partitioned tables over date-sharded tables. Convert once with a CTAS over the wildcard.

Clustering: skip other orgs’ files

Partitioning skips days. Clustering skips the files within a day that can’t hold the value a query filters on.
Speaker notes — Section 2: Clustering
  • Partitioning answered “which day.” It does nothing for “which org within the day.”

What a clustered table stores

With CLUSTER BY org_id, BigQuery sorts each day’s rows by org_id as it writes them.

CLUSTER BY sorts rows by the cluster columns when BigQuery writes them, within each partition.

Each file then covers a narrow range of org_id values, and the metadata records each file’s range. The docs call these units storage blocks and size them adaptively; this module draws them as files.

A filter on the cluster column skips files whose range excludes the value. Partitioning skips storage sets; clustering skips files within them.

Example

Actor: a customer-success query for Acme (o-0071) on 2026-07-21.

Input: org_id = 'o-0071' on partition 20260721.

Mechanism: BigQuery compares o-0071 with each file’s org_id range and opens only files whose range includes it.

Result: ~20 of ~2,000 files read illustrative.

Takeaway: clustering sorts each partition by your column, so a filter on it skips the files that can’t hold the value.
Sources: Clustered tables (verified 2026-09-30).

Creating the clustered table

Clustering set on an existing table sorts only what BigQuery writes afterward. Sorting the year already stored takes a rewrite.

Recommended: partition and cluster in one rewrite

CREATE TABLE telemetry.qos_events_new
PARTITION BY DATE(event_time)
CLUSTER BY org_id
OPTIONS (require_partition_filter = TRUE)
AS
SELECT * FROM telemetry.qos_events;  -- then swap names, as on page 7

Up to 4 cluster columns, each a top-level column of a supported type: STRING, INT64, DATE, TIMESTAMP, DATETIME, BOOL, NUMERIC, BIGNUMERIC, GEOGRAPHY, or RANGE. FLOAT64 isn’t allowed, so audio_mos can’t be a cluster column.

Adding clustering to an existing table (bq update --clustering_fields=org_id) affects only data written afterward. Existing data stays unsorted.

To sort existing data, rewrite it: a CTAS as above, or UPDATE … SET org_id = org_id WHERE TRUE. The UPDATE also resets long-term storage pricing (Section 5).

CorrectionALTER TABLE … SET OPTIONS (clustering_fields = …) is not valid DDL. Use bq update --clustering_fields or the tables.patch API.

Column order decides which filters prune

The SDK team asks for sdk_version as a second cluster column, so their rollout queries cost less.

Rows sort by the first cluster column, then by the second within each value of the first.

Filters on the first column prune best. A later column prunes well only when the query also filters the columns before it.

Put the most frequently filtered or aggregated column first. For Cymbal Meet that’s org_id.

High-cardinality columns cluster well. org_id has 40,000 values: too many to partition on (10,000 limit), and good for clustering.

Example

Actor: the SDK team.

Incremental refresh

The ops on-call keeps a “today so far” tile open. At 10:04, 14M rows have arrived since the MV’s 10:00 refresh.

BigQuery refreshes the MV in the background, best effort: usually within about 5 minutes of a base-table change, if the last refresh was more than 30 minutes ago.

Between refreshes, a query that uses the MV reads the stored rows plus the base-table rows appended since the last refresh. The answer is current.

A change other than an append (an UPDATE, DELETE, or MERGE) invalidates the affected data. For a partitioned MV, only the affected partitions are invalidated; queries read the base table for them until the next refresh.

max_staleness: trade freshness for a cheaper read

An exec report can be hours old; an ops dashboard can’t. max_staleness, set per MV, lets reads skip the base table while the last refresh is recent.

Recap: storage costs

For tables with a retention limit, set partition expiration to it; expired days drop without DML, then sit in time travel and fail-safe.

Partition long-kept tables so untouched partitions move to the long-term rate (≈70% of active for logical, half for physical); writes reset the clock.
