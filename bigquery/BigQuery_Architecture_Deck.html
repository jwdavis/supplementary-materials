The big picture

Three services behind one API: storage, compute, and shuffle. Each scales on its own.
Speaker notes — The big picture
  • Cymbal Meet’s analytics ran on a Postgres read replica. This section answers what they are moving to, and why a 100B-row query can finish in seconds.
  • Ask who has run a BigQuery query before. If most have, move quickly to slots (page 10).

Analytics on a transactional database

At 09:00, Cymbal Meet’s dashboard, the nightly ETL that ran late, and an analyst’s 30-day GROUP BY org_id all hit the same Postgres read replica.

One machine does storage, compute, indexes, and vacuum. Every query competes for the same CPU and disk, so the team can only schedule the jobs around each other or buy a bigger machine.

Transactional databases (OLTP) are tuned for single-row reads and writes. Indexes find a few rows fast; each insert also updates every index.

At 5B new rows a day illustrative, one machine can’t keep up, however well it is tuned. A bigger machine moves the limit; it doesn’t remove it.

What the team wants: keep all the data, query any of it, size no machines, pay for what they use.

Takeaway: The limits come from the architecture, so tuning one machine can’t remove them.
Speaker notes — Analytics on a transactional database

Every query is a job

A query runs on BigQuery’s side, not on the laptop that sent it. What happens to it when the laptop disconnects?

Queries, loads, exports, and copies run as jobs submitted to the BigQuery API.

Jobs are asynchronous. The API returns a job ID at once; clients poll it for the result.

The console, bq, and client libraries all call the same API.

The job ID outlives your connection. Anyone with the job ID and permission on the project can fetch the result.

HTTP: one query, as a request

POST https://bigquery.googleapis.com/bigquery/v2/projects/cymbal-meet/jobs
Authorization: Bearer <oauth2-token>
{"configuration": {"query": {
   "query": "SELECT device_type, COUNT(*) FROM telemetry.qos_events GROUP BY 1",
   "useLegacySql": false}}}

→ 200 OK  {"jobReference": {"jobId": "bquxjob_1a2b3c", ...}, ...}
Example

Mechanism: the query is job bquxjob_1a2b3c, and it keeps running.

Result: on reconnect, the engineer opens the job in Job history and reads the results; nothing re-runs.

Takeaway: A query is a job with an ID, so a dropped connection doesn’t lose it.

Slots: the unit of compute

The same one-year query runs on on-demand capacity, up to ~2,000 slots, and on a 200-slot reservation. It reads the same bytes both times; on the reservation it takes about 10× as long.

A slot is a virtual compute unit that BigQuery uses to run SQL.

Each stage of a query is split into work units; the query plan’s parallel inputs shows how many. “Slots execute the individual work units of a stage in parallel.”

When a query needs more slots than it has, BigQuery queues the work units and runs each as a slot frees up.

On-demand: up to ~2,000 slots per project, may burst, shared fairly with other projects. You pay $6.25 per TiB processed; the first 1 TiB each month is free. Editions: you buy slot capacity, billed per slot-hour.

Fewer slots usually means slower, not failed. Bytes billed don’t change. The 6-hour execution limit still applies.

Takeaway: The data decides how many work units a stage has; your capacity decides how many slots run them at once. When units outnumber slots, they wait in a queue.
Sources: Query plan and timeline; Slots; Quotas and limits; Pricing (verified 2026-09-30).

Columnar: you pay for the columns you name

A product analyst wants yesterday’s poor-audio share by device. The query names 3 of the table’s 12 columns, and filters to one day.

SQL: poor-audio share by device, one day

SELECT device_type,
       COUNTIF(audio_mos < 3.5) / COUNT(*) AS poor_share
FROM telemetry.qos_events
WHERE DATE(event_time) = '2026-07-21'
GROUP BY device_type;

Columnar storage reads only the columns a query names: event_time, device_type, and audio_mos, ~24 B a row illustrative

Bytes processed = the size of each named column, summed over the rows scanned. For STRING, that is 2 bytes plus the UTF-8 length.

On this table, the date filter doesn’t reduce bytes. It is unpartitioned, so every day is scanned. Partitioning, covered in Storage Optimization, fixes this.

The dry-run estimate is the number the console shows before you run. Page 19 shows where it comes from.

Mechanism: only the three named columns are read, for all ~1.8T rows.

Result: 1.8T × 24 B = 43.8 TB per run, ≈ $250 on-demand illustrative. SELECT * would read 1.8T × 400 B = 730 TB (≈ $4,150) illustrative

Takeaway: Name only the columns you need. On this table, a filter doesn’t cut the bytes; naming fewer columns does.

Capacitor: how a column is encoded

Across a year of qos_events, device_type holds 5 distinct values and meeting_id holds ~2.2B. Which column takes more space on disk?

Cardinality is the number of distinct values in a column. device_type: 5. meeting_id over one year: ~2.2B illustrative

Each column is stored separately, in its own compressed blocks.

Dictionary encoding replaces each value with a small code; run-length encoding (RLE) then stores each run of repeated codes as one pair.

Wide, high-cardinality columns drive storage size. Compare logical and physical bytes per table to find them (page 24).

Takeaway: A column with few distinct values stores as a small dictionary plus a few runs, so it takes little space on disk.
Sources: Dremel 2020 §6.2; Inside Capacitor; BigQuery admin reference: storage (verified 2026-09-30).
Speaker notes — Capacitor: how a column is encoded
  • Internals page: the traced values are the example.
  • Sources: Dremel 2020 §6.2 (dictionary and RLE); Inside Capacitor (2016-04-26). The storage admin blog notes that columnar “doesn’t necessarily mean that each column is in its own file”. The old face said “its own Capacitor files”.

Capacitor reorders rows and filters on the dictionary

A new analyst expects LIMIT 10 on qos_events to return the first rows loaded. It can return any 10: Capacitor may reorder rows so each column has fewer, longer runs.

Capacitor may reorder a file’s rows before encoding. Each row stays intact; only the order changes.

Finding the best order is NP-complete, so Capacitor uses heuristics that weigh column types and query patterns.

A filter on a dictionary-encoded column can be evaluated once per dictionary entry, not once per row. The column’s bytes are still billed.

LIMIT without ORDER BY returns arbitrary rows.

Takeaway: Row order belongs to Capacitor. Don’t rely on it, and expect filters on few-value columns to be cheap to compute but not cheaper to bill.
Sources: Inside Capacitor; Dremel 2020 §6.1; Query syntax (verified 2026-09-30).

Colossus: where the files live

Across Google’s data centers, disks fail every day. None of the ~730,000 files in a year of qos_events should become unreadable when one does.

Capacitor files live on Colossus, Google’s distributed file system. Cloud Storage uses it too.

Each file is erasure-encoded across many disks (Reed-Solomon): data chunks plus recovery chunks. Losing some chunks still leaves the file readable.

BigQuery writes data synchronously to two zones in the region.

A multi-region (US, EU) stores your data in one region of it. There is no cross-region copy unless you set up replication.

No file is overwritten in place. Page 17 shows what follows from that.

Example

Actor: Colossus, holding file f7 of qos_events (~1 GB illustrative).

Input: two of the disks holding f7’s chunks fail.

Mechanism: f7 is stored as 4 data chunks plus 2 recovery chunks on 6 disks; any 4 of the 6 rebuild it illustrative

Result: queries keep reading f7; Colossus rebuilds the lost chunks in the background.

Takeaway: Durability is handled below BigQuery. A multi-region doesn’t mean a second region.
Sources: Reliability; Locations; Colossus under the hood (verified 2026-09-30).
Speaker notes — Colossus: where the files live
  • Sources: reliability intro (two zones, Reed-Solomon); locations (a multi-region “does not provide cross-region replication or regional redundancy”). The old face said multi-regions keep an off-region copy; that came from the 2021 admin blog and is outdated. Colossus under the hood (2021-04-19).
  • Erasure coding gives better durability than 3× replication for less than one extra copy of storage (Definitive Guide pp. 212–214, 2019).

Files are never modified

BigQuery never edits a file. Every change to a table writes new files and then updates the table’s metadata; the files it replaced stay on disk for time travel.

Capacitor files are immutable. A load adds new files. A DELETE or UPDATE writes new files for the rows it keeps (pages 25, 26).

The metadata update is what makes a change visible. Until then, queries see the old list of files (page 18).

Readers never block writers. A running query keeps reading the files it started with.

BigQuery can rewrite storage in the background (page 21), and old versions stay readable (page 22).

Changing one row means writing a new file for the group that holds it. Keep mutations rare and batched.

Example

Actor: the 14:00 hourly load into telemetry.meetings.

Input: ~250,000 new meetings illustrative, while a 10-minute report that started at 13:58 is reading the table.

Mechanism: the load writes new files and opens no existing file for writing; one metadata update adds the new files to the table.

Result: the report finishes on the files it started with, with no lock waits. The next query sees the new rows.

Takeaway: Every change is new files plus a metadata update, so reads never wait on writes and old versions stay available.
Sources: DML; Big Metadata (VLDB 2021) (verified 2026-09-30).
Speaker notes — Files are never modified
  • 250,000 = 6M meetings a day / 24 hourly loads.
  • Sources: Big Metadata 2021 §4 (new blocks written, old marked deleted); DML (“performed at the file-group level”). Fine-grained DML (Preview, opt-in) rewrites less; mention it only if asked.
  • This is why BigQuery is wrong for OLTP (page 5): updating one row costs a file rewrite.

A load commits all its files or none

The 14:00 load of telemetry.meetings writes three files. If it dies after the second, what do queries see?

A load writes new files, grouped into a storage set. The storage set is what gets committed.

Lifecycle: PENDING (invisible) → COMMITTED (visible to every query at once) → GARBAGE (replaced by a newer set, kept for time travel, page 22).

A load is all or nothing: a query sees all three files or none.

A failed load leaves nothing, but a lost success reply can make a retry load the data twice. Give the job a fixed ID; a retry with the same ID fails instead of duplicating.

Shell: fixed job ID

$ bq load --job_id=meetings_20260721_14 \
    --source_format=PARQUET \
    telemetry.meetings \
    "gs://cymbal-meet-ingest/meetings/2026-07-21/14/*.parquet"
Example

Actor: the hourly load job for telemetry.meetings, 2026-07-21 14:00.

Input: three Parquet files; the job dies after writing file 2.

Mechanism: the storage set never leaves PENDING, so no query can see it.

Result: queries see zero rows from 14:00, and a retry loads all three files once. If the client had only lost a success reply, a retry with the same job ID would be rejected instead of loading twice.

Takeaway: Loads are all or nothing. A fixed job ID makes a retry safe.
Sources: Batch loading data (verified 2026-09-30).

Metadata answers “which files?” before any data is read

A network engineer types a query for average jitter and packet loss by region. Before she clicks Run, the console says how many bytes it will process, and BigQuery hasn’t read a single row.

SQL

SELECT region, AVG(jitter_ms) AS avg_jitter, AVG(packet_loss_pct) AS avg_loss
FROM telemetry.qos_events
GROUP BY region;

BigQuery’s metadata records which storage sets and files make up a table, with each file’s row count and the byte size of each column.

“Which files, which columns, how many bytes” is answered from metadata before any data is read.

A dry run returns that estimate for free (bq query --dry_run, or the console as you type).

The estimate is an upper bound. Billing rounds up to the MB, with a 10 MB minimum per table.

Result: “This query will process 47.5 TB when run”, ≈ $270 on-demand illustrative. She narrows it before running.

Takeaway: Dry-run anything unfamiliar. It is free, and its estimate is an upper bound on what you’ll be billed.

Streamed rows take a different path to disk

At 14:00 on 2026-07-21, an SDK release starts sending audio_mos = 0. The on-call SRE needs to see it within minutes, not after a nightly load.

qos_events arrives through the Storage Write API, continuously, at ~58,000 rows a second illustrative

Streamed rows land first in write-optimized storage (the streaming buffer) and are queryable within seconds.

A background process later rewrites them into Capacitor files in committed storage sets, typically within minutes.

A query reads both the buffer and the committed files.

The same API also handles batch writes. Its delivery guarantees depend on how you use it, covered in Data Ingestion.

The storage optimizer compacts small files

Streaming leaves qos_events with many small committed files, and every file a query opens adds work that doesn’t depend on its size.

Many small commits fragment a table. Each file adds an open and a metadata read, whatever its size.

The storage optimizer rewrites small files into larger ones in the background, then commits the new set in one metadata change.

The replaced sets become GARBAGE and stay until time travel expires (page 22).

Compaction isn’t instant. Right after a write burst, a query can be slower than the same query an hour later.

Prefer fewer, larger loads.

Example

Actor: the storage optimizer, on qos_events.

Input: 1,000 committed files of 2 MB each, about 90 seconds of traffic illustrative

Mechanism: rewrites them as two 1 GB files beside the originals, then commits the new set in one metadata change.

Result: queries open 2 files instead of 1,000. The 1,000 old files become GARBAGE.

Takeaway: BigQuery compacts small files for you, but not at once; load in fewer, larger batches.
Sources: BigQuery admin reference: storage; Dremel 2020 §7 (verified 2026-09-30).

Time travel reads older storage sets

At 09:00 on Wed 2026-07-22, someone re-runs Tuesday’s hourly loads into telemetry.meetings, and Tuesday’s 6M meetings now appear twice.

Every storage-set change has a timestamp. “The table as of 08:55” means the sets that were COMMITTED at 08:55.

GARBAGE sets are kept for the time-travel window: 7 days by default, configurable from 2 to 7 days.

A 7-day fail-safe follows. It isn’t configurable, and only support can recover from it.

FOR SYSTEM_TIME AS OF is an ordinary query. It bills the bytes of the version it reads.

SQL

CREATE OR REPLACE TABLE telemetry.meetings_restored AS
SELECT *
FROM telemetry.meetings
  FOR SYSTEM_TIME AS OF TIMESTAMP '2026-07-22 08:55:00+00';

Logical vs physical bytes

Omar, on Cymbal Meet’s FinOps team, wants to know whether qos_events would cost less to store under physical billing.

Logical bytes: the uncompressed size. Dry runs, on-demand query billing, and default storage billing count these.

Physical bytes: the compressed Capacitor bytes on disk, including time-travel and fail-safe bytes.

Storage billing is chosen per dataset: logical (default) or physical.

Physical costs more per byte: $0.040 vs $0.023 per GiB-month active (~1.7×), $0.020 vs $0.016 long-term (~1.25×), US. It wins when data compresses well.

Under physical billing, time-travel and fail-safe bytes are billed too, so a table with many DELETEs or rewrites pays for its old versions.

SELECT table_name,
       total_logical_bytes  / 1e12 AS logical_tb,
       total_physical_bytes / 1e12 AS physical_tb
FROM `region-us`.INFORMATION_SCHEMA.TABLE_STORAGE
WHERE table_schema = 'telemetry'
ORDER BY total_logical_bytes DESC;

qos_events   730          120

A DELETE writes new files

An erasure request arrives for participant p_8843c1: one 33-minute session, 200 rows. Files can’t be edited, so what does BigQuery do?

SQL

DELETE FROM telemetry.qos_events
WHERE participant_id = 'p_8843c1';

No file is edited in place. For each file that holds a matching row, BigQuery writes new file(s) holding that file’s remaining rows, then commits a new storage set.

Files without matching rows are carried into the new set, not copied.

The old files stay, so the deleted rows remain recoverable through time travel (2–7 days) plus fail-safe (7 days).

UPDATE and MERGE work the same way: new files for every file they change.

Example

Actor: Cymbal Meet’s privacy engineer.

Mechanism: files are written in arrival order, each holding ~43 seconds of traffic, so a 33-minute session’s rows land in ~46 files illustrative

Result: ~46 new files of ~1 GB replace the old 46 to remove 80 KB; the other ~729,950 files carry over. The old 46 stay for time travel.

Takeaway: A DELETE doesn’t edit rows in place. It writes new files for every file it touches, so a few rows spread over many files mean many new files.

Batch your DML

Cymbal Meet receives about 10,000 erasure requests a day. On-demand, each separate DELETE on the unpartitioned table bills at least the whole table.

On-demand, a DELETE bills q + t: q is the bytes the statement scans, and t is the size of the whole table before the change. The row count doesn’t matter.

On a partitioned table it bills q′ + t′: only the partitions scanned and the partitions updated.

Up to 2 mutating statements (UPDATE, DELETE, MERGE) run at once per table; up to 20 more queue. INSERTs don’t conflict with them.

Row-at-a-time UPDATE or DELETE loops are the anti-pattern. That workload belongs in an OLTP database in front of BigQuery.

Batch the day’s requests into one statement.

SQL: one statement per day

DELETE FROM telemetry.qos_events
WHERE participant_id IN UNNEST(@pending_ids);  -- ~10,000 IDs

JOIN telemetry.meetings AS m USING (meeting_id)
GROUP BY start_hour;

Matching keys start in unrelated files. mtg_58d1 sits in files f1 and f2 of qos_events and file g1 of meetings.

Both sides are shuffled by hash(meeting_id), so identical keys reach the same slot from either table.

Each slot then joins locally, building a hash table from the smaller side it received.

Both sides cross the shuffle. Bytes shuffled jumps. Execution details labels this JOIN EACH WITH EACH.

Skew: one key, one slot

Every free-plan user is filed under one org, org_id = 'free': 18% of all qos_events rows. An SRE counts unique participants per org.

SQL

SELECT org_id, COUNT(DISTINCT participant_id) AS participants
FROM telemetry.qos_events
GROUP BY org_id;

One key goes to one shuffle partition, read by one slot (page 31).

COUNT(DISTINCT) can’t collapse a key the way SUM can, so every file’s 'free' participant IDs go to one slot.

That slot does ~18% of stage 2’s work alone illustrative. The others finish and wait.

Execution details shows it as compute max ≫ avg. More slots usually don’t help, because one key can’t be split.

Example

Actor: the SRE, querying one year.

Mechanism: 'free' has 900M rows a day, ~330B in a year; its participant IDs from every work unit hash to one shuffle partition illustrative

Result: one stage-2 slot runs long after the rest; the stage’s compute max is far above its average.

Takeaway: If one key holds a large share of rows, one slot gets that share; change the key or the query shape, not the slot count.
Sources: Query plan and timeline (verified 2026-09-30).
Speaker notes — Skew: one key, one slot
  • Data sheet: 'free' is 18% of rows (900M/day); ~330B = 900M × 365. Skew appears only where partial aggregation can’t collapse the key (a join on org_id, COUNT(DISTINCT) per org, a window PARTITION BY org_id). A plain per-org SUM or AVG doesn’t skew (tested for the QP deck).
  • Source: query plan explanation (avg and max per phase). “More slots won’t help” isn’t absolute; say “usually”.

Where results go, and the result cache

A dashboard on telemetry.meetings refreshes every 5 minutes, and meetings loads once an hour. Of each hour’s 12 refreshes, how many scan the table?

Every query writes its results to a temporary table, kept about 24 hours. The console pages through it.

The same query text on unchanged tables is served from the cache and bills 0 bytes.

The cache is per user and per project. Enterprise editions can share cached results across users.

Skipped when: a referenced table changed, the query uses a non-deterministic function such as CURRENT_TIMESTAMP(), a destination table is set, or a table has streamed rows in write-optimized storage.

Failed queries, dry runs, and cache hits bill 0 bytes.

Shell: force a real run, skipping the cache

$ bq query --nouse_cache --use_legacy_sql=false 'SELECT …'
Example

Actor: the sales team’s meetings-per-region dashboard.

Input: the same query every 5 minutes on telemetry.meetings, which loads hourly.

Mechanism: the first refresh after each load scans; the next 11 match the cached result.

Result: 11 of 12 refreshes an hour bill 0 bytes illustrative. The same dashboard on qos_events, which always has streamed rows, would scan on all 288 refreshes a day.

Takeaway: Re-running the same query on an unchanged table is free; a table that is always streaming never gets a cache hit.
Sources: Using cached query results (verified 2026-09-30).

A view is a saved query

A data engineer saves page 13’s poor-audio query as the view telemetry.poor_audio_by_device so other teams can use it. Does querying the view cost less than querying the table?

A view stores query text, not data. It has no files and no storage sets.

Querying a view runs its text against the base tables, so it reads and bills the same bytes.

The result cache works through a view, under the same rules as page 39.

A materialized view does store results in its own files. Materialized views are covered in Storage Optimization.

Reading Execution details: a preview

A scheduled report over a year of qos_events usually finishes in about 15 minutes. Today it took 45. Execution details shows why before anyone touches the SQL.

Wait high? Slots may be busy elsewhere, or the stage is waiting for the previous one.

Compute max ≫ avg? Skew: one slot got a large key (page 38).

Bytes spilled > 0? The shuffle outgrew memory (page 35).

Slot-milliseconds ÷ elapsed milliseconds ≈ the average number of slots the query used.

Section 3 recap: the read path

A query becomes an estimated plan of stages that BigQuery can change while it runs; Execution details shows the stages that ran.

Work units come from the data; slots come from your capacity. Units beyond the slot count queue.

Shuffle sends each key to one slot. Ship sums and counts, and divide at the end.

Group by the coarsest key that answers the question; many distinct keys mean a big shuffle and possible spill.

Small side: broadcast. Two large sides: hash join, and both move. One huge key: skew.

Same query, unchanged tables: served from the cache, 0 bytes. Streaming tables never qualify, and views don’t save bytes.
