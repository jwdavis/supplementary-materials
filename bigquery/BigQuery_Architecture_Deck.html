The problem: analytics on a database built for transactions

  • ClearMeet’s current “warehouse”: a Postgres read replica
  • Nightly ETL, indexes to maintain, a vacuum schedule — and a box that is either too big or too small
  • One analyst’s GROUP BY can starve the dashboards
  • 5B new rows/day is not a tuning problem. It is a different architecture problem

Speaker notes — The problem
  • The pain points are chosen to be exactly the things BigQuery’s architecture removes, and each maps to a slide ahead: provisioning → serverless API; contention → slots and fair scheduling; vacuum/indexes → the storage optimizer and no indexes at all; capacity → separated storage and compute.

What the 100-billion-row query actually did

SELECT title, SUM(views) AS views FROM Wiki100B
WHERE REGEXP_CONTAINS(title, '.*Davis.*') GROUP BY title ORDER BY views DESC;
100B rows became ~1,000 independent 100M-row reads.
Speaker notes — The 100B-row query, drawn
  • Draw this on the board rather than showing it, if you can. It is the map for the whole module: every box gets its own slide later. Right now students only need the shape, and the shape is what makes the Do-It-Now result stop feeling like magic.
  • Walk it bottom to top. (1) The table is 7 columns; the query names 2, so only the title and views stripes are read. (2) Those stripes are split into ~1,000 pieces of ~100M rows, and each piece is an independent unit of work — no piece needs to know about any other. (3) Each leaf slot returns counts, not rows: “miles davis = 1000.” (4) Shuffle routes every partial for one title to one slot, which totals it. (5) The root stage assembles 14 rows and orders them.
  • Be precise about direction, because it is the thing everyone gets backwards: the compute does not run on the storage machines. Colossus and Dremel are separate services. The column stripes are shipped over the network to whichever slots are free. This works because the network is fast enough that a remote read costs about what a local read would — that is the enabling fact, not “moving compute to the data.”
  • Where the numbers come from: 100B rows over ~1,000 leaf slots is ~100M rows each. On-demand gives roughly 2,000 slots per project, fair-shared, so the real parallelism depends on what else is running. Have students compare their own elapsed times across the room — the spread is slot contention.
  • Two arithmetic facts worth saying out loud: the data read is ~100B × 2 columns; the data shuffled is a few KB. Reduction happens at the leaves, before anything crosses the network. That single asymmetry is why this query returns in seconds.
  • Park the obvious question: REGEXP_CONTAINS over 100B titles sounds brutal, but Capacitor evaluates it against the column dictionary, not row by row. Two slides ahead.

“Serverless” just means: it’s an HTTP API

  • Every interaction — query, load, export, copy — is a job submitted over REST
  • Jobs are asynchronous by design: you get a job ID immediately; results are fetched when ready
  • bq, the console, and every client library are wrappers around this call
A lost Wi-Fi connection doesn’t kill your query — the job ID is the durable handle, and anyone can reconnect to it.
the entire product, one HTTP requestPOST /bigquery/v2/projects/clearmeet/jobs
Authorization: Bearer <oauth2-token>

{"configuration":
   {"query": {"query": "SELECT 17"}}}

→ 200 OK  {"jobReference":
     {"jobId": "bquxjob_1a2b3c"}, …}
Speaker notes — Serverless = an API
  • Why async matters: client connections are fallible and queries can run for minutes or hours; the job ID is the durable handle. bq polls it; the console polls it; JDBC/ODBC drivers poll it.
  • Everything-is-a-job also means everything is auditable and inspectable after the fact: bq show -j <job_id> — we lean on this in Section 3 to count slots and read plans.
  • Source: Definitive Guide ch. 6 pp. 185–190 walks SELECT 17 through the raw wire request exactly like this.

Slots: the unit of compute

  • A slot ≈ one virtual CPU with working memory, executing one unit of a query at a time
  • On-demand: ~2,000 concurrent slots per project, fair-shared; you pay per TiB scanned ($6.25/TiB, first TiB/month free)
  • Editions / reservations: buy slot capacity that autoscales; pay per slot-hour
  • Fewer slots never fails a query — it only runs longer
Speaker notes — Slots
  • Precision guardrail: “half a CPU core and ~1 GB RAM” is the 2019 book’s definition; current Google material says “roughly a virtual CPU” and measures progress in slot-seconds. Teach it as a unit of progress, not a hardware spec. Sources: Definitive Guide p. 189; BigQuery Admin reference guide: Query processing (Google Cloud blog).
  • Flat-rate and flex slots were retired July 2023, replaced by editions with autoscaling — older material (including the 2019 book) describes a pricing world that no longer exists. Current numbers: cloud.google.com/bigquery/pricing.
  • The scheduler can preempt slots at any time; every unit of work is atomic and idempotent, so preemption or a worker dying costs milliseconds of re-dispatch, not a query restart. This is Borg underneath — the ancestor of Kubernetes.
  • Fairness worked example if asked (book, pp. 194–195): a shared on-demand pool re-divides as users arrive; per user, then per project, then equally among a project’s queries.

Columnar: you read only the columns you touch

  • The dashboard question touches 3 of 12 columns
  • Row storage: read ~1.9 TB — every row, every column
  • Columnar: read three column stripes — ~120 GB
  • Bytes processed = columns touched × rows in the files scanned. Filters don’t reduce it (yet)
SELECT device_type,
       COUNTIF(audio_mos < 3.5) / COUNT(*)
FROM clearmeet_analytics.qos_events
WHERE event_time >= '2026-07-28'
GROUP BY device_type;
Speaker notes — Columnar storage
  • Arithmetic is on the slide on purpose — rounded, but honest about what drives the number: 5B rows × three ~8-byte columns.
  • This is the single biggest lever students control from day one: SELECT * bills every column. Show the dry-run estimate changing live as you add and remove columns in the console — the validator updates per keystroke.
  • Say the yellow bar out loud and park it: the WHERE event_time >= … filter reading “yesterday” still scans all days. That cliffhanger is resolved by partitioning, next module.
  • Query-shape note: COUNTIF(…)/COUNT(*) per device — the same skeleton recurs through Section 3.

Capacitor I: how a column is actually encoded

  • Each column is stored in its own Capacitor files
  • Two workhorse encodings: dictionary + run-length (RLE)
  • device_type: 5 distinct values across billions of rows, so it compresses absurdly well. session_uuid: 5 billion, so it barely compresses
  • Per-column statistics are collected at encode time and stored with the file — the pruning machinery, next module
Why you care: a few high-cardinality columns drive your storage bill, not the row count. Compare logical to physical bytes per table (next slide) to find them.
Speaker notes — Capacitor I
  • Capacitor is BigQuery’s proprietary columnar format, co-designed with the query engine. Nested/repeated data is encoded with the repetition/definition-level scheme from the Dremel paper — the same scheme Parquet adopted. Source: Inside Capacitor (Google Cloud blog).
  • Why proprietary instead of Parquet? Google can evolve format and engine together, and rewrite storage under your feet without you noticing — which is literally the storage optimizer’s job, four slides ahead.
  • The rebuilt slide replaces the old “Capacitor features” bullet list (dictionary encoding, RLE, compression, row reordering as bare bullets) — each feature now walks literal values and connects to bytes billed.

Capacitor II: reorder the rows, filter on the dictionary

  • Rows in a table have no order — so Capacitor permutes rows to make runs longer
  • Optimal ordering is NP-hard; heuristics weigh column types and real query patterns
  • Filters can be evaluated against the dictionary, not the data
-- ~3 evaluations, not 5 billion:
WHERE device_type LIKE '%os%'
Why you care: a predicate on a low-cardinality column is nearly free — filter early. And no row order is yours: LIMIT 10 without ORDER BY returns arbitrary rows.
Speaker notes — Capacitor II
  • Worked numbers from the Inside Capacitor post: reordering a 3-column example cut RLE runs from 21 to 9. The optimizer weighs column data types and actual query usage when choosing the permutation; optimal is NP-complete, so it approximates with bounded runtime.
  • Two student-visible consequences: (1) compression ratios vary wildly by column cardinality — visible as logical vs physical bytes on the next slide; (2) there is no row order you can rely on — SELECT * LIMIT 10 returns arbitrary rows.
  • Within-file sort order belongs to compression, not to you. “Teaching storage an order you can rely on” is clustering — next module.

Two sizes of the truth: logical vs physical bytes

  • Logical bytes: uncompressed size — what the validator and on-demand query billing count
  • Physical bytes: compressed Capacitor bytes on disk
  • Storage billing is a per-dataset choice: logical (default) or physical — roughly 2× the rate on often far fewer bytes
  • Telemetry like qos_events compresses 4–8×: physical usually wins
Under physical billing, time-travel and fail-safe bytes are billed separately — heavily-mutated tables can flip the math.
SELECT table_name,
  total_logical_bytes  / POW(1024,4) AS logical_tib,
  total_physical_bytes / POW(1024,4) AS phys_tib
FROM `region-us`.INFORMATION_SCHEMA.TABLE_STORAGE
ORDER BY total_logical_bytes DESC;
qos_events, one daylogical_tib  1.90   ← what queries bill
phys_tib     0.31   ← what disks hold
Speaker notes — Logical vs physical bytes
  • Switching billing model is per dataset with a 14-day cooldown between switches; there is no performance difference either way. Source: BigQuery storage overview + time travel docs.
  • Rates drift — don’t memorize dollars; the live numbers are on cloud.google.com/bigquery/pricing (checked July 2026: on-demand queries $6.25/TiB; storage now quoted per GiB-hour).
  • The 6× ratio shown (1.9 TB → 0.31 TB) is typical for low-cardinality telemetry, and it’s Capacitor’s dictionary+RLE work from the previous two slides made visible in a system table.

Colossus: durability is not your problem

  • Capacitor files live on Colossus, Google’s distributed file system — the same layer under Cloud Storage
  • Data is erasure-encoded across many disks, plus replicated to a second zone; multi-regions keep an off-region copy
  • No file is ever overwritten in place
Speaker notes — Colossus
  • Erasure (Reed–Solomon) coding stores recovery math instead of full copies: better durability than 3× replication for less than one extra copy of data (Definitive Guide pp. 212–214 — the replicated-vs-erasure figures make a good whiteboard sketch if asked).
  • Tail-latency point worth telling: a big query touches so many files that some disk involved is always dead — recovery reads are the normal case, which is why Colossus’s raw speed matters to query latency, not just safety.
  • One fact with teaching value later: a Colossus file belongs to exactly one table. Copies and snapshots are metadata operations — next module’s snapshots/clones build on this.

The rule that explains everything else

Capacitor files are immutable. Every change to a table is new files plus a metadata change — nothing is ever edited in place.

Everything for the rest of this section — commits, time travel, the storage optimizer, the cost of DML — is a consequence of this one decision.

What it buys you: readers never block writers, snapshots and clones are nearly free, and BigQuery can rewrite your storage in the background without asking.
What it costs you: changing one row rewrites a whole file. Design so mutations are rare, batched, and concentrated — never row-at-a-time.
Speaker notes — The rule: immutability
  • Immutability buys: trivially safe concurrent reads (no locks), cheap snapshots, safe background rewrites, and erasure-coding-friendly large sequential writes.
  • It costs: updating one row means rewriting a file (four slides ahead). This trade is right for analytics and wrong for OLTP — now the “don’t use BigQuery as a transactional DB” advice has a mechanism behind it, not just a slogan.
  • The source module stated this in one buried speaker-note sentence; here it is the hinge of the whole section. Give it a beat of silence.

What a load job actually does: the commit

  • A load writes new Capacitor files, grouped into a storage set — the atomic unit of commit
  • Lifecycle: PENDING (invisible) → COMMITTED (visible everywhere, at once) → GARBAGE (superseded, kept a while)
  • Queries see all of a commit or none of it: loads are ACID
bq load --source_format=PARQUET \
  qos_events \
  gs://ingest/07-28/*.parquet
Why you care: a failed load leaves nothing behind, so retrying is always safe — no dedup pass, no cleanup script.
Speaker notes — The commit: storage sets
  • Terminology flag (say once, then move on): “storage set” comes from the Definitive Guide (pp. 218–219) and Google training decks; current public docs don’t name the concept (they say “blocks”). We teach it because the model is accurate and load-bearing.
  • Half-loaded data is impossible: if the load dies at file 2 of 3, the set never leaves PENDING. No cleanup, no partial reads. This answers a real student question (“what if my load fails halfway?”) with mechanism instead of reassurance.
  • The book’s ACID gloss: Atomic, Consistent, Idempotent, Durable — note the nonstandard I; isolation between queries holds too (readers never see in-flight commits).

The metadata is itself a database

  • Table → storage sets → files, tracked in Spanner
  • “Which files might this query need?” is answered before any data is touched
  • This is how the validator prices your query before it runs
Why you care: a dry run is free and its byte count is not a guess — it is the same number you will be billed. Price anything unfamiliar before you run it: bq query --dry_run, or just read the validator in the console as you type.
Speaker notes — Metadata is a database
  • The Definitive Guide (p. 226) describes the per-table “meta-file” of min/max constraints — itself stored in Capacitor, so BigQuery literally queries your metadata like a tiny table before querying your data.
  • Modern docs call the productized version metadata indexing (CMETA): managed tables > 1 GiB get automatic column-level metadata indexes, maintained free in the background (docs: metadata-indexing-managed-tables; based on the “Big Metadata” VLDB 2021 paper).
  • Plant the seed explicitly: everything next module — partition pruning, cluster block pruning — is this slide plus rules you set. The min/max machinery already exists; partitioning and clustering just make it useful.
  • Also explains why some limits exist (tables per query, columns per table): they are metadata-system limits, not storage limits.

Streaming is a different front door

  • Streamed rows land in a write-optimized buffer, queryable within seconds — before they’re Capacitor files
  • A background process extracts buffered rows into committed, columnar storage sets
  • Modern path: the Storage Write API (gRPC, exactly-once, batch + streaming unified)
Why you care: a table with a streaming buffer never serves a query from cache. A dashboard refreshing every 60 seconds against qos_events pays a full scan every single time. Roll the data up on a schedule and point dashboards at the rollup.
Speaker notes — Streaming
  • This explains two observable oddities: streamed rows appear instantly but behave differently around “bytes processed,” and (next module) buffer rows aren’t in any partition yet — their pseudo-columns are NULL until extraction.
  • Kept shallow deliberately — ingestion patterns (legacy insertAll vs Storage Write API, dedup semantics, quotas) belong to the ingestion module. Here we only need “write-optimized first, read-optimized later.”
  • Source: BigQuery Admin reference guide: Storage internals — “files may be written first in a format that is fast to write; later BigQuery will format them in a way that is fast to query.”

The storage optimizer: the vacuum you never run

  • ClearMeet streams all day → thousands of small commits: a fragmented table (query overhead = file opens + metadata reads)
  • The storage optimizer continuously rewrites small storage sets into consolidated new generations — atomically, in the background, free
  • Superseded sets flip to GARBAGE… and stick around (next slide)
Why you care: nothing to schedule, nothing to pay for — but it is not instant. Prefer fewer, larger loads, and don’t benchmark a table you just finished writing.
Speaker notes — The storage optimizer
  • Worked fragmentation math from the book (p. 220): 100 KB streamed every 2 minutes ≈ 21,000 files a month for 2 TB — without compaction, opening files would dominate query time.
  • Contrast to land hard: Postgres makes you schedule VACUUM; BigQuery’s optimizer is invisible, continuous, and not billed. Sources: storage internals admin blog; Inside Capacitor (“background processes re-optimize data atomically, in parallel with queries”).
  • The same machinery reclusters tables next module — same pattern: new generation beside old, atomic metadata flip.

Speaker notes — Do It Now: Views
  • Prediction first: ask the room whether querying a view is cheaper than querying the table. It is not. A view stores no files and no storage sets — it is text that gets substituted into your query, so the same files get read and the same bytes get billed.
  • That is the point of putting it here, right after the storage optimizer: everything students have just learned about files, storage sets, and generations is what a view does not have. Nothing was materialized, so nothing was optimized.
  • Caching does work through a view, because the cache keys on the resolved query and the underlying tables’ state — useful contrast with the streaming-buffer case two slides ago.
  • The thing that does materialize, and therefore does get its own files and its own background maintenance, is a materialized view. Name it, park it, and let the next module deliver it.

Time travel falls out for free

  • Every storage-set transition is timestamped. “The table as of 2 p.m.” = the sets COMMITTED at 2 p.m.
  • GARBAGE sets are kept through the time-travel window: default 7 days, configurable 2–7; a fixed 7-day fail-safe follows
  • A backfill double-loaded July 27. One statement recovers it:
CREATE OR REPLACE TABLE qos_restored AS
SELECT * FROM qos_events
  FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(
    CURRENT_TIMESTAMP(), INTERVAL 24 HOUR);
Why you care: try this before anyone reaches for a backup — it is an ordinary query, priced like one, and it works on a dropped table.
Speaker notes — Time travel
  • This is the payoff of teaching commits properly: time travel needs no new machinery, just “don’t garbage-collect too eagerly.”
  • Config: ALTER SCHEMA … SET OPTIONS (max_time_travel_hours = 48). Shorter windows cut storage cost only under physical billing, where time-travel bytes are billed separately (tie back to the logical-vs-physical slide). The fail-safe (7 more days, not configurable, recovery via support) sits after the window. Source: BigQuery time-travel docs.
  • Related freebie with the same mechanism: table snapshots and clones are metadata pointers to storage sets — near-zero cost until data diverges. One sentence now; used in the next module.

DML on immutable files: what DELETE really does

  • A GDPR request: delete one participant’s rows
  • The engine can’t edit files. It rewrites the affected files without those rows, then commits a new storage set referencing the rewritten files plus all untouched originals
  • One deleted row can rewrite a ~1 GB file. UPDATE = DELETE + INSERT. MERGE = the same, fused
DELETE FROM clearmeet_analytics.qos_events
WHERE participant_id = 'p_8843c1';
Speaker notes — DML: DELETE
  • Source: Definitive Guide pp. 225–226 (Fig. 6-35) — “if this sounds like a lot of work to delete a single row, you’re absolutely right.”
  • New storage sets can reference old files — deletion isn’t a full-table rewrite if the affected rows are concentrated in few files. Which files a participant’s rows land in is exactly what clustering will control next module — this slide is the setup for “cluster for update locality.”
  • ACID still holds: readers mid-DELETE see SS-3 until the atomic flip to SS-4.
  • Compliance nuance for the notes only: the deleted row remains recoverable through time travel + fail-safe (up to ~14 days) — that’s normally acceptable for GDPR (deletion “without undue delay”), but worth knowing when someone asks where the data physically went.

Consequences: how ClearMeet handles mutations

  • Batch DML. One nightly DELETE covering all pending erasure requests — not one statement per request
  • Concurrency is limited by design: 2 concurrent mutating statements per table (they garbage-collect whole storage sets and must not overlap); INSERTs don’t conflict
  • Single-row UPDATE/DELETE loops are the canonical antipattern — that workload belongs in an OLTP store in front of BigQuery
-- nightly, all requests at once:
DELETE FROM
  clearmeet_analytics.qos_events
WHERE participant_id IN (
  SELECT participant_id
  FROM clearmeet_ops.pending_erasures);
The cost model to carry: DML cost ∝ files touched, not rows changed. 10,000 erasures in one statement ≈ the cost of one, if they hit the same files anyway.
Speaker notes — DML consequences
  • Fuller concurrency detail if asked (training deck material): up to 2 mutating statements run concurrently, up to 20 queue as PENDING per table; conflicts only arise when statements touch the same partition; failed conflicting statements retry up to 3 times. INSERT never conflicts.
  • Commit latency after the job “completes” can exceed execution time for many-partition DML — metadata again.
  • The deck-level rule is just: batch, and don’t design for concurrent mutation of one table.

From SQL to a plan of stages

  • The query master parses your SQL and asks the metadata which files the query needs
  • It builds a plan of stages and requests slots
  • Plans are dynamic: BigQuery re-plans while the query runs, based on what the data looks like
  • That’s why there is no full upfront EXPLAIN — the honest plan doesn’t exist until execution
Speaker notes — From SQL to a plan
  • Dremel history in one breath if useful: built 2006; execution went from a static tree to a dynamically re-planned DAG around 2010 (Definitive Guide pp. 190–192, “Dremel X”).
  • Observable consequence: the Execution details panel shows the plan after the fact, sometimes containing runtime-inserted stages (the repartition slide ahead shows one).
  • Source: BigQuery Admin reference guide: Query processing — dynamic planning, mid-flight repartitioning, failed work units re-queued without restarting the stage.

Stage 1: files become work units

  • The files this query needs become work units — roughly one per file. Here: 8 files, 8 work units
  • Work units are what gets scheduled; slots run them. With 3 slots free, 3 run and the other 5 queue. A slot that finishes takes the next one — slots are reused, not one-per-file
  • Each unit reads only the device_type and audio_mos stripes of its file, then emits partial results
SELECT device_type,
  COUNTIF(audio_mos<3.5) AS poor,
  COUNT(*) AS total
FROM qos_events GROUP BY 1;
-- each unit runs this on its own file
Parallel inputs (8) is a property of the data. Slots (3) is a property of your capacity.
Speaker notes — Stage 1: files to slots
  • Say the distinction out loud, it is the point of the slide: the number of work units comes from the data (how many files/segments the query has to touch). The number of slots comes from your capacity. They are independent numbers. 8 units on 3 slots is not slower per unit; it just takes more waves.
  • Docs language to lean on: parallelInputs is the “number of parallelizable units of work for the stage — the number of columnar segments within a table, or the number of partitions within an intermediate shuffle” (query-plan-explanation). And on scheduling: “If a query requests more slots than are available, BigQuery queues up individual units of work and waits for slots to become available … if 100 slots finish their work, they dynamically pick up 100 units of work from the 1,000 queued up units” (docs: slots).
  • So the honest answer to “how parallel is stage 1?” is: it wants to be as parallel as there are inputs; it is as parallel as you have slots. That gap is exactly what Wait time in Execution details measures.
  • The real table resolves to hundreds of files; eight keeps it traceable. Reproducible version: the book’s NYC-taxi COUNT(*) — 113.5M rows → 9 segments, verifiable with bq show -j → completedParallelInputs: 9. (Note that a bare COUNT(*) can also be answered from metadata alone; use a filtered count if you want to force the real read path.)
  • This is why file sizing (storage-optimizer slide) matters to query performance: thousands of tiny files = thousands of tiny work units and scheduling overhead per unit. Compaction buys parallel efficiency.
  • Units of work are atomic and idempotent: a slot dying mid-unit costs a re-dispatch of that unit, not a query restart.

Stage 2: five billion rows in, a few numbers move

  • Each stage-1 unit emitted, per device it saw, a pair: (poor, total) — rows under MOS 3.5, and rows seen
  • Stage 2 has one slot per device, and all of them run at once. Each sums its own device’s pairs, then divides — 42 / 3.9M happens inside the macos slot
  • So the division is not a third stage. Two stages did the work; a trivial output stage collects the four finished rows
  • Why summing works at all: sums are associative, so partials combine in any order. Averages and percentages are not — which is why stage 1 ships two counts and not its own percentage
Tracing one key (macos) through: four partials, one sum, one division — in one slot.
Speaker notes — Stage 2
  • Stage 2 starts reading as soon as stage-1 units begin finishing — stages pipeline through shuffle rather than waiting on a hard barrier (BigQuery Admin reference guide: query processing).
  • Answer the “how many stages?” question head-on, because the old version of this slide invited the wrong one. There is no dedicated slot or stage that performs the division. Every stage-2 slot owns a set of keys, holds the running (poor, total) for each of them, and once its inputs are exhausted it evaluates the projection — the divide — for its own keys and emits finished rows. Four devices means four slots doing that independently and simultaneously. What follows is an output stage that concatenates four rows and hands them to the API. In Execution details you will typically see two substantial stages plus a small output stage; the row counts, not the stage names, are what tell you which is which.
  • Corollary worth stating: the reason the division can live inside stage 2 is that a single slot holds all of the data for its keys after the shuffle. Nothing outside that slot could contribute another macos row. That guarantee is what the next slide (shuffle) buys.
  • The associativity point is the transferable idea. Ask: why doesn’t stage 1 just compute its own percentage and let stage 2 average them? Because averaging averages is wrong when the files hold different row counts — f1’s 1.2M rows and f7’s 0.8M rows do not get equal votes. Shipping (poor, total) and dividing once at the end is correct for any split of the data. Same reason AVG() is internally a sum and a count.
  • The numbers on the slide are illustrative but internally consistent — 14+11+9+8 = 42 over 3.9M rows. Feel free to do that addition on the board; it is the entire mechanism.
  • Do not use a bare COUNT(*) as the demo here. BigQuery can answer SELECT COUNT(*) FROM t from table metadata — 0 bytes billed, effectively no scan — so it demonstrates the opposite of this slide. If you want a live version, use the COUNTIF/GROUP BY shape above, which forces a real column read and a genuine shuffle of partial aggregates.
  • This slide answers the Do-It-Now anchor question at small scale; the 100B-row demo is the same picture with more partials on the left.

Why GROUP BY needs shuffle

  • Stage 1’s partials for macos are scattered across every slot — someone must bring like keys together
  • Shuffle: each stage-1 slot writes its partials partitioned by hash(device_type)
  • Each stage-2 slot reads exactly one key range — and holds all the data for its keys
Same key ⇒ same shuffle partition ⇒ same slot. Any deterministic function of the key works — that’s all a hash is.
The docs call these partitions within an intermediate shuffle, or buckets. “Sink” is the book’s word, not Google’s.
Speaker notes — Why GROUP BY needs shuffle
  • The hash sidebar from the book (pp. 202–203) is a good spoken analogy: ten friends dividing house listings by summing address digits mod 10 — any deterministic function of the key gives a correct division of labor.
  • The public reproducible version is the wikipedia GROUP BY language staged walkthrough from the original module — keep it as a live demo if wanted.
  • Console vocabulary: stage boundaries in Execution details are shuffles; Bytes shuffled is the width of those colored arrows.

The shuffle tier: in-memory, pipelined, finite

  • Shuffle data lives in a distributed in-memory tier riding the petabit network
  • Pipelined: consumers start reading while producers are still writing
  • The number of shuffle partitions is chosen — and re-chosen mid-query — from observed data size
  • How much do you get? No shuffle dial, no published quota. Shuffle memory comes out of the slot capacity you already have — so “more shuffle” only ever means more slots
  • Overflow spills to Colossus: the query still succeeds, much slower — and you can see exactly how much
When you see spill: shrink what enters the shuffle first — drop unused columns, filter earlier, pre-aggregate. Only then buy capacity.

Speaker notes — The shuffle tier
  • If someone asks “how many GB of shuffle do I get?”, the honest answer is that Google does not publish one — say that rather than invent a number. What is documented: the tier is in-memory, and when purely in-memory shuffling becomes cost-prohibitive BigQuery moves the data to Colossus (In-memory query execution in Google BigQuery, Google Cloud blog); shuffleOutputBytesSpilled in the job statistics tells you when that happened (Admin reference guide: Query processing). Figures like “up to 60% of your slots can act as shuffle slots” or “~2 TB compressed per slot” circulate in third-party posts and older training decks; they are not in Google’s documentation, so keep them off the slide.
  • The version students can act on: shuffle capacity scales with slot capacity. The only two levers are “put less into the shuffle” and “have more slots.” There is nothing in between to tune.
  • Skew preview: one giant key (an org with half the traffic) makes one partition’s slot the straggler — visible as max ≫ avg in stage timings. Full treatment belongs to query tuning; here students just learn to recognize it.
  • Sources: BigQuery Admin reference guide: Query processing; Definitive Guide pp. 196–197 (dynamic resizing of shuffle partitions, spill penalty).
  • Memory-vs-disk latency is orders of magnitude — that’s the whole story of why spill hurts.

Why more keys changes the plan

Same rows, same query shape, one word different. device_type has 5 distinct values; meeting_id has 6M.

SELECT meeting_id, AVG(audio_mos)
FROM qos_events
GROUP BY meeting_id;

Why 5 keys is cheap and 6M is not — two reasons, and the first one matters more

1. Pre-aggregation collapses, or it doesn’t. Grouping 5B rows by device_type, each stage-1 slot turns its whole file into 5 rows before the shuffle. Grouping by meeting_id, a file of 1M rows holds ~1M near-unique keys, so it collapses to almost nothing — millions of rows cross the shuffle instead of a handful.

2. And each stage-2 slot must hold one running total per key it owns: 5 for device_type; 6M / 40 = 150,000 if the planner split the work 40 ways. Enough state, and the slot runs out of memory.

More distinct keys ⇒ less pre-aggregation and more state per partition ⇒ more partitions needed. The planner discovers this while running.
Speaker notes — Why more keys changes the plan
  • Terminology, say it once: Google’s docs do not use the word “sink.” They describe parallelInputs as “the number of columnar segments within a table, or the number of partitions within an intermediate shuffle,” and the COALESCE step as combining “small buckets of data after shuffling” (docs: query-plan-explanation). “Sink” comes from the Definitive Guide. This deck says shuffle partition so that the word students hear matches the word they will read in the console and the docs.
  • “Do you mean 40 slots?” — effectively yes, and it is worth being explicit. A shuffle partition is a bucket of data; one slot consumes one bucket. So the partition count is the width of the next stage, and 40 partitions means up to 40 slots doing stage-2 work concurrently. The two numbers are not the same kind of thing (buckets are chosen by the planner from the data; slots are your capacity), but the mapping is one-to-one.
  • The cardinality question deserves the fuller answer, because “more state per slot” alone is not the main cost. The bigger effect is upstream: a GROUP BY pre-aggregates inside stage 1 before anything is shuffled. Grouping 50M rows by a 5-value column, each slot emits 5 rows — a ~10,000,000× reduction, and the shuffle carries kilobytes. Grouping the same 50M rows by a 6M-value column, most keys appear only a handful of times within any one file, so stage 1 emits nearly as many rows as it read and the shuffle carries the table. Then the memory-per-slot problem arrives on top of that. Low cardinality is not “better” morally — it just means the work collapses early.
  • Work the arithmetic on the board, it does the teaching: 6M keys / 40 partitions = 150k groups per slot; 6M / 1,600 partitions = 3,750 per slot. Same data, same query, different bucket count.
  • Why the planner gets it wrong in the first place: it picks the partition count up front from estimated cardinality. Nobody knows the true number of distinct meeting_id values until the data has actually been read. Guessing and then correcting is cheaper than pre-computing exact statistics for every query.
  • What students can act on: before grouping by something near-unique, ask whether they need it. Grouping by meeting_id to then average across meetings is usually a rollup that wants a coarser key, or an approximate function (APPROX_COUNT_DISTINCT), or a materialized rollup table. If the high-cardinality group-by is genuinely required, expect the bytes shuffled to be large and size capacity accordingly.
  • Docs vocabulary: REPARTITION “aims to rebalance data distribution across worker nodes”; COALESCE “combines these buckets into larger ones, reducing overhead” (docs: query-plan-explanation, stage step operations). Point out both exist — the engine adjusts in both directions.
  • Tie back to the previous slide: spill is the symptom you see when this correction is not enough, or comes too late. Repartition is the engine trying to avoid spilling.
  • Book’s extreme example (Definitive Guide pp. 205–207): sorting 280M distinct titles grew the plan to 15 stages with runtime-lettered stages across 5,384 workers — dynamic planning made visible.

Broadcast join: send the small table to every slot

A join needs matching rows in the same place. If one side is small enough to fit in a slot’s memory, the cheapest way to guarantee that is to give every slot a complete copy of it.

SELECT o.org_name,
  COUNTIF(q.audio_mos<3.5) AS poor
FROM qos_events q   -- 5B rows
JOIN orgs o USING (org_id)
  -- 40k rows
GROUP BY o.org_name;

Each slot then joins locally: load all 40k orgs rows into an in-memory hash table keyed on org_id, then for each qos_events row in its shard, look up that row’s org_id and emit. No network, no waiting on other slots.

40k rows × every slot is a rounding error. 5B rows across the network is not. Move the small thing.
Plan signature: JOIN EACH WITH ALL — each shard of the big side, with all of the small side.
Speaker notes — Broadcast join
  • Start from the requirement, not the name. Any join needs rows that match to be co-located in one slot’s memory. There are only two ways to arrange that: copy one side everywhere, or redistribute both sides by the key. Broadcast is the first; hash (next slide) is the second. Naming them is worthless until students see that both are answers to the same question.
  • Walk the diagram in this order: (1) the shards already exist on Colossus and each slot reads one, (2) the green dashed arrows deliver a complete copy of orgs to every slot, (3) the yellow box is where the join actually executes — inside the slot, against data that is already local.
  • Concrete arithmetic for “why this is cheap”: if orgs is ~2 MB and there are 400 slots, broadcasting costs ~800 MB of network. Shuffling the 5B-row side would cost hundreds of GB. Three orders of magnitude, which is why the planner prefers this whenever the small side qualifies.
  • Mechanically the small side becomes a hash table in memory: org_id → row. Then each of the big side’s rows is a single O(1) probe. That is why memory, not row count, is the limit — the table has to fit.
  • Threshold is adaptive and not documented as a fixed number (the 2019 book said ~150 MB “as of this writing”; training material says ~50–200 MB compressed). Teach the shape, never the number: small enough to fit in a slot ⇒ broadcast.
  • The actionable habit: when a join is unexpectedly slow, check whether the side you thought was small actually looked small to the planner. Wrapping a dimension in a subquery, a UNION, or a UDF can hide its size, and the planner falls back to a hash join. The signature in Execution details tells you which one you got.

Hash join: when neither side can be copied

Now join qos_events (5B) to meetings (24M). Neither fits in a slot, so no copy is possible. The other option: redistribute both sides so matching keys land together.

SELECT m.scheduled_by,
       AVG(q.audio_mos)
FROM qos_events q  -- 5B rows
JOIN meetings m
  USING (meeting_id)  -- 24M rows
GROUP BY m.scheduled_by;

The problem the shuffle solves: meeting_id M-77 sits in shard f2 of one table and an unrelated shard of the other. Nothing lines up by accident.

So both sides apply the same hash(meeting_id). Identical keys compute an identical destination from either table, and arrive at the same slot.

Both sides cross the network. That is the cost, and why Bytes shuffled jumps on this shape.
Plan signature: JOIN EACH WITH EACH — each shard of one side, with each shard of the other.
Speaker notes — Hash join
  • Lead with why the previous trick is unavailable. Broadcast worked because 40k rows fit in memory. 24M rows do not. Once copying is off the table, the only remaining way to co-locate matching rows is to move both sides to a common destination determined by the key. That is the whole idea; “hash join” is just its name.
  • The M-77 detail on the left is the point of the slide, so say it explicitly: the same meeting_id appears in f1 and f2 of the fact table and in g1 of the dimension table. Three slots hold pieces of one key’s answer. No arrangement of the original files fixes that, because the files were written by arrival time, not by meeting_id.
  • Why hashing is the right tool: it is deterministic. hash("M-77") gives the same shuffle partition whether it is computed by a slot reading the fact table or a slot reading the dimension table. No coordination needed — both sides independently compute the same destination. Same property as the GROUP BY shuffle slide, applied to two inputs at once.
  • Inside the slot, once both sides have arrived, it is the same local operation as broadcast: build a hash table on the smaller arriving side, probe it with the larger. The difference is entirely in how the data got there, not what happens on arrival.
  • Cost framing: broadcast moved 40k rows. This moves 5B + 24M rows. That is the trade, and it is why the planner will avoid it whenever the small side qualifies for broadcast.
  • Skew is worth the extra minute because it is the one performance problem that capacity cannot solve. One key = one shuffle partition = one slot, by definition. If that key is 20% of the data, that slot does 20% of the work alone while the rest idle. Point at the compute max-vs-avg bars on the Execution details slide as the tell. Full treatment is in query tuning; here they only need to recognize it.
  • Docs language: broadcast “sends all the data in the smaller table to each slot that processes the larger table”; for hash, BigQuery “uses hash and shuffle operations … so that the matching keys end up in the same slot to perform a local join” (docs: best-practices-performance-compute, query-plan-explanation).

Where results go (and the free lunch)

  • Results land in a temporary table, kept ~24 h — that’s what the console pages through
  • Re-running the same query over unchanged tables → served from cache: 0 bytes billed
  • Cache is per-user and skipped when: tables changed, non-deterministic functions (CURRENT_TIMESTAMP()…), a destination table is set — or the table has a streaming buffer
  • Failed queries: free. Dry runs: free. Cache hits: free
# estimate without running:
bq query --dry_run 'SELECT device_type, …'
# force a real run past the cache:
bq query --nouse_cache 'SELECT …'
ClearMeet’s qos_events streams 24/7, so it always has a streaming buffer and therefore never cache-hits. A dashboard refreshing every 60 seconds against it pays a full scan every single time. Point dashboards at a periodically-refreshed rollup table instead — that table can cache-hit between refreshes. Materialized views, next module.

Back to the opening question

You queried 100 billion rows in seconds, on a table with no index. Six mechanisms did that, and you now know all six.

#MechanismWhat it removed from the problem
1 Metadata answered first
storage sets + per-file stats		 Which files could matter was known before reading any data — and that is how the price was known before running.
2 Columnar storage
Capacitor		 You named 2 columns, so 2 column stripes were read. The rest were never touched, whatever the row count.
3 Files became work units
one per file, run on any free slot		 The scan became thousands of independent pieces. No piece needed to know about any other, so all could run at once.
4 Reduction happened at the leaves
stripes shipped in, counts shipped on		 Storage and compute are separate services, so the stripes were shipped to the slots — over a network that makes a remote read cost about what a local one would. What moved onward was counts, not rows.
5 Shuffle regrouped by key
same key → same partition → same slot		 Partials scattered across thousands of slots were collected one place per key, with no slot coordinating with another.
6 The plan adapted mid-flight
repartition, split points		 Nothing had to be estimated correctly up front. Bad guesses about key counts were corrected while running.
No index exists because none is needed: an index makes finding a few rows fast, while an analytic query reads a large share of the table. Brute force, divided finely enough, wins.
Speaker notes — Answering the anchor question
  • Run this as a learning check, not a lecture. Put the slide up, then ask the room to explain the Do-It-Now result before you reveal the rows. Students who can narrate all six have got the module; where they stall tells you what to revisit. Their narration is the assessment.
  • The framing that makes it stick: each mechanism removes work rather than speeding work up. Metadata removes files from consideration; columnar removes columns; work units remove the need for sequencing; partial aggregation removes almost everything before it crosses the shuffle; shuffle removes coordination between slots; dynamic planning removes the need to be right in advance.
  • The last callout is the sentence to close on. Students arriving from Postgres keep looking for the index. Say plainly that indexes optimize the opposite problem — finding a small number of rows out of many. An analytic query touches a large fraction of the table, so the win comes from dividing the read, not from avoiding it. This reframes every “where is the index?” question for the rest of the course.
  • Both journeys, spoken in one pass if you want the symmetry: write path is encode → immutable files → commit → background optimize; read path is plan → work units → shuffle → results. They meet at exactly two things — immutable files, and the metadata that describes them.
  • Segue to the next slide: every one of these six has a practical consequence you can act on tomorrow morning. That is the next table.
