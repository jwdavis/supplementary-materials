Section 1 of 4

Batch Loading

Files arrive in batches. The oldest, cheapest, most common path into BigQuery — and the only free one.
Batch loadingStreamingPipelines & repl.Query in place
Speaker notes — Section 1: Batch Loading
  • The section's arc: first load (one command) → what a load job actually is (a storage-set commit) → schemas → formats → the same load in SQL → the anti-pattern that hands off to streaming.
  • The punchline to keep repeating: batch loading is free. Whenever data can tolerate batch cadence, this is the default answer — every other door is metered.

Your first load

bq load

Scenario: finance's billing vendor drops a CSV of yesterday's usage into Cloud Storage every morning. Get it into BigQuery.

bq load --source_format=CSV --autodetect --skip_leading_rows=1 \
  billing.daily_usage \
  gs://vc-billing-drop/2026-07-28/usage_*.csv
  • One command: source format, destination table, source files (wildcards allowed). Default appends; --replace truncates first
  • --autodetect infers a schema from a sample of rows — fine for a first look
Batch loading is free — no compute charge, ever; you pay only for storage afterward. That one fact makes "load it" the default answer for anything that tolerates batch cadence.
Speaker notes — Your first load
  • The same load is available from the console (local-file uploads capped at 100 MB — real files go via Cloud Storage), the REST API, and every client library; bq load is just the CLI wrapper over the jobs API.
  • Accepted formats: CSV, newline-delimited JSON, Avro, Parquet, ORC, plus Datastore/Firestore exports (batch loading docs).
  • "Free" precisely: load jobs run on a shared slot pool (named default-pipeline), separate from your query slots — the next slide makes this concrete.
  • Co-locate the bucket and the dataset: cross-region loads bill network data transfer.

What a load job actually does

While the 3.2M-row load runs, an analyst queries the table. What do they see?

one load job = one atomic storage-set commit — all of the data or none of it
  • Loads run on a shared, free slot pool (default-pipeline) — separate from your query slots, but with no throughput guarantee
  • Workers write Capacitor files into a new storage set, state PENDING — invisible; on success it flips to COMMITTED atomically. A failed load leaves the table untouched
Every ingestion method in this module ends exactly here — a storage set committing. Loads, streams, and CDC differ only in how the bytes travel before that commit.
Speaker notes — What a load job actually does
  • This is the Architecture module's PENDING → COMMITTED → GARBAGE lifecycle doing real work: load-job atomicity isn't a bolted-on feature, it is the commit protocol. (Definitive Guide ch. 6; the storage-set slides of the Architecture deck.)
  • The free pool's trade-off: load times vary with what everyone else is running. If you need predictable load throughput, buy Editions capacity and assign a PIPELINE reservation — but note reservation-assigned load jobs stop using the free pool (ingestion pricing).
  • Useful command if asked "where do I see my loads?": bq ls -j lists recent jobs; the console's job history shows the same.

Schemas: autodetect is a starting point, not production

Day 3: the load fails. The vendor uses the string N/A in the minutes column for meetings that never started.

# Error: Could not parse 'N/A' as INT64 for field minutes
bq load --source_format=CSV \
  --schema=daily_usage_schema.json --skip_leading_rows=1 \
  --null_marker='N/A' \
  billing.daily_usage gs://vc-billing-drop/2026-07-29/usage_*.csv
  • Autodetect reads only a sample of the rows. Every sampled minutes value was a number, so it chose INT64 — then row 400,000 held N/A and the load failed
  • Cheap path to a schema file: let autodetect run once, then bq show --schema → review and edit → reload with --schema
A failed load is the lucky outcome — you find out immediately. Had N/A landed in the sample, minutes would have been typed STRING, the load would have succeeded, and every SUM(minutes) after would error or need casting. Pin schemas for anything recurring.
Speaker notes — Schemas: autodetect
  • This is the Definitive Guide's College Scorecard walk (ch. 4) transplanted into our billing feed. Its four fixes for the parse failure, in order of desperation: edit the data, pin an explicit schema, --max_bad_records, --null_marker (the right one here).
  • The schema-file trick in full: bq show --schema --format=prettyjson billing.daily_usage > daily_usage_schema.json — autodetect's guess becomes your reviewed, versioned schema.
  • Self-describing formats (Avro/Parquet/ORC) carry their schema and skip this whole class of failure — that's the next slide's argument.
  • Schema evolution on load (--schema_update_option=ALLOW_FIELD_ADDITION) exists; park it for the storage-optimization module's schema discussion.

The vendor offers exports as gzipped CSV or Parquet. Which do you want?

Prefer Parquet or Avro for loads: self-describing schema (slide 7's failure can't happen) and parallel loading even compressed. Stuck with CSV/JSON? Uncompressed loads faster than gzipped.
Speaker notes — File formats
  • Current docs recommend Avro and Parquet as the fastest, most robust load formats (batch loading docs). The 2019-era "Avro strictly beats Parquet" guidance has leveled out — either is a good answer, and Parquet is the de facto lake standard.
  • Limits worth knowing, not memorizing: 4 GB max per compressed CSV/JSON file, 5 TB uncompressed, 10,000 source URIs per job (quotas).
  • Anticipated question: "does load format affect how it's stored?" No — everything is rewritten into Capacitor regardless; format only affects load speed and schema safety.

The same load in SQL: LOAD DATA

LOAD DATA

Your orchestration is SQL-first — scheduled queries, Dataform. Loads don't have to leave SQL.

SQLLOAD DATA INTO billing.daily_usage
FROM FILES (
  format = 'PARQUET',
  uris = ['gs://vc-billing-drop/2026-07-30/*.parquet']
);
  • LOAD DATA OVERWRITE replaces the table; options cover partitioning, clustering, and schema on first create
  • Composes with SQL tooling: scheduled queries, Dataform/dbt, scripting
bq load, the console, LOAD DATA, and client libraries all create the same load job. Choose by what your automation speaks, not by capability.
Speaker notes — LOAD DATA
  • LOAD DATA reference — GA since 2022, and the natural fit when a scheduled query or Dataform pipeline owns the cadence.
  • Also the cross-cloud door: LOAD DATA can read from Amazon S3 / Azure Blob via Omni cross-cloud transfer — mention only if asked.
  • Foreshadow: "so SQL can run the load… but who schedules the daily run and handles missed days? Hold that — Section 3 (Data Transfer Service) closes the loop."

The anti-pattern: many tiny loads

Support wants fresher usage numbers. Someone proposes: run the load every 15 minutes. What breaks?

  • Every load commits a storage set — 96/day means fragmented tiny files until the optimizer catches up
  • Hard stop: 1,500 load jobs per table per day, failed ones included
  • And 15 minutes still isn't "now" — batch has a cadence floor; below it you're fighting the tool
Cranking load frequency for freshness is the signal to switch doors. Streaming is the next section — and it doesn't touch load-job quotas at all.
Speaker notes — Many tiny loads
  • Mechanics echo the Architecture module: a Capacitor file is the unit matched to a slot in a query's first stage, so many tiny files waste parallelism; the storage optimizer rewrites toward one storage set per partition eventually, on background resources.
  • Quota facts: 1,500 loads/table/day, 100,000 loads/project/day, 15 TB per load job (the 15 TB cap is waived for reservation-assigned jobs) — quotas, optimize load jobs.
  • Streaming ingestion does not count against load-job quotas — one more reason the handoff is clean.
  • Discussion beat: ask the class where the line is. (Hourly loads of decent-sized files: fine. Per-minute 100 KB files: the classic fragmentation story.)

Streaming

Events arrive continuously and there's no natural file anywhere. Rows queryable in seconds — for a price.
Batch loadingStreamingPipelines & repl.Query in place
Speaker notes — Section 2: Streaming
  • Arc: the freshness problem → the Storage Write API front door (default stream) → what happens after a row arrives (the storage-engine connection) → the no-code path (Pub/Sub BigQuery subscriptions) → Dataflow when reshaping is needed → exactly-once for the rare cases that need it.
  • One legacy landmine to defuse early if students have seen older material: tabledata.insertAll ("streaming inserts") is the legacy API — docs now literally brand it "Storage Write API (REST)" and recommend the gRPC Storage Write API for new projects.

The ask: see call quality now

Support's SLA: when a customer's calls degrade, an engineer sees it within seconds — not tomorrow morning.

  • Every client emits telemetry — thousands of events per second, no natural "file" anywhere
  • The batch path's best case: buffer to files, load, wait — minutes at minimum, plus slide 10's fragmentation
  • We need rows queryable seconds after the event, at firehose rates
Streaming inverts the batch contract: rows arrive one-by-one and are queryable immediately — and that path is metered per GiB, unlike free loads. Freshness is what you're paying for.
Speaker notes — The ask: see call quality now
  • Keep the two-questions frame alive: arrival = continuous events; freshness = seconds. That combination is the definition of the streaming door.
  • Canonical use cases: live ops dashboards, support engineers running ad-hoc queries over the last few minutes of telemetry, anomaly detection that aggregates over recent history — anything where "since this morning" is too old.
  • Expect the question "why not Bigtable?" — and concede it, because it's the right instinct. If the requirement is "look up this participant's state in single-digit milliseconds, per event, to make a decision in the call path," that is Bigtable's job, not BigQuery's. BigQuery's streaming door is for analytical freshness: scans, aggregations, and joins over recent plus historical data in one query. Real-time systems commonly use both — Bigtable serving the per-key decision, BigQuery accumulating everything for analysis (the Dataflow slide's diagram shows exactly that fan-out).
  • Cost framing to set expectations before the numbers arrive next slide: streaming is cheap per event but metered — roughly $25 per TiB ($0.025/GiB), with the first 2 TiB each month free.

The front door: the Storage Write API

Storage Write API

The telemetry service sends each event straight to the table as it happens — no files, no jobs, no waiting.

  • Every table has a default stream — start appending, no setup, as many senders as you like. Use it unless you have a reason not to
  • Delivery is at-least-once: a retry can land a row twice. Where that's unacceptable, application-created streams give exactly-once, at the cost of bookkeeping in your client
You aren't choosing a storage format here — fresh rows land row-oriented and BigQuery rewrites them columnar on its own. Same generational storage as the Architecture module; streaming just makes the first half briefly visible.
Speaker notes — Storage Write API
  • Keep this slide conceptual. The three things that matter: no setup (default stream), rows visible in seconds, at-least-once by default. Everything below is answer-if-asked material.
  • Pricing: $0.025/GiB, first 2 TiB/month free. The legacy REST path (tabledata.insertAll, now branded "Storage Write API (REST)") costs ~2× with a 1 KB minimum row size and only best-effort dedup — docs recommend the gRPC API for all new projects (pricing).
  • Mechanics if asked: bidirectional gRPC, client batches rows per AppendRows call (max 20 MB/request), Java/Go/Python libraries wrap it. No SQL surface — that's why this slide is diagram-led. Throughput quota is regional and metered on the dataset's project: 3 GB/s in us/eu multi-regions, 300 MB/s elsewhere (quotas).
  • Exactly-once, if pressed: you create your own stream and number each append with an offset; a reused offset is rejected (OFFSET_ALREADY_EXISTS — the row already landed, safe to ignore), so retries can't duplicate. A pending stream instead holds everything invisible until one atomic commit — batch semantics over the streaming API. Both require the client to persist offsets, which is why the honest advice is: use the default stream and dedup in SQL downstream unless duplicates have real cost. Managed services (Pub/Sub subscriptions, Datastream, Dataflow) handle this for you.
  • Observable seams of the buffer (worth naming so nobody is surprised): on ingestion-time-partitioned tables, un-migrated rows sit in __UNPARTITIONED__ with NULL _PARTITIONTIME; table copy/export can lag the freshest rows by minutes (rarely up to ~90); the console's row-count estimate trails what SELECT COUNT(*) returns. Streaming into clustered tables produces unsorted blocks that background reclustering fixes — storage-optimization module (streaming docs).
  • Streamed rows don't count against load-job quotas — the slide-10 pressure is fully relieved.

Streaming without code: Pub/Sub BigQuery subscriptions

BigQuery subscription

The telemetry events already flow through a Pub/Sub topic — getting them into BigQuery takes zero new services.

gcloud pubsub subscriptions create call-quality-to-bq \
  --topic=call-quality \
  --bigquery-table=vc-analytics:telemetry.call_quality \
  --use-topic-schema
  • Schema options: map the topic schema to columns (as here), or land raw bytes + metadata and parse in SQL
  • Semantics: at-least-once; write failures can route to a dead-letter topic
Already in Pub/Sub and needs no reshaping? This is the current best-practice default — fewest moving parts, and under the hood it's slide 13's Storage Write API.
Speaker notes — Pub/Sub BigQuery subscriptions
  • Pricing: $50/TiB on the Pub/Sub side; no separate BigQuery ingestion charge (it does count against Write API throughput quota) — Pub/Sub BigQuery docs.
  • When not to use it — the docs' own rule: windowed aggregation, cross-message transforms, or exactly-once → put Dataflow between (next slide).
  • Sibling feature: Cloud Storage subscriptions write messages to files in a bucket — the batch-side version of the same trick (feeds slide 5's path).
  • Also writes into Apache Iceberg managed tables — mention only if lakehouse questions come up.

When you need a pipeline in the middle: Dataflow

Product doesn't want the raw events. They want one row per meeting per minute, holding a single quality score computed from all that minute's events — with the customer's plan attached.

  • Neither piece can happen as rows land: summarizing a minute needs the minute's events held together, and attaching the plan needs a lookup against another dataset
  • So that work goes in a pipeline between the topic and BigQuery — Dataflow parses, validates, groups by time, aggregates, enriches, and writes finished rows
  • Rule of thumb: no reshaping → BigQuery subscription (slide 14); reshaping → Dataflow
This deck stops at the doorway: windows, triggers, and watermarks are their own course. Here it's one decision — does the data need to change shape before it lands?
Speaker notes — Dataflow in the middle
  • Beam sink methods for reference (Dataflow → BigQuery guide): STORAGE_WRITE_API (exactly-once), STORAGE_API_AT_LEAST_ONCE (cheaper, recommended when dupes are tolerable), FILE_LOADS (batch default — it's free, same as Section 1!), STREAMING_INSERTS (legacy, avoid). Beam's Managed I/O is now the recommended entry point for most pipelines.
  • The dead-letter pattern on the diagram is deliberate — it's the ingestion-side quality gate students should copy into any pipeline they build.
  • Instructor demo option: roitraining dflow-bq-stream-python (Pub/Sub → Dataflow → BigQuery, includes streaming nested/repeated rows).

Mirroring the operational database: Datastream

Datastream CDC

Support dashboards need plan and seat counts — which live in Cloud SQL Postgres and change all day. Nightly dumps are stale by 9 a.m.

  • Tails the database's change log and continuously applies inserts/updates/deletes to a BigQuery replica
  • Sources: MySQL, PostgreSQL (incl. AlloyDB), Oracle, SQL Server, MongoDB, Spanner, plus SaaS (Salesforce…)
  • Two modes: merge (table mirrors current state — the usual choice) or append-only (every change kept as history)
The old pattern — export, load to staging, hand-written MERGE — is now a managed service. Reach for Datastream before building custom CDC plumbing.
Speaker notes — Datastream
  • Datastream overview · BigQuery destination. Backfill first (snapshot of existing rows), then continuous log tailing.
  • Under the hood Datastream writes via the Storage Write API into a BigQuery feature called BigQuery CDC — Datastream carries the changes, BigQuery CDC applies them. The next slide opens that second half up, because it owns the freshness-vs-cost dial you'll actually tune.
  • Append-only mode lands the raw change log (change type and sequence metadata per row) — choose it when you need history/SCD treatment, then build current state in SQL.
  • Contrast to plant for Section 4: Datastream replicates (analytics-grade, BigQuery speed); EXTERNAL_QUERY federation reaches into the live database per query — fine for small occasional lookups, wrong for analytics.

What Datastream is driving: BigQuery CDC

Datastream reads the change out of the source database. BigQuery CDC is what applies it on this side — and it hands you one dial, max_staleness, that trades freshness against cost.

SQLALTER TABLE crm.customers
  SET OPTIONS (max_staleness = INTERVAL 15 MINUTE);
  • Each change lands as an UPSERT or DELETE row (a _CHANGE_TYPE value) matched to an existing row by the table's primary key — not as a hand-written MERGE
  • Tight staleness forces runtime merges — every query pays to reconcile; relaxed staleness lets cheap background applies do it
  • Datastream sets this up for you; the dial stays yours to tune, and you can drive the same machinery from your own Write API client
max_staleness is the freshness-vs-cost contract in one number. Set it from the consumer's real tolerance — support dashboards rarely need sub-minute customer records.
Speaker notes — BigQuery CDC
  • Open by drawing the division of labor, because the two names are easy to conflate: Datastream is the source-side service — it connects to Postgres, reads the write-ahead log, and streams changes out. BigQuery CDC is the destination-side feature — it accepts those changes as upserts/deletes and folds them into the table. Datastream is the most common driver of BigQuery CDC, but they're separable: Datastream can also write to Cloud Storage or Iceberg, and you can send _CHANGE_TYPE rows to BigQuery CDC yourself with no Datastream involved. Previous slide = the pipe; this slide = what happens where the pipe lands.
  • BigQuery CDC docs: primary key up to 16 columns, not enforced; _CHANGE_SEQUENCE_NUMBER orders changes; docs recommend a slot reservation for apply jobs on busy tables to cap merge costs.
  • Real constraints worth saying: while CDC is active you can't run your own UPDATE/DELETE/MERGE DML on the table; runtime-merge tables also block copies/clones/snapshots and the Storage Read API. Design considerations, not trivia.
  • The machinery is user-accessible: your own Write API client can send _CHANGE_TYPE rows — Datastream is just the managed driver of it.

SaaS on a schedule: Data Transfer Service

DTS

Marketing wants Ads spend joined to signups — but Google Ads won't stream it; something has to fetch its reports, every day, forever.

bq mk --transfer_config --data_source=google_ads --target_dataset=marketing \
  --display_name="Ads spend (daily)" --params='{"customer_id":"123-456-7890"}'
  • Connectors: Google marketing stack · SaaS (Salesforce, Stripe…) · warehouses (Redshift, Snowflake…) · storage (GCS, S3, Azure)
  • The scheduled Cloud Storage transfer closes slide 9's loop — the managed daily billing load, no cron job owned
DTS moves data in on a schedule — load jobs with a calendar and a connector catalog. Not a streaming tool; can't export.
Speaker notes — Data Transfer Service
  • DTS introduction. The connector list has grown far past the old "Google SaaS + S3" story — check the live list before promising a source; where DTS has no connector, this niche is the classic partner-tool slot (Fivetran et al.).
  • Scheduling floors and exact table layouts are connector-specific; the Ads transfer lands a set of report tables, not one table.
  • Scheduled queries are DTS under the hood — the same scheduler powers the ELT pattern on slide 23.
  • Backfills are first-class: re-run any historical window from the console without hand-building date loops.

External tables: the data stays in the bucket

EXTERNAL TABLEBigLake

The acquired company left 40 TB of meeting-archive Parquet in Cloud Storage; legal asks one question a quarter. Loading it means storing it twice.

SQLCREATE EXTERNAL TABLE partner.archived_meetings
WITH CONNECTION `us.gcs-reader`
OPTIONS (
  format = 'PARQUET',
  uris = ['gs://confcall-archive/meetings/*.parquet']
);
  • An external table is schema + pointer: queries read the files in place — nothing is copied into BigQuery storage, and you pay query compute only
  • The CONNECTION makes it BigLake: BigQuery's service account reads the bucket — analysts need only table permissions; row/column security works
Query in place when data is cold, still changing upstream, or not yet understood — and use it as the ELT on-ramp: explore externally, then load exactly what earns its keep.
Speaker notes — External tables
  • Three external flavors, one line each (external data intro): plain external tables (no connection; the user needs bucket access too), BigLake (shown here — the recommended default), object tables (metadata over unstructured files, for ML).
  • Live-database federation (EXTERNAL_QUERY to Cloud SQL / Spanner / AlloyDB) is the same idea pointed at a database — contrast with slide 17: federate for occasional live lookups, replicate for analytics.
  • Lakehouse pointer, don't teach: Apache Iceberg managed tables (renamed from "BigLake tables for Apache Iceberg") are writable open-format tables — full DML, Write API, load jobs (Iceberg docs).
  • Activity fit: the roitraining external tables demo (Hive-partitioned Parquet on GCS) exercises exactly this slide.

Load it, or leave it?

The same four signals decide it every time.

SignalLeave it externalLoad it (native)
Query frequencyrare / exploratoryhot, repeated
Performance need"eventually" is fineinteractive dashboards
Data churn upstreamstill changing / shared with other enginesstable snapshot
Features neededjust SELECTDML, streaming, snapshots, time travel, best pruning
SQL — promoting the hot sliceCREATE TABLE partner.recent_meetings AS
SELECT * FROM partner.archived_meetings WHERE meeting_date >= '2024-01-01';
External tables give up real capabilities: no time travel, no copies/snapshots, weaker statistics and pruning — and cost estimation can't see into the files. When a dataset goes hot, promote it: one CREATE TABLE AS SELECT (or LOAD DATA), and only the useful slice pays for native storage.
Speaker notes — Load it, or leave it?
  • This is the honest version of the old "external tables pitfalls" slide, updated: BigLake metadata caching narrows the performance gap for Parquet, but native storage still wins for hot paths.
  • The promotion statement is ELT in one line — and it's exactly what the running scenario wants: legal's quarterly question stays external; if product starts mining the archive weekly, promote the recent slice.
  • Dry-run caveat is a good demo: a dry run against the external table reports 0 bytes / no estimate, against the native copy it prices the scan — the metadata difference made visible.

Where transformation happens: EL → ELT → ETL

Zoom out: every path so far lands raw-ish data. Who cleans it, and where?

  • EL — data is already clean (Parquet from the vendor): load it, done. Prefer this when you can get it
  • ELT — land raw into a raw/staging layer, transform inside BigQuery with SQL, publish to reporting tables. The default for everything else
  • ETL — transform before landing (Dataflow, slide 15) only when SQL can't: in-flight enrichment, streaming aggregation, non-SQL logic
SQL — publish stepMERGE billing.usage_reporting r
USING billing.usage_staging s
  ON r.customer_id = s.customer_id
 AND r.usage_date  = s.usage_date
WHEN MATCHED THEN UPDATE SET minutes = s.minutes
WHEN NOT MATCHED THEN INSERT ROW;
Prefer EL, then ELT, then ETL — in that order. Keeping raw data in BigQuery is cheap; the expensive thing is a transform you can't redo.
Speaker notes — EL, ELT, ETL
  • The ordering argument (Definitive Guide ch. 1): ELT delays irrevocable decisions. Its example: an ETL step that collapsed "not collected" and "suppressed" into one NULL — unrecoverable afterward. Our slide-7 sentinel (N/A) is the same story in miniature.
  • The raw → staging → reporting layering with a MERGE publish is the strongest slide of the source module, rebuilt here as synthesis instead of preamble.
  • Schedulers, smallest to largest: scheduled queries (DTS-powered) → Dataform → full orchestration (Composer). Continuous queries — SQL that runs forever over arriving rows — exist for streaming ELT (Enterprise edition + reservation); pointer on the Additional material slide.

Choosing an ingestion method

  1. Files, and batch cadence is fine? Load jobs — they're free. Ask upstream for Parquet/Avro; pin schemas for anything recurring
  2. Need rows in seconds? Storage Write API — via a Pub/Sub BigQuery subscription if it's already a topic and needs no reshaping; via Dataflow if it must transform in flight; default stream unless duplicates carry real cost
  3. Mirroring a database? Datastream CDC; set max_staleness from the consumer's real tolerance, not zero
  4. A vendor publishes it on their schedule? Data Transfer Service — or a partner tool where DTS has no connector
  5. Cold, changing, or unexplored? Don't load it — external/BigLake table now; promote the hot slice later
  6. Everywhere: land raw and transform in SQL (EL → ELT → ETL) — and never micro-batch load jobs for freshness; that pressure means switch doors

Activity

Ingesting real data (30–45 min)
  • Load a CSV with bq load — hit the sentinel failure, fix it with a pinned schema
  • Re-run the load as a SQL LOAD DATA statement
  • Create an external table over Hive-partitioned Parquet in Cloud Storage — query without loading
  • Compare: dry-run estimates, performance, and what each table can and can't do
