Batch loading

Files land in Cloud Storage and a load job copies them into a table. Load jobs are free by default.
Speaker notes — Section 1: Batch loading
  • Arc: first load → recall the commit → schemas → formats → the same load in SQL → why many tiny loads fail. Four DINs in this section.
  • “Free by default”: load jobs run on a shared slot pool at no charge. Loads assigned to a reservation use paid slots; cross-region loads bill network transfer (Pricing: data ingestion). External tables and Cloud Storage and Ads transfers also have no ingestion charge (Pricing: Data Transfer Service), so do not say batch is “the only free one”.

Your first load: bq load

Every morning the billing vendor drops yesterday’s usage file into Cloud Storage. Finance wants it in billing.daily_usage before 9 a.m.

Shell

$ bq load --source_format=CSV --autodetect \
    billing.daily_usage \
    gs://jwd-gcp-demos/ingest_demo/daily/usage_2026-07-20.csv

One command, three parts: source format, destination table, source URI. Wildcards (usage_*.csv) load many files in one job.

Loads append by default. --replace empties the table first.

--autodetect infers column names and types from a sample of the file, and detects the header row. Fine for a first look; page 8 shows where it breaks.

Free by default: load jobs run on a shared pool of slots, separate from your query slots, and bill 0 bytes.

Example

Actor: a finance data engineer.

Input: usage_2026-07-20.csv, 32 MB, 1,000,000 rows illustrative.

Mechanism: bq load starts one load job on the shared pool.

Result: billing.daily_usage has 1,000,000 rows, minutes typed INTEGER and event_date typed DATE. Loading Tuesday’s file the same way appends: 2,000,000 rows.

Takeaway: if a source can wait for a daily file, load it: one bq load, no compute charge by default.
Sources: Batch loading data, Schema auto-detection, Pricing: data ingestion (verified 2026-09-30).

Recall: one load, one commit

Tuesday’s load starts at 06:01:00. At 06:01:10 an analyst runs SELECT COUNT(*) on the table. What does the analyst see?

A load job commits all of its data or none of it. A query sees the table before the load or after it, never partway.

A failed load leaves the table unchanged, so a failed load can be retried without cleanup.

The shared pool has no throughput guarantee: a load’s run time varies with other customers’ loads. For predictable load throughput, assign a PIPELINE reservation; those loads then use your paid slots.

Takeaway: a load is all or nothing, so a failed load is safe to retry.
Sources: Loading CSV data, Pricing: data ingestion, Reservation assignments (verified 2026-09-30).
Speaker notes — Recall: one load, one commit
  • Covered in Architecture as the storage-set commit; here the point is retry safety. “Load jobs are atomic and consistent” (Loading CSV data). Test T1: a failed load created no table.
  • Loads, streams, and CDC all end with rows committed to the table; they differ in how rows get there. Simplified: default-stream rows are queryable before any conversion to columnar files (Storage Write API).
  • PIPELINE reservations: reservation-assigned loads “lose access to the free pool” (Pricing: data ingestion, Reservation assignments).
  • bq ls -j lists recent jobs; the console’s job history shows the same.

Autodetect guesses from a sample

The vendor writes N/A in minutes for meetings that never started. Two test files, same bad value, two different outcomes.

Autodetect reads a sample from the top of the file and picks the narrowest type that fits every sampled value.

Loud failure: the sample is all numbers, so minutes becomes INTEGER; the N/A further down fails the whole load.

Silent failure: the N/A falls inside the sample, so minutes becomes STRING; the load succeeds and every SUM(minutes) fails later.

Error from the Monday load

column_type: INT64 value: "N/A"
Takeaway: autodetect is a guess from the top of the file; a recurring load needs a schema you wrote down.
Sources: Schema auto-detection (verified 2026-09-30); error text from test T1.
Speaker notes — Autodetect guesses from a sample
  • Real error text from test T1. The old slide’s “Could not parse ‘N/A’…” was invented.
  • Sample size: the docs say autodetect reads “up to the first 500 rows” (Schema auto-detection). Tests contradict the precise number: rows 700, 1,000, 2,000, and 5,000 were sampled; row 20,000 was not (T1, T2). Do not quote a number; teach “a sample from the top”.

Pin the schema for recurring loads

Finance loads this file every day. The fix is to decide the types once and tell BigQuery what N/A means.

daily_usage_schema.json

[{"name":"meeting_id","type":"STRING"},
 {"name":"user_id",   "type":"STRING"},
 {"name":"minutes",   "type":"INTEGER"},
 {"name":"event_date","type":"DATE"}]

Recurring load, schema pinned

$ bq load --source_format=CSV \
    --schema=daily_usage_schema.json \
    --skip_leading_rows=1 \
    --null_marker='N/A' \
    billing.daily_usage \
    gs://jwd-gcp-demos/ingest_demo/daily/usage_2026-07-21.csv

--schema fixes the types, so a bad value fails the load instead of changing a type.

--null_marker='N/A' loads N/A as NULL.

--skip_leading_rows=1 becomes necessary once the schema is pinned; autodetect had been skipping the header for you.

Cheap way to write the schema file: autodetect one known-good file, dump its schema with bq show --schema --format=prettyjson, review it, commit it.

Example

Actor: the finance data engineer.

Input: both test files reloaded with the pinned schema and --null_marker='N/A'.

Mechanism: N/A becomes NULL; minutes stays INTEGER.

Result: 101,000 rows, 2 NULL minutes, and SUM(minutes) works illustrative.

Takeaway: for any recurring load, pin the schema and name the null marker.
Sources: Loading CSV data, Batch loading data (verified 2026-09-30); result from test T4.
Speaker notes — Pin the schema for recurring loads
  • Tested T4: 101,000 rows, 2 NULLs. Without --skip_leading_rows=1 the pinned load fails on the header (“CSV processing encountered too many errors … errors: 1”).
  • Other fixes for a bad value, from the Definitive Guide ch. 4: edit the data, --max_bad_records (drops rows silently, so usually wrong for billing), or --null_marker (right here).
  • Schema evolution: --schema_update_option=ALLOW_FIELD_ADDITION lets a load add a column (Batch loading data). Schema shape is covered in Storage Optimization; this is the load-time flag.

File formats: what to ask the vendor for

The vendor will export 60 million rows of usage history as one gzipped CSV or as 100 Parquet files. Which is faster to load?

Self-describing: Avro, Parquet, and ORC files store column names and types inside the file, so there is nothing to guess.

Splittable: Parquet and Avro compress each block separately, so many slots read one file’s blocks in parallel.

A gzipped CSV or JSON file cannot be read in parallel, so one slot reads it start to end. Compressed CSV and JSON files are capped at 4 GB each.

FormatSchemaParallel loadUse
Avro, Parquetin the fileyes, even compressedask for these
ORCin the fileyesfine
CSV, JSON, uncompressedyou supply or autodetectyesmany smaller files
CSV, JSON, gzippedyou supply or autodetectnoavoid for large loads
Example

Actor: the data engineer loading usage history.

Input: usage_big.csv.gz, 317 MiB, vs 100 Parquet files, 829 MiB; same 60,000,000 rows.

Mechanism: one slot decompresses and parses the gzip file; up to 100 slots can read the Parquet files at once, with no text parsing.

Result: about 2 minutes vs a few seconds illustrative, though Parquet is over twice the bytes.

Takeaway: ask upstream for Parquet or Avro; if it must be CSV, prefer many uncompressed files over one gzip.
Sources: Batch loading data, Loading CSV data, Quotas: load jobs (verified 2026-09-30); timings from test T7.
Speaker notes — File formats: what to ask the vendor for
  • Measured T7: CSV.gz 107 s job / 114 s wall; Parquet 3 s job / 7 s wall; both 60,000,000 rows. The DIN says “roughly 20x”.
  • Docs: Avro is “the preferred format for loading data”; Parquet is “also a good choice” (Batch loading data). The old note that the Avro-vs-Parquet guidance “has leveled out” was wrong.
  • Limits: 4 GB per compressed CSV/JSON file, 5 TB uncompressed, 10,000 URIs per job (Quotas: load jobs). Uncompressed loads faster but costs more bucket storage and transfer (Batch loading data).
  • Format does not change storage: every load is rewritten into BigQuery’s columnar format.

Many tiny loads

Support wants usage numbers fresher than daily. Someone proposes loading a new file every minute. What breaks?

Quota: 1,500 load jobs per table per day, failed jobs included. One load a minute is 1,440, which leaves 60 retries a day.

Still minutes behind: each file must close, and each job must queue and commit.

Streaming has separate quotas and makes rows queryable in seconds. That is Section 2.

Example

Actor: support’s analytics lead.

Input: 1,440 scheduled loads in one day; 61 of them fail and are retried.

Mechanism: 1,440 + 61 = 1,501 jobs against a quota of 1,500.

Result: the 1,501st job fails, and so does every load to that table until the quota window moves illustrative.

Takeaway: if you need data fresher than a daily load, stream it; don’t shrink the load interval.
Sources: Quotas: load jobs (verified 2026-09-30).
Speaker notes — Many tiny loads
  • Quota facts (Quotas: load jobs): 1,500 loads per table per day including failures; 100,000 loads per project per day (replenishes over 24 h); 15 TB per load job, waived for reservation-assigned jobs.
  • Discussion: where is the line? Hourly loads of reasonably sized files are fine (24 a day). Per-minute files of a few hundred KB are the classic problem.

Recap: batch loading

Load files with bq load, the console, or LOAD DATA; all run free on the shared pool by default.

A load commits all or nothing, so retry a failed load without cleanup.

Pin the schema and name the null marker for any recurring load.

Ask for Parquet or Avro; avoid one large gzip file.

Keep loads to hourly or slower; for fresher data, stream.

Streaming

Events arrive one at a time. Streamed rows are queryable in seconds and cost per GiB.
Speaker notes — Section 2: Streaming
  • Arc: why a load cannot meet a seconds target → the Storage Write API → at-least-once duplicates → step 28 → Pub/Sub primer → BigQuery subscriptions → Dataflow when rows must change shape.
  • tabledata.insertAll is the legacy streaming API, now named “Storage Write API (REST)”; the gRPC API is renamed “Storage Write API (gRPC)” (2026-07-27) and recommended for new work (Release notes, Storage Write API).

Seconds, not minutes

At 10:02:10 web-client calls start dropping audio. The on-call engineer needs to see it in the telemetry within seconds, not after the next file closes.

Load path: buffer events into a file, close it, load it. With 15-minute files the event is visible at about 10:17 illustrative.

Stream path: each event is appended to the table and is queryable about a second later.

Streaming is metered: Storage Write API (gRPC) ingestion costs $0.025 per GiB after the first 2 TiB each month.

Takeaway: stream when a question needs rows seconds old; you pay per GiB for that freshness.
Sources: Storage Write API, Pricing: data ingestion (verified 2026-09-30).
Speaker notes — Seconds, not minutes
  • 10:17 assumes 15-minute files and a two-minute load; illustrative.
  • Pricing: $0.025/GiB, first 2 TiB a month free (Pricing: data ingestion). That is about $25.60 per TiB.
  • “Why not Bigtable?” If the need is a per-key lookup in milliseconds inside the call path, that is Bigtable’s job; BigQuery streaming is for scans and aggregations over fresh plus historical rows. No source fetched; keep it as the instructor’s answer, not a face claim.

Streaming rows with the Storage Write API

Cymbal Meet’s telemetry service writes every 10-second sample straight to telemetry.qos_events, about 58,000 rows a second.

Stream: a channel a client appends rows to. Every table has a built-in one, the default stream, with nothing to create.

Ack: BigQuery confirms each append. A client that gets no ack retries.

Streaming buffer: appended rows are queryable at once; BigQuery converts them to columnar storage in the background, and queries read both.

Many senders, within quota: 5,000 concurrent connections per region, 20,000 in the US and EU multi-regions.

Example

At-least-once: when a retry lands a row twice

telemetry-svc-2 appends a sample, the network drops BigQuery’s ack, and the client retries. The table now has that sample twice.

The default stream is at-least-once: every row lands, and a retry after a lost ack can land it again.

Remove duplicates in SQL on a key that identifies one sample, such as (participant_id, event_time).

Exactly-once needs your own stream: the client creates a stream and numbers each append with an offset; BigQuery rejects a repeated offset with ALREADY_EXISTS. The client must store its offsets.

Dedup in the query

SELECT *
FROM telemetry.qos_events
WHERE DATE(event_time) = '2026-07-21'
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY participant_id, event_time) = 1;
Example

Input: sample p_2f07a9 · 14:31:20, appended twice after a lost ack.

Result: p_2f07a9 shows 7 samples for 14:31 instead of 6 illustrative; the QUALIFY query returns 6.

Takeaway: plan for duplicates from the default stream and remove them in SQL, unless a duplicate costs more than the client bookkeeping.
Sources: Storage Write API, Streaming with the Storage Write API, Storage Write API best practices (verified 2026-09-30).
Speaker notes — At-least-once: when a retry lands a row twice
  • Default stream at-least-once; application-created streams exactly-once (Storage Write API, Streaming with the Storage Write API). Offsets: an ALREADY_EXISTS error means the row already landed and is safe to ignore (Storage Write API best practices). A pending-type stream holds rows invisible until one commit.
  • “Delivery semantics” is the name for at-least-once vs exactly-once; page 40 uses the term.
  • Managed services: Dataflow gives exactly-once only in STORAGE_WRITE_API mode; its at-least-once mode uses the default stream (Dataflow: write to BigQuery). Pub/Sub BigQuery subscriptions are at-least-once (BigQuery subscriptions). The old notes said managed services “handle this for you”; that was wrong.
  • Dedup key: one sample per participant per 10 s (data sheet), so (participant_id, event_time) identifies a sample.

Pub/Sub in one page

Cymbal Meet’s telemetry service already publishes every sample to Pub/Sub for the alerting system. Before BigQuery can read from it, you need four terms.

Topic: a named channel publishers send messages to, here qos-events.

Subscription: a named queue attached to a topic. Each subscription gets its own copy of every message published after it was created.

Ack: the reader confirms a message. If no ack arrives within the ack deadline (10 s by default), Pub/Sub delivers the message again.

Dead-letter topic: after a set number of failed deliveries (5 by default, 5–100), Pub/Sub moves the message to a second topic you can inspect.

Example

Actor: the alerting app, reading qos-to-alerts, which crashes before acking one message.

Input: message {"meeting_id":"mtg_91e0","participant_id":"p_77a3d2","audio_mos":2.4} on qos-events.

Mechanism: no ack within 10 s, so Pub/Sub redelivers it; the qos-to-bq subscription got its own copy and is unaffected.

Result: the alerting app receives the message twice. Pub/Sub delivery is at-least-once too.

Takeaway: a topic fans messages out to subscriptions; each subscription redelivers until the reader acks.
Sources: Pub/Sub subscriptions, Subscription properties, Dead-letter topics (verified 2026-09-30).
Speaker notes — Pub/Sub in one page
  • Pub/Sub is not defined earlier in the course; this page gives page 23 its vocabulary.
  • Sources: redelivery after the ack deadline and possible duplicates (Pub/Sub subscriptions); ack deadline default 10 s, max 600 s; message retention default 7 days (Subscription properties); dead-letter topic, max delivery attempts 5–100, default 5 (Dead-letter topics).
  • Only messages published after a subscription is created are delivered to it (Pub/Sub subscriptions). A new BigQuery subscription does not backfill history.

Streaming without code: Pub/Sub BigQuery subscriptions

The samples are already on qos-events. A BigQuery subscription writes each message to a table, with no reader application to run.

Shell

$ gcloud pubsub subscriptions create qos-to-bq \
    --topic=qos-events \
    --bigquery-table=cymbal-meet:telemetry.qos_events \
    --use-table-schema \
    --dead-letter-topic=qos-events-dead

How message fields map to columns

OptionFlagResult
Topic schema--use-topic-schematopic schema fields map to columns by name

Pub/Sub writes with the Storage Write API and acks each message once the write succeeds.

At-least-once: dedup as on page 20. Messages that fail to write go to the dead-letter topic.

Costs more than writing directly: $50 per TiB of throughput, no separate BigQuery ingestion charge.

Light per-message changes (rename a field, drop one) fit a Single Message Transform (SMT) on the subscription. Grouping or joining messages needs Dataflow (page 24).

Example

Replication and scheduled transfers

Data owned by other systems: an operational database that changes all day, and an ad platform that publishes daily reports.
Speaker notes — Section 3: Replication and scheduled transfers

Change data capture: copy the changes, not the table

Support dashboards need each org’s plan and seat count, which live in Cloud SQL for PostgreSQL and change all day. A nightly export is up to a day old.

Write-ahead log: the database’s append-only record of every insert, update, and delete, written before the table changes.

Change data capture (CDC): read that log and replay each change in another system, so the copy tracks the source without re-exporting whole tables.

Merge mode: the copy holds the current state, one row per key.

Append-only mode: the copy keeps every change as its own row, for history.

Example

Actor: Cymbal Meet’s sales system.

Input: at 10:05 on 2026-07-21, UPDATE orgs SET plan='enterprise', seats=250 WHERE org_id='o-0071'.

Mechanism: Postgres writes an UPDATE record to its log; CDC reads the record and applies it to crm.orgs in BigQuery.

Result: merge mode shows one row, o-0071 · enterprise · 250. Append-only shows two rows, pro · 180 then enterprise · 250, each with change metadata.

Takeaway: CDC keeps a copy current by replaying the database’s log; choose merge for current state, append-only for history.
Sources: Configure the BigQuery destination, Datastream BigQuery destination (verified 2026-09-30).
Speaker notes — Change data capture: copy the changes, not the table
  • CDC and write-ahead log were used on the old slide without definition; this page is the definition beat.
  • Merge is the default and needs a primary key; append-only lands change type and order in datastream_metadata (Configure the BigQuery destination, Datastream BigQuery destination). Change type labels in the figure are simplified.
  • The old pattern (nightly export, load to staging, hand-written MERGE) is what CDC replaces. MERGE itself is shown on page 39.

Replicating Cloud SQL with Datastream

Cymbal Meet wants CDC for orgs without writing a log reader. Datastream is Google Cloud’s managed CDC service.

Backfill, then tail: Datastream first copies the existing rows, then reads the write-ahead log continuously.

Writes with the Storage Write API (gRPC) into BigQuery change data capture ingestion, which applies each change to the replica (page 29).

Sources: MySQL, PostgreSQL (including AlloyDB), Oracle, SQL Server, MongoDB, Spanner, and Salesforce.

Costs on both sides: Datastream bills per GiB processed; BigQuery bills ingestion, apply compute, and storage.

Example

Actor: the platform team.

Input: a Datastream stream from Cloud SQL orgs (40,000 rows) to crm.orgs.

Mechanism: backfill copies 40,000 rows; then the 10:05 UPDATE flows through the log.

Result: crm.orgs shows o-0071 · enterprise · 250 minutes later, with no export files and no MERGE job to maintain.

Takeaway: use Datastream before writing your own export-and-merge job.
Sources: Datastream overview, Datastream sources, Configure the BigQuery destination, Datastream pricing, BigQuery CDC ingestion (verified 2026-09-30).
Speaker notes — Replicating Cloud SQL with Datastream
  • Sources (Datastream sources, Datastream overview); SaaS sources other than Salesforce are Preview. Backfill then log tailing (Datastream overview, Datastream pricing). Writes via “BigQuery Storage Write API (gRPC)” (Configure the BigQuery destination).

Applying changes: max_staleness

The support dashboard can show plan data up to 15 minutes old. max_staleness tells BigQuery how old query results may be.

SQL

ALTER TABLE crm.orgs
SET OPTIONS (max_staleness = INTERVAL 15 MINUTE);

Primary key: you declare it (PRIMARY KEY (org_id) NOT ENFORCED); BigQuery does not enforce it, and CDC uses it to find the row each change replaces.

Each change arrives as an UPSERT or DELETE in a _CHANGE_TYPE field and waits until a background apply job merges it into the table.

If the last apply is within max_staleness, a query reads the applied table only.

If apply has fallen behind, or max_staleness is unset or 0, the query merges pending changes at run time, which reads more and costs more.

Example

Actor: the support dashboard.

Input: apply at 10:00 (o-0071 · pro · 180); UPSERT enterprise · 250 arrives at 10:05; queries at 10:10 and 10:20, no apply in between.

Mechanism: at 10:10 the last apply is 10 minutes old, within 15; at 10:20 it is 20 minutes old.

Result: 10:10 returns pro · 180 (allowed staleness); 10:20 runs a merge at query time and returns enterprise · 250 illustrative.

Takeaway: set max_staleness to the staleness the consumer accepts; never 0 unless every query may pay to merge.
Sources: BigQuery CDC ingestion, Datastream BigQuery destination, Configure the BigQuery destination (verified 2026-09-30).
Speaker notes — Applying changes: max_staleness
  • Rule (BigQuery CDC ingestion): a query uses the applied baseline if it was applied within max_staleness; otherwise it merges unapplied changes at run time. The old slide’s “freshness forced” query does not exist.
  • Background apply jobs bill on-demand unless the project has a BACKGROUND reservation (BigQuery CDC ingestion, Datastream BigQuery destination); the old slide’s “cheap” was overstated.
  • Conflict to name: the Configure the BigQuery destination page says the staleness limit “doesn’t affect the frequency of the BigQuery merge jobs”, while the BigQuery CDC ingestion page describes staleness as the tuning lever. Teach the query-time rule, which both agree on.
  • Constraints (BigQuery CDC ingestion): primary key up to 16 columns; _CHANGE_SEQUENCE_NUMBER orders changes; no user DML while CDC is active; tables that need runtime merges block copy, clone, snapshot, and the Storage Read API; a runtime merge on a partitioned table scans the whole table. Your own Write API client (default stream, protobuf) or a Pub/Sub BigQuery subscription can send _CHANGE_TYPE rows without Datastream.

Hive partitioning: directory names become a column

The 2019–2023 meeting archive sits in Cloud Storage as 40 TB of Parquet, one directory per day. Legal asks about one day’s meetings.

Hive layout: each directory name is key=value, for example meeting_date=2019-04-02/.

BigQuery reads the key from the path and adds it as a column, meeting_date, when it loads or queries the files.

A filter on that column skips whole directories, the same pruning a partitioned table gets (covered in Storage Optimization).

require_hive_partition_filter rejects queries that don’t filter on the key.

Example

Actor: a legal analyst.

Input: WHERE meeting_date = '2019-04-02' over 1,826 daily directories.

Mechanism: BigQuery matches the filter to directory names before opening files.

Result: reads 1 directory, ~22 GB, instead of 40 TB illustrative.

Takeaway: lay files out as key=value directories, and a filter on the key reads only the matching directories.
Sources: Hive-partitioned data (verified 2026-09-30).

External tables: the data stays in the bucket

Legal asks one question a quarter about the archive. Loading 40 TB would store a second copy for four queries a year.

SQL

CREATE EXTERNAL TABLE archive.meetings
WITH PARTITION COLUMNS
WITH CONNECTION `us.archive-reader`
OPTIONS (
  format = 'PARQUET',
  uris = ['gs://cymbal-meet-archive/meetings/*'],
  hive_partition_uri_prefix = 'gs://cymbal-meet-archive/meetings'
);

An external table is a schema and a pointer to files. Queries read the files in place; nothing is copied into BigQuery storage.

Costs still apply: queries bill as usual, Cloud Storage bills for the files, and metadata-cache refreshes bill if enabled.

WITH CONNECTION makes it a BigLake table: BigQuery reads the bucket with the connection’s service account (the identity BigQuery uses to read files), so analysts need permission on the table only.

Where transforms happen: EL, ELT, ETL

The vendor reissues Tuesday’s usage file with late meetings. Finance’s reporting table must change, and the raw data should stay as delivered.

EL: the data arrives clean (Parquet from a careful vendor); load it and stop.

ELT: land it raw, transform in BigQuery with SQL, publish to reporting tables. The default for most sources.

ETL: transform before landing (Dataflow, page 24) only when SQL can’t, such as per-minute aggregation of a stream.

Keep the raw table so you can rerun a transform after finding a mistake.

SQL: publish step, run as a scheduled query

MERGE billing.usage_by_org r
USING billing.usage_staging s
  ON r.org_id = s.org_id
 AND r.usage_date = s.usage_date
WHEN MATCHED THEN UPDATE SET minutes = s.minutes
WHEN NOT MATCHED THEN INSERT ROW;
Takeaway: prefer EL, then ELT, then ETL; keep raw data so every transform can be rerun.
