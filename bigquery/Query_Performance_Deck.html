stages & slots

How BigQuery runs the Monday query

Here is the query behind the dashboard tile — and what actually executes when you press Run.

SQLSELECT o.name,
       AVG(c.packet_loss_pct) AS avg_loss,
       COUNT(DISTINCT c.user_id)
         AS affected_users
FROM vc.call_quality AS c
JOIN vc.orgs         AS o USING (org_id)
WHERE c.event_ts >= TIMESTAMP '2026-07-20'
  AND o.plan = 'enterprise'
GROUP BY o.name
ORDER BY avg_loss DESC;
  • The query becomes a plan of stages; each stage runs in parallel across many slots (a slot ≈ one virtual CPU's worth of compute)
  • Stages hand results to each other through the in-memory shuffle
  • The plan is dynamic — BigQuery re-plans mid-query as it learns real data sizes
Speaker notes — How BigQuery runs the Monday query
  • This is a recap in a new costume. Students met stages, slots and shuffle in the architecture module as concepts. Here they meet them as things the console will show them by name in two minutes. Don't re-teach the internals; re-anchor the vocabulary on this specific query.
  • The one genuinely new point: the plan is dynamic. BigQuery does not commit to a plan up front. As stages finish, it learns actual row counts and data sizes and can change what happens next — adding repartition stages, changing the number of shuffle sinks, switching a join strategy because a filtered input turned out to be small. Consequence for the student: there is no useful ahead-of-time EXPLAIN in BigQuery. You inspect the plan of a run that already happened. That is why every lever in this deck is taught as "run, look, change, re-run."
  • Reading the diagram aloud: stage S00 does everything it can while the data is already in memory — read the needed partitions, apply the WHERE, join the broadcast copy of orgs, and compute partial per-org aggregates. Only those partials cross the shuffle (48 GB), keyed by org_id so each S01 slot owns a set of orgs and can finalize them. The sort is last, small, and single-threaded — harmless here because there are only a few thousand enterprise orgs.
  • Scale detail if asked: a big query can generate millions of small work units over its lifetime; on-demand projects get a soft target of about 2,000 concurrent slots shared across everything running in the project (Section 6). Slots are handed out and taken back continuously — work units are small and idempotent, so rebalancing is cheap.

stage timing

Anatomy of a stage: wait, read, compute, write

Each stage's time splits four ways — and the split names your bottleneck for you.

  • Wait — queued for slots · Read — pulling input from storage or shuffle · Compute — CPU work · Write — pushing output to shuffle or result
  • Each phase shows an average and a max across the stage's workers
  • A big gap between average and max means some workers got far more work than others
Read the bars as a diagnosis — this is also this module's table of contents:
high wait → not enough slots (§6) · high read → too many bytes in (§2) · high compute → too much work per row (§4) · high write → too much output/shuffle (§3)
Speaker notes — Anatomy of a stage: wait, read, compute, write
  • Say the table-of-contents line out loud and pause on it. "High wait means section 6. High read means section 2. High compute means section 4. High write means section 3." Students should leave this slide knowing that the console tells them which part of the day's material applies to their problem. Everything after this is just detail.
  • Why avg vs. max is the most useful pair of numbers in the pane. A stage's elapsed time is governed by its slowest worker, not its average one — the next stage can't start until the last worker finishes. So a stage with avg 300 ms and max 9 s takes 9 seconds no matter how many slots you throw at it. Adding capacity cannot fix a skewed stage; only changing the data distribution can (slide 22).
  • Mapping to the API, for anyone building tooling: these are waitMsAvg/waitMsMax, readMsAvg/Max, computeMsAvg/Max, writeMsAvg/Max per entry in the job's queryPlan, also available through INFORMATION_SCHEMA.JOBS (slide 10). The console is drawing exactly these fields — nothing is hidden from you.
  • One nuance to pre-empt: "read" here includes reading from the shuffle, not just from storage. A stage in the middle of a plan reads its input from the previous stage's shuffle output. So high read time in a middle stage points at Section 3 (too much shuffled), while high read in the first stage points at Section 2 (too many bytes scanned).

shuffle & spill

Shuffle on the meter: bytes shuffled, bytes spilled

The Monday query shuffled 48 GB and spilled nothing. What kind of stage outgrows the memory tier?

  • Shuffle runs in a fast in-memory tier with a finite capacity for your query. When a stage's output outgrows it, the overflow goes to disk: bytes spilled
  • Disk is orders of magnitude slower than memory — and a retry re-runs the same volumes and spills again
Bytes spilled > 0 is a check-engine light: one stage's output outgrew shuffle memory. Find that stage in the plan, then shrink its output — the table names the usual suspects.
What makes a stage's output hugeShrink it by
Two big tables joined row-for-row, nothing reduced firstFilter, project, pre-aggregate each side first (§3)
Fan-out join: keys repeat on both sides — a self-join can square the row countDeduplicate keys; window function instead of self-join
GROUP BY shuffles rows by key before it can shrink them — ~100 M+ scattered keys, so partials barely collapseGroup to a coarser key; stage results in a temp table
ARRAY_AGG / STRING_AGG shrink row count, not bytes — every input value survives into the outputAggregate to metrics; build giant arrays in their own job
Speaker notes — Shuffle on the meter
  • Mechanism recap from the architecture module, in one sentence: when a stage finishes, its output is written into shuffle "sinks" partitioned by some key, so that each worker in the next stage can read exactly the key range it owns. The number of sinks is chosen dynamically — and re-chosen if the data turns out bigger than expected.
  • Why spilling is so expensive. The shuffle tier is memory across the cluster, connected by a very fast network. When a stage's intermediate data exceeds what's available, the excess is written to disk and read back. Nothing about your query changed; it just got dramatically slower. This is also why "just retry it" is not a fix — the same query will produce the same volume and spill again. The corresponding performance insight (next slide) is insufficient shuffle quota: "more data that needs to get written to shuffle than you have shuffle capacity."
  • Where shuffle pressure comes from — the keystone for the whole table: only stage outputs occupy the shuffle tier. A scan's input comes from storage, not shuffle — that's how a query can read 60 TB while shuffling 48 GB. So each stage boundary's pressure equals the writing stage's output volume, and the first oversized output is what spills. A spill deep in a plan whose early stages were clean means some middle stage grew the data (a fan-out join) or failed to shrink it (the GROUP BY row below).
  • Why each row of the table is there — the mechanism behind each cause:
    • Unreduced join: a hash join shuffles both entire sides by key (slide 17); the intermediate data is the sum of both tables as filtered. Reducing either side reduces it one-for-one.
    • Fan-out join: a key with m rows on the left and n on the right emits m×n joined rows. The docs' anti-pattern page warns a self-join "potentially squares the number of output rows" — the output of the join stage, not the tables read, is what hits shuffle next.
    • High-cardinality GROUP BY: aggregation can only shrink rows after co-locating them, so rows are shuffled by group key and the collapse to one-row-per-group happens on the far side of the shuffle. The escape hatch is partial pre-aggregation on the scan workers — and it's a pure cardinality game. GROUP BY device (10 values): 400 workers × ≤10 partials ≈ 4,000 rows cross. GROUP BY a scattered 800 M-value key: keys almost never repeat within one worker's chunk, partials collapse nothing, and nearly the whole input crosses as one-row "partials." The final output is small; the intermediate data was input-sized. The shuffle-quota insight doc names GROUP BY alongside JOIN as the shuffle-heavy operations to minimize.
    • Giant per-key aggregates: AVG over 45 rows returns one number; ARRAY_AGG over 45 rows returns one row containing all 45 values — aggregation without reduction. The full input volume still crosses the shuffle, now concentrated in single rows that must fit in one worker's memory (the classic "could not be executed in the allotted memory" error).
  • Remediations beyond filter/pre-aggregate, for when students ask: carry fewer columns through the shuffle (row width counts as much as row count); split the query and materialize an intermediate result to a temp table so no single stage carries the whole load; and on capacity pricing, shuffle capacity scales with the reservation's slots — an administrator lever, not a query fix.
  • Vocabulary bridge for anyone reading the API or INFORMATION_SCHEMA: the field is shuffleOutputBytesSpilled. Non-zero there and the console's "bytes spilled to disk" are the same fact.
  • References: Query performance insights (insufficient shuffle quota: definition, and slots/reservations as the capacity remediation); Optimize query computation (GROUP BY and JOIN use shuffle; anti-pattern sections on self-joins and cross joins; splitting queries into stages with temp tables); Troubleshoot queries (memory-exceeded errors).
insights

The console diagnoses with you

The Execution graph tab doesn't just draw the stages — it flags known pathologies by name.

  • Slot contention — stages sat in wait; the project was out of slots
  • Insufficient shuffle quota — more data headed to shuffle than the query's capacity: the spill story, named
  • High-cardinality join — a key repeated on both sides multiplies: m matches × n matches emit m·n rows, so output far exceeds input
  • Data input scale change — this run read ≥50% more from a table than your last run of the same query
  • Partition skew — a few workers got most of the data
Check insights first. If one fires, your diagnosis is done and the lever is named — every insight maps to a slide in this deck.

    • Slot contention — nothing is wrong with your SQL. Someone else (or your own ETL) was using the slots. Section 6.
    • Insufficient shuffle quota — the docs' definition is "more data that needs to get written to shuffle than you have shuffle capacity" — the spill story from the previous slide, named.
    • High-cardinality join — per the docs, it fires when join keys are non-unique on both sides and the ratio of output rows to input rows is high. Worked micro-example for the room: key m17 appears 3 times on the left and 4 times on the right → 12 output rows from 7 inputs.     • Data input scale change — fires when the query reads at least 50% more data from an input table than the previous run of the same query; BigQuery keeps per-table input sizes in job history, so it can compare run over run. Usually a date filter that stopped pruning, a table that grew, or a wildcard that started matching more tables.
    • Partition skew — a small number of workers processed most of the rows; the avg-vs-max gap from slide 7.

Finding the query worth optimizing

Finance's question isn't about one query. Which jobs cost the most last week, across the whole project?

SQLSELECT job_id, user_email,
       total_bytes_processed, total_slot_ms,
       LEFT(query, 80) AS query_start
FROM `region-us`.INFORMATION_SCHEMA.JOBS
WHERE creation_time >
        TIMESTAMP_SUB(CURRENT_TIMESTAMP(),
                      INTERVAL 7 DAY)
  AND job_type = 'QUERY'
ORDER BY total_slot_ms DESC
LIMIT 10;
  • Every job's stats land here in real time — bytes, slot-ms, cache hits, errors, even the per-stage plan. 180 days of history
  • Sort by total_bytes_processed on-demand; by total_slot_ms under capacity pricing
Optimize by evidence, not by complaint volume: the slowest-feeling query is often not the most expensive one.

columns

SELECT * reads everything, every time

An analyst's exploration query got pasted into the dashboard: SELECT * over call_quality, then two fields used.

SQL-- 2.8 TB: reads all 14 columns
SELECT * FROM vc.call_quality
WHERE event_ts >=
      TIMESTAMP '2026-07-20';

-- 410 GB: reads 3 columns
SELECT org_id, packet_loss_pct
FROM vc.call_quality
WHERE event_ts >=
      TIMESTAMP '2026-07-20';
  • Columnar storage means each column is its own set of files — you're billed for exactly the columns the query touches
  • Nearly all columns? SELECT * EXCEPT (raw_payload, debug_blob)
Speaker notes — SELECT * reads everything
  • Why the columnar layout makes this so stark. In a row-oriented warehouse, reading two fields still means reading the rows they live in, so SELECT * costs little extra. In BigQuery each column is stored and compressed separately, so the cost is genuinely proportional to the columns you touch. Naming three columns out of fourteen isn't a micro-optimization — here it's a 7× difference.
  • The nuance that keeps students honest: the WHERE column is read too. That's why the "good" version is three strips, not two. Students who count only the select list will mis-predict the dry-run number and lose trust in the model.
  • Where SELECT * is genuinely fine: inside a view or subquery whose outer query selects only a few fields — the optimizer prunes down to what is actually referenced. So SELECT a, b FROM (SELECT * FROM t) reads two columns. The danger is SELECT * at the outermost level, or a view that a BI tool then does SELECT * against.
  • How to peek at a table for free: the console's Preview tab and bq head read table metadata/storage directly and cost nothing. SELECT * FROM t LIMIT 10 is not free — it fully scans the columns, then throws away all but ten rows. That's the next slide.
  • Reference: Optimize query computation — "avoid SELECT *".
pruning

Filters that prune, filters that don't

The table is partitioned by day and clustered by org — but only if the query's filter lets BigQuery use that.

SQL-- 60 TB: column wrapped in a function
WHERE FORMAT_TIMESTAMP('%Y%m%d', event_ts)
        = '20260720'

-- 290 GB: bare column, constant range
WHERE event_ts >= TIMESTAMP '2026-07-20'
  AND event_ts <  TIMESTAMP '2026-07-21'
  • Pruning happens before execution, from metadata — but only when the filter compares the bare partition column to constants
  • Wrap the column in a function and BigQuery must read every row to evaluate it
  • Same idea for cluster columns: a plain filter on org_id skips blocks
Pruning is a contract with your WHERE clause: bare column, constant on the other side. require_partition_filter=TRUE turns "forgot the date filter" into an error instead of a 60 TB scan.
Speaker notes — Filters that prune, filters that don't
  • Why the function version can't prune, mechanically. Pruning is a metadata decision made before any data is read: BigQuery knows each partition's time range, so it can discard partitions whose range can't satisfy event_ts >= X. Wrap the column in FORMAT_TIMESTAMP and the condition is no longer about event_ts ranges — it's about the output of a function that has to be computed per row. There is nothing in the metadata that can answer it, so everything gets read. Same trap with CAST(event_ts AS DATE) = ..., DATE_TRUNC(event_ts, DAY) = ..., or arithmetic on the column.
  • Kill the myth from the older course material explicitly: "put the partition filter first in the WHERE clause" is not a thing. Predicate order is irrelevant — the optimizer decides evaluation order. Predicate shape is everything. If a student remembers one sentence from this slide, make it that one.
  • What about the validator? The console's byte estimate accounts for partition pruning, so you can see the win before running. It does not predict clustering savings — block-level skipping is decided during execution, so clustered savings only show up in the actual bytes processed afterwards. Students who trust the estimator as an upper bound won't be confused by this.
  • Bonus mechanism worth mentioning once: when you join against a clustered table on its cluster key, BigQuery can build a filter from the other side at run time and skip blocks it now knows can't match. One more reason join keys and cluster keys should agree — a storage-module decision that pays off in this module.
  • Design of partitions and clusters was the previous module; this slide is only the query-side half. Reference: Query partitioned tables.

Speaker notes — Know the bytes before you run
  • The dry run is the single most underused feature in BigQuery. It validates the SQL and returns the byte estimate without executing or being billed. In the console you get it for free as you type — the byte estimate in the corner of the editor. Teach students to look at that number reflexively before pressing Run, especially on a 60 TB table.
  • Why LIMIT feels like it should help and doesn't. LIMIT is applied to the result, after the scan that produced the rows. The scan is what you're billed for. The one partial exception: on a clustered table, a LIMIT can let BigQuery stop early once it has enough rows, so bytes may come out lower — but never rely on it as a cost control.
  • Guardrails, in increasing order of blast radius: maximum_bytes_billed per query (in the console's query settings, the bq flag, or the API), a project-level default for it, and custom per-user or per-project daily quotas for organizations that need a hard ceiling. Failed-because-capped queries cost nothing, which makes the cap cheap insurance.
  • Price anchor — verify the current figure before teaching, pricing changes: on-demand analysis has been on the order of $6–7 per TB scanned in US regions with the first TB per month free. Do the arithmetic live: 2.8 TB per dashboard refresh, every five minutes, is a number that gets people's attention. Under capacity pricing the same discipline buys back slot time instead of dollars.

broadcast join

The join you get for free: broadcast

Monday query, the join: 60 TB of telemetry against 14 MB of orgs. Why does the plan show no shuffle for it?

  • When one side is small, BigQuery copies the whole small table to every slot scanning the big one
  • The big table is joined in place, during its own scan stage: one pass, and 60 TB never crosses the network
  • This is why star schemas with small dimension tables stay fast with no tuning at all
A small-side join is nearly free. Keep dimension tables lean — fewer columns, filtered early — so they stay broadcastable. The size threshold is an internal heuristic, not a knob you set.
Speaker notes — The join you get for free: broadcast
  • The key insight to land: a join is fundamentally about getting matching rows into the same place. There are only two ways to do that — move the small side everywhere, or move both sides to agreed-upon meeting points. Broadcast is the first; hash join (next slide) is the second. Everything students need to reason about join cost follows from that pair.
  • Why copying 14 MB to hundreds of slots is cheap: 14 MB × a few hundred workers is a few gigabytes of network traffic, and it happens once, in parallel, before the real work. Compare to shuffling even the filtered telemetry — hundreds of gigabytes, with all the sorting and bucketing that implies.
  • How to recognize it in a plan: the join appears inside the big table's scan stage rather than as its own stage with two inputs. You'll often see a small preceding stage that gathers the little side (historically shown as a "Coalesce" step). In older plan text this was written JOIN EACH WITH ALL; you don't need the legacy vocabulary, just the shape.
  • BigQuery chooses, not you — and it chooses dynamically. A filtered subquery over a huge table can turn out small enough to broadcast, and BigQuery will do it because it learns the actual size mid-query. This is another reason there's no useful ahead-of-time EXPLAIN.
  • Note the optimizer applies o.plan = 'enterprise' before broadcasting, so what actually ships is a fraction of 14 MB. Filter placement in your SQL doesn't matter much here; the optimizer pushes predicates down. What matters is not making the dimension table needlessly wide.

hash join

When both sides are big: the hash join

New ask: average packet loss by device type. Device lives in participants (2.4 TB). Now both sides are huge.

SQLSELECT p.device,
       AVG(c.packet_loss_pct) AS avg_loss
FROM vc.call_quality AS c
JOIN vc.participants AS p
     USING (meeting_id, user_id)
WHERE c.event_ts >=
      TIMESTAMP '2026-07-20'
GROUP BY p.device;
  • Neither side fits in a slot's memory, so BigQuery shuffles both tables by the join key — equal keys land in the same bucket, one worker joins each bucket
  • The plan may add repartition stages mid-join as it discovers bucket sizes — normal, but a sign of heavy lifting
You can't pick the join algorithm — but you decide how much data arrives at the join. That's the next three slides, and it's where the real savings are.
Speaker notes — When both sides are big: the hash join
  • Walk the literal rows in the diagram. The key (m17, amy) hashes to bucket 1, so both the two telemetry rows for Amy in meeting 17 and her participant row land in bucket 1. That's the entire trick: hashing the join key sends matching rows from both tables to the same worker, which can then join them without talking to anyone else. Once students see that, "why does a join need a shuffle?" answers itself.
  • The cost sentence to say out loud: before a single row is joined, roughly 800 GB has been written into shuffle and read back out. That is where bytes shuffled comes from, and it's the number that turns into spill (slide 8) when the query is bigger.
  • Repartitioning, in one sentence: if BigQuery discovers a bucket is far bigger than expected, it can split it and re-shuffle. Seeing REPARTITION stages in a plan isn't an error; it means the engine had to adapt because the data was lumpier than the initial estimate. If they dominate the plan, look at skew (slide 22).
  • Small free win worth mentioning: INT64 join keys compare and hash more cheaply than STRING keys. On a join of this size that's a few percent for nothing. It's a schema decision, but it shows up in query time — which is why it belongs in both modules.
  • Legacy vocabulary, only if someone has read older material: this was JOIN EACH WITH EACH. Today just read the plan shape: a join stage with two shuffled inputs.

Help the planner: table order and declared keys

Two cheap declarations that improve join plans for every query that follows.

SQLALTER TABLE vc.meetings
  ADD PRIMARY KEY (meeting_id) NOT ENFORCED;

ALTER TABLE vc.participants
  ADD FOREIGN KEY (meeting_id)
  REFERENCES vc.meetings (meeting_id)
  NOT ENFORCED;
  • Habit: write joins largest table first, then smallest, then descending. The optimizer usually reorders anyway — you've just made the good plan obvious
  • PK/FK constraints are metadata only (NOT ENFORCED — nothing is checked). The optimizer uses them to reorder joins and even eliminate them
You guarantee the constraint is true — BigQuery never checks it. Declare a false PK or FK and queries can silently return wrong results.
Speaker notes — Help the planner: table order and declared keys
  • On table order, be honest about how much it matters. Modern BigQuery reorders joins itself, so ordering largest-first is a habit rather than a requirement — it costs nothing and occasionally helps, particularly in complex multi-join queries. Don't let students believe it is the main lever; slides 19–20 are the main lever. The reason to teach it at all is that they will read it in older material and should know how much weight to give it.
  • Why join elimination is such a good deal. The example is not contrived — it's what BI tools do constantly. A modeling layer defines a view that joins the fact table to five dimensions; a given dashboard tile selects two columns from one of them. Without constraints, every tile pays for all five joins. With PK/FK declared, the optimizer can drop the joins that cannot affect the result, because the FK promises each row matches exactly one parent row.
  • Read the warning as a real risk, not a formality. NOT ENFORCED means BigQuery takes your word for it. If meeting_id is not actually unique in meetings, an eliminated join changes row counts — and you get a wrong answer with no error. Only declare keys you can prove; a one-off GROUP BY ... HAVING COUNT(*) > 1 check before declaring is cheap insurance, and worth re-running if a loader ever changes.
  • Limits to be aware of: top-level columns only (no fields inside structs), up to 16 columns in a primary key, and a bounded number of foreign keys per table — check current limits in the docs before designing around them. Primary and foreign keys.

predicate pushdown

Reduce each side before it joins

The device query joins 60 TB of telemetry to 2.4 TB of participants. The join never sees those numbers — and the first reduction happens without you.

  • A join's cost is set by what arrives at it: rows × columns shuffled in from each side (slide 17)
  • You wrote one WHERE, after the join — the optimizer pushes the predicate down into the scan it applies to, so rows are dropped before they travel
  • Columns are pruned the same way: each scan reads only the fields the query references — SELECT * defeats this (slide 12)
  • Verify rather than trust: the scan stage's steps in Execution details should show the filter
Pushdown drops rows; it can't change what a row is. The telemetry has one row per second, the question needs one per participant, and only aggregation gets from one to the other. The optimizer never writes that for you — next slide.
Speaker notes — Reduce each side before it joins
  • Why this slide exists: students who learn "reduce before you join" immediately start hand-writing filtered subqueries on each side of every join "to help." Usually that's a no-op — the optimizer already pushes eligible predicates and the column list below the join, so write the query the readable way. The transferable skill is knowing what pushdown does, and checking that it happened.
  • The concept before the feature: everything the join shuffles costs shuffle bytes (and spill risk, slide 8). So the goal is that each side arrives as small as the answer allows — fewer rows (filters), fewer columns (projection), fewer/coarser rows still (aggregation, next slide). Pushdown automates the first two; nothing automates the third.
  • What pushdown can't do for you: it relocates predicates without changing results, so anything that would change results stays put. The classic case is an outer join: a WHERE on the nullable side of a LEFT JOIN can't move below the join (it would change which rows survive — in fact it quietly turns the outer join into an inner one; ON vs. WHERE placement is a semantics decision there, not a performance one). And it never invents work you didn't write: no filter expresses "one row per participant" — collapsing many rows into one is an aggregation, and that's the next slide.
  • How to verify: open Execution details and read the scan stage's steps — the filter shows up as a step inside S00, and the READ step lists exactly the columns pulled. The same filter, on the partition column, is also what prunes partitions at the storage level (slide 13) — the dry-run estimate confirms that part before you run anything.
  • The 410 GB / 380 GB arrival sizes match the hash-join picture two slides back; they're illustrative but consistent deck-wide: one week of partitions, 4 of 14 columns.

biggest win

Shrink before you join: aggregate first

New ask: total call time by device type. Count per participant, join the small summary, add at the end.

SQLWITH per_participant AS (
  SELECT meeting_id, user_id,
         COUNT(*) AS secs  -- seconds on the call
  FROM vc.call_quality
  WHERE event_ts >= TIMESTAMP '2026-07-20'
  GROUP BY meeting_id, user_id  -- 2.1B → 46M rows
)
SELECT p.device, SUM(secs) AS total_secs
FROM per_participant
JOIN vc.participants AS p
     USING (meeting_id, user_id)
GROUP BY p.device;
  • 46 M summaries reach the join, not 2.1 B samples — big side ~45× smaller, spill gone
  • Counts and sums add up across a join, so SUM(secs) is exact — an AVG doesn't; carry sum + count instead (notes)
The optimizer pushes filters; it will never aggregate for you. Deciding what each side can be reduced to before it joins is this module's biggest lever.
Speaker notes — Shrink before you join: aggregate first
  • If students take one technique home from this module, this is it. Google's join guidance says it directly: "perform aggregation earlier in the query to reduce the amount of data processed" before a JOIN. It's also the most common fix for the high-cardinality-join insight from slide 9. The reframe that makes it click: a join is a meeting, and it's cheaper to send a summary to the meeting than to send everyone who contributed to it.
  • Why the example counts seconds: counts and sums recombine losslessly — the sum of per-participant counts is the device total no matter how the rows were batched. That property makes aggregate-then-join safe as-is for SUM, COUNT, MIN, and MAX (small gotcha: the outer operation on inner counts is SUM, not COUNT). COUNT(DISTINCT) has no such property at all — partial distinct-counts don't recombine, which is why the sketches on slide 25 exist.
  • The AVG variant — teach it right after, because slide 17's ask is an average: averages don't add, so carry the ingredients instead: SUM(packet_loss_pct) and COUNT(*) per participant, join, then divide. Napkin check for the room: amy's samples (2, 4, 3) → (9, 3); bo's single sample (8) → (8, 1); both on laptops. True per-second average: (2+4+3+8)/4 = 4.25. Sum/count: (9+8)/(3+1) = 4.25 — identical. Average-of-averages: (3+8)/2 = 5.5 — wrong, because bo's one second silently gets the same weight as amy's three (sometimes equal-weighting is the question: if so, do it on purpose). This decomposition reappears in the skew fix on slide 22.
  • Honest mechanics, if a sharp student pushes: the pre-aggregation's own GROUP BY also uses shuffle — but scan workers emit partial aggregates (the slide-5 pattern), so what crosses is near the 46 M summaries, not 2.1 B rows. And the total isn't 45× smaller: the participants side still shuffles its 380 GB, so total shuffle roughly halves (790 → 389 GB). The dramatic wall-clock win comes from the 180 GB spill disappearing — the biggest single stage input now fits the memory tier. All figures illustrative but internally consistent (46 M rows × ~200 B ≈ 9 GB).
  • Same principle, other shapes: pre-aggregate both sides when both carry many rows per join key; join on the smallest key set that is still correct; if you only need existence, a semi-join (WHERE EXISTS / IN) moves less than a full join. The docs' cross-join advice is this same idea: "use a GROUP BY clause to pre-aggregate the data."
  • References: Reduce data before using a JOIN; same page, anti-pattern sections (cross joins, self-joins).
anti-pattern

The self-join trap

"Show each org's packet loss this week vs. last week." The instinctive answer joins the table to itself — and doubles every cost.

SQL-- instead of joining the weekly CTE to itself:
SELECT org_id, week, loss,
       loss - LAG(loss) OVER (PARTITION BY org_id
                              ORDER BY week)
         AS wow_change
FROM (
  SELECT org_id,
         DATE_TRUNC(DATE(event_ts), WEEK) AS week,
         AVG(packet_loss_pct)             AS loss
  FROM vc.call_quality
  GROUP BY org_id, week
);
  • A self-join reads and shuffles the table twice, and duplicate keys can multiply rows — wrong answers, not just slow ones
  • Row-to-row relationships are what window functions are for
  • Compare across categories instead? Conditional aggregation: AVG(IF(device='mobile', loss, NULL))
A self-join on a big table is almost always a window function or a conditional aggregation wearing a disguise. It tops Google's own anti-pattern list.
Speaker notes — The self-join trap
  • Lead with correctness, not speed. Students discount performance advice; they don't discount "this returns the wrong number." The self-join's real danger is the fan-out: if the join key isn't unique on both sides, every left row multiplies against every matching right row and any average or count downstream is silently wrong. Slow is recoverable. Wrong-and-shipped is not.
  • The classic teaching case from the Definitive Guide: a self-join over a baby-names dataset to compare year over year reported roughly 982 million babies named Jordan — took 74 seconds and was wildly wrong, because the join multiplied rows. The conditional-aggregation rewrite ran about 30× faster and correct. Worth telling; the absurd number is what students remember.
  • Two rewrites, two situations:
    • Row-to-row within a group (this vs. previous period, running totals, first/last per key) → window functions: LAG, LEAD, SUM() OVER, ROW_NUMBER.
    • Category-vs-category in one row (mobile vs. desktop side by side) → conditional aggregation: AVG(IF(cond, value, NULL)) per category in one pass.
    Both replace a second read of the table with a second look at rows already in memory.
  • Note the naive version has a second, quieter cost: it references the weekly CTE twice, and CTEs are not materialized — so the aggregate may be computed twice as well. Slide 26 makes that general.

Skew: when one key is a whale

The per-org rollup crawls. The plan says compute avg 300 ms, max 9 s. One org — the free tier's shared org_free — is 18% of all telemetry.

SQL-- who are the whales?
SELECT APPROX_TOP_COUNT(org_id, 5)
FROM vc.call_quality
WHERE event_ts >=
      TIMESTAMP '2026-07-20';

-- [{org_free: 378M}, {org_acme: 9M}, ...]
--   one key is 40x the next
  • Shuffle sends each key's data to one worker. A whale key hands one worker a terabyte while its peers finish in seconds
  • Spot it three ways: avg << max on the stage bars, the partition skew insight, or APPROX_TOP_COUNT
  • Fix: exclude whales when the question allows — otherwise aggregate at a finer key first, then re-aggregate
Speaker notes — Skew: when one key is a whale
  • Connect it back to slide 7 explicitly: the avg-300ms/max-9s gap students saw in the "stage in trouble" chart is this picture. That's the payoff for teaching plan-reading first — the symptom already has a name and now it has a cause.
  • Why more capacity cannot help. A stage finishes when its last worker finishes. The whale's worker has a terabyte to chew through, and no amount of extra slots can split one key's data across workers — the shuffle already decided where it goes. This is the clearest example in the module of a problem that looks like a capacity problem and isn't.
  • Where whales come from in real schemas — help students recognize their own: a shared or default tenant (our org_free), a null or empty key that swallows every unmatched row, an "unknown/other" bucket, a single enormous customer, a bot or test account. Nulls are the most common surprise: GROUP BY puts all nulls in one group.
  • The two-step pattern in detail. First aggregate at a finer key that includes something high-cardinality (here org_id, meeting_id) — the whale's data now hashes to many buckets, so many workers share the load. Then aggregate that much smaller result to the key you actually wanted. Crucially, decompose the metric: carry SUM and COUNT through step one and divide in step two, or you get an average of averages (the SUM/COUNT decomposition from slide 20's notes).
  • Joins skew the same way for the same reason — a whale join key floods one bucket. Same diagnosis (avg vs. max), same medicine (reduce first, or handle the whale separately and union the results).
  • APPROX_TOP_COUNT is the cheap detection tool: it's one pass with sketches rather than a full GROUP BY ... ORDER BY COUNT(*) DESC, so you can afford to run it on a huge table. Slide 25 explains how those sketches work.

per-row cost

Cheap rows: functions and filters

A support tool scans meeting titles for a product name — with a regex, through a JavaScript helper someone wrote in 2024.

SQL-- slower: full regex engine, per row
WHERE REGEXP_CONTAINS(title, r'foo')

-- faster: simple substring matcher
WHERE title LIKE '%foo%'
  • Prefer the simplest operator that answers the question — LIKE beats REGEXP_CONTAINS when you don't need regex power
  • Comparisons on INT64, BOOL, DATE are cheaper than on STRING — filter on IDs and dates where you can
  • JavaScript UDFs launch a separate V8 process per worker; SQL UDFs inline into the plan at essentially zero cost
Spend function complexity only where the question requires it. On billions of rows, "slightly more expensive per row" is the whole bill.
Speaker notes — Cheap rows: functions and filters
  • Keep the honest proportion in view. These are single-digit-to-tens-of-percent wins, not the 7× and 40× wins of Sections 2 and 3. Teach them as habits to adopt while writing, not as a rescue plan for a slow query. If someone's query is slow and they reach for LIKE instead of checking bytes processed, they've learned the wrong lesson.
  • Regex vs. LIKE: REGEXP_CONTAINS compiles and runs a regular expression engine per row. LIKE with leading/trailing wildcards is a substring search. If the pattern genuinely needs alternation, anchors, or capture groups, use the regex — correctness first. The waste is using a regex to look for a fixed string.
  • SQL UDFs vs. JavaScript UDFs. A SQL UDF is a macro: the optimizer substitutes the expression into the plan, so it costs exactly what writing the expression inline would cost. Use them freely for readability and reuse. A JavaScript UDF runs in a separate V8 runtime alongside the worker — there's process overhead, data has to cross into and out of the JS runtime, and there are memory limits that can fail large queries outright. They're the right tool when SQL truly can't express the logic; they're a performance trap when someone reached for a familiar language.
  • Correct the older material here. Some course decks state as an absolute rule that BigQuery does not reorder WHERE expressions, and therefore that you must hand-order predicates most-selective-first. Today's optimizer does reorder and push down predicates. Keep the underlying habit (put cheap conditions in your head first, don't wrap columns in functions) but don't teach it as a rule the engine depends on — students who believe it will write brittle SQL and mistrust the plan they see.
  • Do It Now (activity 9, routines): compare a SQL UDF and a JavaScript UDF doing the same job on the same data, and read the slot time for each. It makes the "separate runtime" cost concrete in about five minutes. roitraining.github.io/gcp-demos

approximate

Close enough, far cheaper: approximate aggregation

The Monday query's COUNT(DISTINCT user_id) forces every user ID through the shuffle. The dashboard renders it as "≈12k users" anyway.

SQL-- exact: every distinct ID must meet
COUNT(DISTINCT c.user_id)
  AS affected_users

-- approximate: workers send small sketches
APPROX_COUNT_DISTINCT(c.user_id)
  AS affected_users
  • Exact distinct-counting can't be pre-aggregated — every distinct value has to reach the same place. That's a shuffle of every ID
  • APPROX_COUNT_DISTINCT keeps a fixed-size HyperLogLog sketch per worker; sketches merge, so the shuffle is tiny. Typical error ~1%
  • Only pays on large cardinalities — on small data it can be slower. Measure
Ask the stakeholder: does this number drive a decision at ±1%? Dashboards, trends, capacity planning — yes. Billing and compliance — no. The family also includes APPROX_QUANTILES (that P95) and APPROX_TOP_COUNT.
Speaker notes — Close enough, far cheaper: approximate aggregation
  • Why exact COUNT(DISTINCT) is structurally expensive. Most aggregates decompose: to sum a column, each worker sums its own rows and the partial sums merge. Distinct counting doesn't decompose that way — worker 1 and worker 2 might both have seen bo, and neither can know that without comparing. So every distinct value has to end up in the same place, which means shuffling the values themselves. That's the cost, and no amount of clever SQL removes it.
  • What a sketch is, in one plain paragraph. Instead of keeping the IDs, each worker keeps a small fixed-size summary built by hashing each value and recording statistical fingerprints of what it has seen. The size of that summary doesn't grow with the number of IDs — a million IDs and a billion IDs produce the same-size sketch. Two sketches can be merged into a sketch of the union, and a count estimated from the result. That mergeability is what lets the work be done in parallel with almost nothing crossing the network.
  • Reference numbers worth quoting (Definitive Guide, GitHub dataset): about 3.35 million distinct values — exact 7.1 s, approximate 3.2 s, error about +1.5%. And the counterexample that keeps students honest: 13.7 thousand distinct values — exact 0.9 s, approximate 1.6 s. The sketch machinery has fixed overhead; on small cardinalities it loses. "Measure" is not a throwaway line here.
  • The advanced move worth planting a flag on: HLL_COUNT.INIT and HLL_COUNT.MERGE let you store sketches in a table. Compute one sketch per org per day, and monthly or quarterly unique counts become a merge of 30 or 90 small sketches instead of a rescan of the raw events. It's also a privacy tool — the stored sketch holds no user IDs. This is the pattern behind most large-scale "unique users" reporting.
  • Do It Now (activity 18): have students compute both the percentage of time saved and the percentage error on the 100-billion-row table. Framing it as a two-number trade-off, rather than "approximate is faster," is what makes them able to defend the choice to a stakeholder.

Don't compute it twice: CTEs are not cached

A report defines bad_calls in a WITH clause and references it three times. The plan shows the scan… three times.

SQL-- multi-statement: compute once, reuse cheaply
CREATE TEMP TABLE bad_calls AS
SELECT org_id, meeting_id,
       user_id, packet_loss_pct
FROM vc.call_quality
WHERE event_ts >= TIMESTAMP '2026-07-20'
  AND packet_loss_pct > 5;

SELECT … FROM bad_calls …; -- reads temp table
SELECT … FROM bad_calls …;  -- again, no rescan
  • A CTE is a name for a subquery, not a result — BigQuery may re-evaluate it at every reference. Views and repeated subqueries behave the same way
  • Referenced once? Use CTEs freely, they're for readability
  • Referenced repeatedly and expensive? Materialize it
WITH improves readability, never performance. If a CTE is expensive and used more than once, write it to a temp table.
Speaker notes — Don't compute it twice: CTEs are not cached
  • Name the mental model students arrive with, then correct it. Almost everyone reads WITH x AS (...) as "compute x, then use it." It is closer to "wherever you write x, paste this subquery." Inlining is often the right choice — but when the subquery is a 290 GB scan and it's pasted three times, you pay three times. The plan is the proof: students should look for the same scan appearing repeatedly.
  • Views behave identically, and that matters more in practice: a view over a huge table referenced twice in one query can be scanned twice. This is one reason BI-generated SQL can be surprisingly expensive — and one reason materialized views (slide 29) exist.
  • The fix is a multi-statement query (what used to be called scripting): several statements separated by semicolons, submitted as one job. CREATE TEMP TABLE inside one lives for the duration of the script, costs essentially nothing in storage, is invisible to other users, and disappears on its own. In the plan it appears as an ordinary table read — which is exactly the point. For results that must outlive the session, write to a real destination table instead.
  • The honest counterpoint, worth stating. Inlining sometimes wins: when each consumer applies a different filter, the optimizer can push those filters down into the inlined subquery, so each evaluation reads far less than a full materialization would. That's why the rule is "measure, then decide" and not "always materialize." Run both shapes, read Execution details, keep the cheaper one.
  • Do It Now (activity 3, views and WITH): shows the repeated-scan behavior directly, which is much more convincing than being told.
  • Reference: avoid multiple evaluations of the same CTEs.

result cache

The result cache: free, automatic, fussy

Every dashboard refresh re-submits the Monday query verbatim. The second run costs $0 and returns in about a second — when the cache is allowed to work.

  • Results persist about 24 hours in a temporary table; an exactly identical query is served from it — zero bytes billed
  • Cache misses when: the query text differs at all (whitespace counts) · non-deterministic functions like CURRENT_TIMESTAMP() or RAND() · any referenced table changed · a destination table is set · the table has a streaming buffer
  • That last one is ours: call_quality streams 24/7, so queries touching it effectively never cache. Queries on nightly-loaded orgs and meetings cache all day
$ bq query --nouse_cache   # benchmarking
$ bq query --require_cache # fail unless cached
The cache rewards stable query text over stable tables. Dashboards on streaming tables need the next slide's tool instead.
Speaker notes — The result cache: free, automatic, fussy
  • Lead with the economics: a cache hit is the only optimization in this entire module that costs literally zero bytes and zero slot time. It is also the one most often accidentally disabled. So the practical skill isn't "use the cache" — it's "stop breaking it."
  • How it works, briefly: results are written to a temporary anonymous table and a hash of the exact query text (plus the referenced tables' state) is the key. That's why byte-for-byte identical text matters — adding a comment or reformatting the SQL is a different key and a full re-execution.
  • The ways teams break caching without realizing:
    • CURRENT_TIMESTAMP() or CURRENT_DATE() in the query. Non-deterministic, so no caching — and a dashboard that computes "today" this way never caches. Have the template write a literal date into the SQL instead; then it caches all day and only misses at the date rollover.
    • A BI tool that appends a session ID or reorders the select list per user.
    • Setting a destination table (caching is skipped).
    • A streaming buffer on any referenced table — our case.
  • Measure rather than assume: cache_hit in INFORMATION_SCHEMA.JOBS (slide 10) gives the real hit rate for a dashboard's queries. Teams are routinely surprised.
  • Cross-user caching is available on Enterprise editions: same query, same tables, a teammate already ran it, and your run is free too. Very valuable for shared dashboards; check your edition before promising it.
  • Security nuance from the docs, worth one sentence: if someone's column-level access is revoked, an already-cached result they can still reach may reveal that data for up to 24 hours. Not a reason to avoid caching — a reason to know it exists during an access review.
  • Do It Now (activity 4): run a query, look at the anonymous dataset's temp table, re-run it and observe the cache hit, then disable caching and compare. Ten minutes, and it makes every rule on this slide concrete.

Materialized views: the standing query

The dashboard asks the same shape of question all day. Define the rollup once, and let BigQuery keep it fresh and use it automatically.

SQLCREATE MATERIALIZED VIEW
  vc.daily_org_quality AS
SELECT org_id,
       DATE(event_ts)  AS day,
       AVG(packet_loss_pct)  AS avg_loss,
       APPROX_COUNT_DISTINCT(user_id)
         AS users
FROM vc.call_quality
GROUP BY org_id, day;
  • A materialized view stores its result and refreshes incrementally — newly streamed rows are merged in; the base table isn't rescanned
  • Smart tuning: queries against the base table are rewritten to read the view when it can answer them. The dashboard changes nothing
  • Unlike a temp table (slide 26): always fresh, shared by everyone, maintained by the service
The cache answers identical text. A materialized view answers a family of queries — filters and coarser groupings over the same aggregation — and it works on streaming tables, where the cache can't.
Speaker notes — Materialized views: the standing query
  • Draw the contrast with the previous two slides deliberately — it's the clearest way to make each one's role stick:
    • Result cache: same text, same tables, free, 24 h, dies on any change. Zero effort, zero flexibility.
    • Temp table (slide 26): you decide when to compute; stale the moment you finish; scoped to your script.
    • Materialized view: the service keeps it current as data arrives, everyone benefits, and queries don't even have to know it exists.
  • Why "incremental" is the important word. A materialized view isn't re-running the aggregation over 60 TB on a schedule. When new rows land, only the new rows are folded into the stored result. That's what makes it viable on a continuously streamed table — and it's also why the SQL is restricted: BigQuery has to be able to combine partial results.
  • Smart tuning is the feature people underestimate. The dashboard keeps querying call_quality. BigQuery notices a materialized view can satisfy the query and silently rewrites it. So you can add a view to an existing system with no code change anywhere — and if you later drop the view, everything still works, just slower. Cheap to try, cheap to reverse.
  • Constraints to state so nobody hits a wall: incremental views support aggregations like SUM, COUNT, AVG, MIN/MAX and APPROX_COUNT_DISTINCT over a single table, with no ORDER BY and no window functions. Broader SQL (joins, more exotic logic) needs a non-incremental view with a max_staleness setting, which trades freshness for capability. Mention it exists; don't teach the details here.
  • It isn't free: the view occupies storage and refreshes consume compute. Both are small next to a 2.8 TB scan every five minutes — but meter it rather than assuming, especially if someone creates a dozen views speculatively.
  • Do It Now (activities 16 then 17): activity 16 builds the manual version — a derived table you refresh yourself — and lets students feel the staleness problem. Activity 17 replaces it with a materialized view. Running them in that order is the best in-class demo in this section, because the pain comes before the cure.

Speaker notes — Speed you don't have to ask for
  • Why this slide is here at all. Students should know the platform is improving under them, both so they don't waste effort hand-optimizing what the engine will handle, and so they aren't confused when the same query gets faster with no code change. It also reinforces the module's opening rule: don't optimize prematurely.
  • History-based optimizations, in plain terms: BigQuery records what actually happened when a query ran — real row counts, real data sizes — and uses that history to plan the next run of a similar query more aggressively than it could plan a first run. Typical examples are reducing one side of a join before shuffling (semi-join reduction), reordering joins, and adjusting parallelism. Applied conservatively: only where the predicted benefit is high, and automatically reverted if a run regresses.
  • Check, don't assume. Availability and defaults have shifted over time, and it's configurable at the project/organization level (a query-optimizer option that turns adaptive behavior on). Verify your project's state before telling students "you already have this" — and use the optimization_details query on the slide, which reports what was actually applied rather than what should have been.
  • Advanced runtime and short query mode: the former is enhanced vectorized execution — more work done per CPU instruction on encoded data. The latter removes the job-creation round trip for small queries, which matters enormously for interactive dashboards firing many tiny queries. Both have been in Preview at various points; check current status before promising them, and don't build a lesson on the internals — the student decision here is simply "know it exists, verify it's on."
  • Gemini Cloud Assist can look at a slow job and propose rewrites. Worth naming as tooling that exists. Frame it honestly: it proposes, you evaluate — and evaluating is exactly what this module has been teaching. It has been Preview; verify before demoing.

contention

Wait time: starved, not slow

Friday 6 p.m.: the month-end billing ETL kicks off. The Monday query — untouched — takes 4 minutes. Its plan shows wait avg 140 s.

  • Slots are a shared pool: on-demand projects get a soft target of about 2,000 slots, divided fairly among whatever is running in that project
  • Run two heavy queries at once and each gets roughly half. Queries beyond what the pool supports queue — they wait, they don't fail
  • The signature: slot time and bytes are unchanged from good runs. Only wait and elapsed grew
Before optimizing SQL, check when it ran and who else was running. INFORMATION_SCHEMA.JOBS_TIMELINE shows slot usage second by second — contention has a timestamp.
Speaker notes — Wait time: starved, not slow
  • This slide exists to prevent wasted work. The most common failure in query tuning is optimizing a query that was never the problem. The tell is precise and easy to teach: compare a slow run to a fast run of the same query. If bytes processed and slot time consumed are the same and only elapsed and wait differ, stop editing SQL and go look at the calendar.
  • How fair scheduling actually feels. BigQuery divides available slots among running queries in the project, adjusting continuously. So the same query genuinely takes longer when the neighbourhood is busy — not because it was deprioritized, but because it's getting a smaller share. Preemption is safe here precisely because work units are small and idempotent: a slot can be taken away mid-flight and the unit re-run elsewhere, which is what makes second-by-second rebalancing possible.
  • Queues, and what changed. Older material (and older certification questions) describe a hard concurrency limit — roughly 50 interactive queries, then errors. That world is gone: excess queries now queue, with configurable limits and timeouts, and run when capacity frees up. So the modern symptom of over-subscription is latency, not failure. If someone reports "my query never started," look at the queue before looking at the SQL. Query queues.
  • Tools for the diagnosis: the slot-contention performance insight from slide 9 is this exact analysis, automated. INFORMATION_SCHEMA.JOBS_TIMELINE gives per-second slot consumption so you can see the ETL's ramp and your query's starvation on the same axis. The Admin resource charts are the click-path version.
  • Cheapest fixes first, before anyone buys anything: move the ETL, stagger the dashboard refresh, or reduce the ETL's own footprint using Sections 2–4. Structural separation (next slide) is for when scheduling isn't enough.
reservations

Buying and fencing capacity

Fix the Friday fight structurally: give the ETL and the dashboards their own lanes.

  • Two ways to pay: on-demand (per TB scanned, shared slot pool) or capacity — BigQuery editions, where you buy slots billed per slot-hour
  • A reservation is a fenced slot pool; assign projects or folders to it, and dashboards can't be starved by ETL again
  • Autoscaling: set a baseline (which can be 0) and a maximum. The reservation grows for spikes and you pay only for the scaled-up time
Choose by arithmetic, not ideology: steady heavy usage favours editions, spiky or light usage favours on-demand. INFORMATION_SCHEMA.JOBS has the slot-ms and bytes to compute both bills from your real history.
Speaker notes — Buying and fencing capacity
  • The mental model in one sentence: a reservation is a fence around a quantity of slots, and an assignment says which projects run inside that fence. Everything else — commitments, autoscaling, editions — is about how you pay for what's inside the fence.
  • Why autoscaling changed the calculus. Under the old commitment model you sized for peak and paid for peak all month. Now you set a baseline and a maximum: the reservation grows when demand arrives and you pay for the scaled-up capacity only while it's up. A baseline of zero with a generous maximum is a genuinely reasonable configuration for bursty batch work — which is exactly our ETL.
  • Fencing doesn't have to mean waste: by default, idle slots in one reservation can be shared with your other reservations, so the dashboard pool's quiet hours aren't thrown away. Worth saying, because "reserve separately" sounds expensive and usually isn't as expensive as it sounds.
  • Editions tiers gate features, not just capacity — things like cross-user caching (slide 28) and some BI Engine and security capabilities differ by tier. Point students at the pricing page rather than memorizing a matrix that changes.
  • Make the choice quantitative. On-demand bills bytes scanned; capacity bills slot-hours. Both figures are already in INFORMATION_SCHEMA.JOBS for your real workload, so this is an arithmetic exercise, not a philosophical one. The slot estimator and admin resource charts help size baselines and maximums from historical demand.
  • Resolving the source course's quiz scenario (ML jobs starving analyst dashboards) with current primitives: separate reservations for the two workloads, autoscaling instead of a fixed commitment, and query queues absorbing bursts. Worth walking through if anyone has seen the old flat-rate answer.
