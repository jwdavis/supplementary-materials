Where query cost comes from

Cymbal Meet’s tables are already partitioned, clustered, and served by a materialized view where it pays. What a query costs now depends on its SQL.

On-demand pricing bills bytes. You pay $6.25 per TiB billed; the first 1 TiB per month is free.

Capacity pricing bills slots. You pay for slots provisioned, by the slot-hour, whether queries use them or not. Less slot time per query means the same slots serve more queries.

Slot time is the work. It is the sum of every slot’s busy time, and it drives elapsed time and contention on both models.

The method for this deck: measure where a query spends, change the part that is largest, then measure again.

Review: how BigQuery runs a query

An analyst owns a weekly report: poor-audio share by plan and device over last week. Here is the report’s plan, in the terms Execution details uses.

SELECT o.plan, q.device_type,
       COUNTIF(q.audio_mos < 3.5) / COUNT(*) AS poor_share
FROM telemetry.qos_events AS q
JOIN crm.orgs AS o USING (org_id)
WHERE q.event_time >= TIMESTAMP '2026-07-20'
  AND q.event_time <  TIMESTAMP '2026-07-27'

Review: the plan is a set of stages; each stage runs as work units on slots; stages pass rows through shuffle.

Deeper: the plan is dynamic. BigQuery can add or resize stages while the query runs, so you read the plan of a finished run, not an EXPLAIN beforehand.

Bytes shuffled and bytes spilled

The page 6 report read 1.1 TB and shuffled a few MB. A row-for-row join over the same week of telemetry can shuffle far more, and spill to disk. The difference is what each stage wrote.

Review: shuffle is an in-memory tier between stages; when a stage writes more than fits, the excess goes to disk and is read back: bytes spilled.

Deeper: only stage output goes to shuffle. The first stage reads from storage, so bytes read and bytes shuffled are independent.

Any bytes spilled means one stage wrote more than shuffle memory held. Find that stage in the plan and shrink its output. A rerun usually spills again; spill is not guaranteed to repeat.

Filters that prune partitions

A reporting template converts “yesterday” to epoch seconds before filtering. Its dry run reads every partition to answer a question about one day.

730 TB: no partition is skipped

SELECT * FROM telemetry.qos_events
WHERE UNIX_SECONDS(event_time) BETWEEN 1784505600 AND 1784591999;

2 TB: one partition

SELECT * FROM telemetry.qos_events
WHERE event_time >= TIMESTAMP '2026-07-20'
  AND event_time <  TIMESTAMP '2026-07-21';

Review: BigQuery skips partitions before it reads any data, using each partition’s date range. The filter must be one it can evaluate against that range.

Prunes: the bare column compared to constants, or wrapped in a supported function with constant arguments: DATE(event_time) = '2026-07-20', CAST(event_time AS DATE), DATE_TRUNC, TIMESTAMP_TRUNC, FORMAT_TIMESTAMP('%Y%m%d', …).

Doesn’t prune: unsupported functions or arithmetic on the column, such as UNIX_SECONDS(event_time), EXTRACT(MONTH FROM event_time), FORMAT_TIMESTAMP('%d/%m/%Y', …). Move the conversion to the constant side.

Deeper: a plain filter on the cluster column org_id skips blocks inside each partition. The order of conditions in WHERE doesn’t matter; their form does.

Guardrail: require_partition_filter = TRUE turns an unprunable filter into an error instead of a 730 TB scan.

Speaker notes — Filters that prune partitions
  • Tested on pageviews_2025 (day-partitioned, dry runs, 2026-09-30): DATE(), CAST AS DATE, TIMESTAMP_TRUNC, FORMAT_TIMESTAMP('%Y%m%d') and ('%Y-%m-%d') all prune to the bare-range bytes; UNIX_SECONDS, EXTRACT(MONTH…), FORMAT_TIMESTAMP('%d/%m/%Y') error with “no filter can be used for partition elimination” under require_partition_filter. DATE_TRUNC(order_date, MONTH) also prunes (isolate the partition column).
  • Older material listed FORMAT_TIMESTAMP('%Y%m%d'), CAST AS DATE, DATE_TRUNC as filters that break pruning; all three prune. Storage’s “what breaks pruning” page agrees with this list.
  • Epoch literals: 1784505600 = 2026-07-20 00:00 UTC; 1784592000 = 2026-07-21. Fix: event_time >= TIMESTAMP '2026-07-20', or TIMESTAMP_SECONDS(1784505600) as the constant (confirm with a dry run). Cost: one year of partitions (the table has no expiration) = 730 TB = 663.9 TiB × $6.25 ≈ $4,150; Acme 1% of 2 TB = 20 GB, an upper bound because the table is clustered.
  • Predicate order doesn’t matter (clustered tables). Run-time block skipping on a join to a cluster key is unverified; leave it out.

Broadcast join: the small table goes to every slot

A customer success analyst asks for poor-audio share by plan for yesterday. The query joins 5B telemetry rows to 40,000 orgs, and the plan shows almost no shuffle for the join.

Review: when one side is small, BigQuery copies all of it to every slot scanning the large side, and each slot joins its own rows locally.

Deeper, in the plan: the small side has its own input stage; the large table has none. Its scan runs inside the join stage, and the JOIN step reads EACH WITH ALL.

Deeper: keep dimension tables narrow and filtered so they stay small enough to copy. The size cutoff is internal; you can’t set it.

Aggregate before you join

The page 26 question is per network type, but the join receives 5B samples. Each session’s 200 samples can become one row before the join.

WITH per_session AS (
  SELECT meeting_id, participant_id,
         COUNT(*) AS samples                 -- 200 per session on average
  FROM telemetry.qos_events
  WHERE DATE(event_time) = '2026-07-20'
  GROUP BY meeting_id, participant_id       -- 5B rows → 24M
)
SELECT p.network_type, SUM(s.samples) AS samples
FROM per_session AS s
JOIN telemetry.participants AS p USING (meeting_id, participant_id)
WHERE DATE(p.join_time) = '2026-07-20'
GROUP BY p.network_type;

Aggregate each side to the grain of the question before the join. 24M session rows reach the join instead of 5B samples. illustrative

SUM, COUNT, MIN, and MAX give the same totals whether rows are combined before or after the join; the outer step sums the inner counts.

The optimizer doesn’t change your query’s grain for you; only you know the question is per network type.

The rewrite is valid only when the result needs no per-sample column.

Declared keys let the optimizer drop a join

Cymbal Meet’s BI layer defines a view that joins participants to meetings. A dashboard tile selects only participant columns, yet every query also reads meetings.

ALTER TABLE telemetry.meetings
  ADD PRIMARY KEY (meeting_id) NOT ENFORCED;
ALTER TABLE telemetry.participants
  ADD FOREIGN KEY (meeting_id)
  REFERENCES telemetry.meetings (meeting_id) NOT ENFORCED;

Primary and foreign keys in BigQuery are metadata only. NOT ENFORCED is required; BigQuery never checks them.

With them declared, the optimizer can drop a join that can’t change the result: every row matches exactly one parent, and no parent column is selected.

A false key gives wrong results with no error. Check uniqueness and orphans before declaring, and again after loads change the data.

Writing joins largest table first, then smallest, then by decreasing size is docs guidance; the optimizer usually reorders anyway.

Replace self-joins with window functions

An engineer wants each sample’s change in audio quality from the same participant’s previous sample. The first draft joins qos_events to itself on participant_id.

Self-join: ~19,900 pairs per session

SELECT a.participant_id, a.event_time, a.audio_mos - b.audio_mos AS change
FROM telemetry.qos_events a
JOIN telemetry.qos_events b
  ON a.participant_id = b.participant_id AND b.event_time < a.event_time
WHERE DATE(a.event_time) = '2026-07-20' AND DATE(b.event_time) = '2026-07-20'
-- still needs "keep only the latest b per a"

Window function: one pass

SELECT participant_id, event_time,
       audio_mos - LAG(audio_mos) OVER (
         PARTITION BY participant_id ORDER BY event_time) AS change
FROM telemetry.qos_events
WHERE DATE(event_time) = '2026-07-20';

A self-join matches every row to every row with the same key, so a key with n rows emits up to n × n rows.

A window function computes over rows already grouped by PARTITION BY and ordered by ORDER BY; LAG reads the previous row in that order.

LAG returns the previous existing row. If a sample is missing, it compares across the gap.

Example

Actor: the engineer.

Input: 24M sessions, ~200 samples each.

Mechanism: the self-join pairs each sample with every earlier sample of its session: ~200 × 199 / 2 ≈ 19,900 pairs per session.

Result: ~480B joined rows vs 5B rows through the window. illustrative

Takeaway: When a row needs a value from a neighboring row, use a window function instead of joining the table to itself.
Sources: Avoid self-joins (verified 2026-09-30).
Speaker notes — Replace self-joins with window functions
  • Docs anti-pattern: a self-join “potentially squares the number of output rows”; the docs suggest window functions.
  • 24M × 19,900 ≈ 478B. PARTITION BY participant_id has 24M small partitions, so no skew; page 36 shows what happens when the partition key has a hot value.
  • A self-join on an aggregate with unique keys (org, week) can’t fan out, and the optimizer can read a self-joined CTE once (tested 2026-09-30). The fan-out risk is at raw grain.

Approximate: each slot builds a HyperLogLog++ sketch, a bounded-size summary of the values it saw; sketches merge without the original IDs.

Typical error is about 1%. The family includes APPROX_QUANTILES, APPROX_TOP_COUNT, APPROX_TOP_SUM.

The gain shows at high cardinality; on small data, measure.

Actor: the product analyst.

Input: ~24M participant IDs over 5 devices.

Mechanism: exact shuffles the distinct pairs; approximate shuffles one sketch per slot per device.

Result: measured on 172M Wikipedia rows: exact 194 slot-s and 2.78 GB shuffled; approximate 37 slot-s and 15.7 MB; error within 0.6%. illustrative

Takeaway: When a count drives a trend rather than a bill, use APPROX_COUNT_DISTINCT.

A CTE can run once per reference

A daily quality report defines poor in a WITH clause and reads it three times: by org, by region, by device. Execution details shows three reads of qos_events.

WITH poor AS (
  SELECT org_id, region, device_type
  FROM telemetry.qos_events
  WHERE DATE(event_time) = '2026-07-20' AND audio_mos < 3.5
)
SELECT 'org', … FROM poor GROUP BY org_id
UNION ALL SELECT 'region', … FROM poor GROUP BY region
UNION ALL SELECT 'device', … FROM poor GROUP BY device_type;

A CTE is a named subquery, not a stored result. BigQuery may evaluate it at every reference; views and repeated subqueries behave the same.

On-demand bytes count each column once per query: three references bill 200 GB, the same as one. illustrative The repeats cost slot time.

To compute it once, write it to a temp table in a multi-statement query. The temp table’s own write and reads add bytes; it’s kept up to 24 h and its storage is billed.

Measure both shapes in Execution details and keep the cheaper one; the optimizer sometimes evaluates a CTE once.

Example

Actor: the report owner.

Input: poor over one day: 5 columns × 8 B × 5B rows = 200 GB read.

Mechanism: three READ stages in the plan; bytes billed counted once.

Result: 200 GB billed either way; slot time for the scan paid three times. illustrative A temp table of the 50M–250M poor rows (1–6 GB) is read three times instead. illustrative

Takeaway: A CTE referenced several times can be computed several times; if it’s expensive, measure a temp table against it.
Sources: Avoid multiple evaluations of the same CTEs; Multi-statement queries (verified 2026-09-30).
Speaker notes — A CTE can run once per reference
  • Test (2026-09-30): a CTE read 3 times had 3 READ stages and billed 1,485,707,586 bytes, the same as one read; a self-joined CTE had one READ; the temp-table version billed 1,541 MB and used 14.0 slot-s vs 5.5 for the CTE. On that cheap CTE, the temp table lost.

  • 200 GB = org_id, region, device_type, event_time, audio_mos × 8 B × 5B. Poor rows: 1–5% of 5B = 50M–250M; × 24 B (3 columns) = 1.2–6 GB.

Recap: compute less

Prefer LIKE over a regex for fixed strings, and SQL over JavaScript UDFs.

Filter and join on INT64, BOOL, and DATE where you can.

Use APPROX_COUNT_DISTINCT when ±1% is acceptable, and measure.

Check the plan for repeated reads of a CTE; measure a temp table against it.

When the result cache hits and misses

Finance’s “meetings per day last week” query runs from a shared notebook dozens of times a day against telemetry.meetings, which loads hourly. Some runs cost 0 bytes; some pay in full.

Review: results are kept about 24 h; an identical query on unchanged tables is served from them at 0 bytes billed.

Misses: any text difference, including whitespace; non-deterministic functions such as CURRENT_DATE(); a referenced table changed; a destination table set; a table with a streaming buffer.

Deeper: qos_events streams continuously, so queries on it never hit the cache.

Deeper: the cache is per user per project; Enterprise editions can share it across users.

Benchmark with --nouse_cache; --require_cache fails unless cached. Measure the real hit rate with cache_hit in INFORMATION_SCHEMA.JOBS.

Materialized views and smart tuning

The ops dashboard reads telemetry.mv_daily_quality, the materialized view built in Storage Optimization. An analyst asks whether her own queries on qos_events will read the view too.

SQL: the view from Storage Optimization, for reference

CREATE MATERIALIZED VIEW telemetry.mv_daily_quality
PARTITION BY DATE(day) CLUSTER BY org_id AS
SELECT TIMESTAMP_TRUNC(event_time, DAY) AS day, org_id, device_type,
       COUNTIF(audio_mos < 3.5) AS poor, COUNT(*) AS total
FROM telemetry.qos_events
GROUP BY day, org_id, device_type;

Review: the view stores its result and refreshes incrementally from appended rows; a read combines stored rows with recent changes.

Deeper, smart tuning: BigQuery rewrites a query on the base table to read the view only when it can match the query to the view: same base tables, filters written as the view’s columns, aggregates the view can combine.

Updates or deletes on the base table force a full refresh. Incremental views support INNER JOIN; LEFT OUTER JOIN and UNION ALL are Preview.

Standard edition can query existing views but can’t create them or use smart tuning.

High wait time means no free slots

A weekly report ran slower on Friday at 18:00, during the month-end billing ETL, than it did on Monday. The SQL did not change.

On-demand projects share up to about 2,000 slots, divided fairly among running queries. Two heavy queries each get roughly half.

Queries beyond what the slots can run wait in a queue, up to 1,000 interactive queries per project per region; queue timeouts apply.

The signature: bytes processed and slot time match the good run; wait time and elapsed time grew.

Check when it ran and what else was running: INFORMATION_SCHEMA.JOBS_TIMELINE shows slot use per second, and the slot contention insight flags it.
