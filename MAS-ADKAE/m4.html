What is Agent Runtime?

A managed runtime for agents in production: deploy, run, and scale agentic applications without provisioning servers or building your own API layer.

Part of Google Cloud Agent Platform (formerly Vertex AI Agent Engine) — the umbrella that also holds the console tooling, evaluation, and managed agents.

Fully managed infrastructure: autoscaling, authenticated endpoints, IAM integration, and VPC Service Controls support.

Framework-agnostic: ADK is the first-party path, but LangGraph, LangChain, CrewAI, and custom Python agents deploy to the same runtime.

Three names, one service — teach this explicitly. The docs and console say Agent Runtime; the CLI command is still adk deploy agent_engine; and the underlying resources are still named projects/*/locations/*/reasoningEngines/*. Students will meet all three within ten minutes of the lab.

The deployable unit is the agent directory — the same root_agent convention used by adk web and adk run.

The agent directory carries its own requirements.txt: that file defines what the runtime installs on the server side.

The .env travels with the agent, so the deployed copy knows its project, location, and model.

Watch the [adk] extra. It declares google-adk>=1.0,<2.0: a fresh install resolves the newest 1.x (1.36.1 as of July 2026) and floats as 1.x patches land. Pin google-adk explicitly for reproducible deploys — and note that a 2.x deployment can never be reached by bumping aiplatform.

Deploy: one command

adk deploy agent_engine transcript_summarization_agent \ --display_name "Transcript Summarizer" \ --region us-central1 \ --staging_bucket gs://PROJECT_ID-bucket # ~10 minutes later, from the command output: # AgentEngine created. Resource name: # projects/430282503153/locations/us-central1/ # reasoningEngines/2902138951282196480 # To use this AgentEngine in another session: agent_engine = vertexai.agent_engines.get( 'projects/.../locations/us-central1/reasoningEngines/NNNN')

Packages the agent: source, its requirements.txt, and extra dependencies are bundled locally.

Stages the bundle in the Cloud Storage bucket; the service builds containers and spins up HTTP servers.

Creates a reasoningEngines resource — the handle for querying, updating, and deleting.

--project and --region can load from the agent's .env when present.

Deploy options beyond the basics

OPTION

--api_key — deploy with just an API key, no GCP project, against the Gemini API backend. The fastest path from prototype to hosted endpoint.

OPTION

--agent_engine_id — update-in-place: redeploy onto an existing instance instead of creating a new resource. This is how iteration works in practice; the lab's quiz already asks about it.

2.x

--trigger_sources pubsub,eventarc — exposes /trigger/* endpoints so Pub/Sub messages or Eventarc events invoke the agent. Event-driven and batch invocation, not just request/response.

OPTION

--adk_version — pin which ADK version the managed runtime runs, independent of your local install.

DEPRECATED

--adk_app, --adk_app_object, --absolutize_imports — the AdkApp wrapper mental model is retired (2.2). Your agent or App deploys directly; there is no wrapper class to explain anymore.

Sessions in production

Locally, ADK defaults to InMemorySessionService: state vanishes when the process exits. Fine for development, wrong for production.

Deployed apps automatically use VertexAiSessionService: persistent, managed, multi-turn state with zero configuration — the same agent code gains durable sessions just by being deployed.

Session TTL / expiration arrived in 2.4 — expire stale sessions instead of accumulating them forever. 2.x

Clients create and reference sessions explicitly: create_session(user_id=...), then pass the session ID with each query — next slide.

Upgrade awareness: sessions written by ADK 2.0 are readable by 1.28 and later only. For database-backed session stores, adk migrate session upgrades stored data — plan for it when moving a production deployment across the 2.0 line.

Query the deployed agent (the lab's query_agent_engine.py)

import vertexai from vertexai import agent_engines vertexai.init(project=project_id, location="us-central1", staging_bucket=f"gs://{project_id}-bucket") # Find the deployed app by display name ae_apps = agent_engines.list( filter=f'display_name="Transcript Summarizer"') remote_app = next(ae_apps) # Sessions are created on the managed service remote_session = remote_app.create_session(user_id="u_456") # Stream the response as a series of dict events for event in remote_app.stream_query( user_id="u_456", session_id=remote_session["id"], message=transcript_to_summarize): for part in event.get("content", {}).get("parts", []): if part.get("text"): print("[remote response]", part["text"])

Discovery by display name: agent_engines.list(filter=...) finds the app without hard-coding the resource name.

Remote sessions: create_session runs on the managed session service, not in your process.

Streaming events: stream_query yields plain dicts — dig out content.parts[].text for the response.

Same agent, new transport: nothing in agent.py changed to go remote.

IAM: who is the deployed agent?

By default, the deployed agent runs as a Google-managed service agent: the AI Platform Reasoning Engine Service Agent. This is what the lab uses.

Before the agent can call models, grant that service agent the Agent Platform User role — the lab does this in the IAM console page. (Service agents are hidden by default: check Include Google-provided role grants.)

The identity is configurable: set service_account in the agent config (.agent_engine_config.json or --agent_engine_config_file) to run as a custom service account you own. The deployer needs iam.serviceAccounts.actAs on it.

Why you'd configure it: the default service agent is shared by every agent engine in the project — granting it BigQuery access grants it to all of them. A per-agent custom service account is the least-privilege pattern for tools that reach other services.

# Default identity (the lab): service-PROJECT_NUMBER@ gcp-sa-aiplatform-re .iam.gserviceaccount.com # Role to grant (from the lab): Agent Platform User # Custom identity (production): # .agent_engine_config.json {"service_account": "my-agent@PROJECT.iam .gserviceaccount.com"}
A deploy that succeeds but returns permission errors on the first query is almost always a missing grant — on whichever identity the agent runs as.

Manage and clean up from the SDK

# agent_engine_utils.py — the lab's helper (exposed via fire) from vertexai import agent_engines def list(): for agent in agent_engines.list(): print(agent.display_name) print(agent.resource_name + "\n") def delete(resource_name): agent_engines.delete(resource_name, force=True) # Usage in the lab: $ python3 agent_engine_utils.py delete \ projects/.../locations/us-central1/reasoningEngines/NNNN

Deletion takes the full resource name — copy it from Deployment details or from list().

force=True deletes even with child resources (sessions) attached.

Deployed agents bill while they exist — clean up is part of the workflow, not an afterthought.

Beyond self-managed deploys (1 of 2): ManagedAgent NEW IN 2.4 PRE-GA PREVIEW

# .env — these lines SELECT the Agent Platform (GEAP) backend; # without them, ManagedAgent uses the Gemini API (GEMINI_API_KEY) GOOGLE_GENAI_USE_ENTERPRISE=TRUE GOOGLE_CLOUD_PROJECT=my-project GOOGLE_CLOUD_LOCATION=global # Managed Agents API is global-only # agent.py — a local PROXY to Google's hosted agent from google.adk.agents import ManagedAgent from google.adk.tools import google_search managed_search = ManagedAgent( name="managed_search", description="Answers questions needing fresh web data.", agent_id="antigravity-preview-05-2026", # the only agent environment={"type": "remote"}, # on Agent Platform tools=[google_search], # per-interaction override )

Scenario: your agent needs web grounding and server-side code execution — capabilities that need managed sandboxes. ManagedAgent is a local proxy to an agent running entirely on Google's servers.

Backend is chosen by environment — this example is Agent Platform (Cloud credentials, global only). Omit those lines and set GEMINI_API_KEY for the Gemini API backend, which offers additional first-party agents (e.g., Deep Research).

You consume Google's agent; you never deploy anything. On Agent Platform, antigravity is the agent — the only supported base. agents.create can layer a named configuration over it (your system_instruction, a tool subset, sandbox settings), referenced as agents/ID — but it's still antigravity underneath. No model choice, no code of yours.

Per-interaction override = tools/environment are sent with each request and apply to that request only; the hosted configuration is unchanged. No client-side Python or MCP tools — though MCP servers and skills can be configured into the server-side sandbox at creation.

Compose and state: wrap in AgentTool (coordinator chooses) or use as a Workflow node (mode="single_turn"). Its conversation and sandbox persist server-side; your session stores only previous_interaction_id + environment_id.

Beyond self-managed deploys (2 of 2): agents-cli 2.x

# One-time: add deployment scaffolding to your project agents-cli scaffold enhance --deployment-target agent_engine # generates Terraform IaC, CI/CD pipelines, deploy artifacts # Connect to the target project gcloud auth application-default login gcloud config set project my-prod-project # Deploy — builds a container, pushes it, deploys to # the target configured in pyproject.toml agents-cli deploy # Optional: terraform-apply the full stack — the agent app itself, # service account + IAM, logs bucket, BigQuery telemetry sinks agents-cli infra single-project

Scenario: the lab's summarizer graduates to production. Now you need dev/staging/prod environments that match, infrastructure someone can review, and a deploy that runs on every merge — not a hand-typed adk deploy from a laptop.

What it generates: Terraform for the Google Cloud resources, CI/CD pipeline config, and deployment artifacts added to your existing ADK project (it backs the project up first). Review the generated config against your org's standards before production.

Targets: the same three as adk deploy — Agent Runtime, Cloud Run, or GKE — read from pyproject.toml.

Roles: Agent Platform User suffices to deploy; the full Terraform + CI/CD setup needs Owner.

Where this module's flow fits: adk deploy agent_engine remains the interactive and teaching path; agents-cli is what production teams graduate to, and ManagedAgent is for consuming Google-hosted agents rather than deploying your own.
