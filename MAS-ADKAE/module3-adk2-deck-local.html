Why build multi-agent systems?

Specialization: each agent gets a focused instruction, its own model choice, and only the tools it needs — smaller prompts, better behavior.

Modularity and reuse: a well-described specialist (a researcher, a critic, a search agent) can be dropped into many systems.

Control: deterministic pipelines where order matters; LLM-driven routing where flexibility matters. ADK lets you mix both in one tree.

Scale: independent sub-tasks run in parallel; iterative work runs in loops with explicit exit conditions.

LLM-driven transfer: who can hand off to whom

An agent can transfer the conversation to a sub-agent, back to its parent, or to a peer (an agent sharing the same parent).

Transfers are decided by the LLM based on each agent's description — write descriptions for the router, not for humans.

Disable peer handoffs per agent with disallow_transfer_to_peers=True. Why: it forces a hub-and-spoke shape — specialists must return through the coordinator, which keeps routing decisions in one well-instructed place, prevents two similar specialists from ping-ponging the conversation between themselves, and stops a wrong-but-plausible peer (say, two different lookup agents) from being picked directly.

A transfer is a handoff, not a call: the target becomes the active agent and owns subsequent user turns until something transfers control again. There is no automatic return.

That last point is the classic multi-agent bug: a sub-agent finishes its job but nobody told it (in its instruction) to transfer back. ADK 2.x adds a structural fix — next slide.

Passing information (1 of 3): state via output_key

# The writer: its final response is saved automatically screenwriter = Agent( name="screenwriter", instruction="Write a plot outline for: { PROMPT? }", output_key="PLOT_OUTLINE", ) # The reader: templating pulls the value from state critic = Agent( name="critic", instruction="""Give critical feedback on this plot outline: { PLOT_OUTLINE? }""", )

Zero code: when the screenwriter's turn ends, its entire final response text is written to state["PLOT_OUTLINE"] automatically.

Any later agent reads it with { PLOT_OUTLINE? }, resolved from session state at request time. The ? tolerates a key that doesn't exist yet.

All-or-nothing: it always saves the whole response. When an agent should save selectively or accumulate across turns, use a tool — next slide.

Works in 1.x and 2.x alike; if the agent has an output_schema, the validated object is what gets saved.

Passing information (2 of 3): state via a tool and ToolContext

# The researcher agent carries the tool… researcher = Agent( name="researcher", instruction="Research the PROMPT. Use 'append_to_state' to save notes to the 'research' field.", tools=[append_to_state], ) # …and the MODEL calls it during the researcher's turn def append_to_state(tool_context: ToolContext, field: str, response: str) -> dict[str, str]: existing = tool_context.state.get(field, []) tool_context.state[field] = existing + [response] return {"status": "success"} # A later agent reads it via instruction templating screenwriter = Agent(..., instruction=""" Write an outline using this research. RESEARCH: { research? } """)
1
The LLM decides to call append_to_state as an ordinary tool call during the researcher's turn (its instruction tells it when).
2
Writes to tool_context.state are recorded as the event's state_delta and committed by the Runner — yes, this is session state.
3
When the screenwriter runs, { research? } is resolved from session state at request time (the ? tolerates a missing key).
Appending to a list instead of overwriting is deliberate: each loop iteration adds to the record rather than clobbering it.

Passing information (3 of 3): typed hand-offs with Event(output=...) 2.x GRAPHS

class Outline(BaseModel): title: str acts: list[str] # An agent node: its response is parsed into an Outline, # and that OBJECT becomes its output on the edge screenwriter = Agent( name="screenwriter", instruction="Write a three-act outline for the user's idea.", mode="single_turn", output_schema=Outline, ) # A function node: the parameter named 'node_input' # receives the previous node's output def save_pitch(node_input: Outline): path = write_pitch_file(node_input.title, node_input.acts) return Event( message=f"Pitch saved to {path}", # for the user output=path, # for the next consumer ) pitch_pipeline = Workflow( name="pitch_pipeline", edges=[("START", screenwriter, save_pitch)], )

Graph-only. Data rides the edge like a return value on a conveyor belt: each node's output is the next node's input. State is not involved.

The wrapping is automatic. An agent node's response is parsed against its output_schema and set as event.output for you; a function node's plain return value is wrapped too. Write Event(...) explicitly only when you need route or message.

Function nodes: the name matters — the parameter called node_input gets the incoming output. Parameters with other names are bound from state keys, and ctx: Context is also available.

Event fields, two audiences: message is text for the user; output feeds the next node. A user-facing terminal node should set message, or the user sees nothing from that step.

At the end of the graph, the terminal node's output becomes the workflow's own output — a Workflow is itself a node, so nested graphs and Workflow-as-tool consume it the same way.

The Workflow graph engine NEW IN 2.0

# From the official quickstart: agent → function → agent from google.adk import Agent, Workflow city_generator = Agent(name="city_generator", instruction="Return the name of a random city, nothing else.", mode="single_turn", output_schema=str) def lookup_time(node_input: str): # plain Python node return Event(output=CityTime(time_info="10:10 AM", city=node_input)) city_report = Agent(name="city_report", input_schema=CityTime, mode="single_turn", instruction="Report the current time in the city.") root_agent = Workflow( name="city_time_report", edges=[("START", city_generator, lookup_time, city_report)], )

One primitive for sequence, parallelism, routing, and (conditional) cycles — edge syntax on the next slide.

Nodes can be agents, plain Python functions, tools, or nested workflows — AI steps and code steps alternate freely.

LLM agents used as graph nodes must be mode="single_turn" (or task, currently disabled in graphs).

ADK now describes itself as built on two main classes: Agent and Workflow; in 2.0 every agent is a node on this engine.

How to read an edge

Nodes do the work (agents, functions, joins); edges are the arrows between them. One entry draws a straight line; you write more entries wherever the flow forks, merges, or loops — together they define one graph. Entries come in two shapes: tuple (sequence) edges and routing (dict) edges.

Tuple (sequence) edge

("START", a, b, c)

Run a, then b, then c, in order. The string "START" marks the graph's entry point. Each node's event.output feeds the next.

Several tuple edges fan out and join

gather = JoinNode(name="gather") ("START", b, gather) # b and c both start ("START", c, gather) # from START, in parallel (gather, d) # d runs after both finish

b and c both run from "START" in parallel. gather is an ordinary variable holding a JoinNode object — not a keyword — that waits for every predecessor before d runs.

Routing (dict) edge

def router(node_input): if is_urgent(node_input): return Event(route="ESCALATE", output=node_input) return Event(route="RESOLVE", output=node_input) (router, {"ESCALATE": human_queue, "RESOLVE": closer})

The router returns Event(route="KEY"); the dict edge sends execution to the node under that key. Re-emit output so the chosen node still receives the payload — a route-only Event forwards None.

A dict route pointing at an earlier node creates a cycle — that's how loops work (next slides). Unconditional cycles are rejected at build time.

Branch vs. loop: it's all in where the route points

Branch — every route points forward
router
task_B
task_C
route="B"
route="C"

Both targets are downstream. One runs, execution continues forward, done — nothing repeats.

Loop — one route points backward
researcher
critic
router
file_writer
route="REVISE" — back to a node that already ran
route="APPROVE"

The backward route re-activates an earlier node — that re-activation is the loop. The forward route is the exit. There is no loop construct; a loop is just a branch aimed at the past.

Iteration: exit_loop vs. conditional cycles

1.x — the lab's writers_room DEPRECATED
from google.adk.tools import exit_loop critic = Agent(..., tools=[append_to_state, exit_loop], instruction="If the outline is ready, call exit_loop.") writers_room = LoopAgent( name="writers_room", max_iterations=5, sub_agents=[researcher, screenwriter, critic], )
EXIT

The loop's condition lives in review_router: "REVISE" points back to an earlier node (the cycle), "APPROVE" leaves it. Unconditional cycles are rejected at build time.

CAP

There is no max_iterations parameter — count passes in state and force "APPROVE" at the limit (shown at right). Use a temp:-scoped key or reset at entry so a later run in the same session doesn't inherit the count.

RETRIES

Separate concern: any node takes reliability knobs — node(critic, retry_config=RetryConfig(max_attempts=3), timeout=60.0). A timed-out node raises NodeTimeoutError.

2.x — a conditional cycle: critic verdict → router → back-edge
class Critique(BaseModel): approved: bool feedback: str # the four nodes (agents abbreviated) researcher = Agent(..., mode="single_turn") screenwriter = Agent(..., mode="single_turn") critic = Agent(..., mode="single_turn", output_schema=Critique) # typed verdict file_writer = Agent(..., mode="single_turn") def review_router(node_input: Critique, ctx: Context): passes = ctx.state.get("passes", 0) + 1 # count loops ctx.state["passes"] = passes if node_input.approved or passes >= 5: # short-circuit return Event(route="APPROVE", output=node_input) return Event(route="REVISE", output=node_input) # always re-emit output: route-only Events forward None writers_room = Workflow(edges=[ ("START", researcher, screenwriter, critic, review_router), (review_router, {"REVISE": researcher, # back-edge = the loop "APPROVE": file_writer}), # the routed exit ])

Fan out and gather: ParallelAgent vs. graph fan-out

1.x — the lab's preproduction_team DEPRECATED
preproduction_team = ParallelAgent( name="preproduction_team", sub_agents=[ casting_agent, box_office_analyst, ], ) # isolated branches; results gathered # into state, read by the next agent
2.x — fan-out edge + JoinNode
from google.adk.workflow import JoinNode gather = JoinNode(name="gather") # an ordinary node object preproduction = Workflow( name="preproduction", edges=[ ("START", casting_agent, gather), # both run from ("START", box_office_analyst, gather), # START in parallel (gather, greenlight_report), # runs after both ], max_concurrency=4, )
A JoinNode proceeds only after every predecessor emits output — one failed branch stalls the join. Give flaky branches a RetryConfig and a failsafe output. The join passes the collected outputs (keyed by node) to the next node. max_concurrency caps how many branches run at once — it's in the SDK but not yet on adk.dev, so students won't find it in the docs.

What else the graph engine gives you

Function nodes

Plain Python steps via FunctionNode or the @node decorator — no LLM call for mechanical work.

Typed data flow

Nodes exchange values through event.output instead of hand-plumbed state keys.

Dynamic nodes

ctx.run_node(node, input) spawns work decided at runtime.

Resilience

Per-node RetryConfig; deterministic pause/resume and rehydration from session history.

Human input

HITL interrupts (request_input) pause the graph; resume continues exactly where it stopped.

Composition

Nested workflows; Workflow-as-tool (2.4); to_a2a(workflow) for remote exposure.

Current limits to teach honestly: a Workflow cannot yet be a sub-agent of an LlmAgent (why the legacy classes remain); live/BiDi streaming is not supported inside workflows; task mode is disabled inside graphs in 2.0.

Custom orchestration: custom agent → native Workflow

1.x — subclass BaseAgent, override the run method BYPASSED IN 2.0
class BudgetRouter(BaseAgent): async def _run_async_impl(self, ctx): pitch = ctx.session.state["PITCH"] # conditional orchestration in hand-written code if pitch["budget"] > 100_000_000: async for e in self.blockbuster.run_async(ctx): yield e else: async for e in self.indie.run_async(ctx): yield e writers_room = BudgetRouter( name="writers_room", sub_agents=[blockbuster, indie], )
2.x — a function router node + dict edge
def budget_router(node_input: Pitch): if node_input.budget > 100_000_000: return Event(route="BIG", output=node_input) return Event(route="SMALL", output=node_input) writers_room = Workflow(edges=[ ("START", pitch_agent, budget_router), (budget_router, {"BIG": blockbuster, "SMALL": indie}), ])

Conditional logic, dynamic selection, and unusual flow patterns are native graph features now — the docs say to reach for graph or dynamic Workflows before writing a custom agent.

Callbacks are not the replacement for orchestration — before/after_agent_callback are per-agent hooks, not a control-flow engine.

Who decides it runs? Tool call vs. graph step

ApproachWho decidesGuarantees and costReach for it when
Tool on an agent
tools=[save_pitch]		The model — whether, when, and with what argumentsCan be skipped or mis-called; the result loops back through the model for another LLM passThe agent should choose among capabilities mid-conversation
Agent as a graph node
mode="single_turn"		The graph — always runs at its stepOne LLM call; typed input/output via schemasThe step needs judgment or language
Function node
def save_pitch(node_input)		The graph — always runs at its stepNo LLM: deterministic, testable, fast; input validated at the edgeMechanical steps: save, transform, route
Rule of thumb: reasoning steps get agents, mechanical steps get code, and the graph — not the model — owns the ordering. The save_pitch example earlier is a tool-shaped job promoted to a graph step precisely so it cannot be skipped, mis-called, or double-billed through the model.
