Why agent evaluation is different

Nondeterminism: the same request can take different paths on different runs. Evaluation has to be systematic — defined cases, repeated runs, explicit thresholds — not spot-checked by feel.

The path matters, not just the answer: an agent can reach a right-looking answer through wrong or wasteful tool calls. You evaluate the trajectory (which tools, with which arguments, in which order) and the final response.

Multi-turn by nature: agents hold conversations, carry session state, and pursue goals across turns — a single prompt/response pair rarely captures the behavior you care about.

Evaluation moves into the developer loop: a model gets benchmarked once per release, but an agent's behavior shifts with every commit — instructions, tool code, pins. Behavioral evals become your regression suite, run like unit tests — and adk conformance makes that affordable in CI by replaying recorded runs without live LLM calls (covered later this module).

Comparing trajectories against ground truth

Given an expected trajectory and the agent's actual one, there is more than one reasonable definition of "matches." ADK's default metric uses the strictest; the others are useful lenses when you build custom metrics or analyze failures.

Exact match

The actual trajectory equals the expected one: same tools, same order, nothing extra, nothing missing. This is what tool_trajectory_avg_score at 1.0 demands.

In-order match

The expected tool calls appear in the right order; extra calls in between are tolerated.

Any-order match

All expected tool calls happen, in any order; extras tolerated. Useful when steps are legitimately independent.

Precision

Of the tool calls the agent made, what fraction were expected? Penalizes wasteful or spurious calls.

Recall

Of the expected tool calls, what fraction did the agent make? Penalizes skipped steps.

Single-tool use

Did one specific tool get used at all, anywhere in the trajectory? The narrowest check.

Eval data today: the EvalSet schema CHANGED

{ "eval_set_id": "home_automation_tests", "name": "...", "description": "...", "eval_cases": [{ "eval_id": "turn_off_bedroom_device", "conversation": [{ // one Invocation per turn "user_content": {"parts": [{"text": "Turn off device_2."}]}, "final_response": {"parts": [{"text": "Device_2 is now OFF."}]}, "intermediate_data": { "tool_uses": [{ "name": "set_device_info", // expected FunctionCall "args": {"device_id": "device_2", "status": "OFF"} }] } }], "session_input": {"app_name": "home_automation", "user_id": "test_user", "state": {}} }] }

This replaces the legacy flat format the previous deck showed: a bare JSON list of turns with query / expected_tool_use / reference fields. Students won't find those field names in today's docs.

Legacy files still load: AgentEvaluator.migrate_eval_data_to_new_schema converts them automatically. But author new eval data in the current schema.

An EvalCase can also carry rubrics, or a conversation_scenario in place of a fixed conversation — both covered in a moment.

You rarely hand-write this JSON: the Dev UI Eval tab captures live sessions into it for you.

Rubric-based evaluation: your standards, an LLM judge

A rubric is a plain-language property you declare on the EvalCase — "the response is courteous," "the agent confirms before acting."

Three metrics score against them: rubric_based_final_response_quality_v1 judges answers, rubric_based_tool_use_quality_v1 judges tool choices, rubric_based_multi_turn_trajectory_quality_v1 judges whole conversations.

Reach for rubrics where text similarity fails: qualitative standards with no single reference answer — tone, process, policy compliance.

// on the EvalCase, alongside conversation: "rubrics": [ { "rubric_id": "tone", "rubric_content": { "text_property": "The agent's response is courteous and concise." } }, { "rubric_id": "confirmation", "rubric_content": { "text_property": "The agent confirms the device and room before changing any state." } } ]

User simulation: eval cases without scripted turns 2.x-ERA

An EvalCase can carry a conversation_scenario instead of a fixed conversation: a starting prompt and a goal, rather than a script of user turns.

At eval time, an LLM plays the user — generating each user turn in response to what the agent actually says, so the conversation can wander the way real ones do.

Pairs naturally with safety_v1 and hallucinations_v1: probe how the agent behaves under conversations you didn't script.

per_turn_user_simulator_quality_v1 closes the loop — it grades the simulator's turns, so a failing eval can be traced to a bad simulated user rather than a bad agent.

adk eval_set generate_eval_cases goes one step further: an LLM authors the scenarios themselves from your agent's definition.

Three ways to run evals

1 · Dev UI — Eval tab

Converse with your agent, then capture the current session as an eval case in an eval set. Re-run the set against a new agent version, adjust metric threshold sliders, and open the trace view on any failing case. The interactive authoring surface.

2 · pytest

Call AgentEvaluator.evaluate from a test function so evals run alongside your unit tests — locally and in CI. The test fails when any metric falls below its criterion. Best for the *.test.json unit-style files.

3 · CLI

adk eval runs eval sets from the shell: select individual cases, supply metric criteria from a config file, print per-case detail. Scriptable for automation; eval sets and results can live in GCS via an eval-storage URI.

All three run the same eval sets against the same metric registry — pick by workflow: explore in the UI, gate in pytest, script with the CLI.

The CLI in practice

# Run every case in an eval set file against your agent adk eval path/to/my_agent evalset.json # Select specific cases, supply metric criteria, show per-case detail adk eval path/to/my_agent evalset.json:case_1,case_2 \ --config_file_path=criteria.json --print_detailed_results # criteria.json — metric names from the registry, with thresholds { "criteria": { "tool_trajectory_avg_score": 1.0, "response_match_score": 0.8 } } # Manage eval sets without the UI adk eval_set create path/to/my_agent regression_suite adk eval_set add_eval_case path/to/my_agent regression_suite \ --scenarios_file=scenarios.json --session_input_file=session.json adk eval_set generate_eval_cases path/to/my_agent regression_suite \ --user_simulation_config_file=sim_config.json
--eval_storage_uri=gs://... points eval sets and results at a GCS bucket, so a team (and CI) share one store.

Evals as tests: AgentEvaluator with pytest

import pytest from google.adk.evaluation.agent_evaluator import AgentEvaluator @pytest.mark.asyncio async def test_basic_capabilities(): """Session-level eval, run with the unit tests.""" await AgentEvaluator.evaluate( agent_module="home_automation_agent", eval_dataset_file_path_or_dir= "tests/fixture/home_automation_agent/simple.test.json", )

evaluate is async today — the old deck's synchronous call needs @pytest.mark.asyncio and await.

Pass a directory instead of a file and it discovers every *.test.json beneath it.

Legacy-format files are migrated on the fly, so old test data keeps working while you convert it.

The test fails when any metric misses its criterion — your eval thresholds become CI gates.

Conformance testing: record / replay regression NEW

Record once: run your agent live and capture each run — requests, model responses, tool calls — as YAML test cases.

Replay deterministically: re-run the cases against recorded responses, with no live LLM calls — fast, free, and flake-proof, unlike metric evals.

Use it in CI before bumping dependency pins or editing instructions: replay tells you whether behavior shifted; metric evals tell you whether it got worse.

No dedicated adk.dev page yet — adk conformance --help is the current reference.

# 1. capture live runs as YAML test cases adk conformance record tests/conformance # 2. after a change: replay them, no live calls adk conformance test tests/conformance # or compare against live model behavior adk conformance test --mode=live tests/conformance

Corrections and neighbors: tracing, install, optimization

The old tracing slide is dead: AF_TRACE_TO_CLOUD=1 was a pre-1.0 relic. Today you launch with --otel_to_cloud (or the older --trace_to_cloud, deprecated in 2.x) after pip install "google-adk[otel-gcp]".

ADK now emits native OpenTelemetry: standard gen_ai.* spans and metrics, viewable in Cloud Trace and the Dev UI's trace view — the same traces you read when an eval case fails.

Install for this module: pip install "google-adk[eval]" pulls the eval extras — rouge-score, pandas, the Vertex evaluation SDK, and GEPA.

Adjacent payoff: adk optimize (GEPA prompt optimization) uses an eval set as its fitness function — it rewrites your agent's instruction and keeps the variant that scores best. A good eval set is reusable leverage, not just a gate.
