What are the key concepts in ADK?

Agent

The fundamental worker unit. LLM-driven, with instruction, tools, and delegation.

Tools & Toolsets

Functions, built-ins, and dynamic bundles (toolsets) that extend agent capabilities.

Workflow 2.0

Graph engine for sequence, fan-out, and routing. Replaces the workflow-agent classes.

Callbacks

Custom code at agent, model, and tool checkpoints.

Session & State

One conversation: history as Events, working memory as State.

Events

The basic unit of communication: user message, agent reply, tool use.

Memory

Cross-session, long-term recall, distinct from session State.

Artifacts

Versioned files and binary data, per session or user.

App & Plugins NEW

The application container; app-wide lifecycle hooks and policies.

Context management NEW

Prefix caching and events compaction to control cost and window size.

Streaming

Bi-directional text and audio with the Gemini Live API.

Code execution

Executor family: built-in, Vertex, container, GKE, sandboxes.

Evaluation

Built-in multi-turn eval via CLI, pytest, and the Dev UI.

Deployment

Agent Runtime (managed), Cloud Run, or GKE via adk deploy.

Runner & Runtime

The event loop that executes agents and coordinates services.

Models

Gemini first; Claude, OpenAI, LiteLLM, and open models via the Base LLM interface.

Sessions, State, Events, and Memory

A Session is the context of a single conversation: its history is a sequence of Events, and its working memory is State.

An Event is the basic unit of communication: a user message, an agent reply, or a tool call and its result.

Memory is long-term, cross-session recall, distinct from session State.

Session services range from InMemorySessionService (local development) to database, Firestore, and Vertex-managed services in production.

ADK 2.0 compatibility: sessions written by 2.0 are readable by ADK 1.28 and higher, but incompatible with older 1.x. Upgrading a production database is a schema migration: adk migrate session --source_db_url ... --dest_db_url ...

The Runner and the event loop

The Runner is the engine that manages execution flow, orchestrates agents based on Events, and coordinates with backend services (sessions, artifacts, memory).

Agents produce work by yielding Events; the framework commits them to the session and routes them onward.

In ADK 2.0, every agent is a node in an execution graph. Two contracts follow: never append events directly to session.events (yield them), and never swallow exceptions broadly — a broad except traps NodeInterruptedError and breaks pause/resume and retries.

Custom agents that override _run_async_impl() are bypassed by the 2.0 engine — use before/after agent callbacks instead.

The App container NEW IN THIS COURSE

from google.adk.apps import App app = App( name="my_app", # identity: sessions key on this root_agent=root_agent, # an Agent — or a Workflow in 2.x plugins=[LoggingPlugin()], # app-wide lifecycle hooks context_cache_config=..., # Gemini prefix caching events_compaction_config=..., # summarize long histories resumability_config=..., # pause/resume support ) runner = Runner(app=app)

An Agent is a worker; an App is the application.

Policies set here apply to every agent in the tree.

Runner(agent=..., app_name=...) still works — it builds an App internally.

ADK project structure

adk_project/ agent_grammar/ __init__.py agent.py .env agent_maths/ __init__.py agent.py .env

One directory per agent; the directory name is the agent's app name for the CLI tools.

agent.py must define the agent in a root_agent variable — unchanged since 1.x.

__init__.py imports from agent.py so ADK can discover the agent.

This structure is what adk web, adk run, and adk api_server discover and serve.

Four ways to interact with your agents

1 — Web UI (adk web)

Local Dev UI with chat, Trace, Events, Eval, and agent-graph tabs. For local development only — not production.

2 — Command line (adk run)

Terminal chat with an agent folder. Quick local testing.

3 — API server (adk api_server)

Local FastAPI server on port 8000 exposing REST endpoints (/run, /run_sse, session endpoints).

4 — Programmatic (Runner)

Your own Python process: build an App, create a session, iterate the async event stream.

The agent definition is identical across all four — only the surface changes.

Programmatic interface — the async pattern CHANGED

root_agent = Agent(model=os.getenv("MODEL"), name="trivia_agent", instruction="Answer questions.") app = App(name="app_agent", root_agent=root_agent) runner = InMemoryRunner(app=app) async def main(): session = await runner.session_service.create_session( app_name="app_agent", user_id="user1") content = types.Content(role="user", parts=[types.Part.from_text(text="What is the capital of France?")]) async for event in runner.run_async( user_id="user1", session_id=session.id, new_message=content): if event.content.parts and event.content.parts[0].text: print(f"{event.author}: {event.content.parts[0].text}") asyncio.run(main())

The previous deck showed sync runner.run(...); current practice (and the lab code) is run_async with async for.

Session creation is awaited; sessions here are in-memory and ephemeral.

Content / Part come from google.genai.types.

Six callbacks, three pairs

PairApplies toBefore — can skip by returning…After — can replace the result
Agent lifecycle
before/after_agent_callback		Any agentContent → skips the agent entirelyAugment or replace final output
LLM interaction
before/after_model_callback		LLM agentsLlmResponse → skips the model callInspect / rewrite the raw response
Tool execution
before/after_tool_callback		Function & Agent toolsdict → used as the tool resultReplace the tool response
More important than ever in 2.x: callbacks are the sanctioned replacement for custom run-method overrides, which the 2.0 node engine bypasses. Typical uses: guardrails, request caching, dynamic instructions, logging, auth checks.

Callback example: a model guardrail

def block_pii(callback_context: CallbackContext, llm_request: LlmRequest) -> Optional[LlmResponse]: last = llm_request.contents[-1].parts[0].text or "" if contains_pii(last): # Returning a response SKIPS the model call return LlmResponse(content=types.Content( role="model", parts=[types.Part.from_text( text="I can't process personal data.")])) return None # proceed normally root_agent = Agent(..., before_model_callback=block_pii)

Plugins: app-wide hooks NEW IN THIS COURSE

from google.adk.plugins import BasePlugin class QuotaFallback(BasePlugin): def __init__(self): super().__init__(name="quota_fallback") async def on_model_error_callback(self, *, callback_context, llm_request, error): if "429" in str(error): return canned_response # suppress error, keep demo alive app = App(name="my_app", root_agent=root_agent, plugins=[QuotaFallback()])

16 hook points: user message, run, agent, model, and tool callbacks — plus error hooks callbacks don't have.

Write once on the App, applies to every agent.

Shipped: LoggingPlugin (and DebugLoggingPlugin), ReflectAndRetryToolPlugin, SaveFilesAsArtifactsPlugin, BigQueryAgentAnalyticsPlugin, AutoTracingPlugin, GlobalInstructionPlugin, ContextFilterPlugin, MultimodalToolResultsPlugin.

Context management on the App NEW IN THIS COURSE

# Reuse the processed prompt prefix across turns context_cache_config=ContextCacheConfig( min_tokens=8192, # extra gate; 0 by default ttl_seconds=600, # default 1800 cache_intervals=10) # refresh after N uses

Gemini enforces a hard 4096-token floor measured on the whole prior prompt (instruction + tools + history); caching starts on turn 2 at the earliest. min_tokens only adds a gate above that floor. See also static_instruction.

# Summarize old events to stay in the window events_compaction_config=EventsCompactionConfig( compaction_interval=10, overlap_size=2)

Long-running sessions keep a rolling summary instead of replaying the full transcript.

Delegation: AgentTool wrapper → task mode
