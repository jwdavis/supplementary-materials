### Logging

1. Organizing idea: one agent process produces four log streams, configured in different places, landing in different places. Your code (Python `logging`), the `google_adk` framework tree, the web server (`uvicorn.access`), and OpenTelemetry (spans, `gen_ai.*` events, metrics). Most "my logs look wrong" problems are one stream configured and another expected to follow.
   1. ADK logs automatically
      1. Run locally, prints to console (text lines, `adk web/api_server --log_level`)
      2. Run in Cloud Run or GKE, stdout/stderr land in Cloud Logging as `textPayload` with **Default** severity. ADK's own logs are never JSON unless you add a formatter (slide 8 is wrong on this)
      3. Agent Runtime captures stdout/stderr by default: `reasoning_engine_stdout` / `reasoning_engine_stderr` on the `aiplatform.googleapis.com/ReasoningEngine` resource. A native deploy's platform handler owns the format; BYOC keeps yours. Both keep your level, both leave severity Default
   2. You can write logs yourself. List all three options, then take a position with the motivations behind it:
      1. Arbitrary log entries (Python `logging` under your own logger name, or the Cloud Logging client)
      2. Per-agent callbacks (`before_/after_*_callback` on one agent)
      3. A plugin on the `App` (`BasePlugin`, 14 hooks incl. three error hooks; fires for every agent and tool; receives objects, so token counts and latency are numbers; independent of the level dial; can short-circuit like a callback)
      4. Position: a plugin for production telemetry across agents; a per-agent callback when the logic belongs to one agent or must block or rewrite a step for that agent; arbitrary entries for your own code. Both callback and plugin are in addition to the framework logger, not instead of it
      5. OOB plugins and their limits: `LoggingPlugin` writes with `print()` and ANSI codes, ignores levels and handlers, dev only. `DebugLoggingPlugin` buffers one whole turn to a redacted YAML file (mode 0600), a capture for a bug report, not a sink. Neither is queryable in Cloud Logging
   3. OpenTelemetry logging is a fourth stream, not a replacement: ADK emits `gen_ai.*` log events (metadata only unless content capture is on), and you can bridge your own `logging` records into the same exporter with an OTel `LoggingHandler` so they carry the trace and span ids
   4. Compare/contrast the options; which to use when
2. Make clear how logging is configured per server and platform
   1. Agent Runtime with the service-generated container/server
   2. Cloud Run/GKE with `get_fast_api_app` (via `adk deploy` or agents-cli)
   3. Cloud Run/GKE with a custom API server (`dictConfig` owns all four streams; JSON with explicit `severity` and `logging.googleapis.com/trace` to stdout)
   4. How the level and the format reach each platform. There is no ADK log-level environment variable: `--log_level` is a flag on `adk web/api_server`; `adk deploy cloud_run --log_level` sets gcloud's verbosity and the container runs at INFO; Agent Runtime has no flag; `LOG_LEVEL` is a convention your own code implements. The environment variables that do differ by platform are the OpenTelemetry ones, and the injection path is the point: shell exports for CLI-launched servers (`.env` loads after the exporters are built), `.env` for your own server, the agent folder's `.env` copied into an `adk deploy agent_engine` deployment, `--set-env-vars` for Cloud Run
   5. GKE is Cloud Run with the env vars in the manifest (`adk deploy gke --otel_to_cloud`): one table row, not pages
3. How to consume logs in Cloud Logging
4. How to consume logs with a log sink to BigQuery (one tour page: one table per log name, sink writer identity needs `roles/bigquery.dataEditor`), and the BigQuery Agent Analytics plugin as the agent-shaped alternative: one row per lifecycle event with `session_id`, `invocation_id`, `trace_id`, tokens per call, and content

### Tracing

1. Make clear how to configure tracing
   1. Agent Runtime deploy. `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY` is the switch; `adk deploy agent_engine --otel_to_cloud` writes it. Unset means off unless the platform sets it. The root span there is `invoke_workflow` (schema v2, selected by `GOOGLE_CLOUD_AGENT_ENGINE_ID`), not `invocation`. Where the exported telemetry lands on a native deploy is re-verified before delivery; the page says "docs say" and "observed" separately
   2. Cloud Run and GKE with `adk deploy` and/or agents-cli deployment (`--otel_to_cloud` baked into the container `CMD`; the image needs `google-adk[otel-gcp]` in the agent's `requirements.txt` or it boot-crashes; `--trace_to_cloud` is deprecated)
   3. Cloud Run and GKE with custom API servers (`get_gcp_exporters` + `maybe_set_otel_providers`, plus the resource)
   4. The two content knobs, as verified on 2.9.0 (eight-run matrix, 2026-09-12):
      - `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS` governs only ADK's own spans (`call_llm`, `execute_tool`: `gcp.vertex.agent.llm_request/llm_response/tool_call_args/tool_response`). Default **on**
      - `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` governs the `gen_ai.*` log events, and under `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` also the `generate_content` span in `SPAN_ONLY` / `SPAN_AND_EVENT`. Default `NO_CONTENT`; `true` coerces to `EVENT_ONLY`
      - They do not override each other. ADK `true` + `NO_CONTENT` leaves the prompt on ADK's spans and off the events; ADK `false` + `SPAN_AND_EVENT` puts it on the instrumentor's span anyway. "Content off" is both knobs
      - `adk deploy agent_engine --otel_to_cloud` writes the ADK knob `false` only if absent from `.env`; Cloud Run and GKE deploys write nothing (the agent folder's `.env` ships in the image and is read per turn); no deploy tool touches the OTel variable
      - On a native Agent Runtime deploy the Vertex SDK's `AdkApp.set_up` overwrites the ADK knob to `false` at startup (`true` only with the legacy `enable_tracing=True`), so the deployment's value of that knob is moot there. BYOC behaves like Cloud Run
      - Production position: both off; text goes to an access-controlled BigQuery table when it is needed
2. Walk through how to consume the traces
   1. How to use Cloud Trace
   2. What kinds of questions/troubleshooting you can do with traces (the slow step, the failed step, one user's request, a trace is not proof the task got done)
   3. How they are correlated to log entries: a log entry joins a span through `trace` + `spanId` in the same project. ADK's `gen_ai.*` events carry them for free; your `logging` records need a bridge (OTel `LoggingHandler`, `CloudLoggingHandler`, or a JSON formatter that reads the current span). On Cloud Run the request log and ADK's spans carry different trace ids unless a custom server propagates the inbound `traceparent` and sets `OTEL_TRACES_SAMPLER=always_on`

### Metrics

1. What is free: the seven `gen_ai.*` histograms ADK emits (agent, model, and tool duration; token usage by type; inference and tool calls per turn; workflow duration). Token usage and tool frequency are not custom metrics (slide 13 is wrong on this)
2. Metrics or rows, decided by cardinality: bounded attributes (tool, model, error type) on metrics; unbounded ids (session, user, invocation) only in BigQuery rows. ADK never puts ids on metric attributes
3. Three different facts on one run: tool error ratio, invocation error ratio, task outcome. A tool can fail inside a successful turn; no framework metric says whether the user got what they asked for. One custom counter recorded in an `after_tool_callback` closes the gap, and it is the number to alert on
4. Tokens per call as the cost signal: input tokens climb across a session as context accumulates while output stays flat; the mean hides it; tokens per session comes from rows, not metrics
