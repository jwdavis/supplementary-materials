## Order and why

The spine is **where text enters → what screens it, and where → who may cross each boundary, as whom**.

Section 1 (concepts 1–8) opens with the boundaries picture (1) because every later page is a control at one of them, and because it disposes of "put it in the system prompt" in the first beat. The API (2) before floors and templates (3), so that a template is understood as a configuration of filters the student has already seen. Enforcement and logging sit with floors (3) because the default is inspect-only and that fact changes what a student sees in the lab. Then the four enforcement points in order of how much of the world each covers: the model call (4), which is free but narrow; the plugin (5), which is yours and wide; MCP and edge (6). The decision table (7) needs all of 4–6, and the SDP page (8) closes because de-identify-and-continue is the one thing only the DIY row can do.

Section 2 (concepts 9–14) opens with the matrix (9) as the frame, then walks the three boundaries in request order: UI (10), server (11), tools (12–13). 11 comes before 12 because the `user_id` asserted at the server is what 13 turns into a user credential. Service account before Agent Identity inside 12 because the SA is what most rooms run today and Agent Identity is the same code with a better principal; 12 precedes user-auth (13) because "as itself" is the default and "as the user" is the exception the student must justify. Workload → agent (14) closes the section because it reuses everything: the caller identities from 12, the per-target grants from 11, and WIF from M2. SPIFFE is not a page: it is one sentence on 12 (the standard under Agent Identity and under GKE's managed workload identities), with SPIRE absent because no Google Cloud doc describes running it.
