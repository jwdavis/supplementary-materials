What is billed, what multiplies, what hides

Dana runs a support agent on Gemini 3.5 Flash. The month-end bill is one line per model. Before touching a lever she needs to know which of the “cost drivers” are costs at all, and which are the ordinary infrastructure bill wearing a new name.

Billed units

Model tokens (input, output, and cached input at a discount) and tool or API calls to other services. These are the lines on the bill.

The one multiplier

Model tier scales the price of every token by a constant factor. On today’s ladder the steps are uneven: Pro is only 1.3× Flash, while Flash is 5× Flash-Lite. The expensive step is Flash to Flash-Lite, not Flash to Pro. Output costs 6× input on every tier.

Multi-agent: shared session or second copy

Sub-agents in one ADK app share one session: each re-sends the shared history plus its own, usually smaller, instruction and tools. Routing adds turns, not copies. An A2A remote agent is different: it receives a message, not your session, and runs its own instruction, tools, and history in its own process and project. Its context is a second copy, and its tokens land on its owner’s bill.

A gap out of the box, closable

Cost per conversation is not on the bill. Billing aggregates by project, model, and label, never by conversation, so a runaway 40-turn session hides inside the monthly line. Nothing in Cloud Billing closes this. One addition does: per-model-call token rows from the Agent Analytics plugin (pages 15 and 16).

Trim the re-sent input first

Every token in the prefix is paid for on every call. The cheapest lever is to send fewer of them, and each of these changes is reversible with no model change.

01
Shorten the instruction. Remove repeated rules and examples the model no longer needs. Move examples the model does need into static_instruction, where caching (page 8) can discount them.
02
Trim tool declarations. Every tool’s full schema (name, description, every parameter) is re-sent on every call. Split the toolset across sub-agents so each carries only its own; filter a toolset with tool_filter; shorten descriptions and drop optional parameters.
03
Cap the history. Context compaction (page 9) summarizes older events once the prompt crosses a token threshold and keeps the newest ones raw.
04
Limit retrieval. Retrieval-augmented generation splits documents into chunks of a few hundred tokens, embeds them, and pastes the K most similar into the prompt. Every chunk is input, re-sent each turn: 20 chunks of 500 tokens is 10,000 tokens per call. Lower K to 3–5, or retrieve broadly, rerank, and keep only the chunks above a relevance threshold.
05
Ask for structured output. A JSON response schema cuts output tokens, which cost 6× input, and removes a re-parse round trip.
06
Only then change the model (page 11). Model tier is a constant multiplier you apply after the token count is right.
Example

Caching: two mechanisms, two names

“Caching” is used for two different things. One skips the model. The other runs the model every time and discounts the part of the input it has seen before. Which one you have decides what you save.

Context caching

The model runs every turn. The part of the input that matches a recent request (the instruction, the tool declarations, the earlier history) is billed at 10% of the input price instead of being processed again. Output is full price. Gemini does this implicitly by default (page 7); ADK can do it explicitly (page 8).

Response caching

A lookup keyed on the request. On a hit, the stored answer is returned and the model is not called: zero model cost, near-zero latency. Useful when the same question arrives again. ADK does not ship one; page 10 shows the adk-redis integration that provides it.

Example

Actor: Dana’s FAQ agent.

Input: “What is your return window?” arrives 900 times a day.

Mechanism: a response cache answers the second and later copies without a model call. Context caching cannot do that; it makes each of the 900 calls cheaper by discounting the shared instruction and tools.

Result: the response cache saves the whole call, about $0.008 each at 5,000 input tokens; context caching saves about $0.005 of it illustrative.

Takeaway: response caching reuses the answer; context caching reuses the work on the repeated input. They compose: skip the call when you can, discount the prefix when you cannot.
Sources: context cache overview · ADK callback patterns: caching (verified 2026-09-13).

Implicit caching: automatic, free, best effort

Dana has configured nothing. Her bill already shows cached input tokens, because Gemini reuses its work on any request that begins the way a recent one did.

What it is. Gemini keeps the computed state of recently processed request prefixes. When a new request to the same model starts with the same bytes as a recent one, and the shared prefix reaches the model minimum (4,096 tokens on Gemini 3; 6,144 on some 3.x Flash variants), the cached part is billed at 10% of the input price.

What you do. Nothing. It is on by default in every Google Cloud project. There is no cache object, no storage charge, and no time-to-live you control.

What makes it hit. Same model, byte-identical prefix, requests close together in time. Put large shared content at the start of the prompt. ADK’s request order (system instruction, tools, then history) already does this.

Why agents hit often. History is append-only, so the second call of a turn begins with the whole first call. The prefix that can hit is the entire request so far, not just the instruction.

What the bill shows. Cached input is priced as its own item: the pricing page lists a cached-input price per model, and the docs say the savings are “automatically passed on to you.” Per response, cachedContentTokenCount says how many tokens hit; the Agent Analytics view exposes it as usage_cached_tokens.

What it does not promise, and where it does not apply. A hit is best effort, never guaranteed. It is a Gemini feature (plus some open models served through Vertex). Partner models such as Claude on Vertex have their own prompt caching with their own cache-write and cache-read prices.

Example

Actor: Dana’s agent, turn 5.

Result: call B’s input costs $0.0027 instead of $0.0147, and usage_cached_tokens reads 8,900 illustrative. On a miss the same call costs full price and nothing in the code changed.

Takeaway: implicit caching is free and already on. Keep the prefix stable and read usage_cached_tokens to see how often it hits; when you need a guarantee, that is page 8.

Explicit context caching in ADK

When Dana wants the discount guaranteed rather than hoped for, she asks ADK to create the cache. ADK stores the system instruction, the tool declarations, and the leading contents as a server-side cache object and references it on later calls.

google-adk 2.9.0

from google.adk.agents.llm_agent import Agent
from google.adk.agents.readonly_context import ReadonlyContext
from google.adk.agents.context_cache_config import ContextCacheConfig
from google.adk.apps.app import App
from google.genai import types

def steer(ctx: ReadonlyContext) -> str:              # dynamic: appended to contents, never in the prefix
    return f"The customer's tier is {ctx.state['tier']}. Be concise."

agent = Agent(
    name="support_agent",
    model="gemini-3.5-flash",
    static_instruction=types.Content(          # the cached prefix: durable, byte-identical every turn
        role="user", parts=[types.Part(text=SUPPORT_PERSONA_AND_SCHEMAS)]),
    instruction=steer,
    tools=[lookup_order, issue_refund],
)

cache = ContextCacheConfig(min_tokens=0, ttl_seconds=1800, cache_intervals=10)   # the defaults
app = App(name="support_app", root_agent=agent, context_cache_config=cache)

What is in the fingerprint: the system instruction, the tool declarations, the tool config, and the leading contents. Caching starts on turn 2, once a previous request’s token count is known, and only if that count reaches the model minimum (2,048 on Gemini 2.x, 4,096 on Gemini 3).

The three knobs: min_tokens raises the floor above the model’s; ttl_seconds is how long the cache object lives; cache_intervals is how many invocations reuse it before ADK refreshes it.

What it costs: the cached tokens at 10% of the input price, plus storage at $1.00 per 1M tokens per hour on Flash and $4.50 on Pro. The model still runs every turn.

Example

Actor: Dana’s agent over the 12-turn conversation from page 4.

Input: a 4,000-token prefix; turns 2 to 12 make 22 calls.

Mechanism: each call references the cache instead of re-sending the prefix.

Result: 22 × 4,000 tokens move from $1.50 to $0.15 per 1M, saving $0.119 of the $0.401 input bill; storage for the 30-minute lifetime is $0.002 illustrative.

Resets the cache silently

A value that changes per turn inside static_instruction. f"Today is {date.today()}" or a customer tier makes the prefix differ from the cached one, so every turn creates a new cache and never reuses it. Put anything that varies in the dynamic instruction.

A tool added, removed, or renamed mid-session. Tools are part of the fingerprint. A prefix below the model minimum never caches at all.

Takeaway: explicit caching guarantees the discount on a byte-identical prefix and bills storage for it. Everything that varies goes in the dynamic instruction.
Sources: context_cache_config.py at v2.9.0 · gemini_context_cache_manager.py at v2.9.0 · ADK context caching · pricing: context cache storage (verified 2026-09-13).

  • Defaults on 2.9.0: cache_intervals=10, ttl_seconds=1800, min_tokens=0; the class docstring states the model minimums and that caching begins on turn 2. The source deck showed min_tokens=4096, cache_intervals=4 as if they were defaults. The API is marked experimental.

Context compaction caps the history

Caching changes what the re-sent history costs, not how much of it there is. Every call still carries all of it: it still fills the context window, still adds latency, and a cache miss bills it in full. Compaction is the lever that makes the history smaller.

google-adk 2.9.0

from google.adk.apps.app import App, EventsCompactionConfig

app = App(
    name="support_app",
    root_agent=agent,
    events_compaction_config=EventsCompactionConfig(
        token_threshold=20_000,      # trigger: the last model call sent this many prompt tokens in total
        event_retention_size=6,      # keep the newest 6 events raw; summarize everything older
    ),
)

What is measured. The threshold is compared with the prompt token count Gemini reported for the most recent model call: everything that request contained, meaning the static and dynamic instruction, every tool declaration, and the whole history. Not one part of it. The same number page 4 tracks per turn.

What happens. token_threshold and event_retention_size are set together. When the invocation ends and that count met the threshold, ADK summarizes every event older than the newest event_retention_size with one model call and stores the summary as a compaction event. Later requests are built from the summary plus the retained events, so their history is short again.

Sliding-window trigger. compaction_interval compacts every N completed events, with overlap_size events carried into the next window. Use the token trigger when the goal is cost.

The summarizer is a model call. Each compaction reads the range it replaces and writes a summary. On short sessions that is a cost with no payoff; on long ones it pays back within a turn or two.

Example

Actor: Dana’s agent on a 40-turn session.

Input: token_threshold=20000, event_retention_size=6; history grows 1,200 tokens per turn.

Mechanism: after turn 14 the prompt passes 20,000 tokens; ADK summarizes the older events into about 1,500 tokens and keeps the last 6 raw.

Result: each later call carries about 7,300 tokens instead of 24,000 and rising; the compaction itself is one Flash call costing about $0.04, recovered within two turns illustrative.

Takeaway: compaction bounds the history at a price of one model call per compaction. Turn it on for long sessions; leave it off for short ones.
Sources: apps/_configs.py at v2.9.0 (EventsCompactionConfig) · ADK context compaction (verified 2026-09-13).
Speaker notes — Context compaction
  • Why this page exists: page 4 showed history outweighing the prefix by mid-conversation; this is the lever for that bar. The source deck did not cover it.
  • Validator on 2.9.0: token_threshold and event_retention_size must both be set or both be unset. The docstring: “ADK will attempt a post-invocation compaction when the most recently observed prompt token count meets or exceeds this threshold.” apps/compaction.py reads that count from the latest event’s usage_metadata.prompt_token_count, the total input of that model call; when no count is available it estimates one from the session contents at four characters per token.
  • Caching and compaction are not in tension: caching makes the re-sent history cheap on a hit, compaction makes it short. A cached hit still sends every token, and the next call after a miss pays full price for all of them. Say this if page 7 left anyone thinking caching solves growth.
  • The summarizer defaults to LlmEventSummarizer; you can pass your own summarizer= and choose a cheaper model for it.
  • Arithmetic: compaction reads about 20,000 tokens ($0.03) and writes about 1,500 ($0.014). Each later call saves at least 13,000 input tokens ($0.02), and there are two calls per turn.
  • A summary loses detail. If the agent must quote an exact earlier value, keep event_retention_size large enough or store the value in session state.

Response caching: the adk-redis integration

For the questions that arrive again and again, Dana wants to skip the model entirely. ADK supplies the hook, and the adk-redis package supplies the cache: two callbacks backed by a Redis store that matches on meaning, not on exact wording.

google-adk 2.9.0 with adk-redis (pip install 'adk-redis[all]'; needs a Redis 8.4+ instance)

from google.adk.agents import Agent
from redisvl.utils.vectorize import HFTextVectorizer
from adk_redis import (LLMResponseCache, RedisVLCacheProvider,
                       RedisVLCacheProviderConfig, create_llm_cache_callbacks)

provider = RedisVLCacheProvider(
    config=RedisVLCacheProviderConfig(
        redis_url="redis://localhost:6379",
        ttl=3600,                    # a stored answer expires after one hour
        distance_threshold=0.1,      # how close a paraphrase must be to count as a hit
    ),
    vectorizer=HFTextVectorizer(model="redis/langcache-embed-v2"),   # embeds each prompt
)
llm_cache = LLMResponseCache(provider=provider)
before_model_cb, after_model_cb = create_llm_cache_callbacks(llm_cache)

agent = Agent(
    name="faq_agent", model="gemini-3.5-flash", instruction=FAQ_INSTRUCTION,
    before_model_callback=before_model_cb,     # a hit returns the stored answer; the model is skipped
    after_model_callback=after_model_cb,       # a miss stores the new answer
)

The mechanism is ADK’s. A before_model_callback that returns an LlmResponse short-circuits the call; the after_model_callback sees the miss and stores it. The provider supplies the two callbacks, the key, and the store.

What the provider adds. The prompt is embedded and compared with stored prompts; anything within distance_threshold is a hit, so rephrasings share an answer. The store is shared across replicas and outlives a restart; ttl bounds how stale an answer can be. LangCacheProvider is the managed version with server-side embeddings.

What to watch. A loose threshold serves one question’s answer to a different question; start tight and widen while watching false hits. Never cache turns whose answer is an action (a tool call) or reads live data. If answers are personalized, scope the cache per user, or one user gets another’s answer.

Example

Actor: Dana’s FAQ agent with the callbacks above.

Input: the return-window question, 900 times a day, in about 40 wordings.

Mechanism: the first wording misses, runs the model, and is stored. Every later wording embeds within the threshold of it and is served from Redis without a model call.

Result: roughly 800 model calls a day skipped, about $6 a day at 5,000 input tokens each, and those answers return in milliseconds illustrative. An exact-match cache would have hit about one call in ten.

Takeaway: a response cache is two callbacks and a key. adk-redis supplies both with semantic matching; you set the threshold, the TTL, and the rule for what never gets cached.
Sources: ADK Redis integration: semantic caching · ADK callback patterns: caching · base_llm_flow.py at v2.9.0 (verified 2026-09-13).
Speaker notes — Response caching
  • Why this page exists: the source deck promised “zero model cost on a hit” and attributed it to ADK. The mechanism is real; adk-redis is the maintained implementation, and this page is its shape.
  • Mechanism: _handle_before_model_callback in base_llm_flow.py returns the callback’s LlmResponse as the model result and never calls the model. The ADK callback-patterns doc (section 4, Caching) describes building the same thing by hand with a dict keyed on the request; that version matches exact text only and lives in one process.
  • Snippet is the adk.dev integration page’s self-hosted example with the model id and names changed; the LangCache variant swaps the provider for LangCacheProvider(config=LangCacheProviderConfig(cache_id=…, api_key=…, ttl=…)) and drops the vectorizer.
  • Cost of the cache itself: a Redis instance (Memorystore or self-hosted) and the embedding of each prompt on the local vectorizer. Both are small next to a skipped Flash call, but they are not zero.
  • Arithmetic: 800 calls × 5,000 input tokens × $1.50 per 1M = $6.00 plus output.
  • Generic page: a semantic cache in front of any API works the same way. What is agent-shaped is the rule for what never gets cached: tool-calling turns are actions, not answers.

Fine-tuning is a volume decision with a surcharge

A tuned model can drop the few-shot examples from every prompt. But on Gemini 3 and later, a tuned endpoint bills 1.5× the base model per token, so the saving has to come from a shorter prompt or a lower tier, and the break-even has to include the surcharge.

Training cost is dataset tokens × epochs at the tuning price ($0.01 per 1,000 training tokens on Gemini 3.5 Flash). Inference on the tuned endpoint is 1.5× the base model’s token price.

Break-even requests = training cost ÷ (base cost per request − tuned cost per request). If the second term is not positive, tuning never pays.

Tuning is the last lever. Trimming, caching, compaction, and right-sizing are reversible and need no training pipeline. Tuning adds a model artifact you re-train when the base model version retires.

Routing: three ways to pick the model per request

Most of Dana’s traffic is easy and some of it is not. Rather than pay the hard-case price for every request, the agent chooses the model at run time. All three ways are code.

Router agent

ADK’s idiomatic option: a root LlmAgent with sub_agents, each with its own model=. The router’s own call is the fixed cost of routing.

Override per request

A before_model_callback sets llm_request.model for this call only. The same hook as an app-wide plugin covers every agent.

Model as a tool

A tool whose body calls another model. Fits when the hard cases are a distinct sub-task the agent already delegates.

google-adk 2.9.0: override per request · run against Vertex AI on 2026-09-13

def pick_model(ctx: CallbackContext, llm_request: LlmRequest) -> None:
    if needs_long_reasoning(ctx.user_content):        # your rule or classifier
        llm_request.model = PRO_MODEL_ID                # this call only; the agent default is unchanged

agent = LlmAgent(
    name="support",
    model=FLASH_LITE_MODEL_ID,                          # default for every call
    before_model_callback=pick_model,
)

Setting up BigQuery Agent Analytics

The per-conversation view needs one row per model call with the session id and the token counts. Nothing in Cloud Billing produces that. The Agent Analytics plugin does: register it on the App and every model call, tool call, and agent step writes a row.

google-adk 2.9.0 (pip install 'google-adk[bigquery-analytics]')

from google.adk.apps.app import App
from google.adk.plugins.bigquery_agent_analytics_plugin import BigQueryAgentAnalyticsPlugin

analytics = BigQueryAgentAnalyticsPlugin(
    project_id="my-project",
    dataset_id="agent_events",       # the dataset must already exist
    table_id="agent_events",         # created on first run if missing, partitioned by day
    location="US",
    create_views=True,                # one view per event type; page 16 queries v_llm_response
)
app = App(name="support_app", root_agent=agent, plugins=[analytics])

What you create, what it creates. You create the dataset. On first run the plugin creates the table, partitioned by timestamp per day, and with create_views=True a view per event type. Rows are written through the BigQuery Storage Write API in batches from the agent process.

Who needs what. The identity the agent runs as needs to write the table and create it: roles/bigquery.dataEditor on the dataset. Creating the views runs DDL, which needs roles/bigquery.jobUser on the project guidance. Readers of the dataset can read the content column, which holds what users typed (Module 3).

What it costs. Three BigQuery lines, all small at agent scale: Storage Write API ingestion at $0.025 per GiB after the first 2 TiB a month; active storage at about $0.02 per GiB-month after the first 10 GiB; on-demand queries at $6.25 per TiB scanned after the first 1 TiB a month. Partitioning by day is what keeps the query line small: page 16’s query scans one day.

Example

Actor: Dana’s support agent on Cloud Run with the plugin above.

Input: 1,000,000 model calls a month, each writing a row of about 2 KB with content included.

Mechanism: about 2 GiB a month written through the Storage Write API, stored, and scanned one day at a time by the cost query.

Result: ingestion inside the free 2 TiB, storage a few cents a month, and the daily query scanning about 70 MiB, inside the free 1 TiB. The rows cost less than one of the conversations they explain illustrative.

Takeaway: one plugin on the App, one dataset you create, two IAM roles, and a BigQuery bill that rounds to cents. That is the whole price of per-conversation cost.

Cost per conversation is one query

Dana wants yesterday’s twenty most expensive conversations and why they cost what they did. Billing cannot group by conversation. The table from page 15 can, because every model call wrote a row with its session id and token counts.

BigQuery, over the view the plugin on page 15 created

-- cost per conversation, yesterday; prices are query parameters in $ per 1M tokens
SELECT session_id,
       COUNT(*)                                 AS model_calls,
       SUM(usage_prompt_tokens)                 AS input_tokens,
       SUM(IFNULL(usage_cached_tokens, 0))      AS cached_tokens,
       SUM(usage_completion_tokens)             AS output_tokens,
       ( (SUM(usage_prompt_tokens) - SUM(IFNULL(usage_cached_tokens, 0))) * @in_price
         + SUM(IFNULL(usage_cached_tokens, 0)) * @cached_price
         + SUM(usage_completion_tokens)        * @out_price ) / 1e6 AS usd
FROM   agent_events.v_llm_response
WHERE  DATE(timestamp) = DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)
GROUP BY session_id
ORDER BY usd DESC
LIMIT 20;

What the columns are. usage_prompt_tokens is the whole input including the cached part; usage_cached_tokens is the part billed at the cached price; usage_completion_tokens is the output. Prices are parameters so the query outlives a price change.

What the top rows are. The long conversations. Page 4 showed why: twelve turns cost twelve times two turns, because every turn re-sends the ones before it.

What to do with them. Read the trace of the top row (Module 3). Then alert on prompt tokens per session: a conversation past the threshold is one that should have gone to a human, or one where compaction is off.

Example

Actor: Dana.

Input: the query with @in_price=1.50, @cached_price=0.15, @out_price=9.00.

Mechanism: one row per session summed over its model calls.

Result: the top row is a 31-turn conversation at $1.12, 30× the median; its trace shows a tool failing and the model retrying it eleven times. She adds an alert on sessions past 60,000 prompt tokens and fixes the tool illustrative.

Takeaway: cost per conversation comes from the agent’s own event rows, not from billing. The expensive conversations are the long ones, and the trace says why they were long.

The AI FinOps loop: validate is the step that is different

Classic FinOps measures, analyzes, and optimizes. An agent adds a fourth step, because a cheaper agent can be a worse one and nothing on the bill will say so.

Measure

Token counts per model call from the Agent Analytics rows (page 15); labels on every model API request (page 14).

Analyze

Cost per conversation (page 16), by agent, by label, by day. Find the long sessions and the expensive agents.

Optimize

Trim (5), cache (7–8), compact (9), skip repeated calls (10), right-size (11), route (13). Cheapest lever first.

Validate

Run the eval set (Module 4) on the changed agent. Cheaper and worse is a regression, not a saving.

Example

Actor: Dana.

Input: the order-lookup agent moved from Flash to Flash-Lite.

Mechanism: the pipeline runs the eval set before the model id change merges.

Result: trajectory score 0.91 against a 0.90 threshold, so the change ships and the agent’s input price drops 5×. Had the score come back 0.86, the saving would have been a regression and the change would not merge illustrative.

Takeaway: every cost change goes through the eval set. The validate step is what makes agent FinOps different from the classic loop.
