Four log streams in one process

One request to an agent served by adk api_server can write log lines from four different sources; the fourth appears only when telemetry export is on. Each source is configured in a different place.

Streams 1 and 2 reach the root logger, so one logging.config.dictConfig call (the standard-library call that sets every logger, handler, and formatter from one dictionary) configures both.

Stream 3 does not. uvicorn gives its uvicorn and uvicorn.access loggers their own handlers and stops them passing lines to the root logger, so your root configuration never sees them.

Stream 4 exists only when telemetry export is on. OpenTelemetry (OTel) is the open standard ADK uses for traces, metrics, and log events; section 2 turns it on.

Example: one POST /run, four sources

ADK: INFO - google_llm.py:263 - Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False

Your tool: INFO - agent.py:21 - get_weather city=London

uvicorn: INFO: 127.0.0.1:58569 - "POST /run HTTP/1.1" 200 OK

OpenTelemetry: a gen_ai.user.message and a gen_ai.choice event, only with export on

Takeaway: configuring one stream does not configure the others. Know which source wrote a line before you try to change it.
Sources: local adk api_server run, google-adk 2.11.0 (2026-10-07) · cli/utils/logs.py, telemetry/google_cloud.py:339-368 at v2.11.0 · uvicorn 0.54.0 config.py · ADK: Logging.

What ADK logs on its own

ADK writes plain-text lines with a level word inside them. Which severity Cloud Logging stores depends on the platform, not on that word.

Text, not JSON: 2026-10-07 23:35:58,112 - INFO - google_llm.py:263 - Sending out request, model: …

Cloud Run and Agent Runtime store every such line at DEFAULT, the severity that means “unspecified” and sorts below DEBUG. The word ERROR inside the text does not change it.

GKE stores stdout at INFO and stderr at ERROR. ADK’s handler writes stderr, so on GKE every routine ADK line is ERROR.

An uncaught stack trace is the exception: Cloud Run stores it as one ERROR entry, whether it went to stdout or stderr.

Example

Actor: the on-call engineer for an order-status agent on Cloud Run.

Input: a log-based alert on resource.type="cloud_run_revision" AND severity>=ERROR.

Mechanism: the shipping tool catches its own errors and logs tool failed: carrier API timeout through ADK’s format. Each line is stored at DEFAULT.

Result: six hours of failures, and the alert never notifies anyone. A log-based metric (a Cloud Logging counter of entries that match a filter) on textPayload:"tool failed", with an alert above 0 over 5 minutes, does fire.

Takeaway: with ADK’s default text logging on Cloud Run or Agent Runtime, a severity>=ERROR alert misses every line ADK and your code write; on Cloud Run it matches only uncaught stack traces. Alert on content, or write your own severity field (p9).
Sources: Cloud Run job and Agent Runtime log tests, jwd-dev-5, 2026-10-07 · GKE: about logs · LogSeverity · log-based metrics.

Log fields, not sentences

The callback hands you token counts as integers. Pass them to the logger as separate fields, and time the model call yourself, because the response does not carry a latency.

Two agent callbacks: start a timer, then log fields

import logging, time
logger = logging.getLogger("weather")

def start_timer(callback_context, llm_request):
    callback_context.state["temp:t0"] = time.monotonic()

def log_model_call(callback_context, llm_response):
    u = llm_response.usage_metadata
    if u is None:
        return
    logger.info("model_call", extra={
        "agent": callback_context.agent_name,
        "input_tokens": u.prompt_token_count,
        "reply_tokens": u.candidates_token_count,
        "latency_ms": round((time.monotonic() - callback_context.state["temp:t0"]) * 1000),
    })
extra= alone is not enoughThe keys land on the Python log record, but a default formatter prints only the message. They reach Cloud Logging as fields once a JSON formatter writes them out (p9).
Example: “what was p95 model latency this week?”

Logged as a sentence: f"tokens {n}, latency {ms}ms" needs a regex extractor in a log-based metric, which breaks when the wording changes.

Logged as fields: a distribution metric on jsonPayload.latency_ms, no regex.

In BigQuery: APPROX_QUANTILES(jsonPayload.latency_ms, 100)[OFFSET(95)] once a sink copies the logs there (p11).

Takeaway: the callback gives you typed values. Log them as fields, not as a sentence you will have to parse later.
Sources: models/llm_response.py (no latency field) at v2.11.0 · local run of this code, gemini-3.5-flash, 2026-10-07 · distribution metrics · logs in BigQuery.
Speaker notes — Log fields, not sentences
  • Tested 2026-10-07: one London turn logged two records, input_tokens 64 and 131, reply_tokens 16 and 15, latency_ms 2,407 and 1,217.
  • temp: state keys last for one invocation and are not saved to the session, so the timer does not leak into stored state (tested 2026-10-07: session state was empty after three turns).
  • usage_metadata is optional and can be None (for example on some streamed partial responses), hence the guard. candidates_token_count excludes thinking tokens, which Gemini bills as output, so the field is named reply_tokens rather than output tokens; add thoughts_token_count for a cost figure (p27).
  • How extra= works: Python copies each key onto the LogRecord; the formatter decides what is printed. Formatter() prints %(message)s; the adk CLI’s format prints time, level, file, and message. Neither prints extra= keys (local test, Python 3.14, 2026-10-07).
  • BigQuery: a log sink writes one table per log name, e.g. run_googleapis_com_stdout, date-sharded by default; the field is jsonPayload.latency_ms.

One JSON formatter for ADK’s lines and yours

Cloud Run, GKE, and Agent Runtime read a JSON line on stdout or stderr as structured fields. A formatter on the root logger turns ADK’s lines and yours into that JSON.

In your agent module, at import time

import json, logging, logging.config

_STD = set(logging.LogRecord("n", 0, "p", 0, "", (), None).__dict__) | {"message", "asctime"}

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {"severity": record.levelname, "message": record.getMessage()}
        for k, v in record.__dict__.items():   # the keys passed with extra=
            if k not in _STD:
                payload[k] = v
        return json.dumps(payload, default=str)

logging.config.dictConfig({
    "version": 1, "disable_existing_loggers": False,
    "formatters": {"json": {"()": JsonFormatter}},
    "handlers": {"out": {"class": "logging.StreamHandler", "formatter": "json"}},
    "root": {"handlers": ["out"], "level": "INFO"},
})

What this formatter writes to stderr: ADK’s line, then p7’s model_call line (each is one line; wrapped here)

{"severity": "INFO", "message": "Sending out request, model: gemini-3.5-flash, backend: …"}
{"severity": "INFO", "message": "model_call", "agent": "weather_agent",
 "input_tokens": 68, "reply_tokens": 16, "latency_ms": 2233}

severity is lifted out of the JSON into the entry’s own severity; the other keys stay under jsonPayload, and numbers stay numbers.

Keep "disable_existing_loggers": False. The standard-library default, True, silences every logger already created, including ADK’s.

Lines written before your module loads stay in ADK’s text format. Under the adk CLI the agent module loads on the first request.

Takeaway: one dictConfig makes every later line from ADK and from your code a queryable JSON entry with a real severity. uvicorn’s lines are configured separately.

Reading logs back: filters and rows

A log filter shows what happened in one conversation. Asking which conversations used the most tokens needs rows you can group, which is what ADK’s BigQuery plugin writes.

Log Explorer filter, e.g. jsonPayload.session_id="s-8841": works only if your code logs that field. ADK’s own lines carry no session or trace id.

A log sink to BigQuery copies entries into one table per log name. Generic; the service account the sink writes as (its writer identity) needs roles/bigquery.dataEditor on the dataset.

BigQueryAgentAnalyticsPlugin writes one row per agent event with session id, token counts, latency, and content, plus views per event type.

Python: register the plugin on the app

app = App(name="support_app", root_agent=root_agent, plugins=[
    BigQueryAgentAnalyticsPlugin(project_id=PROJECT, dataset_id="agent_analytics")])

BigQuery SQL: the ten sessions with the most tokens today

SELECT session_id, SUM(usage_total_tokens) AS tokens
FROM agent_analytics.v_llm_response
WHERE DATE(timestamp) = CURRENT_DATE()
GROUP BY session_id ORDER BY tokens DESC LIMIT 10;
Example

Question 1: a ticket says “the agent failed for my order.” Support looks up the session id, s-8841, from the order. A Log Explorer filter on that field returns its lines in order.

Question 2: “which ten sessions used the most tokens today?” No filter answers it; the query above does.

Takeaway: filters answer “what happened in this session”; grouped rows answer “which sessions.” Log the session id yourself if you want the first.

Four states between a span and Cloud Trace

ADK creates spans on every turn with no code from you. Whether you can see them depends on two more pieces: a tracer provider that records them, and an exporter that sends them somewhere.

Example: one weather question, four ways to run it

Script calling Runner: the answer comes back; the span inside the tool is a non-recording span with trace id 000…0; nothing is stored.

adk api_server without --otel_to_cloud (what adk deploy runs): the server installs a provider with no exporter, so Cloud Trace stays empty.

adk web: the Trace tab shows the tree; restart the server and it is gone.

With --otel_to_cloud: the tree is in Cloud Trace, read back from the Trace API.

Takeaway: ADK creates the spans either way, so if a deployed agent shows no trace, check first whether an exporter was installed.

Why a failed tool shows no error

A weather tool returns {"status": "error", …} for a city it does not know, and the model tells the user it has no data. In the trace, no span is marked as an error.

After each tool call, ADK calls the tool’s _detect_error_in_response with the returned value. On FunctionTool it returns "TOOL_ERROR" for a dict with a truthy error key and None for anything else.

{"status": "error"} has no error key, so ADK writes no error.type and leaves the span status UNSET, which is also the status of a successful span. (OpenTelemetry statuses are UNSET, OK, ERROR; ADK sets only ERROR.)

Override the method to return a short failure name; it becomes error.type on the tool span and sets the span to ERROR.

For tools that report failure in a status field

from google.adk.tools import FunctionTool

class StatusAwareTool(FunctionTool):
    def _detect_error_in_response(self, response):
        if isinstance(response, dict) and response.get("status") == "error":
            return "lookup_failed"
        return None

agent = Agent(…, tools=[StatusAwareTool(get_weather)])

A span of your own inside a tool

A tool span shows how long the whole tool took. When the tool makes two calls of its own, a span around each one shows which call the time went to.

Inside the tool function

from opentelemetry import trace
tracer = trace.get_tracer("weather")

def get_weather(city: str) -> dict:

What ADK measures, and the switches that add more

With export on, ADK records durations for every turn, model call, and tool call, token counts for every model call, and model and tool calls per turn. You write no code for these.

Core: gen_ai.*, 7 names

invoke_agent.duration · execute_tool.duration · client.operation.duration (model call) · client.token.usage · invoke_agent.inference_calls · invoke_agent.tool_calls · invoke_workflow.duration

A single agent records the first six. The seventh appears for a Workflow (ADK’s agent type that runs steps as a graph), or with telemetry schema v2, the default on Agent Runtime.

Experimental: adk.experimental.*, 18 names

Token counts per turn by kind (input, output, total, cache read, reasoning, tool use), and the same per workflow.

Off by default. On with ADK_EXPERIMENTAL_TELEMETRY=true, per feature with ADK_EXPERIMENTAL_TELEMETRY_FEATURES=token_usage, or per request in RunConfig. Names may change between releases.

They land in Cloud Monitoring as prometheus.googleapis.com/gen_ai.client.token.usage/histogram and so on, queried in PromQL (the Prometheus query language, which Cloud Monitoring accepts) by the gen_ai.* name.

The core names follow the OpenTelemetry GenAI conventions, which are still marked Development (OpenTelemetry’s label for conventions that may still change). They are the most stable names ADK offers, not a promise that nothing changes.

Two libraries can write the gen_ai.client.* metrics. ADK writes them, unless the Gemini instrumentation package is installed (it is in google-adk[otel-gcp]); then it does, with different labels and no agent name.

Reading the token histogram

The token metric is a histogram: each model call adds one value per token type. Two queries on it answer two different questions.

Total input tokens, and input tokens per model call, over 48 hours

# total input tokens
sum(increase({"gen_ai.client.token.usage_sum", "gen_ai.token.type"="input"}[48h]))

# average input tokens per model call
sum(increase({"gen_ai.client.token.usage_sum",   "gen_ai.token.type"="input"}[48h]))
  / sum(increase({"gen_ai.client.token.usage_count", "gen_ai.token.type"="input"}[48h]))

increase(x[48h]) is how much the counter grew over 48 hours; sum adds the series together.

_sum is the total of the recorded values (tokens); _count is how many values were recorded (model calls); _bucket counts values under each bound (used for percentiles, next page).

_count is model calls, not turns. A turn with one round of tool calls makes two model calls.

The plain name with no suffix returns an empty result, not an error.

Example

Input: the two queries over 48 hours on a weather agent.

Result: 77,243 input tokens over 132 model calls, 585 per call illustrative

What it is not: tokens per turn. These turns used a tool, so each made two calls, and per turn is about twice 585. Tokens per conversation need the BigQuery rows (p11).

Output tokens depend on the writerADK’s own count of output tokens includes thinking tokens; the Gemini instrumentation counts only the reply. Gemini bills thinking tokens as output, so a cost chart on the instrumented metric undercounts output.
Takeaway: divide _sum by _count for tokens per model call, and remember that a turn that calls a tool makes more than one call.

Which layer is slow: the turn, the model, or a tool

Users say the weather agent is slow. Measuring the turn, the model call, and each tool separately shows which one owns the time.

Turn and tool: p95 from buckets. Model call: the mean, _sum over _count

histogram_quantile(0.95, sum by (le, "gen_ai.tool.name") (
    rate({"gen_ai.execute_tool.duration_bucket"}[10m])))

Why the model call gets a meanA p95 is estimated inside one bucket. Example: who owns the time

Model: 1.57 s per call, two calls per turn, so about 3.1 s of every turn.

Tools: get_forecast adds a second or two, only on forecast turns (its p95 is a bucket estimate); get_weather adds nothing measurable.

Result: the model is the largest share of a typical turn (about 3.1 s); get_forecast adds time only on forecast turns. Shortening prompts or choosing a faster model helps every turn; fixing the forecast API helps only forecast turns.

Three ways to count failure, and which one to alert on

In a test run, half the questions asked about a city the weather tool does not know. Three measurements of that run disagree about how much failed.

QuestionMeasured howThis run
How many tool calls failed?execute_tool.duration values with an error.type label, over all tool calls; needs the p17 override50%
How many turns failed?invoke_agent.duration values with an error.type label, over all turns0%
How many users did not get the weather they asked for?a counter your code records once per turn, with an outcome label (next page)50%

Turn failures are zero because every turn completed. The model read “unknown city” and answered “I have no data for Atlantis.” ADK records an error on a turn only when an exception ends it.

Tool failures say a dependency is failing, not whether users were affected: if a second tool answered, the first tool’s error is still counted.

Only your code knows whether the user got what they asked for, so the outcome counter is one you write.

Example: choosing the alert

On turn failures > 20%: never fires, not even in this run.

On tool failures > 20%: fires here; it would also fire after a backup weather provider is added and users get answers.

On the share of turns with outcome="unavailable" > 20%: fires when users did not get weather, whichever tool failed.

Takeaway: ADK can tell you whether a turn completed. Only your code can count whether the user got an answer; alert on that, and file tool failures as tickets for the dependency’s owner.

Count the outcome once per turn

The tool writes the outcome to a temp: state key, which lasts one turn and is not saved; one agent callback reads it when the turn ends and adds one to a counter. The turn, not the tool call, is what gets counted.

Tool writes the outcome; the root agent’s after_agent_callback counts it

from opentelemetry import metrics
turns = metrics.get_meter("weather").create_counter("weather.turns")

def get_weather(city: str, tool_context: ToolContext) -> dict:
    report = lookup(city)
    if report is None:
        if tool_context.state.get("temp:outcome") != "answered":
            tool_context.state["temp:outcome"] = "unavailable"
        return {"status": "error", "error_message": f"No data for {city}."}
    tool_context.state["temp:outcome"] = "answered"
    return {"status": "ok", "report": report}

def count_outcome(callback_context):
    turns.add(1, {"outcome": callback_context.state.get("temp:outcome", "no_lookup")})

root_agent = Agent(…, tools=[get_weather], after_agent_callback=count_outcome)

Input tokens grow as a conversation gets longer

With ADK’s default settings, each model call includes the conversation so far. The later a call comes in a conversation, the more input tokens it costs.

Why input grows: with the default include_contents="default", the request for turn 20 carries turns 1 to 19 plus the new message.

Why output stays flat: each reply is about the same length.

Cost per conversation is not a metric: ADK puts no session or user id on any metric, and adding one yourself creates a time series per id, billed per sample. Use the BigQuery rows (p11).

Example

Input: the same run read as tokens per minute: 4,757 input, 62 output illustrative

Mechanism: at gemini-3.7-flash list prices through 2026 ($0.75 per million input, $3.75 per million output) input is $0.0036 a minute and output $0.0002.

Result: in this conversation input was about 94 % of token cost as counted by this metric, which leaves out thinking tokens (p27), and its share grows with every turn.

Takeaway: the cost of a model call rises through a conversation. The climb shows when one conversation runs alone. In production, compare input tokens per call against conversation length in the BigQuery rows (p11).
