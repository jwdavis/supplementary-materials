Four log streams in one process

An ADK process writes logs from four independent sources. Each is configured somewhere different, and three of the four are not yours.

dictConfiglogging.config.dictConfig is the Python standard-library call that configures every logger, handler and formatter in the process from one dictionary. It is how you reach streams 1–3 at once; page 9 uses it.
Example — one request, four sources

google_adk: Sending out request, model: gemini-3.7-flash

your tool: tool get_weather called for city='London'

uvicorn.access: INFO: "POST /run HTTP/1.1" 200 OK

OpenTelemetry: a gen_ai.client.inference.operation.details event — only if a LoggerProvider is installed

Takeaway: configuring one stream does not configure the others. Know which of the four a line came from before you try to change it.
Sources: cli/utils/logs.py (configures the root logger and google_adk) · telemetry/google_cloud.py:357-374 (OTel logs go to OTLPLogExporter, not stdout) · ADK: Logging, google-adk 2.9.0 (verified 2026-09-12).
Speaker notes — Four log streams in one process
  • Why this page is first: every later question in this section — what level, what format, why is that line still printing — depends on knowing which stream produced the line.
  • Generic. Any Python process with a web server has streams 1–3. Stream 4 is the agent-specific one: it carries the trajectory, and section 2 is about it.
  • Stream 4 does not go to stdout. get_gcp_exporters wires OTel log records to an OTLP exporter aimed at telemetry.googleapis.com. On a native Agent Engine deploy they historically went to reasoning_engine_stdout, which is why the code still carries a comment about it — but on 2.9.0 the OTLP path is what runs.
  • The --log_level flag reaches streams 1 and 2 (it sets the root logger and google_adk) and not stream 3, because uvicorn configures its own access logger at startup. That is page 10’s subject; here it is only an example of “configured somewhere different.”
  • Delivery beat: ask which of the four they have ever deliberately configured. Usually only stream 2.

What ADK logs on its own

The framework writes log lines before you add any. They are plain text, and Cloud Logging stores them with no severity attached.

Text, not JSON. 2026-09-03 21:51:45,037 - INFO - agent.py:53 - tool get_weather called for city='London'

Captured with no setup on Cloud Run, GKE and Agent Engine — all three collect container stdout and stderr.

Stored as textPayload with severity DEFAULT. The word INFO in that line is text ADK printed. Cloud Logging does not read a level out of it.

Stderr does not change that. Cloud Run and Agent Engine both map stderr to DEFAULT as well, so a Python traceback is stored at the same severity as a startup message.

DEFAULT severity, and what an alert does with itCloud Logging severities run DEFAULT (0), DEBUG, INFO, NOTICE, WARNING, ERROR, CRITICAL, ALERT, EMERGENCY (800). DEFAULT means “unspecified” and sits below all of them. A log-based alert is built from a filter, and the filter severity>=ERROR matches no ADK line, because none of them carry a severity at all.
Example

Actor: Marco, on call for a weather agent on Cloud Run.

Goal: be paged when the forecast tool starts throwing.

What he did first: a log-based alert on resource.type="cloud_run_revision" AND severity>=ERROR. The tool threw for six hours; the alert never fired, because the traceback is stored at DEFAULT.

What worked: a counter log-based metric on textPayload:"Traceback", with an alert when it exceeds zero over five minutes.

Takeaway: ADK’s own lines carry no severity, so alert on their content — or emit your own severity field and alert on that instead.
Sources: logging tutorial 1.4, 1.5, 1.6 (Cloud Run Job, Cloud Run service, Agent Engine; captured 2026-09-03) · Cloud Logging: LogSeverity · Cloud Logging: log-based metrics (verified 2026-09-12).
Speaker notes — What ADK logs on its own
  • Generic. This is container stdout capture, not something ADK does — but it is the first thing people trip over when they try to alert on an agent.
  • The confusion to defuse: students see INFO in the line and assume Cloud Logging knows the level. It does not. The whole line, timestamp and level word included, is one textPayload string.
  • The counter-metric route in detail, since Marco’s fix is the one people copy: Logging → Log-based Metrics → Create, type Counter, filter textPayload:"Traceback", then an alert policy on that metric with a threshold above 0. It works today and needs no code change, and it breaks when the text changes — which is the argument for page 9.
  • GKE behaves the same when the cluster has Cloud Logging enabled, which is the default on Autopilot and Standard. A cluster with logging turned off collects nothing at all.

Speaker notes — Three places to put your own log line

Log fields, not sentences

The hook gives you four numbers. Whether they arrive in Cloud Logging as queryable fields or as one string depends on how you call the logger.

Formatted into the message

logger.info(f"tokens: {n}, latency: {ms}ms")
# jsonPayload.message = "tokens: 141, latency: 1617ms"
# to chart latency you must first parse it back out of the string

Passed as fields

logger.info(
    "llm_response",
    extra={"event": "llm_response", "input_tokens": 141,
           "output_tokens": 6, "latency_ms": 1617},
)
# jsonPayload.latency_ms = 1617 — a number, chartable directly
extra= alone is not enoughPython’s extra= merges those keys into the LogRecord, but the default formatter ignores them. They reach Cloud Logging only once a JSON formatter writes them out — page 9.
Example

Actor: Priya again, a week after shipping the cost logging from page 6.

Goal: answer “what did p95 model latency do this week?” for the weekly review.

If she logged the message form: a log-based metric with a regex extractor pulling digits out of the message text. It works, and it breaks the day someone rewords the string.

If she logged fields: a distribution metric on jsonPayload.latency_ms directly — or APPROX_QUANTILES(latency_ms, 100) once a sink lands the logs in BigQuery.

Takeaway: the hook already gives you typed values. Pass them through as fields rather than formatting them into a sentence you will have to parse later.
Sources: Python logging — extra= (stdlib) · Cloud Logging: structured logging · Cloud Logging: distribution metrics · logging tutorial 4.1 (verified 2026-09-12).
Speaker notes — Log fields, not sentences
  • Both forms record the same information — the difference is whether the structure survives to the destination. The first form keeps the numbers only inside a human-readable string; the second keeps them as separate typed values.
  • How extra=, the LogRecord and the formatter fit together. Three steps, and each one can drop your fields:
    • 1. You call logger.info(msg, extra={…}). Python builds a LogRecord object for this one line and copies every key from your dict onto it as an attribute, alongside its own built-ins (levelname, pathname, lineno, and about twenty more). Your keys are now on the record, but nothing has been rendered yet.
    • 2. The handler passes the record to its formatter. The default formatter renders "%(levelname)s:%(name)s:%(message)s" — it reads three attributes and ignores everything else, which is why extra= appears to do nothing out of the box.
    • 3. A JSON formatter reads the rest. Page 9’s format() walks record.__dict__, skips the known built-ins, and writes what is left into the JSON object. That is the step that turns your extra= keys into jsonPayload fields.
    So extra= is where the data enters, the LogRecord is where it waits, and the formatter decides whether it survives. Page 9 supplies step 3.
  • The regex-extractor route is real and supported, so do not tell people it is impossible. Tell them it couples their alerting to their message wording.
  • Field naming matters: avoid message, severity, and anything starting logging.googleapis.com/ as your own field names — Cloud Logging reserves those and will lift them out of the payload. Page 9 uses them deliberately.
  • The numbers in the block are from a captured turn, not invented.

Speaker notes — The two shipped plugins
  • Mode 0600 is a Unix file permission: read and write for the file’s owner only, nothing for the group or anyone else. ADK sets it because the YAML still contains complete prompts and responses after redaction — the docstring says the file “is not safe to hand around.”
  • Why print() is disqualifying, concretely. print() writes straight to stdout without creating a LogRecord. So --log_level WARNING does not silence it, the JSON formatter from page 9 never sees it, and in a structured setup its ANSI escape sequences show up as ^[[90m inside the message field. It is not that the output is ugly — it is that it bypasses the entire logging configuration you just set up.
  • What you get from a plugin that a callback does not give you (revisiting page 6 with a concrete case): one registration covering every agent, plus on_user_message_callback to capture what was asked before any agent runs, on_event_callback to see each event as it is emitted, and on_run_error_callback for failures that happen outside any model or tool call. A per-agent callback cannot see any of those, because by the time it runs an agent has already been selected.
  • The redaction detail worth repeating: the temp: rule blanks all temporary state, not only credentials. An intermediate value passed between agents under a temp: key reads as [REDACTED], which surprises people debugging multi-agent handoffs.

One formatter for every stream

A JSON formatter on the root handler applies to streams 1–3 at once, so the framework’s lines and the server’s come out in the same shape as yours.

Configure once at startup — tested against google-adk 2.9.0

import logging, logging.config, json, contextvars

trace_id = contextvars.ContextVar("trace_id", default="")
_STD = set(logging.LogRecord("n",0,"p",0,"",(),None).__dict__) | {"message", "asctime", "taskName"}

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {"severity": record.levelname, "message": record.getMessage()}
        if trace_id.get():
            payload["logging.googleapis.com/trace"] = trace_id.get()
        for k, v in record.__dict__.items():   # the keys you passed via extra=
            if k not in _STD:
                payload[k] = v
        return json.dumps(payload, default=str)

logging.config.dictConfig({
    "version": 1, "disable_existing_loggers": False,
    "formatters": {"json": {"()": JsonFormatter}},
    "handlers": {"out": {"class": "logging.StreamHandler", "formatter": "json"}},
    "root": {"handlers": ["out"], "level": "INFO"},
})

Speaker notes — One formatter for every stream
  • This page is step 3 of the chain from page 7. There, extra= put the keys on the LogRecord and the default formatter ignored them. Here the JsonFormatter walks record.__dict__, subtracts the built-in attributes, and writes the remainder into the JSON — which is the step that makes extra= actually reach Cloud Logging. The second code block is the producer; the first is what renders it.
  • Why _STD exists: extra= merges your keys into record.__dict__ alongside roughly twenty built-ins. Subtracting a throwaway record’s attribute names is what isolates yours. A formatter that forgets this either emits nothing extra or dumps pathname, lineno and the rest into every entry.
  • ContextVar is a standard-library variable scoped to the current task rather than the process, so concurrent requests each see their own value. Set the trace id into it once when a request starts and every line logged during that request picks it up — including google_adk’s own lines, which is the point.
  • The trace value must be the full resource name, projects/<project>/traces/<32-hex>. A bare trace id is silently ignored.
  • To place a log line under a span in Trace you also need logging.googleapis.com/spanId. Page 23 covers the handler that fills both in for you.

  • Why the native deploy loses your format: logging.basicConfig does nothing if the root logger already has handlers. What has to be true to see a trace

ADK opens spans on every turn regardless of configuration. Whether they are kept, and where they go, are two further switches you do not write any agent code for.

Example — where the traces are

Running adk web: open the Trace tab and the tree is there, with no flag. Restart the server and the history is gone.

Deployed with --otel_to_cloud: the same tree in Cloud Trace, and it persists.

Running a script that calls Runner directly: no trace anywhere. The agent answers normally; the spans are created and thrown away.

Takeaway: if you see no trace, the usual cause is that nothing installed a tracer provider — not that the agent is missing instrumentation.
Sources: cli/api_server.py:1188-1196 (adk web installs a provider and two in-memory exporters), :650-666 (the flag’s branch) · no-provider check on google-adk 2.9.0 (2026-09-12) · ADK: Cloud Trace.
Speaker notes — What has to be true to see a trace
  • Tracer provider is the OpenTelemetry object that decides whether a span is recorded and what happens to it afterwards. Without one installed globally, the OTel API hands back a no-op span: the calls succeed, nothing is stored. Verified on 2.9.0 — a real turn with no provider yields a NonRecordingSpan with an all-zero trace id.
  • How the exporter gets configured: --otel_to_cloud makes adk api_server call get_gcp_exporters(), which builds OTLP exporters for traces, metrics and logs pointed at telemetry.googleapis.com, then maybe_set_otel_providers() installs them as the global providers. In a runtime you wrote, those are the two calls you make yourself — page 18.
  • Why adk web works with no flag: it unconditionally installs a provider with two in-memory exporters, one of which backs the Trace tab. That is a development convenience, and it is why “it traced on my laptop” does not predict what a deployment does.

Finding where the time went

A turn took 11 seconds. The waterfall shows which part of it to look at — and the answer here is not the model.

Compare each span to its siblings, not to the total. Here 7.2 of 11 seconds is one tool.

Two model calls per tool-using turn is normal — ask, then phrase. That is not the anomaly to hunt for.

Count the tool spans. The same tool appearing three times in one turn usually means the model is retrying something that returned an unhelpful result.

A failed tool in a green trace

A tool that returns {"status": "error"} leaves no mark on the trace. Every span is green, and the user was told there is no data.

ADK cannot tell that your dict means failure. {"status": "error"} is an ordinary return value; the convention is yours, not the framework’s.

So it asks the tool class. Every tool has a _detect_error_in_response method; FunctionTool’s returns None, meaning “not an error,” for every response.

Override it to return a short string for your failure shape. That string becomes error.type and turns the span red.

After overriding: filter on error.type="lookup_failed", group by hour, and read the failing city off each tool span.

Speaker notes — A failed tool in a green trace
  • The three bullets in one sentence: a returned error dict is just data, so ADK asks the tool class whether it counts as a failure, and the default answer is always no.
  • Bullet 1 — there is no universal failure convention. Your tool might return {"status": "error"}, another might return {"ok": false}, a third might return an empty list. ADK cannot guess, so it does not try.
  • Bullet 2 — the hook is the escape hatch. BaseTool._detect_error_in_response(response) is called after every tool returns; a string return marks the span ERROR with that string as error.type, and None leaves it alone. FunctionTool inherits the do-nothing version.
  • Bullet 3 — the override is a subclass with one method, about ten lines: check the shape your tools use, return a short stable identifier like "lookup_failed", else None. Use identifiers you would group by, not sentences.
  • Why the parents stay green even after the override: the turn completed and the user got a reply. “I do not have data for that city” is a successful invocation containing a failed step. That is correct, and it is exactly why page 28 needs a separate counter for whether the task was accomplished.
  • If asked about raising instead: an exception propagates and fails the whole turn, so the user gets an error rather than a graceful answer. Most teams want the graceful answer and the red span, which is what the override gives.

The exporter packages

Two things Agent Engine does differently

The same agent code produces slightly different telemetry there, and neither difference is something you configure.

The root span is named invoke_workflow {name}, not invocation. Agent Engine sets GOOGLE_CLOUD_AGENT_ENGINE_ID, which selects telemetry schema v2; every other runtime defaults to v1.

Metrics are flushed when a request ends, not on a background timer.

Why: the runtime throttles CPU the moment a response finishes, so a periodic exporter’s thread would only run while a request happened to be in flight. ADK installs a request-driven reader instead.

Spans carry service.name = <engine id> and cloud.platform = gcp.agent_engine on the resource — that is how you find them.

Joining logs to spans

The tool span is red. Its Logs & Events tab is empty. The warning your tool wrote is sitting in the console with nothing tying it to that span.

Two fields do the joining: logging.googleapis.com/trace (the full name projects/<project>/traces/<32-hex>) and logging.googleapis.com/spanId (16 hex). Trace shows a log under a span when the entry carries both.

ADK’s gen_ai.* events already carry them, because they are emitted through OpenTelemetry, which knows the active span.

Your logger.warning() calls do not. Python’s logging knows nothing about OpenTelemetry, so the fields are simply absent.

LoggingHandler is the piece that bridges them — a handler that reads the active span at the moment you log and writes both fields onto the entry. ADK ships none; you install it. One on the root logger covers every stream, the framework’s included.

Speaker notes — What ADK measures without any code from you

histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (
    rate({"gen_ai.invoke_agent.duration_bucket"}[5m])))

# model call, one line per model

    rate({"gen_ai.client.operation.duration_bucket"}[5m])))

# tool call, one line per tool
histogram_quantile(0.95, sum by (le, "gen_ai.tool.name") (
    rate({"gen_ai.execute_tool.duration_bucket"}[5m])))
Why the metric name ends in _bucketCloud Monitoring stores each ADK duration histogram as three series: <name>_bucket, <name>_sum and <name>_count. Percentiles are computed from _bucket. If you query the plain name with no suffix, you get an empty result, not an error.

Speaker notes — Which layer is slow
  • Why a percentile and not an average. The average hides the slow tail, and the slow tail is what users complain about. p95 says: one call in twenty is at least this slow. The queries use histogram_quantile(0.95, …); change the number for p50 or p99.
  • Why the bars do not add up. invoke_agent.duration covers the whole turn: in this agent that is two model calls (one to choose the tool, one to write the reply), the tool call between them, and ADK’s own work. On top of that, each bar is a percentile over a different population, and percentiles do not add. Read the bars as “which layer is large,” not as a sum.
  • Agent-specific: the model is an external dependency with its own latency, and tools are further external dependencies nested inside the same request. A three-level breakdown is not something an ordinary web service needs.
  • If asked whether overlapping turns distort each other’s timings: no. Each duration is measured from the span that wraps that one call, not from a shared clock. The tutorial’s deep dive runs the same scenario with turns in parallel and gets the same percentiles.
  • Delivery beat: show the turn number alone and ask what they would do with it. Nothing useful is the right answer; that is what the other two bars are for.

Three ways to count failure, and which one to alert on

In this test run, about half the requests asked for a city the weather tool does not know. Three different measurements describe that same run, and they disagree.

QuestionMeasured howThis run
How many tool calls returned an error?execute_tool.duration values that carry error.type, divided by all tool calls47.6%
How many turns ended in an error?invoke_agent.duration values that carry error.type, divided by all turns0%
How many users did not get the weather they asked for?a counter your own code records: tutorial.weather.requests with an outcome label; outcome="unavailable" divided by all47.6%

Row 2 is zero because every turn finished normally. The tool reported “unknown city,” the model read that and replied “I don’t have data for Atlantis,” and the turn ended. ADK counts that as a completed turn, which it was.

Row 1 tells you a dependency is failing. It does not tell you whether users were affected. If the agent retried, or answered from a second source, the tool error is still counted and the user still got an answer.

Row 3 is the only one that measures what the user experienced. ADK cannot record it, because only your code knows what “the user got an answer” means for your tool. It is one counter you increment in an after_tool_callback, with a label for the outcome.

Example

Actor: Marco, setting up the first alert for the weather agent.

Goal: be paged when users stop getting weather, and not otherwise.

First try, row 2: alert when turn errors exceed 20%. It never fires, not even in this run, where half the users got no weather.

Second try, row 1: alert when tool errors exceed 20%. It fires here, and correctly. But when Priya later adds a backup weather provider, the first tool still errors, the backup answers, users are happy, and the alert still pages him.

What he keeps, row 3: alert when outcome="unavailable" exceeds 20%. It fires only when users did not get an answer, whatever happened inside the turn.

Takeaway: ADK can tell you whether a turn finished. Only your code can tell you whether the user got what they asked for. Put the alert on that.
Sources: metrics tutorial 3.7, unknown-city scenario, 40 turns (captured 2026-09-12) · queries/errors.promql, queries/outcome.promql, queries/alert-policy.json.
Speaker notes — Three ways to count failure
  • Connect this to page 17. There, a failed tool inside a completed turn left every span green. This is the same situation seen as numbers instead of as a trace: the turn-level measure reports nothing wrong, because nothing went wrong with the turn.
  • Why rows 1 and 3 show the same number here. Every turn in this run called the tool exactly once and there was no retry or fallback, so a failed tool call and an unanswered user were the same event. In a real agent with retries or a second data source they come apart, and the gap between them is exactly the thing row 1 cannot see.
  • How the counter is written. An after_tool_callback receives the tool’s return value. The callback maps the tool’s own status field to an outcome label (ok, unavailable, and so on) and adds one to the counter. It is a lookup on a field the tool returned, not anything parsed out of the model’s reply text. That keeps it a metric rather than an evaluation.
  • The alert policy shape, if anyone wants to see one: a Cloud Monitoring policy with a conditionPrometheusQueryLanguage condition. The threshold is written inside the PromQL (… > 0.2) and the policy carries a duration of 300s, meaning the condition must hold for five minutes before it fires.
  • One naming trap. The counter appears in Cloud Monitoring as tutorial.weather.requests, with no _total suffix. Prometheus convention adds _total to counters, and Cloud Monitoring adds _count and _sum to histograms, but this counter gets neither. Querying the _total form returns an empty result and no error.
  • If asked whether to alert on both: yes, at different severities. A rising tool error rate is a ticket for whoever owns the dependency. Users not getting answers is the page.

Input tokens grow as a conversation gets longer

The model has no memory between calls, so ADK sends the whole conversation so far with every request. The later in a conversation a model call happens, the more input tokens it costs.

To draw this chart: Monitoring → Metrics Explorer → <> PromQL, paste, set the time range to cover the conversation, Run query

# tokens per model call, one line for input and one for output
sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_sum"}[1m]))
  / sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_count"}[1m]))

Why input grows: the request for turn 20 contains turns 1 to 19 plus the new message. Every earlier turn is sent again.

Why output stays flat: each reply is about the same length, so output tokens per call barely change.

Why it matters: you pay per token, and input is most of the bill. This conversation used 72,308 input tokens against 1,735 output.

How to see it: chart input tokens per model call over a short window, as above. The average for the whole day is one flat number and hides the climb.

Cost per conversation or per user is not available as a metric, because conversation and user ids cannot be metric labels. That is a BigQuery question, using the rows from page 11.

Speaker notes — Input tokens grow as a conversation gets longer
  • Agent-specific: per-token cost grows with context. This is a property of how the agent loop works, not of how much traffic you receive. Two users sending the same number of messages can cost very different amounts depending on how long their conversations run.
  • The query on the slide divides tokens by model calls over each one-minute window, and grouping by token type is what produces two lines from one query. Metrics Explorer runs it as a range query and draws it; no other setup. The dashed average line is not something the Console adds; it is on the slide to make the point. The [1m] window matters: the tutorial’s dashboard uses [5m], which smooths the climb.
  • Hand off to Module 6 explicitly. Limiting the history sent per call, summarizing older turns, and caching are all cost-management choices, not observability ones. This page only shows the curve.
  • Two different output-token numbers, if the room is engaged. In the Agent Runtime capture, ADK’s call_llm span reported output_tokens=69 including 48 reasoning tokens, while the generate_content span for the same call reported 21. ADK counts reasoning tokens as output; the Gemini client instrumentation does not. Know which one your dashboard is reading.
  • These are tokens, not dollars. Multiply by the model’s price per token. Whether any of the input was served from cache is not in this metric; it is in the BigQuery rows.

Seven stable gen_ai.* instruments, sixteen adk.experimental.* — the prefix is a promise about the name, not a feature switch.

Check the grain before dividing by count: token.usage counts model calls, not turns.

One percentile at three grains names the layer that owns a slowdown — turn, model, tool.
