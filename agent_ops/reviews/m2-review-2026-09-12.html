Assessment

The deck has a useful technical foundation and concrete examples, especially the distinction between an evaluation score and an enforced CI gate. It needs corrections before learners can implement the central workflow reliably.

The highest priorities are to supply the executable gate, correct how failed conversations become regression cases, and explain the checks that protect the final merge. The largest instructional opportunity is to simplify deployment configuration for live delivery while retaining the detailed material as a reference.

This review does not recommend a wholesale rewrite. Keep the behavior-change scenarios, explicit version baseline, separation of deployment tools from hosting targets, and attention to content capture.

What to keep

  • The page 6 exit-code demonstration. Independently reproduced with ADK 2.9.0: the same failed case returned 0 through the CLI and 1 through pytest. This is the strongest worked mechanism in the deck.
  • The page 9 scaffold investigation. Inspection of the installed 1.5.0 package confirmed 24 pipeline YAML files with no “eval” occurrence, and the sample integration test checks for text rather than answer correctness. Keep the evidence, with the scope corrections in F01 and F05.
  • The session-service explanation on page 13. The tagged deployer writes the engine URI into the generated command, and managed sessions are not inherently restricted to an agent hosted on Agent Runtime.
  • The separation of export from captured content on page 14. The version-specific ADK default and AdkApp override deserve preservation. The source supports the special wrapper path; it should not be discarded based on generic tracing guidance. Simplify the presentation and correct literal settings.
  • Examples, consequence-oriented teaching, and version dates. These provide a stronger basis for decisions than a product-name tour. Keep them while replacing guarantees with conditions learners can verify.

F01P1Technical + instruction• Confirmed

Show the missing executable evaluation test

p. 6 · p. 8 · p. 9 · p. 16

“that is the one edit to make on day one”
Finding and impact
Page 9 correctly finds no evaluation step in the scaffold, but the proposed fix is incomplete. The 1.5.0 scaffold’s tests/eval contains a dataset, eval_config.yaml, and response_quality.py, not a pytest test that invokes AgentEvaluator. Its dataset belongs to the Agents CLI workflow. Running pytest on the copied scaffold evaluator collected no tests and exited 5. Page 8 even warns that the two formats are incompatible, but the workflow never bridges that difference.
Recommendation
Choose one complete path. For ADK, add an ADK eval set, a threshold config, and a discoverable test_*.py that awaits AgentEvaluator.evaluate; include the evaluation dependencies and pytest-asyncio. Alternatively, retain the scaffold’s Agents CLI dataset and add an explicit results checker. Show the small test wrapper on the face and link the complete example.
Acceptance check
A fresh project collects at least one eval test. A deliberately bad response fails with a score assertion; a corrected response passes. Neither missing tests nor missing dependencies count as a working behavioral gate.

Evidence: Agents CLI 1.5.0 package · ADK 2.9.0: AgentEvaluator · pytest exit codes.

F02P1Technical + instruction• Confirmed

Correct the expected answer before saving a regression case

p. 8

“she reproduces it in adk web, saves the session into the eval set with one click, then runs pytest tests/eval to confirm it fails”
Finding and impact
The save-session route converts recorded events into eval invocations. It does not infer the correct behavior from a bug report. Saving the bad answer or wrong tool trajectory unchanged can make that behavior the reference, so repeating the bug may pass a reference-based metric. The example skips the step that makes the case a useful regression test.
Recommendation
Teach: reproduce the input; capture the session; replace the reference answer and expected tool calls with reviewed correct behavior (or capture a verified correct interaction); then demonstrate red before the fix and green after it. Preserve relevant initial state and remove customer data before committing the case.
Acceptance check
The unchanged broken agent fails against a human-checked expectation. The case does not reward the originally recorded failure.

Evidence: ADK 2.9.0: session-to-eval conversion · Google Codelab: capture golden interactions.

F03P1Technical + instruction• Confirmed

Complete the merge-gate mechanism

p. 4 · p. 7 · p. 9 · p. 10 · p. 22

“the PR trigger already evaluates the merge result for free”
Finding and impact
The default GitHub pull-request checkout does test a synthetic merge with the base branch. It does not include an unrelated, still-unmerged branch. The Marco/Priya example needs Marco’s change in main first. A failing job also blocks merging only when required checks are configured. Under loose checks, a previous pass can become stale after main changes. The notes’ merge-queue claim omits the additional trigger.
Recommendation
Draw the sequence explicitly: Marco merges; Priya’s check runs against updated main; the eval fails. Require the eval check and use up-to-date checks or a merge queue. For GitHub Actions queues, add merge_group. Scope the default-checkout statement to the shown GitHub workflow; verify Cloud Build’s resolved revision for its particular connection/trigger instead of claiming every PR system works identically.
Acceptance check
The walkthrough identifies the tested commit, required check, and behavior when main advances. Both the PR event and queue event run the gate when a queue is used.

Evidence: GitHub: pull_request event · GitHub: required status checks · GitHub: configuring CI for merge queues.

F04P2Technical + instruction• Internal inconsistency

Use one consistent evaluation cadence and format story

p. 4 · p. 7 · p. 8 · p. 10

“in the loop, on push, on the pull request”
Finding and impact
The page 10 recap contradicts pages 4 and 7, which teach on-demand local checks, a PR gate, and an optional nightly/weekly suite. Page 7 says every tier needs a gate, while page 4 says the local run has no gate. Page 7 also promises the same format across tiers but uses Agents CLI for the scheduled example, while page 8 recommends ADK locally and says those formats are not interchangeable. The illustrative case counts appear as unqualified sizes in the table.
Recommendation
Use local feedback, PR blocking checks, and optional scheduled monitoring consistently. Call the sizes workload-dependent examples on the table itself. Keep one evaluation stack across the worked example, or name the format conversion and threshold checker required for the alternative. Give a scheduled failure an owner and response, rather than describing it as a merge gate.
Acceptance check
A learner can state when each suite runs, what it blocks or alerts on, and which dataset format it consumes without reconciling contradictory pages.

Evidence: deck face and notes at the linked pages; module brief and course format where applicable.

F05P2Technical + instruction• Confirmed

Describe the sample tests without redefining all testing

p. 4 · p. 5 · p. 10

“Unit and integration tests tell you the agent ran. Only the eval tells you what it decided.”
Finding and impact
The scaffolded integration test really checks only that an event contains text. That is evidence about this test, not a limit of integration testing. Integration tests can assert correct outputs or tool calls, and evaluation can run inside unit/integration test harnesses, as page 6 demonstrates. A source change can affect behavior even when application control flow is unchanged. The current contrast teaches mutually exclusive categories that do not hold.
Recommendation
Label the rows as the checks in this sample project. Compare what executes, whether the model is real or mocked, and what the assertion measures. Use: “These smoke tests do not assert behavioral quality; add task and trajectory checks.” Retain the concrete sky-blue example.
Acceptance check
The learner distinguishes test scope, model execution, and quality criteria, and understands why an eval can be a pytest test.

Evidence: ADK: why and how to evaluate · ADK 2.9.0: AgentEvaluator.

F06P2Technical• Confirmed

Use exact telemetry settings and distinguish their roles

p. 14 · p. 17

“ENABLE_TELEMETRY=true in ./app/.env turns the flag on the same way”
Finding and impact
The literal variable read by the deployer is GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY. The shortened ENABLE_TELEMETRY is not interchangeable when copied into a file. The page also calls three settings content variables, although the semconv opt-in selects a schema, and its “Neither variable” explanation does not describe event capture accurately. “./app/.env only” is stronger than the code: a deprecated --env_file and config environment values also exist.
Recommendation
Show the full variable name in every copyable setting. Organize the explanation into export, legacy ADK span content, GenAI content placement, and schema selection. Say “recommended .env path” rather than “only.” Keep the AdkApp override qualification scoped to this pinned native deployment path; do not flatten it into a platform-wide impossibility.
Acceptance check
A reader can copy each literal correctly and predict which setting enables export, which includes content, and which changes the schema.

Evidence: ADK 2.9.0: Agent Runtime deployment · ADK 2.9.0: telemetry content controls · ADK 2.9.0: AdkApp integration.

F07P2Technical• Confirmed

Correct when secrets resolve and who needs access

p. 15 · p. 21

“resolves the Secret Manager version at deploy time into an environment variable”
Finding and impact
On the Cloud Run path, Agents CLI translates the secret specification into gcloud --update-secrets. Cloud Run retrieves an environment secret before an instance starts; deployment checks the service identity’s access. The CLI is not reading the plaintext into a normal deployment variable. This distinction changes how learners reason about permissions, rotation, and startup failure.
Recommendation
Separate reference configuration at deployment from value retrieval at instance startup. Show the runtime identity’s Secret Accessor permission and retain the pinned version example. For Agent Runtime, state its own reference/resolution behavior with a target-specific source instead of inheriting the Cloud Run description.
Acceptance check
The learner can explain why a new instance may fail after secret access is revoked and why a numbered secret version makes startup reproducible.

Evidence: Agents CLI 1.5.0 package · Cloud Run: secret resolution and identity.

F08P2Technical• Confirmed

Separate image tags, image digests, and revision names

p. 16 · p. 17 · p. 21 · p. 22

“tag with $COMMIT_SHA, so the revision names its own commit”
Finding and impact
A commit image tag does not set the Cloud Run revision name. Cloud Run assigns a suffix unless one is supplied, and it resolves the image tag to a digest when creating the revision. The deck repeats the naming claim four times. The underlying advice to retain source provenance is useful, but the promised output of gcloud run revisions list does not follow from tagging alone.
Recommendation
Record commit-to-image-digest provenance and promote that digest. If the visible revision name should contain the commit, use a valid revision suffix, such as --revision-suffix=sha-$SHORT_SHA, or appropriate revision metadata. Keep service.version for application telemetry, qualified as a resource attribute on spans emitted through the configured provider.
Acceptance check
An example distinguishes the Git commit, container digest, revision name, and telemetry version and shows how to navigate between them.

Evidence: Cloud Run: revision names and management · Cloud Run: image tags resolve to digests.

F09P2Technical• Confirmed

Distinguish inventory, enforcement, and dependency pinning

p. 20

“consume tools through a registered server rather than an arbitrary URL, so access is governed and revocable”
Finding and impact
The face implies registration itself enforces runtime access and pins the consumed tool surface. Agent Gateway uses registry metadata together with identities and configured policies to enforce access; a catalog entry alone is not the whole mechanism. The notes mention this distinction, but the main claim omits it. An eval detects covered behavioral changes, not every description change, and it is not the only possible detector.
Recommendation
Put a short mechanism on the face: registry records owner/endpoint; an enforced gateway or server policy authorizes calls; a versioned endpoint or approved tool-schema snapshot controls the dependency. Pair schema/description diffs with scheduled behavioral evals. Qualify detection by test coverage and client refresh behavior.
Acceptance check
The learner can name what lists a tool, what authorizes a call, what pins a version, and what detects a change.

Evidence: Agent Registry overview · Agent Gateway: runtime enforcement and policies.

F10P2Technical + instruction• Confirmed

Align the worked pipeline with the workflow already taught

p. 4 · p. 9 · p. 12 · p. 16

“Building a container image is a release step, not a per-commit one.”
Finding and impact
Page 4 presents an ordering preference as a rule. Page 16 then builds before evaluating and does not specify whether this is a PR job or post-merge release. Its eval executes source in a separate Python image, so it does not prove the deployed container starts or behaves correctly. The “same container either way” takeaway on page 12 also hides differences in generated Dockerfiles, dependencies, and entrypoints.
Recommendation
Label page 16 as a post-merge release example and show the PR gate separately. Say source evals can run before an image exists; container builds/tests may also run in CI. Preserve a smoke/integration check of the built image or staging deployment, then promote the tested digest. Put trigger-only $COMMIT_SHA, prerequisites, target identity, and cross-project access assumptions beside the example or in a linked runnable file.
Acceptance check
The diagram and YAML agree on trigger, tested source, tested artifact, and deployment destination. A packaging failure is caught before production.

Evidence: Cloud Run: image tags resolve to digests · GitHub: pull_request event.

F11P2Technical + instruction• Overstatement

Turn the troubleshooting table into evidence-based decisions

p. 15 · p. 22

“raise --memory whenever you raise --concurrency”
Finding and impact
Concurrency can increase memory use, but it does not require a memory increase on every change. An agent does not necessarily populate its full context-window capacity, and memory also depends on tools, buffers, artifacts, and sandbox workloads. “Logs end mid-request” does not uniquely diagnose OOM. Other consequence rows similarly turn possible explanations, such as a model alias change or vague tool description, into proven causes.
Recommendation
Teach an estimate based on measured incremental memory per active request and available headroom. Verify an OOM termination reason and peak memory before reducing concurrency or increasing memory. Change the consequence columns to “Possible cause / Check / Action,” or make each row a diagnosed scenario with its evidence stated.
Acceptance check
The recommendation follows an observed cause and a load test; it does not prescribe extra memory or prompt edits for every similar symptom.

Evidence: Cloud Run sandboxes.

F12P2Technical• Confirmed

Qualify the controls for behavioral variability

p. 5 · p. 19 · p. 22

“The fixes are temperature=0, rubric-based metrics, or several samples”
Finding and impact
Temperature zero does not guarantee deterministic results, and a rubric alone does not eliminate judge noise. Pinning a stable model id reduces alias-driven upgrades but does not guarantee all behavior changes happen only when the application changes. The model-selection setting is also not an input the model itself reads, as page 2’s fourth objective and page 18 imply. Instructions, retrieved content, state, and tool results affect decisions too.
Recommendation
Keep production generation settings in evaluations, use repeated runs and a documented treatment of borderline failures, and record agent/judge/model versions. State the narrower benefit of a stable model id. Label gemini-flash-latest as a Gemini API example and verify an exact supported id for the course’s backend. Reframe section 3 as governing model and tool dependencies.
Acceptance check
The learner understands what pinning and sampling control, and what variability remains. A model upgrade still includes evaluation and retirement planning.

Evidence: Gemini: generation parameters · Gemini API: stable and latest model names.

F15P2Technical• Confirmed

Qualify vulnerability scanning as an enabled service

p. 21

“Stores the built image; scans it for vulnerabilities on push.”
Finding and impact
Artifact Registry stores the image. Automatic vulnerability scanning is provided by Artifact Analysis through the Container Scanning API, with repository scanning settings. Merely pushing to an Artifact Registry repository does not establish that scanning is enabled, and a scan result is not itself a release gate.
Recommendation
Use: “Stores images; Artifact Analysis scans supported images on push when scanning is enabled.” If a pipeline claim depends on the scan, show the separate policy/check that decides whether the image can be promoted.
Acceptance check
The tour does not imply that repository creation alone provides vulnerability assessment or blocks deployment.

A workable 35-minute teaching plan

This is a proposed delivery allocation, not a measured rehearsal. It retains the brief’s two focus areas and makes room for learners to apply them.

Two short checks with answer criteria

Gate repair, about 90 seconds. Give learners a job that only runs adk eval and a folder with a dataset but no test. Ask what must change. A complete answer names the chosen format, executable grader/assertion, threshold, non-zero failure, and required PR status check. Show the red/green result.

Deployment decision, about 90 seconds. Give a team a company-domain/WAF requirement, managed sessions, and a policy to omit prompt content from telemetry. Ask for the target, endpoint infrastructure, session URI and access, full capture settings, and one verification step. Discuss why selecting a runtime does not by itself configure every surrounding service.

Revision order: fix F01–F03 first; reconcile the technical claims and recaps; then reduce live-slide density. Add practice by moving reference detail, not by increasing the 35-minute budget.

Reproduced gate evidence and the missing wrapper

The bad agent always returned “I cannot help with that.” The eval expected “Your refund is issued.” The config used {"criteria": {"response_match_score": 0.9}}.

adk eval app simple.evalset.json --config_file_path test_config.json
Tests passed: 0
Tests failed: 1
Process exit: 0

pytest test_evals.py
AssertionError: Following are all the test failures.
response_match_score for app Failed. Expected 0.9, but got 0.0.
Process exit: 1

The existing one-case reproduction was copied into a separate temporary directory and re-run. Its wrapper, shown here as the missing teaching bridge, was:

import pathlib
import pytest
from google.adk.evaluation.agent_evaluator import AgentEvaluator

HERE = pathlib.Path(__file__).parent

@pytest.mark.asyncio
async def test_refund_evalset():
    await AgentEvaluator.evaluate(
        agent_module="app",
        eval_dataset_file_path_or_dir=str(HERE / "simple.evalset.json"),
    )

This assumes an importable app module, the ADK-format eval file, and test_config.json beside it. It is not a drop-in consumer for the scaffold’s Agents CLI dataset.
