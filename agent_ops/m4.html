What gets graded

A recorded conversation, a metric that reads it, a score, a threshold, and the program that turns a low score into a failed build.
Speaker notes — Section 1 divider
  • The question this section answers: what does an eval grade that the tests the room already runs cannot, and how does a low score stop a merge?

A test checks execution. An eval grades the decision.

A developer edits one clause of a refund agent’s instruction. Every unit test passes. The agent now refunds orders without checking that they shipped.

A unit test checks that the agent runs. It sends an input and checks that the agent returns a response with no error. It does not judge whether the response is good, and it does not compare the response with an exact expected text, because a model can word the same answer differently on each run. The edit changed no code path, so the agent still runs and still responds, and the test passes.

An eval grades the quality of that run. It runs the agent on a recorded input and grades the reply and the trajectory, which is the list of tool calls with their arguments, in order.

Two properties of agents make this necessary. The same input can produce a different trajectory on another run, and correctness has several parts at once: the path, the answer, safety, grounding (whether each claim is backed by the tool results or the instruction).

The instruction, the tool definitions, and the model id are code too. They live in the repo and change in a reviewed diff. A unit test cannot show that such a diff made the agent worse; running the eval set can.

Example

Actor: the developer who edited the instruction.

Input: “refund order 6041”, run before and after the edit.

Unit test: checks that the agent returned a response and raised no error. It passes both times.

Eval: the expected calls are get_order, verify_shipment, issue_refund. After the edit the agent skips verify_shipment, so tool_trajectory_avg_score scores the run 0.0 and the case fails.

Takeaway: a unit test shows that the agent ran and returned a response. An eval grades whether it did the right thing, so grade the tool calls as well as the reply.
Sources: adk.dev/evaluate · trajectory_evaluator.py, google-adk 2.11.0 (tested 2026-10-07).

Choose which model the agent will use

Before writing an agent, a team has to choose which model it will use. They have two candidate models and a handful of prompts that look like the traffic the agent will get. Model evaluation runs both models on the same prompts and scores the answers.

Score two candidate models on the same prompts (aiplatform 2.4.0)

from agentplatform import Client, types
client = Client(project=PROJECT, location="global")

# prompts: a DataFrame with a "prompt" column
flash = client.evals.run_inference(src=prompts, model="gemini-3.5-flash")
pro   = client.evals.run_inference(src=prompts, model="gemini-3.1-pro-preview")

result = client.evals.evaluate(
    dataset=[flash, pro],
    metrics=[types.RubricMetric.TEXT_QUALITY,
             types.RubricMetric.INSTRUCTION_FOLLOWING])
result.show()

run_inference generates one response set per model; evaluate scores them. Given a list of datasets, it scores each one and reports, per metric, how often each candidate won and how often they tied.

Scoring each model on its own is pointwise; given both result sets, evaluate then reports how often each model won. A pairwise judge, which compares two answers directly, is only in the older vertexai.evaluation module.

After you choose, you evaluate the agent, not the model. The agent’s code names the chosen model id. To try a different model later, change that id in a reviewed diff and run the agent’s eval set against the change.

Example (measured 2026-10-07)

Input: three short customer-reply prompts, run with the code above.

Result: text quality: the Pro preview won one prompt, two tied. Instruction following: all three tied.

What it means: this result does not pick a model. One win in three prompts could change on the next run, so run the comparison on more prompts, and choose a model only if the same one wins when you run the comparison again.

GenericModel selection is not agent-specific. It is here because this is where model evaluation fits: before the agent exists.
Takeaway: evaluate models to choose one; after that, evaluate the agent.
Sources: Gen AI evaluation overview · agentplatform/_genai/evals.py (run_inference, evaluate), google-cloud-aiplatform 2.4.0 · run end to end 2026-10-07.

An eval case is a recorded conversation with the right answer in it

A support team’s orders agent should check an order’s status before cancelling it. To grade that, they write down one conversation and what the agent should have done in it.

orders.test.json — one eval set, one case, one turn

{
  "eval_set_id": "orders",
  "eval_cases": [{
    "eval_id": "cancel_7732",
    "conversation": [{
      "user_content":   {"role": "user",  "parts": [{"text": "Cancel order 7732."}]},
      "final_response": {"role": "model", "parts": [{"text": "Order 7732 is cancelled."}]},
      "intermediate_data": {
        "tool_uses": [
          {"name": "get_order",    "args": {"order_id": 7732}},
          {"name": "cancel_order", "args": {"order_id": 7732}}
        ]}
    }],
    "session_input": {"app_name": "orders_agent", "user_id": "test_user", "state": {}}
  }]
}

One entry in conversation is an invocation: one user message, the tool calls it triggered, and the agent’s reply. A case is a whole conversation of one or more invocations.

Each invocation can carry the expected reply (final_response) and the expected tool calls (tool_uses). Each metric reads the fields it needs. session_input sets the app name, user id, and starting session state for the run.

Reference-based metrics compare the run with an answer written here. Reference-free metrics judge the run on its own (safe? grounded? met a list of yes/no rules (rubrics, p12)?), so their cases need no expected reply or tool list.

The file is code. It lives in the repo, and a change to an expected answer is a reviewed diff.

Example

Input: the case above, run against the orders agent.

Mechanism: the trajectory metric compares the agent’s calls with tool_uses; a reply metric compares its reply with final_response; a safety metric reads only the prompt and the reply.

Result: one file feeds all three. Delete tool_uses and only the trajectory metric can no longer run.

Takeaway: a case records a conversation and its right answer. Reference-based metrics need that answer; reference-free ones do not.
Sources: eval_case.py (Invocation), google-adk 2.11.0 · adk.dev/evaluate · criteria (Reference-Based column). File parsed as an EvalSet at 2.11.0, 2026-10-07.

How a trajectory becomes a number

A helpdesk agent answers two messages in one conversation. In the second, it closes ticket 519 without looking the ticket up first.

Each invocation scores 1.0 or 0.0: its whole list of calls matches the expected list, or it does not. The case’s score is the mean over its invocations.

With no test_config.json (the file beside the eval set that names criteria and thresholds, p10), ADK’s default threshold for this metric is 1.0, so every invocation must match. A config file sets your own threshold.

match_type sets what counts as a match: EXACT (the default: same calls, same order, nothing extra), IN_ORDER (expected calls in order, extra calls allowed between them), ANY_ORDER (expected calls in any order, extras allowed).

It reads tool names and arguments only, not what the tool returned. A call that returned an error still matches.

Example

Input: the same case, but in invocation 2 the agent calls get_ticket(519), then an extra get_user, then close_ticket(519).

Result: under EXACT invocation 2 scores 0.0 and the case 0.5, FAILED. Under IN_ORDER it scores 1.0 and the case passes.

Averaging stays inside one caseADK never averages separate eval cases together; each case passes or fails on its own score.
Takeaway: a case passes this metric only if every invocation’s calls match. Use IN_ORDER when helper calls may vary.
Sources: trajectory_evaluator.py, eval_metrics.py (match types), eval_config.py (default config), google-adk 2.11.0 · every score on this page computed with TrajectoryEvaluator, 2026-10-07.

Grading the answer: shared words, or a judge

A billing agent’s case expects the reply “Your refund of $42 has been issued.” Two runs come back with different wording. One is right, one is wrong.

ReplyROUGE-1 Fresponse_match_score at 0.8
A (right, reworded): “I have issued your $42 refund.”0.615fail
B (wrong, reuses the words): “Your refund of $42 has been denied.”0.857pass

response_match_score counts shared words. It is the ROUGE-1 F-measure: one score that combines how many of the reply’s words are in the expected reply and how many of the expected reply’s words are in the reply. Each word is first cut to its stem, so ‘issued’ becomes ‘issu’. A reply that reuses the words scores high whatever it means.

A judge is a second model call that grades the first. final_response_match_v2 sends the reply and the expected reply to a judge model and asks whether they mean the same thing. The score is the fraction of invocations judged valid.

The judge is non-deterministic too, so ADK asks it several times and takes a majority vote (page 13).

Test the judge with a reply it must reject. A judge that answers “valid” to everything passes every case; reply B is that test.

Example

Input: the expected reply and replies A and B above.

Mechanism: after stemming, the expected reply has 7 tokens. A shares 4 of them; B shares 6.

Result: word overlap fails the right reply and passes the wrong one. A judge asked “same meaning?” reads “issued” against “denied”, which word overlap cannot.

Takeaway: use response_match_score for short, fixed replies. Where a reply can be worded two ways, use final_response_match_v2, and keep a must-reject case in the set.
Sources: final_response_match_v1.py, final_response_match_v2.py, google-adk 2.11.0 · criteria · ROUGE scores computed with RougeEvaluator (rouge-score 0.1.2), 2026-10-07.

A rubric turns a house rule into a pass rate

A support team’s delay replies must apologize, give the new delivery date, and stay under three sentences. None of that is a reference answer. Each rule becomes a rubric.

test_config.json — three rubrics

{"criteria": {"rubric_based_final_response_quality_v1": {
  "threshold": 0.66,
  "rubrics": [
    {"rubric_id": "apology",
     "rubric_content": {"text_property": "The reply apologizes for the delay."}},
    {"rubric_id": "new_date",
     "rubric_content": {"text_property": "The reply states the new delivery date."}},
    {"rubric_id": "short",
     "rubric_content": {"text_property": "The reply is under three sentences."}}
  ]}}}

A rubric is an id and one statement a judge can answer yes or no. The judge answers each rubric for each invocation; the score is the fraction answered yes.

Rubrics can sit at three levels, and the judge applies all of them together: on the criterion in test_config.json, on an eval case (every invocation), or on one invocation. A repeated rubric_id across levels is an error.

ADK’s three rubric_based_* criteria need at least one rubric; with none, evaluation raises “Rubrics are required.”

Example

Input: a reply that apologizes and gives the new date, in four sentences.

Mechanism: yes, yes, no: 2 of 3. ADK passes a case when score >= threshold.

Result: 0.667 passes at threshold 0.66. At 0.67 the same reply fails, because 0.6666… is below 0.67.

Takeaway: write one rubric per rule you can state, and set the threshold from the number of rubrics you allow to fail.
Sources: eval_rubrics.py, rubric_based_evaluator.py, google-adk 2.11.0 · criteria.

Two scorers, several ways to drive them, two dataset formats

A team meets four names: ADK eval, Gen AI evals, the console’s Evaluation page, and agents-cli. Two of them compute scores; the others drive one of those two.

Two scorers. ADK’s evaluators run in your process; Gen AI evals scores on Google’s side. Both produce real scores. Only the service can read production traces.

Alerting on a quality score

A monitor writes task-success scores to Cloud Monitoring. An ordinary alert policy on that metric opens an incident when the score stays low.

policy.yaml — accepted by gcloud monitoring policies create --policy-from-file

displayName: "Low task success"
combiner: OR
conditions:
- displayName: "Task success < 0.8"
  conditionThreshold:
    filter: >
      metric.type="aiplatform.googleapis.com/online_evaluator/scores"
      AND resource.type="aiplatform.googleapis.com/OnlineEvaluator"
      AND metric.labels.evaluation_metric_name="task_success"
    comparison: COMPARISON_LT
    thresholdValue: 0.8
    duration: 1800s
    aggregations:
    - alignmentPeriod: 60s
      perSeriesAligner: ALIGN_DELTA
      crossSeriesReducer: REDUCE_MEAN

The score metric is a distribution. A monitor run scores many traces. Cloud Monitoring does not store each score as its own number. It stores one point that counts how many scores fell in each range, like a histogram. Each point covers only its own stretch of time (the metric’s kind is DELTA).

A time series is one stream of points for one set of labels, such as one agent and one evaluation_metric_name. Alignment puts a series on a regular clock: it cuts the series into equal blocks of time and makes one value per block, so that the policy can compare it with a threshold and combine it with other series.

LineWhat it doesWhy here
alignmentPeriod: 60scuts each series into 60-second blocksrequired with an aligner; 60 s is the minimum
perSeriesAligner: ALIGN_DELTAmakes one value per block: what the metric recorded in that blockvalid for DELTA metrics, and the value stays a distribution
perSeriesAligner: ALIGN_MEAN (the docs’ sample)would average the numbers in each blockrejected: “cannot be applied to metrics with kind DELTA and value type DISTRIBUTION”. It accepts only numeric values, and a point here is a set of counts, not a number
crossSeriesReducer: REDUCE_MEANcombines every series the filter matches into one line, with a mean for each blockaccepts distributions and outputs a plain number, which is what the policy compares with 0.8
If…Then
every point stays under 0.8 for 1800 s, such as 0.74, 0.77, 0.72, 0.75 from four consecutive runsan incident opens, labeled with the monitor; the monitor’s Sampled traces lead to the failing conversations
one point is 0.8 or higher in that windowthe 1800 s clock restarts

Check the label value before you rely on the alert. The docs’ sample uses task_success, but a safety monitor’s scores carry safety_v1. A value that matches nothing never fires, so copy it from Metrics Explorer.

Two required parts: the filter must name the resource.type, which the docs’ sample leaves out, and the policy needs a combiner. Add a channel with --notification-channels.

The console offers templates: a monitor’s Create alerting policy (one per metric on the monitor), or the dashboard’s Recommended Alerts.

Takeaway: alert on the score with a duration that spans several monitor runs.

Conformance replay: did a code change alter what the agent sends the model?

A developer tidying a weather agent’s code renames a tool and wants to know whether the agent still behaves the same. An eval can’t answer that cleanly: model output varies from run to run, so a different reply could come from the rename or from the model.

Conformance replay removes that variation. You record one real run of the agent, saving every model request and answer. Later, you run the agent again and supply the model’s answers from the recording. Those answers can’t vary, so if the agent now sends the model something different, your code change caused it.

The three steps for one test, adk conformance, google-adk 2.11.0 (tested 2026-10-31)

# 1. Write the test: tests/weather/paris/spec.yaml
description: Asks for the weather in Paris
agent: weather_agent
user_messages:
  - text: "What's the weather in Paris?"

# 2. Record: start the agent's local server with the recording plugin
$ adk web --extra_plugins=google.adk.cli.plugins.recordings_plugin.RecordingsPlugin . &
$ adk conformance record tests/weather/paris none
$ ls tests/weather/paris
generated-recordings.yaml  generated-session.yaml  spec.yaml

# 3. Test: restart the server with the replay plugin, then run the test
$ adk web --extra_plugins=google.adk.cli.plugins.replay_plugin.ReplayPlugin . &
$ adk conformance test tests/weather/paris
Running weather/paris... ✓ PASS

You write spec.yaml: which agent to run and what the user says. Each folder is one test. Here, weather_agent is an agent folder in the directory where adk web starts.

record runs the agent for real and calls the model. It sends the spec’s messages to the server, and the plugin saves the run. none means no streaming, and is required; sse records a streaming run instead. ADK writes the two generated- files.

test sends the same messages and calls no model. Each model request must match the recording, and so must each tool call’s name and arguments. The test passed with an invalid project and no credentials.

Your tools still run during test, so their side effects happen: a tool that writes data writes it again. The model is then given the recorded result, not the new one.

Example: the rename (tested 2026-10-31)

Actor: the developer from the top of the page, with the recording above.

Input: get_weather renamed to fetch_weather in the agent’s code, then the server restarted and the test run.

Mechanism: the first model request now declares a tool called fetch_weather, and the recording says get_weather. The model reads tool names, so this is a real change to its input.

Result: ✗ FAIL with ReplayVerificationError: LLM request mismatch in turn 0 for agent 'weather_agent'. “LLM request” is ADK’s name for the model request, and turn 0 is the first user message. No model was called and the tool did not run.

Next: the rename was intended, so the developer reruns step 2 with the recording plugin. The new recording replaces the old one and the test passes again.

What the result does not tell youA FAIL means the request changed, not that the agent got worse. A PASS means the requests did not change, not that the answers are good or that the tools still work. Judging quality is the eval’s job, and a tool’s own logic needs its own unit tests. Generic: record and replay is a common testing technique; what is specific here is that the recorded dependency is the model.
Takeaway: after one recording, replay checks with no model calls whether a code change altered the agent’s model requests or tool calls; use an eval to judge whether a change is good.

User simulation

Since ADK 1.18.0. A ConversationScenario (starting_prompt, conversation_plan) drives a model playing the user; personas (EXPERT, NOVICE, EVALUATOR) since 1.26.0. Reference-free criteria only. Example: a NOVICE user cannot correct the agent, so a wrong refund amount goes unchallenged.

Environment simulation (experimental)

Since 1.24.0. Mock a tool, or inject errors and latency (up to 120 s) with a probability per injection. Example: a 503 injected on a check_stock tool; a rubric expects the agent to say it could not check stock.

adk optimize (experimental)

Since 1.24.0. GEPA, a prompt-search method that proposes and tests rewritten instructions, rewrites the root agent’s instruction against a training eval set and reports validation scores. It does not change sub-agents.

Custom metrics

Since 1.18.0. A Python function taking the metric, the actual and expected invocations, and the scenario, returning an EvaluationResult; listed under custom_metrics with code_config.name. Example: the refund amount in the reply equals the amount the tool returned.

Takeaway: user simulation and custom metrics go in the eval set and config you already have; environment simulation wraps the agent; adk optimize is a separate command.
