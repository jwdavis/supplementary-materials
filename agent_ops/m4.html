What gets graded

A recorded conversation, a metric that reads it, a score, and a threshold. Eleven pages, one case: the refund agent and order 6041.
Speaker notes — Section 1 divider
  • Say up front that the section reuses one case throughout, so nobody waits for a new scenario each page.
  • The question this section answers: what does an eval grade that the tests the room already runs cannot?

A test checks execution. An eval grades the decision.

Priya changes one clause of the refund agent’s instruction. Every test passes. The agent now refunds orders that never shipped.

A test checks correct execution of deterministic code. It asserts on a code path. No code path changed here; the instruction is text.

An eval grades the quality of a response and the path the agent took to produce it. The path is the trajectory: which tools, which arguments, in what order.

Two properties of agents make this necessary. The same input can produce a different trajectory on the next run; and correctness has several dimensions at once — trajectory, answer, safety, hallucination.

The instruction, the tool definitions, and the model id are source files. They change in a reviewed diff, and an eval is how that diff gets checked.

Input: “refund order 6041”, before and after the edit.

Mechanism: before, the trajectory is get_order → verify_shipment → issue_refund; after, get_order → issue_refund. The final reply is the same sentence both times.

Result: an answer check passes. A trajectory check scores the second run 0.

Takeaway: an eval replays a recorded conversation and grades what the agent decided. Nothing else in the test suite reads a decision.

Model evaluation happens first, and picks the model

Before the refund agent exists, Marco has to choose a model. That is the one place model evaluation belongs in this module.

Pointwise scores one model’s responses against metrics. Pairwise runs two candidates on the same prompts and reports which one wins.

The Gen AI evaluation service runs either. You give it a set of prompts and the metrics to grade on; it runs each candidate model over the prompts and scores the answers.

After the decision, the model id is a line in the repo. From then on the agent is what gets evaluated, and a model change is a diff the agent eval set catches.

Score two candidate models on the same 30 prompts

from agentplatform import Client, types
client = Client(project=PROJECT, location="us-central1")

# prompts: a DataFrame or dataset with one row per prompt
# step 1: run each candidate over the prompts
flash = client.evals.run_inference(src=prompts, model="gemini-3.5-flash")
pro   = client.evals.run_inference(src=prompts, model="gemini-3.1-pro")

# step 2: score both response sets in one call
result = client.evals.evaluate(
    dataset=[flash, pro],
    metrics=[types.RubricMetric.TEXT_QUALITY,
             types.RubricMetric.INSTRUCTION_FOLLOWING])
result.show()   # per-model averages you compare side by side

An eval case is a recorded conversation with the expected trajectory inside it

Page 5 scored a model’s answer to pick a model. From here on we grade the agent’s decisions — and to do that we record one conversation and say what the agent should have done in it.

refunds.test.json — one eval case, one turn

{
  "eval_set_id": "refunds",
  "eval_cases": [{
    "eval_id": "refund_6041",               // names this case
    "conversation": [{                       // one entry per turn; here, one turn
      "user_content":   {"parts": [{"text": "refund order 6041"}], "role": "user"},
      "final_response": {"parts": [{"text": "Your refund of $42 has been issued."}], "role": "model"},
      "intermediate_data": {
        "tool_uses": [                        // the tools the agent should call, in order
          {"name": "get_order",       "args": {"order_id": 6041}},
          {"name": "verify_shipment", "args": {"order_id": 6041}},
          {"name": "issue_refund",    "args": {"order_id": 6041}}
        ]                                     // order_id 6041 is the same in all three: same order
      }
    }],
    "session_input": {"app_name": "refund_agent", "user_id": "test_user", "state": {}}
  }]
}

A case is a whole conversation. conversation holds one entry per turn; this case has one turn (page 8 has two). Each turn carries the user’s message, the expected reply, and the expected tool calls.

A metric reads whichever of these three it needs: the expected reply (final_response), the expected tool calls (tool_uses), or just the prompt and whatever the agent actually did. Different metrics read different fields.

Reference-based metrics compare the agent to a right answer you wrote here — the reply, or the tool list. Reference-free metrics judge the run on its own (was it safe, was it grounded), so their cases need no expected reply or trajectory.

The file is code. It lives in the repo, and a change to it is a reviewed diff.

Takeaway: a case records a conversation and the right answer for it. A reference-based metric needs that right answer; a reference-free one does not.
Sources: eval_set.py, eval_case.py:84-112, google-adk 2.9.0 · adk.dev/evaluate schema block.
Speaker notes — An eval case is a recorded conversation
  • Vocabulary: one entry in conversation is an invocation — one turn (a user message, the tool calls it triggered, the agent’s reply). A case is the whole session; page 8 uses a two-turn case.
  • Reference-based vs reference-free is the split that decides whether a case needs a hand-written answer. Reference-based: tool_trajectory_avg_score (needs tool_uses), response_match_score and final_response_match_v2 (need final_response). Reference-free: safety_v1, hallucinations_v1, the rubric metrics — they judge the run itself, so a generated case (page 15) with no answer still works with them.
  • The order_id in args is a tool argument, not a call id. Trajectory matching compares name and args only (an ignore_args option relaxes the args check); it does not match on any id.
  • The legacy flat format ([{query, expected_tool_use, reference}]) still loads with a warning; that is page 7. session_input.state pins initial session state — a logged-in user, a cart.

Speaker notes — Test file and evalset: one schema, two suffixes
  • Both files load through _load_eval_set_from_file, which parses EvalSet and, on a parse failure, falls back to the legacy flat list with a warning. So the “old format vs. new format” question is orthogonal to the suffix, and applies to either.
  • Why AgentEvaluator.evaluate scans a folder: pytest points it at a directory, and it walks it for every .test.json so a test can cover a whole folder of cases at once. How a trajectory becomes a number

tool_trajectory_avg_score is the default trajectory metric. Here is what it computes for one two-turn conversation.

Each turn is scored, then averaged into the case. A turn scores 1.0 or 0.0 (its tool calls match the expected list, or they do not). The case’s score for this metric is the mean of its turns: here (1.0 + 0.0) / 2 = 0.5.

The default threshold is 1.0, so every turn must pass. A mean of 0.5 is below 1.0, so the case fails. Lower the threshold only if a partial trajectory should still pass.

match_type decides what counts as a match: EXACT (same calls, same order, nothing extra), IN_ORDER (expected calls present in order, extras allowed), ANY_ORDER.

What it does not see: the metric reads tool names and arguments only, not what the tool returned. A correctly named call that returned an error still scores 1.0.

Averaging is within a case, not across casesThe mean here is over the turns of one conversation. Separate eval cases are not averaged together: the run reports Tests passed / Tests failed as a count of cases, so a passing case and a failing case are one pass and one fail, never a 50% that passes.
Example

Actor: Marco, on the case above.

Mechanism: turn 1 matches: 1.0. Turn 2 skipped verify_shipment: 0.0. Mean 0.5, threshold 1.0.

Result: the case fails. Under IN_ORDER, turn 2 would still fail (a required call is missing) — but a turn with an extra get_customer call inserted between the expected ones would pass, because the three expected calls still appear in order computed from the 2.9.0 code path.

Takeaway: a case passes this metric only if every turn’s trajectory matches. Set IN_ORDER when helper calls may vary, and use a different metric when tool success is the question.
Sources: trajectory_evaluator.py:106-173, agent_evaluator.py:847-858 (mean over turns), eval_metrics.py:193-240, eval_config.py:237-239, google-adk 2.9.0 · criteria.
Speaker notes — How a trajectory becomes a number
  • The one misread to prevent: that the 0.5 average spans separate tests. It does not. Within a case, per-turn scores are meaned (statistics.mean, agent_evaluator.py:854); across cases, results are grouped by eval_id and reported as a pass/fail count (agent_evaluator.py:772).
  • So “threshold 1.0” means every turn in the case must match. A single-turn case is the common shape, and there the mean is just that one turn’s 1.0 or 0.0.
  • Argument comparison is exact: {"order_id": 6041} vs {"order_id": "6041"} is a mismatch. The ignore_args criterion option relaxes this to name-only matching.
  • Field-name note for anyone who saw older material: the metric compares tool_uses (name + args). Names like determine_intent / use_tool are not ADK fields.
  • Production-side, tool success is the outcome counter from Module 3 page 28.

Grading the answer: shared words, or a judge

Both answer metrics compare the agent’s reply against the reference reply in the case (page 6’s final_response). The reference here is “Your refund of $42 has been issued.” Two replies come back; one is right and fails, one is wrong and passes.

Compared against the referenceROUGE-1 Fresponse_match_score @ 0.8final_response_match_v2
reference: “Your refund of $42 has been issued.”—the answer to matchthe answer to match
A (correct, reworded): “I have issued your $42 refund.”0.615failvalid
B (wrong, reuses words): “Your refund of $42 has been denied.”0.857passinvalid

response_match_score counts shared words. ROUGE-1 F-measure between reply and reference: tokens [a-z0-9], Porter-stemmed. Default threshold 0.8. A reply that reuses enough of the reference’s words scores high whatever it means; a correct reply in other words scores low.

final_response_match_v2 asks a judge. The reply and the reference go to a judge model with the question “valid or invalid”; the judge is sampled num_samples times, each invocation is majority-voted, and the score is the fraction of valid invocations.

The judge is a model call with its own non-determinism. That is why it is sampled, and why page 13 shows the cost.

Example

Actor: Priya, choosing an answer metric for the refund agent.

Input: the reference and the two replies above.

Mechanism: reply A shares 4 of the reference’s 7 stemmed tokens; reply B shares 6 of 7.

Result: ROUGE passes the wrong reply and fails the right one. The judge gets both right computed with rouge_score, 2026-09-13.

Takeaway: use response_match_score for short, fixed replies. For anything a person could phrase two ways, use final_response_match_v2.
Sources: final_response_match_v1.py:68-69, 180-199, final_response_match_v2.py:134-136, 196-209, google-adk 2.9.0 · criteria · scratchpad run.
Speaker notes — Grading the answer: shared words, or a judge
  • Generic (text similarity vs. model judgment); say so. The agent-shaped part is that the judge is another non-deterministic model.
  • Ties in the judge’s majority vote count as invalid (aggregate_per_invocation_samples).
  • The judge prompt tells the model to trust the reference for arithmetic and to treat unit changes (miles vs. km) as invalid.
  • Off the face: response_evaluation_score is a third answer metric — the service’s coherence score on a 1–5 scale; it is in page 10’s table.

Speaker notes — The thirteen ADK criteria
  • Reference? yes = the case must carry a hand-written right answer for this metric to compare against: tool_uses for the trajectory metric, final_response for the response-match metrics. no = reference-free, the metric judges the run on its own merits (safe? grounded? met the rubric?), so a case needs no answer.
  • Rubrics? yes = you supply a list of pass/fail statements about the reply or the tool use (page 12), and the score is the fraction that pass. no = the metric has its own fixed scoring and takes no rubrics from you.
  • Judge? yes = the score comes from an LLM reading the output, so it is non-deterministic and is sampled (page 13). no = a deterministic computation (ROUGE word overlap, or exact tool-call matching).
  • Agent-specific: correctness is multi-dimensional, and the five service criteria make the eval itself depend on an external service with regions and quotas.
  • The criteria page on adk.dev lists 13; the overview page says 12 and omits response_evaluation_score. This deck follows the criteria page.
  • Delivery beat: cover the “Runs” column first — it is the one that changes what a CI job needs (a project, a region, a network call).

A rubric is one testable criterion; the score is the fraction that passed

“Under three sentences” is not a reference answer and not a word count the framework knows. It is a rubric.

Shape: an id, a text property the judge can test, and an optional type. Each rubric gets Pass or Fail per invocation; the metric’s score is the fraction that passed.

You write them for ADK’s three rubric_based_* criteria, in test_config.json or on the case (EvalCase.rubrics, additive). An empty effective list raises at evaluation time.

Or the service writes the rubrics for you — its “adaptive” metrics (TOOL_USE_QUALITY, FINAL_RESPONSE_QUALITY…) read your agent’s instruction and tool declarations and turn them into pass/fail rubrics per case, so you write none. Page 20 shows the exact rubrics one produced.

Static metrics (SAFETY, HALLUCINATION) return a single score rather than a pass rate — Safety is binary, 1 for safe and 0 for unsafe.

{"criteria": {"rubric_based_final_response_quality_v1": {
  "threshold": 0.66,
  "rubrics": [
    {"rubric_id": "amount",  "rubric_content": {"text_property": "The reply states the refund amount."}},
    {"rubric_id": "no_date", "rubric_content": {"text_property": "The reply does not promise a delivery date."}},
    {"rubric_id": "short",   "rubric_content": {"text_property": "The reply is under three sentences."}}
  ]}}}

Speaker notes — A rubric is one testable criterion
  • Agent-specific: the rubrics are derived from, or written against, the agent’s configuration, which is code.
  • Per-case rubrics are filtered by type (FINAL_RESPONSE_QUALITY, TOOL_USE_QUALITY, TRAJECTORY_QUALITY).
  • Custom LLM metrics on the service (types.LLMMetric) are the third home: a prompt template you write, registered once, applied to runs and monitors alike.

Configuring a judge, and what a run costs

The criteria on page 10 with a “judge” tick each take a judge model, a sample count, and a threshold. Those three numbers set the cost of a run.

test_config.json — judge options and match type

{"criteria": {
  "tool_trajectory_avg_score": {"threshold": 1.0, "match_type": "IN_ORDER"},
  "final_response_match_v2": {
    "threshold": 0.8,
    "judge_model_options": {"judge_model": "gemini-3.5-flash", "num_samples": 5}
  }
}}

A bare float is a threshold. An object adds judge_model_options (judge_model, the LLM that grades; num_samples), match_type for the trajectory criterion, rubrics[] for the rubric criteria.

num_samples stabilizes a non-deterministic judge. The judge is an LLM, so it can score the same reply differently twice. ADK asks it num_samples times (5 here) and aggregates — majority vote for valid/invalid, mean for a numeric score — so one stray answer does not swing the result.

AgentEvaluator also runs every case num_runs=2 times by default, because the agent is non-deterministic too — a different run, then, is a different trajectory to grade.

Cost, in calls: one case with one judge criterion is 2 agent runs and 10 judge calls (2 runs × 5 samples), before the agent’s own tool and model calls.

Example

Actor: Priya, sizing the PR set.

Input: 60 cases, final_response_match_v2 at defaults.

Mechanism: 60 × 2 runs = 120 agent runs; 120 × 5 samples = 600 judge calls per pipeline run.

Result: num_samples: 3 for the PR set, 5 for the nightly set: 360 judge calls on a PR computed from defaults.

Takeaway: two defaults, num_runs=2 and num_samples=5, exist because the agent and the judge are both non-deterministic. Know them before you size a set.
Sources: eval_metrics.py:81-115, agent_evaluator.py:73, eval_config.py:97-135, google-adk 2.9.0 · criteria config samples.
Speaker notes — Configuring a judge, and what a run costs
  • Model choice: this deck names gemini-3.5-flash as the judge because it is current. Note that the shipped default in google-adk 2.9.0 is gemini-2.5-flash (eval_metrics.py:85); the docs’ samples say gemini-flash-latest. The point of the config field is that you pick, so pick the current model rather than inheriting the default.
  • Aggregation across the num_samples judge answers: valid/invalid metrics majority-vote (ties count invalid); numeric metrics take the mean.
  • Cost is one bullet, not a headline — a useful gotcha, not the module’s point.
  • parallelism_limit (default 1) serializes judge calls; raise it for speed at the price of rate limits. include_intermediate_responses_in_final sends pre-tool-call text to the judge as well.

Speaker notes — A score is not a pass until something compares it to the threshold
  • Generic (assert vs. print); say so. This module states the fact and stops.
  • Module 2 has the four ways to run an eval, the exit-code detail for agents-cli eval run, and the set tiering. If asked now: adk eval is built for a person reading scores, and it declines to choose a pass threshold for you.
  • The missing await is the single most common way a scaffolded eval test passes without running.

Two ways to grow a set

A customer was refunded twice. The conversation that did it is the next eval case.

Capture: start from a real session — reproduce it in adk web, or import the production trace itself (page 25). Save it as a case, then edit the expected trajectory and reference. Every production failure and bug report becomes a case.

The pieces, and how they fit

ADK eval, the Gen AI evaluation service, Agent Platform agent evaluation, agents-cli. Four names, but two scorers and a shared service — not four systems. Both scorers grade; they differ in where they run and what data they can reach.

Two scorers, both real. ADK’s metrics run in your process and grade there; the Agent Platform service grades server-side. ADK eval with local metrics does score — the difference is where the computation happens, and that only the service can reach production traffic.

ADK borrows the service for five of its criteria. Eight run in-process; five hand the job to the service (page 10’s “service” rows), so one ADK config can mix both scorers in a run.

agents-cli, the SDK, and the console are all front ends to the service. Only the drivers differ: a CLI, a notebook, a web UI. From the console you browse results, launch an offline evaluation over past traces, and configure monitors — the same service the SDK calls.

Two dataset formats, by lineage. ADK’s EvalSet is older and trajectory-first: you record the expected path. The service’s format is prompt-first: you give prompts and rubrics, and the agent runs at grade time. agents-cli/SDK/console all use the service’s format; ADK keeps its own.

The service’s seven agent metrics, and what a run returns

One recorded conversation from the weather agent, two service metrics, twenty-three seconds. The service wrote the rubrics itself, from the agent’s own instruction and tools. (Here EVAL_SET came from a production trace — page 25 shows how to get one; don’t worry about that yet.)

agentplatform SDK, aiplatform 2.1.0 — server-side run

from agentplatform import Client, types
client = Client(project=PROJECT, location="us-central1")

run = client.evals.create_evaluation_run(
    dataset=types.EvaluationRunDataSource(evaluation_set=EVAL_SET),
    metrics=[types.RubricMetric.TOOL_USE_QUALITY(version="v1"),
             types.RubricMetric.FINAL_RESPONSE_QUALITY(version="v1")],
    dest="gs://BUCKET/eval-results/", display_name="weather-v7")
# poll get_evaluation_run until SUCCEEDED; summary metrics on the run,
# per-item JSON with every rubric, verdict, and reasoning in dest

Single-turn: FINAL_RESPONSE_QUALITY, TOOL_USE_QUALITY (adaptive), HALLUCINATION, SAFETY (static). Multi-turn: MULTI_TURN_TASK_SUCCESS, MULTI_TURN_TOOL_USE_QUALITY, MULTI_TURN_TRAJECTORY_QUALITY (adaptive).

Two ways to run it: client.evals.evaluate returns scores inline for a notebook. create_evaluation_run creates a durable run resource — it writes results to a bucket and appears in the console’s Evaluation list, so a teammate can open it, browse the per-case rubrics, and compare it to other runs.

Each adaptive rubric returns its text, an importance, a verdict, and a reasoning sentence.

Custom metrics (types.LLMMetric, types.CodeExecutionMetric) register once with create_evaluation_metric and apply to runs and monitors alike.

Conformance testing is replay, not scoring

Marco renamed a tool. He wants to know if anything else changed, with no model call and no score.

adk conformance — google-adk 2.9.0; record and live mode marked work in progress

$ tree tests/refund/verify_before_refund
spec.yaml                    # description, agent, user_messages
generated-recordings.yaml    # every LLM request/response and tool call/result
generated-session.yaml       # the session as recorded
$ adk conformance record tests/refund none
$ adk conformance test tests/refund
Event count mismatch -
Actual: 6   Recorded: 7
--- recorded function_call
+++ actual function_call
-  "name": "verify_shipment"
+  "name": "check_shipment"

record runs the agent with a recordings plugin and writes the LLM requests and responses and the tool calls and results.

test (replay, the default) reruns the agent against the recording and fails on any difference: event count, request, response, tool call. No model is called; the recording answers for it.

It is a deterministic regression test whose fixture is the model’s recorded behavior. It cannot say whether a new behavior is better. Evaluation does that.

Status in 2.9.0: record prints “work in progress”; --mode live is not implemented.

Example

Actor: Priya, then Marco.

Input: the refund case, recorded once.

Mechanism: Marco renames verify_shipment to check_shipment; replay reruns the case.

Result: failure at the first tool call, with a unified diff of the recorded vs. actual function call. Nothing was graded; something changed.

Takeaway: replay tells you that behavior changed. An eval tells you whether it is still good. Use replay for cheap, deterministic regression on things that must not move.
Sources: cli/conformance/cli_test.py, _replay_validators.py:124-141, cli_tools_click.py:568-700, google-adk 2.9.0 · adk.dev/evaluate conformance section.
Speaker notes — Conformance testing is replay, not scoring
  • Generic (record/replay); say so. The agent-shaped fact is that the thing mocked is the model.
  • Recording needs adk web started with --extra_plugins=google.adk.cli.plugins.recordings_plugin.RecordingsPlugin. The trailing streaming-mode argument is required: none, sse, or bidi.
  • Not to be confused with adk test, which replays a JSON fixture against a mocked BaseLlm (Module 2 page 5).

Related topics

Four things this module names and does not teach. Each plugs into the same config and the same harness.

User simulation v1.18+

A ConversationScenario (starting_prompt, conversation_plan, user_persona) drives a simulated user; personas EXPERT, NOVICE, EVALUATOR. Reference-based criteria unsupported. Example: a NOVICE cannot correct the agent, so a wrong refund amount goes unchallenged.

Environment simulation experimental

Mock a tool or inject failures and latency. Example: a 503 injected on verify_shipment; the rubric expects the agent to say it could not verify.

adk optimize experimental

GEPA rewrites the root agent’s instruction against a training eval set and reports validation scores. Example: 100 metric calls; the best candidate’s instruction printed.

Custom metrics v1.18+

A Python function (eval_metric, actual, expected, scenario) → EvaluationResult, registered under custom_metrics with a code_config.name. Example: the refund amount in the reply equals the tool’s return.

Takeaway: each of these plugs into the same config and the same harness. Learn the harness first.
Sources: user-sim, environment_simulation, optimize, custom_metrics · simulation/pre_built_personas.py:460-510, google-adk 2.9.0.
Speaker notes — Related topics
  • Status labels come from the docs: environment simulation “is an experimental feature”; GEPARootAgentPromptOptimizer “is experimental” and warns on construction. The version tags are the “Supported in ADK Python vX” badges.

  • Audio (live) evaluation exists from 2.6.0 and is out of scope.
