The check that is new

Everything else in your pipeline already works. One kind of check is missing — and the tooling makes it easy to add it and still catch nothing.
Speaker notes — Section 1 divider
  • The question this section answers: what does a pipeline for an agent need that a pipeline for a web service does not?
  • Answer in one word now — evaluation — then spend the section on what that actually means mechanically.

What changes, and when you check it

A pull request changes one sentence of the refund agent’s instruction. Every test passes. The agent now refuses refunds it used to grant.

The instruction is a source file. So are the tool definitions, the model id, and the generation config. They live in the repository, they show up in a diff, and they are reviewed — but a few words of English can change behavior as much as a rewritten function.

No test you already run would catch it. Unit tests assert on code paths, and no code path changed.

An eval run would. It runs the agent over recorded cases and grades what it decided — which tool, which trajectory, which answer.

RuleBuilding a container image is a release step, not a per-commit one. Evals do not wait for it — they run against the agent in your working tree, or against the merge result, long before anything is packaged.
Example

Actor: Priya. Input: the instruction changes from “offer a refund when appropriate” to “only offer a refund after confirming the order shipped.” Mechanism: she runs a dozen cases locally and two fail, so she fixes the wording and opens a pull request; the PR job runs the larger set against the merge result. Result: three unshipped-order cases the local dozen never covered fail at the PR, and the merge is blocked illustrative.

Takeaway: the same kind of check runs at two or three cadences with different breadths — and none of them needs an image built first.
Sources: companion M2 §04 · martinfowler.com, Continuous Integration (verified 2026-09-12).
Speaker notes — What changes, and when you check it
  • Why this page exists: it frames the whole module. The thing that changed is a source file; the checks that would catch it run at three different moments, at three different breadths.
  • Delivery beat: read the lede, then ask “which of your existing tests would catch that?” before revealing the rows. The answer is none of them.
  • Be explicit that the three moments are a cadence, not a pipeline: the local loop is not a build step, and the image build belongs to release, after the gate. Page 7 covers how the sets differ in size; page 9 covers what actually runs them.
  • Two cadences are the common case: the local loop and the PR gate. The scheduled run is the optional third — page 7 sizes all three. If someone asks about running evals on every branch push: you can, but it costs model calls on work that is not ready for review, which is why most teams put the gate at the PR.
  • Kept off the face: the source deck defines CI as “frequently merging code changes into a central repository.” That is half of Fowler’s definition — the other half is that each integration is verified by an automated build including tests. The verification half is what this module is about.
  • Also off the face: continuous delivery and continuous deployment are different. “Several times a day” describes deployment. For agents, delivery plus a canary is the usual choice, because an eval set is a sample of the conversations the agent will actually see.

Three kinds of check, three different things they catch

“We have tests” is not an answer to “does it still behave?” Three mechanisms, and only one of them grades a decision.

CheckWhat runsWhat it catchesWhat it cannot
pytest tests/unityour functions; model mocked or absentlogic bugs, schema errors, bad parsinganything the model decides
pytest tests/integrationthe agent, against the real modelwiring: does a turn complete and come back with textwhether the answer was right
adk testrecorded events replayed, model mockedregressions against a fixture, deterministicallyanything not already in the fixture
eval runthe agent, real model, output gradedwrong tool, wrong trajectory, wrong or unsafe answerdeterminism — scores move between runs
RuleAn eval is not a slower unit test. A unit test asserts; an eval scores — and a score is only a pass or a fail once you choose a threshold.
Example

Actor: the scaffolded integration test that ships with a new project. Input: the prompt “Why is the sky blue?” Mechanism: it runs the real agent and asserts that at least one event came back carrying text. Result: it passes whether the agent explained Rayleigh scattering or replied “I cannot help with that.” It is a wiring check, and it is not pretending to be more.

Takeaway: unit and integration tests tell you the agent ran. Only the eval tells you what it decided.
Sources: agent_test_runner.py (mocks BaseLlm) and the scaffolded tests/integration/test_agent.py, google-adk 2.9.0 / google-agents-cli 1.5.0 (verified 2026-09-12).
Speaker notes — Three kinds of check
  • Why this page exists: “eval” has to be a defined term before the next page can correct how it is wired. Define it by contrast, against the two things the room already has.
  • Delivery beat: read the scaffolded integration test’s assertion aloud — assert len(events) > 0 and “at least one part has text.” It reliably gets a reaction, and it makes the point that a passing integration suite says nothing about quality.
  • adk test is the one people miss: it mocks the model and replays recorded events, so it is a deterministic regression harness, not an evaluation. adk test --rebuild re-records the fixtures by running the real agent.
  • Gotcha for the last column: eval scores move between runs because the model is non-deterministic. The fixes are temperature=0, rubric-based metrics, or several samples — not deleting the case. A flaky eval is signal about the agent.

The gate that isn’t

You add an eval step to your pipeline, push a change that breaks a case, and the build goes green.

The command reports the failure — and succeeds

$ adk eval app/ simple.evalset.json --config_file_path test_config.json
Eval Run Summary
simple:
  Tests passed: 0
  Tests failed: 1
$ echo $?
0   <-- a build step here would carry on to push and deploy
CorrectionFailed cases do not change the exit code. adk eval exits non-zero only when a dependency is missing or the eval-set file cannot be read; agents-cli eval run behaves the same way. The scores are the result — the exit code is not.

Run the same case from pytest, and the threshold is enforced

$ pytest tests/eval
E   AssertionError: Following are all the test failures.
E   response_match_score for app Failed. Expected 0.9, but got 0.0.
1 failed in 4.56s
$ echo $?
1   <-- the build stops here
Why this worksThe threshold lives in the eval config (response_match_score: 0.9). AgentEvaluator compares each score against it and raises AssertionError when one falls short — so pytest fails, and the build fails with it. Comparing a score against a threshold is the gate; the only question is whether something does it.
Example

Actor: one agent whose model always replies “I cannot help with that.” Input: one eval case expecting “Your refund is issued,” with a threshold of 0.9. Mechanism: the same case run both ways on google-adk 2.9.0. Result: both report the failure; adk eval exits 0 and pytest exits 1 — the difference is entirely in who checks the score reproduced.

Takeaway: something has to compare the score to a threshold and fail. Wrap the eval in a test, or read the results file and check it yourself — but never trust the command’s exit code.
Sources: cli_tools_click.py (cli_eval) and agent_evaluator.py at tag v2.9.0 · agents-cli eval guide: “eval run exits 0 whatever the scores are, so the numbers you paste are the gate, not the exit code” (verified 2026-09-12).
Speaker notes — The gate that isn’t
  • Why this page exists: this is the correction the section is built around. Someone in the room will go home and add an adk eval build step; without this page it will silently pass forever.
  • Delivery beat: show the first block, ask “what is this build’s exit code?”, let them answer 1, then reveal the 0.
  • Both blocks are real output from the same one-case reproduction on 2.9.0, not composed. The pytest failure text is quoted verbatim — the Expected 0.9, but got 0.0 line is the threshold comparison the first command declines to make.
  • The next page covers the four ways to run an eval and which of them gate. The short version: only the pytest path fails on its own; everything else needs you to check the numbers.
  • If asked why the CLI behaves this way: it is built for the interactive improvement loop, where a human reads the scores and decides what to fix. Picking a pass threshold is a project decision, so it declines to pick one. agents-cli eval grade raises only when grading itself fails — never because a score was low.
  • The non-pytest gate, for teams not using it: parse results_<timestamp>.json from eval grade and fail the step on your own threshold. Same principle — you own the comparison.

Two eval sets, maybe three

The set that answers “did I just break it?” in forty seconds is not the set that answers “is this release good?”

TierWhen it runsSizeWhat it is for
On demandyou changed something you believe moves behavior~10–15 casesthe local loop: an answer before you lose the thread
On pull requestautomatically, on the same trigger as the unit tests~50–100 casesthe gate: nothing merges past it
Periodicnightly or weekly, on a schedulethe full setdepth you cannot afford on every PR

Two sets is the common case. The third appears when PR volume makes the full set too slow or too expensive to run every time.

They differ in comprehensiveness, not in kind. Same format, same metrics, same gate mechanics — only the breadth and the cadence change.

Failing production conversations become new cases. That is how the sets grow, and why the large one drifts away from the small one over time.

Example

Actor: a four-person team shipping about ten pull requests a day. Input: a 12-case smoke set, a 60-case PR suite, a 400-case nightly set. Mechanism: the smoke set runs locally in about 40 seconds; the PR suite runs beside the unit tests in about six minutes; the nightly set runs through agents-cli eval submit, the managed asynchronous path documented for large or CI-driven runs. Result: a broken trajectory is caught in the loop, at the PR, or overnight — three nets with different mesh illustrative.

Takeaway: two eval sets, maybe three, differing in size and cadence — and every one of them needs its own gate.
Sources: agents-cli eval guide, eval submit / eval results for “large or CI-driven runs” (google-agents-cli 1.5.0, verified 2026-09-12).
Speaker notes — Two eval sets, maybe three
  • Why this page exists: it answers the two questions developers actually ask — do I run evals per commit, and is the CI set the same one I use locally? No: different sizes, different cadences, same mechanics.
  • The numbers are illustrative and worth saying so. Cost scales with cases × turns × judge calls, and the judge is itself a model call, so a large set is real money and real minutes.
  • Epistemic status, and say it plainly if asked: this tiering is field practice, not a documented prescription. No vendor document says “two eval sets.” What is verifiable is that the tooling for each tier exists — a local run, a PR job, and a managed asynchronous path built for large or CI-driven runs. The placement is a team decision, and the sizes below are one team’s shape, not a standard.
  • Worth adding if the room is experienced: hold a slice of cases out of the local loop entirely and grade them only when you think you are done. Otherwise you fit the agent to the cases you have been iterating against, and you cannot tell a fix that generalizes from one that memorized.
  • Delivery beat: ask how long their unit suite takes, then ask what they would tolerate for evals on every PR. The answer sets which tiering they need.

Four ways to run an eval

Two CLIs, a test harness, and a browser UI. They are not interchangeable, and only one of them fails a build on its own.

MechanismWhat it is forDataset and thresholdsGates?
adk webthe inner loop: chat with the agent, then save that session as an eval case; run a set and read results in the browserADK .evalset.json, built by hand or from a sessionno — you read them
adk evalrunning an ADK eval set from a terminal or a scriptADK .evalset.json + test_config.jsonno — exits 0 (page 6)
agents-cli evalgrading runs on the Agent Platform evaluation service: its metric set, custom LLM judges, and it can run against a deployed agentAgent Platform dataset + eval_config.yamlno — writes a results file
pytest + AgentEvaluatorthe gate: the same ADK eval set, wrapped in a testADK .evalset.json + test_config.jsonyes — asserts
adk eval vs. agents-cli evalDifferent lineages, not versions of each other. adk eval runs an ADK eval set against a local agent module, and grades it in your process. agents-cli eval splits the job into generate (run the agent, record traces) and grade — and grading calls the Agent Platform evaluation service, so it needs a project and an eval-supported region, and its built-in metrics are the service’s. That is also what buys custom LLM judges, a deployed target via --url, and the managed path via eval submit. The two dataset formats are not interchangeable.
Example

Actor: Priya, adding a case for a bug just reported. Input: the conversation that misbehaved. Mechanism: she reproduces it in adk web, saves the session into the eval set with one click, then runs pytest tests/eval to confirm it fails. Result: a regression case that came from a real conversation, and a gate that now blocks it — the same file the PR job will run illustrative.

Takeaway: use the UI to build cases, a CLI to explore scores, and pytest where something must actually fail.
Sources: adk eval --help, the dev-server eval routes (.../eval-sets/{id}/add-session, /run), google-adk 2.9.0 · agents-cli eval --help, google-agents-cli 1.5.0 (verified 2026-09-12).
Speaker notes — Four ways to run an eval
  • Why this page exists: “run an eval” is four different commands with different file formats, and picking the wrong one wastes an afternoon. This is also the page that stops anyone leaving with the impression that one CLI is the way.
  • The add-session route is the one people miss: chat until the agent does the wrong thing, save that exact session as a case. It is the cheapest way to grow an eval set, and it means your cases come from real conversations rather than imagination.
  • Delivery beat: ask how they would turn a bug report into a regression test. That is the example.
  • Choosing between the two CLIs: ADK format, local module, grading in-process, no GCP project needed → adk eval. Service metrics, custom judges, a deployed target, or the managed cloud run → agents-cli eval. A team usually settles on one; the cost of mixing is two dataset formats to maintain.
  • The service dependency has practical consequences: eval grade defaults to the global endpoint rather than your manifest region, only some regions are supported, and it is rate-limited (hence --qps). For data-residency cases where no eval region fits, a local custom_function metric grades in-process instead.
  • For the PR job specifically: pytest tests/eval is the recommendation, because it needs no extra threshold-checking code. The alternative is agents-cli eval run followed by a script that reads results_<timestamp>.json and exits non-zero — fine, just more to maintain.
  • adk test is deliberately not in this table — it replays fixtures against a mocked model, so it is regression testing rather than evaluation. Page 5 covers it.

What Google ships, and what it leaves you

agents-cli scaffolds a complete, working pipeline. It is worth knowing exactly where the eval step sits in it.

StageTriggerWhat it runs

The gaptests/eval/ is scaffolded — datasets, and an LLM-as-judge metric — and no pipeline stage calls it. Across the 24 shipped pipeline files there is not one occurrence of the word “eval.” The wiring is yours to add.

What to keep: the three-stage shape, Workload Identity Federation so there are no long-lived service-account keys, and staged promotion with an approval before production.

What to add: the eval gate at the CI stage, beside the unit and integration tests that are already there.

What the PR trigger already gives youThe CI stage runs on on: pull_request, and actions/checkout then checks out GITHUB_REF — the merge branch. So everything at this stage, evals included, runs against your branch merged into main, not against your branch tip.
Example

Actor: Marco and Priya, on separate branches. Input: Marco renames the tool get_order to lookup_order; Priya’s new instruction says “call get_order to confirm the order shipped.” Mechanism: each branch passes its evals alone, and git reports no conflict — one change is in a tool module, the other in an instruction file. The PR job evaluates the merge result, where the instruction names a tool that no longer exists. Result: caught on the pull request instead of after the merge, with one diff to read rather than two people’s work to bisect illustrative.

Takeaway: the scaffold gives you the pipeline and the eval artifacts and does not connect them — that is the one edit to make on day one, and the PR trigger already evaluates the merge result for free.
Sources: google-agents-cli 1.5.0 scaffold templates (.cloudbuild/, .github/workflows/) · agents-cli deployment guide, CI/CD pipeline stages · GitHub Actions: events that trigger workflows (verified 2026-09-12).

How sessions get wired — one mechanism, every target

ADK’s service registry maps the URI scheme agentengine://<engine> to VertexAiSessionService (and the memory scheme to VertexAiMemoryBankService). On Agent Runtime, adk deploy agent_engine names the engine it just created and writes --session_service_uri=agentengine://<engine> into the container’s start command, so nothing is left to configure. On Cloud Run or GKE you pass the same flag with any engine id, and the agent uses managed sessions there too. A server you write yourself calls the registry, or constructs the service, itself.

Example

Actor: a two-person team with no infrastructure owner. Input: an ADK agent directory, no Dockerfile. Mechanism: adk deploy agent_engine creates the engine, generates a Dockerfile whose start command names that engine as the session store, and hands the source to Agent Engine to build and run. Result: callers reach it with a Google token, and every conversation is already in managed Sessions. When security later requires a company domain behind Cloud Armor, the target moves to Cloud Run with adk deploy cloud_run --session_service_uri=agentengine://<same id> — same source, same session store illustrative.

Takeaway: the tool builds the image and can wire managed sessions on any target; choose the target on what you need in front of the container and how much of it you want to operate.

Speaker notes — Choosing a deployment target
  • Why this page exists: the decision is usually made on vague impressions. The real framing is narrow: what form you hand over, and how much of the endpoint and infrastructure you then operate.
  • Both deploy tools build the image from source on every target: Agent Engine builds for Agent Runtime; adk deploy cloud_run runs gcloud run deploy --source, which builds in Cloud Build; agents-cli deploy does the same unless --image is passed. Nobody hand-builds an image unless they want to own that step.
  • The five Agent Runtime methods, from the docs: Developer Connect (recommended for repos it is linked to), source files (“well-suited for CI/CD and Terraform”), Dockerfile, container image (when you want to own the build, and lower deploy latency), and the SDK path that pickles an in-memory object (Colab; only for agents without non-serializable parts). A custom container or Dockerfile must meet the runtime contract: port 8080, /api/reasoning_engine and /api/stream_reasoning_engine.
  • Sessions, precisely: create_dockerfile_for_agent_engine sets agent_engine_uri = f'agentengine://{resource_name}' and passes it as the session and memory URI into the CMD adk api_server … line; service_registry.py registers agentengine_session_factory, which returns VertexAiSessionService(**params). The same flag on adk deploy cloud_run and gke accepts a full resource name or a bare id. The agents-cli scaffold has three modes in app_utils/services.py: cloud_sql (Postgres via DatabaseSessionService), agent_platform_sessions (finds or creates an engine by display name and uses agentengine:// — on any target), or the default, which honours SESSION_SERVICE_URI, then the injected GOOGLE_CLOUD_AGENT_ENGINE_ID, then in-memory.
  • Memory Bank: adk deploy points the memory service at the engine the same way. Whether the engine has a memory bank configured is a separate resource-side setting; check context_spec if memory reads come back empty.
  • Delivery beat: ask what they need in front of the agent — a company domain? IAP? a WAF? Each answer pushes down the table.
  • Accelerators deliberately do not appear. The agent loop is I/O-bound on every target; a GPU only matters if you serve a model in the same container, which is a serving decision.
  • DatabaseSessionService takes a database URL — PostgreSQL, MySQL or SQLite. Cloud SQL is one way to host that database, not a session backend of its own.
  • Launch stages move — Cloud Run sandboxes and Agent Runtime Code Execution were Preview on 2026-09-12, GKE Agent Sandbox GA since May 2026. Re-check before delivery.

The three content variables — read from the environment on every path

Neither variable adds or removes a span; each decides whether attributes on spans that exist anyway carry text or a placeholder. ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=true fills the gcp.vertex.agent.llm_request, llm_response, tool_call_args and tool_response attributes on the call_llm and execute_tool spans; false writes {}. OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=EVENT_ONLY puts them in the GenAI log events instead of <elided> — and under the semconv opt-in its SPAN_ONLY and SPAN_AND_EVENT modes put them on the generate_content span as well, so this variable is not “the events one.” OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental selects the current event shape. GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY is not one of them: it is Agent Runtime’s export switch, the one the Console toggle sets. It never puts content anywhere.

Example

Actor: Priya, moving the refund agent from Agent Runtime to Cloud Run to put it behind a company domain. Input: the same ./app and .env; adk deploy agent_engine --otel_to_cloud becomes adk deploy cloud_run --otel_to_cloud. Mechanism: the Agent Runtime deploy had been writing ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false for her; the Cloud Run deploy writes nothing, so the library default applies. Result: the first Cloud Run trace has full prompts on every call_llm span. She adds --env ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false and redeploys illustrative.

Takeaway: export is a flag on adk deploy, a variable the scaffolded server reads on agents-cli deploy, and four lines of startup code in a runtime you wrote. Content is the same three variables on every path, and only the two Agent Runtime deploys and agents-cli turn it off for you — on a native Agent Runtime deploy they turn it off whether you like it or not.

Speaker notes — Configuring a deployment: telemetry
  • Why this page exists: the brief asks for the configuration each target needs, and telemetry is where the paths differ most. Read the table by row: the export switch moves; the content variables do not. Delivery beat: ask “you deployed with tracing on and every prompt says elided — which column did you miss?”
  • What --otel_to_cloud does, on every adk deploy target: it lands in the container’s CMD adk api_server … --otel_to_cloud, and at boot _setup_gcp_telemetry calls google.auth.default(), builds OTLP exporters for traces, metrics and logs to telemetry.googleapis.com, and installs them as the global providers. adk deploy agent_engine additionally writes GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true into the deployment environment, and reads that variable from ./app/.env as a way to turn the flag on; if both are present the flag wins with a notice. Note that adk api_server itself never reads the variable — in this path the exporters come from the flag, and the variable is what the platform and Console see.
  • Is ENABLE_TELEMETRY the same as the OTel variables? No. It is an on/off switch for export on Agent Runtime, read by the platform, by the SDK’s AdkApp (frameworks/adk.py, _telemetry_enabled), and by the agents-cli scaffold’s fast_api_app.py. The OTEL_INSTRUMENTATION_GENAI_* variables decide what content is inside the export. The docs’ three-variable example sets both kinds side by side, which is what makes them look interchangeable.
  • What ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=true shows, from tracing.py: gcp.vertex.agent.llm_request and llm_response on call_llm, tool_call_args and tool_response on execute_tool, gcp.vertex.agent.data on send-data spans. When false they are {} or N/A. The GenAI variable is separate: EVENT_ONLY and SPAN_AND_EVENT fill the gen_ai.* log events; SPAN_ONLY and SPAN_AND_EVENT put content on the generate_content span only under the semconv opt-in; unset or unrecognised means NO_CONTENT; true is a back-compat alias for EVENT_ONLY.
  • Precedence on adk deploy agent_engine, and why the row says “not settable to on.” Two things happen at two different times, and the second one wins. At deploy time: dotenv_values(<agent_dir>/.env) is the only source for the deployment environment, then if 'ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS' not in env_vars: env_vars[…] = 'false'. The deploy fills a gap in the file and never overrides a value in it, so true in .env really is written into the deployment and you can see it on the resource. At runtime: the platform wraps your agent in the Vertex SDK’s AdkApp, whose set_up runs on every container start and does an unconditional os.environ["ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS"] = "false" (templates/adk.py:990-996, google-cloud-aiplatform 2.1.0) unless the deprecated enable_tracing=True was passed. ADK re-reads the variable per turn, so the overwrite is what every turn sees. Net effect on a native deploy: the value in the deployment environment is cosmetic and content stays off. This is the only path where that is true — on Cloud Run, GKE, BYOC, and any runtime you wrote, nothing overwrites it and .env decides. Verified on a live 2.9.0 --otel_to_cloud deploy, 2026-09-12: the resource carries GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true and ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false.
  • agents-cli to Agent Runtime, precisely (deploy/agent_runtime.py): .env is read, --update-env-vars is merged on top, then setdefault for ENABLE_TELEMETRY=true, OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT and ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false. Same shape on Cloud Run and GKE (cmd_deploy.py) except only the ADK variable is defaulted there. If someone asks why rows 1 and 2 differ when both land on Agent Runtime: an agents-cli deployment ships a container running the scaffold’s own FastAPI server, so the SDK’s AdkApp wrapper never runs and never overwrites the content variable. The outcome matches row 1 anyway because the deploy writes false explicitly — same answer, different reason, and here --update-env-vars can genuinely turn it back on. The scaffolded server passes otel_to_cloud=True on Cloud Run and GKE, and on Agent Runtime derives it from ENABLE_TELEMETRY, so the Console toggle really turns export off in that container. When the project is Terraform-managed, service.tf also sets OTEL_SEMCONV_STABILITY_OPT_IN and the upload hook that writes full completions to a GCS bucket — that tier ignores the content variable, so “no content in traces” does not mean “no content stored.”
  • The SDK path, for completeness: client.agent_engines.create(agent=AdkApp(…), env_vars={"GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY": "true", …}). The SDK adds the variable as "unspecified" if you omit it so the Console can own the toggle. This is the same AdkApp whose startup overwrite is described three bullets up — the SDK path and adk deploy agent_engine land in the same container wrapper, which is why the content answer is the same for both.
  • Where the variables go, in detail: Cloud Run’s deployer reads .env only for project and region; adk deploy gke has no --env; it writes a Deployment manifest carrying only project, location and the enterprise flag and runs kubectl apply on it, so variables go on afterwards with kubectl set env deployment/<service_name> K=V, which rolls the pods. On every target ADK also runs load_dotenv_for_agent at startup, so a .env that shipped inside the image is read too, with values already in the environment preserved — but the deploys honour .gitignore and .gcloudignore, and most repos ignore .env, so do not rely on it.
  • The custom-runtime snippet is the ADK docs’ “telemetry modules” pattern. maybe_set_otel_providers also honours the standard OTEL_EXPORTER_OTLP_*ENDPOINT variables, and is a no-op for any provider your code already set globally. get_fast_api_app does the same thing behind otel_to_cloud=True, and with the flag off it still wires generic OTLP exporters if those endpoint variables are set. Sizing — the defaults, and the one that bites

$ agents-cli deploy --cpu 1 --memory 4Gi --concurrency 8 --min-instances 0 --max-instances 10
                    ^ all four are the defaults; --min-instances 0 scales to zero,
                      but the generated Terraform pins 1 to avoid cold starts

# the adk equivalent, for a project without the agents-cli manifest:
$ adk deploy cloud_run --project my-proj --region us-central1 \
    --provider-args "--cpu=4,--memory=16Gi,--concurrency=16,--max-instances=20" ./app
CaveatThe sizing parameters are coupled. Each in-flight request holds its whole context window in memory while it waits on the model, so peak memory is roughly base plus concurrency × per-request memory. Raising --concurrency without raising --memory is the usual cause of OOM restarts heuristic.
Takeaway: secrets and identity are one flag each; sizing is where you have to think, because memory bounds concurrency.
Sources: agents-cli deploy --help (1.5.0) · agents-cli deployment guide, “Sizing a deployment” · adk deploy cloud_run --help, google-adk 2.9.0 (verified 2026-09-12).
Speaker notes — Configuring a deployment: secrets, identity, size
  • Rotation, if asked: add a new secret version, redeploy pointing at it, verify, then disable the old one. No commit and no rebuild — the diff is a version number in the deploy command, and the previous version is still there to switch back to.
  • Pin the secret version (:3) rather than taking latest, for the same reason you pin a model id: otherwise the thing your agent authenticates with can change without a deploy.
  • adk deploy has no first-class sizing flags — --provider-args passes them through to gcloud run deploy. On GKE the sizing flags are rejected outright; size in the manifests and the HorizontalPodAutoscaler.
  • The min-instances inconsistency is worth naming: the CLI default is 0, the generated Terraform pins 1. Two defaults for one setting, depending on the path you deploy through.
  • Concurrency 8 is conservative because per-request memory is agent-specific. Light agents go to 16–32 after load testing — and the staging stage’s load test is exactly that tool.

The pipeline, corrected

The widely-copied example pipeline for deploying an agent has three defects, and two of them are silent.

Three defects

01
The deploy step uses ${_PROJECT_ID}, an undefined user substitution, while the build step uses the built-in $PROJECT_ID.
02
The image carries no tag, so every build overwrites the same reference and no running revision names the commit that produced it.
03
There is no eval step at all.

Fixed — the four steps that matter

substitutions:
  _DEPLOY_PROJECT_ID: "my-deploy-project"   # declared, not assumed
  _REGION: "us-central1"
  _REPO: "my-repo"
steps:
  # 1. build, tagged with the commit
  - name: gcr.io/cloud-builders/docker
    args: ["build","-t","$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA","."]
  # 2. the gate: AgentEvaluator asserts, so a failed case fails the build
  - name: python:3.12
    entrypoint: bash
    args: ["-c", "pip install -q -r requirements.txt pytest &&
            pytest tests/unit && pytest tests/eval"]
  # 3. push only after the gate passes
  - name: gcr.io/cloud-builders/docker
    args: ["push","$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA"]
  # 4. deploy non-interactively, to a project named explicitly
  - name: gcr.io/cloud-builders/gcloud
    args: ["run","deploy","lab-agent",
           "--image","$_REGION-docker.pkg.dev/$PROJECT_ID/$_REPO/agent:$COMMIT_SHA",
           "--region","$_REGION",
           "--project","$_DEPLOY_PROJECT_ID","--quiet"]
Takeaway: tag with the commit, declare your substitutions, run the gate before the push, and deploy with --quiet so the build never waits on a prompt.
Sources: Cloud Build substitutions and cloudbuild.yaml schema · companion M2 §29 (verified 2026-09-12).
Speaker notes — The pipeline, corrected
  • Why this page exists: it is where section 1’s gate becomes a line of YAML, and it fixes an example that circulates widely with these defects intact.
  • Step 2 is the payoff from page 6: pytest tests/eval, not adk eval. If a student takes one line home, it is that one.
  • $COMMIT_SHA is empty for a manual gcloud builds submit, because there is no commit context — an image tagged with it then gets an empty tag. Only trigger-started builds have it, along with $BRANCH_NAME, $TAG_NAME and $SHORT_SHA.

Governing what the model reads

The model decides from two things you control: which model it is, and what your tools say they do.
Speaker notes — Section 3 divider
  • Framing: governance here is not paperwork. Both of these inputs change agent behavior at runtime without a code change, which is exactly why they need the pipeline.
  • This section is deliberately short — two pages and a tour. The brief marks it as secondary to evaluation and deployment.

Model governance

You deploy on Tuesday against gemini-flash-latest and run the full eval set: green. Nothing is deployed on Thursday. On Thursday the agent starts formatting tool calls differently.

An alias is a moving target. -latest is documented to be hot-swapped with every new release of that model variation. Your deployment did not change — the thing it points at did.

Pin a version, and change it deliberately. The model id is a source file like any other: change it, run the eval set, compare against the recorded baseline, canary, promote.

Promote one version through the environments. Staging exists to test the version production is about to run — so they match by the end of a release, not by accident in the middle of one.

Model families retire on a schedule. The upgrade is a matter of when, not whether, so rehearse it rather than meeting it as an incident.

Where Model Registry fitsAgent Platform’s Model Registry versions models you register — a tuned or custom model — with version aliases, lineage and stage labels, and it is what a deployment or an approval gate points at. If your agent calls a Google foundation model by id, you are not registering anything: the pinning rule above is the whole practice. Register when you tune.
Example

Actor: the refund agent, pinned to gemini-3.5-flash verify the current id. Input: a pull request that changes the id to the next version. Mechanism: the PR job runs the eval set against the merge result; tool-call accuracy drops on five cases where the new version formats arguments differently. Result: blocked at the gate. The instruction is adjusted and re-run, and the new version reaches staging and production as one promoted change rather than a surprise illustrative.

Takeaway: pin the version so the model changes only when you change it — then put that change through the same gate as any other.
Sources: Gemini model version aliases (-latest is hot-swapped on each release) · Model Registry versioning and aliases · companion M2 §21 (verified 2026-09-12).
Speaker notes — Model governance
  • Why this page exists: the source spends two slides on lineage, hyperparameters and semantic versioning — advice for teams training models. Almost nobody in the room is. The alias problem is what will actually bite them.
  • The lede is the whole argument, and the timing is the point: nothing was deployed between the green eval run and the behavior change. That is what makes it hard to debug — there is no diff to look at.
  • Say explicitly that pinning does not mean staging and production run different versions as a steady state. Staging runs the candidate first, briefly; when the release promotes, they match. A permanent skew between environments means staging is testing something production will never run.
  • Verify the current model id before delivery — the Gemini line moves fast, and the deck names one only as an example.
  • ADK 2.9.0 adds FallbackModel for automatic failover to a backup model on error. Availability, not governance — but note the implication: with a fallback configured, the model that answered may not be the one you pinned, so the traces need to record which one served the turn.

Governing tools and MCP servers

Your agent’s tools are an MCP server another team deploys on their own schedule. Nothing in your repository changes when they add, rename, or repurpose one.

A tool you do not own is a dependency that moves. A remote MCP server’s tool list and descriptions are read at runtime, so its release changes your agent’s behavior without touching your pipeline.

Agent Registry is the inventory and the control point. It catalogs MCP servers, tools, and agents across the organization, with search, IAM, audit logging, and auth bindings for connecting an agent to a tool.

Register what you publish, and pin what you consume. Register your deployed agent with agents-cli publish; consume tools through a registered server rather than an arbitrary URL, so access is governed and revocable.

Put the tool surface in the eval set. Your gate is the only thing that notices when a dependency’s description changes — run it on a schedule, not only on your own commits.

Example

Actor: the payments team, who own the MCP server your refund agent uses. Input: they reword issue_refund from “Issue a refund” to “Issue a refund or store credit” and ship it on a Wednesday. Mechanism: your agent reads tool descriptions from the server at runtime, so it starts offering store credit — with no commit, no deploy, and no pipeline run on your side. The nightly eval set is what fails. Result: the registry entry names the owning team and the server version, so the conversation takes minutes instead of a day of bisecting illustrative.

Publishing your ownApigee can expose an existing API as an MCP server with no code; MCP Toolbox for Databases gives governed access to Cloud SQL, AlloyDB, Spanner and BigQuery without a hand-written tool per query. Both land in the registry the same way.
Takeaway: a tool the agent reads at runtime is an undeployed dependency — catalog it in Agent Registry so you know who owns it, and let a scheduled eval run tell you when it changes.
Sources: Agent Registry overview (agents, MCP servers, tools, skills; auth bindings and audit logging) · agents-cli publish · companion M2 §24–25 (verified 2026-09-12).
Speaker notes — Governing tools and MCP servers
  • Why this page exists: it is the CI/CD-shaped part of tool governance. “Write good docstrings” and “use least privilege” are ordinary engineering; what is specific here is that a tool description is an input the model reads, and a remote one can change without any event in your pipeline.
  • Delivery beat: ask what in their current setup would notice the Wednesday change. Usually nothing until a customer complains — which is the argument for the scheduled tier from page 7.
  • If your tools are in your own repository, the story is simpler: the description is a diff, review it like code, and the PR gate catches the behavior change. The hard case is the one on the page — a dependency you do not deploy.

The one specific worth keepingCarry the commit in two places. Tag the image with it — agent:$COMMIT_SHA — so gcloud run revisions list names the commit that built what is serving. And stamp it on the telemetry, so a trace does too: 
$ agents-cli deploy --update-env-vars "OTEL_RESOURCE_ATTRIBUTES=service.version=$COMMIT_SHA"
