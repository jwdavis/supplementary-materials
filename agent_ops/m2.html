The check the pipeline is missing

Unit and integration tests say the agent ran. One more check scores what it decided, and it has to fail the build when the score drops.
Speaker notes — Section 1 divider
  • The question this section answers: what does a pipeline for an agent need that a pipeline for a web service doesn’t? One word now (evaluation), then the mechanics.

What the repository holds

A team lead asks who changed an agent’s instruction last week. In a project made by agents-cli create (Google’s CLI that generates a starter ADK project with tests, pipeline files, and Terraform), the answer is in git log app/agent.py.

The instruction, the tool docstrings, and the model id are lines of Python in app/agent.py. A wording change is a diff, reviewed and reverted like any code.

The pipeline and the infrastructure are files too: three Cloud Build (Google Cloud’s hosted CI runner) files and the Terraform that creates the services and triggers.

.env is git-ignored, so CI never sees it. Deploys run from your machine may read it and copy values into the service; Section 2 shows which.

Example

Actor: a developer undoing last week’s wording change.

Input: commit c4e19d0, one changed line inside instruction=.

Mechanism: git revert c4e19d0, then the normal pull request and pipeline.

Result: the old wording ships through the same checks as any code change. Only the model itself and remote tools sit outside the repo; Section 3 covers both.

Takeaway: everything that shapes the agent’s decisions, except the model and remote tools, is a file in the repo and moves through the pipeline like code.
Sources: project generated with agents-cli create <name> -a adk -d cloud_run --cicd-runner google_cloud_build, google-agents-cli 1.9.0 (verified 2026-10-07).

Three kinds of check, and what each one catches

A pull request changes one sentence of a returns agent’s instruction. Unit and integration tests pass. The agent now refuses returns it used to accept.

CheckWhat runsWhat it catchesWhat it misses
Unit
pytest tests/unit		your functions; no model calllogic bugs, schema errors, bad parsinganything the model decides
Integration
pytest tests/integration		the agent, calling the real modelwiring: a turn completes and returns textwhether the answer was right
Evaluationa saved list of test conversations (cases), each with expected tool calls and answer, run through the agent and the real model; each result scored against themwrong tool, wrong sequence of tool calls, wrong answerwhether the next run gives the same result; model output varies
RuleA unit test asserts; an eval scores. A score passes or fails only against a threshold you set.
Example

Actor: the integration test that agents-cli create generates.

Input: the prompt “Why is the sky blue?”

Mechanism: it runs the agent against the real model and asserts that at least one event came back with text.

Result: it passes whether the agent explains Rayleigh scattering or replies “I cannot help with that.”

Takeaway: unit and integration tests say the agent ran; only an eval scores what it decided.
Sources: scaffold tests/unit/test_dummy.py, tests/integration/test_agent.py (google-agents-cli 1.9.0) · ADK: Why evaluate agents (verified 2026-10-07).
Speaker notes — Three kinds of check
  • Why this page exists: define evaluation by contrast with the two checks the room already runs, before any page uses the word. Agent-specific mechanism: model output is non-deterministic and correctness has several dimensions (tool choice, sequence, answer).
  • Delivery beat: read the lede and ask which existing test would catch it. None: no code path changed.
  • Evidence (agents-cli 1.9.0 scaffolds generated 2026-10-07 with agents-cli create <name> -a adk -d {agent_runtime,cloud_run,gke} --cicd-runner {google_cloud_build,github_actions}): the unit test is assert 1 == 1; the integration test asserts len(events) > 0 and that one part has text; CI runs it against Gemini with GOOGLE_CLOUD_LOCATION=global. “Sequence of tool calls” is what ADK calls the trajectory, scored by tool_trajectory_avg_score (eval_metrics.py).
  • If asked about adk test or adk conformance: they replay recorded interactions against a mocked model and fail on mismatch, a regression check rather than a scored eval; adk.dev recommends adk conformance test on every pull request. Flaky evals: run cases more than once (AgentEvaluator runs each twice by default, agent_evaluator.py) and prefer rubric metrics; the Gemini prompting guide advises keeping Gemini 3.x at its default temperature. Metrics and judges are Module 4.

When evals run, and how many cases

A team has 400 eval cases. Running all of them on every edit is slow and costs model calls; waiting until release finds a problem after the change has merged.

Smoke testThe full set ran in CI, so it never touched the deployed agent. A smoke test sends a few conversations to that agent to confirm that its permissions, configuration, and tools work there. It does not grade quality. Generic: any deployed service needs this check.
When a subset makes senseFrequent pull requests or a slow, expensive set can justify a smaller gate. Choose its cases on purpose: business-critical behaviors, past production failures, and at least one case per tool. Then run the full set after merge, before production.
Example

Actor: a developer editing a travel agent’s instruction.

Input: “offer a rebooking when appropriate” becomes “only offer a rebooking after confirming the flight was cancelled.”

Mechanism: the 12 local cases show two failures; after the developer fixes the wording, all 12 pass. The full set on the pull request also has three delayed-flight and missed-connection cases that expect a rebooking offer, and the agent now refuses all three.

Result: the three cases fail on the pull request and the merge is blocked, before any image is built illustrative.

Takeaway: gate every pull request on the full set unless cost or speed rules it out, and smoke-test the deployed agent before production.
Sources: Evaluate agents (development, CI/CD, and production evaluation) · agent_evaluator.py (NUM_RUNS = 2) (verified 2026-10-07).
Speaker notes — When evals run
  • Why this page exists: developers ask whether evals run on every commit and whether the CI set is the one they use locally. Answer: same case format, and each stage has its own job and consequence. The stages are this course’s recommendation; no authoritative standard sets them. Google’s Evaluate agents page names a similar split (Rapid Evaluation in development, Test Case Evaluation for regression in CI/CD, Online Monitoring in production) but says nothing on set sizes or subsets. Practitioner guides mostly use a subset on pull requests with the full set later, for cost and speed (DZone, Autonoma); this page makes the full set the default and the subset the fallback, because only a gate before merge can keep a regression off main.
  • Each stage answers a different question. Pull request: did this diff break anything? Staging: does the deployed agent work? Schedule: did something change with no change to our code? If asked why the schedule still matters after a full gate: it is not there for coverage. With a pinned model and mocked tools it has little to detect, so weekly may be enough.
  • The smoke test is a step you add: the scaffold’s staging stage runs only a load test (page 9). AgentEvaluator runs the agent in process, so a deployed run uses agents-cli eval run --url plus a script that checks the results file and exits non-zero (page 8). This combination has not been run end to end.
  • Cost: each case runs the agent (model calls) plus any judge calls, and AgentEvaluator runs each case twice by default (num_runs), so a 400-case PR set is at least 800 agent runs on every push, and 60 cases is at least 120. The scaffold’s PR job already calls Gemini in its integration tests.
  • Caveat: a scheduled run against a deployed agent (agents-cli eval run --url, or eval submit, marked experimental in agents-cli eval --help 1.9.0) does need the deploy first. The local and PR runs do not.
  • For experienced rooms: hold some cases out of the local loop, so a fix that only fits the cases you iterated on doesn’t pass unnoticed.

Four ways to run an eval

A bug report arrives: a booking agent cancelled a reservation the customer wanted to keep. Four tools run evals, and they read two file formats.

ToolWhat it is forFilesFails a build?

pytest + AgentEvaluatorthe same ADK eval set, run as a test; AgentEvaluator is ADK’s Python class that runs an eval set inside a pytest testADK .evalset.json + test_config.jsonyes; asserts

Example

Actor: a developer turning the bug report into a regression case.

Input: the conversation from the report, replayed in adk web.

Mechanism: the developer saves the session into booking.evalset.json. The saved case records the calls the agent actually made, including cancel_reservation, so the developer edits its expected calls to leave that call out, then runs pytest tests/eval.

Result: the new case fails until the instruction is fixed, and the PR job runs the same file from then on illustrative.

Takeaway: build cases in adk web, explore scores with a CLI, and gate with pytest.

Speaker notes — Four ways to run an eval
  • Why this page exists: “run an eval” is four commands and two dataset formats. Picking the wrong pair costs an afternoon.
  • Evidence: adk web routes POST /dev/apps/{app}/eval-sets/{id}/add-session and .../run (dev_server.py). agents-cli 1.9.0 grades with the managed service only for built-in metrics (eval/cmd_grade.py); the scaffold’s default metric is a local LLM judge in tests/eval/response_quality.py that calls Gemini directly. Gen AI evals is the current name of the Gen AI evaluation service (release notes, 2026-04-22).
  • Gotchas: adk eval grades trajectory and ROUGE match in process, but safety_v1 and judge metrics call a model or the eval service and need a project (safety_evaluator.py). eval grade defaults to the global endpoint and 15 queries per second (--qps). agents-cli eval compare compares two results files, useful for baseline vs candidate. eval submit and results are experimental in 1.9.0.
  • Saving a session with add-session records the agent’s actual tool calls and replies as the expected ones, so a case saved from a buggy conversation passes until someone edits the expected calls. Say this out loud; it is the step people skip.
  • Metric choice, rubrics, and judges are Module 4, Agent Evaluation.
  • Hand-off: don’t explain why adk eval can’t fail a build yet. The next page shows it, and the room gets to guess the exit code first.

A failing eval that passes the build

You add adk eval as a build step, push a change that breaks a case, and the build goes green.

adk eval reports the failure and exits 0

$ adk eval app tests/eval/simple.evalset.json --config_file_path tests/eval/test_config.json
Eval Run Summary
simple:
  Tests passed: 0
  Tests failed: 1
$ echo $?
0
CorrectionFailed cases never change adk eval’s exit code. It exits non-zero on errors, for example google-adk[eval] not installed, an unreadable eval set, or an agent that fails to import. agents-cli eval run reports scores and never compares them to a threshold.

The same case in a pytest test, tests/eval/test_regression.py

import pytest
from google.adk.evaluation.agent_evaluator import AgentEvaluator

@pytest.mark.asyncio
async def test_regression_cases():
    await AgentEvaluator.evaluate(
        agent_module="app",
        eval_dataset_file_path_or_dir="tests/eval/simple.evalset.json",
    )

The failed case fails the step

$ pytest tests/eval
E   AssertionError: Following are all the test failures.
E   response_match_score for app Failed. Expected 0.9, but got 0.0.
1 failed
$ echo $?
1
Example

Actor: an agent whose model always replies “I cannot help with that.”

Input: one case expecting “Your refund is issued,” with response_match_score: 0.9 in test_config.json.

Mechanism: AgentEvaluator compares the score with the threshold and raises AssertionError; adk eval prints the same result and returns.

Result: exit 0 from adk eval, exit 1 from pytest, on google-adk 2.11.0.

Takeaway: gate on pytest with AgentEvaluator, or on your own check of a results file, never on adk eval’s exit code.
Sources: cli_tools_click.py (summary, no exit code) · agent_evaluator.py (the assertion) · reproduced locally 2026-10-07.
Speaker notes — A failing eval that passes the build
  • Why this page exists: page 7 listed the tools; this page shows which one can fail a build. Someone will go home and add adk eval as a build step. Without this page it passes forever.
  • Delivery beat: show the first block, ask for the exit code, let the room say 1, then show the 0.
  • Evidence: tested 2026-10-07 on google-adk 2.11.0 with a fake model and a one-case eval set: adk eval printed “Tests failed: 1” and exited 0; pytest tests/eval printed the two AssertionError lines and 1 failed, 9 warnings in 5.85s, exit 1. The real adk eval output also prints a “Using evaluation criteria” line first. adk eval exited 1 on a missing eval extra, an unknown eval-set id, and an agent that raises on import.
  • Thresholds: test_config.json next to the eval set is picked up by both tools. Without it ADK uses defaults of 1.0 for tool_trajectory_avg_score and 0.8 for response_match_score (eval_config.py). agents-cli eval grade writes results_<timestamp>.json; a script that reads it and exits non-zero is the non-pytest gate. No --fail-on flag exists at 2.11.0.

Speaker notes — Adding the eval to the generated pipeline
  • Why this page exists: page 8 showed which command can fail a build. This page shows where that command goes in the project students will generate.
  • Walk through it in order: the table shows that no stage runs an eval; the PR stage is the place to add it, so a bad change fails before merge; the three steps are the whole edit.
  • Likely question: “Why can’t the test use the files already in tests/eval/?” They are the agents-cli dataset and eval_config.yaml, used by agents-cli eval run. AgentEvaluator reads the ADK eval set format. That folder also has no test_*.py, so pytest tests/eval finds nothing until you add one.
  • On GitHub Actions, the same command goes in a new step of the pull request workflow.

  • If asked why a PR ran no checks: the generated triggers only fire on changes under app/**, tests/**, and deployment/**, or to uv.lock.

The pull-request job tests the merge result

One developer renames the tool get_order to lookup_order and merges. A second developer, on another branch, writes an instruction that says “call get_order to confirm the order shipped.” Each branch passed its own evals.

Git reports no conflict: the two edits touch different lines.

A GitHub Actions pull_request job checks out the merge of the branch into main, as of the last push to the pull request.

A merge queue (a GitHub option that re-tests each pull request on the latest main just before merging) catches a main that moved after the last run, if the workflow also listens for the merge_group event.

CaveatCloud Build’s pull-request trigger docs don’t say which commit it builds. Check before relying on it.
Example

Input: PR #42 after the rename is on main.

Mechanism: the PR job evaluates the merge commit; the model is told to call a tool that no longer exists, so it may skip the shipping check or attempt a call the agent rejects.

Result: the cases that expect a lookup_order call fail on the pull request, and the diff to read is the one paragraph in PR #42 illustrative.

Takeaway: on GitHub, the PR job tests your branch merged into main, which is where two changes that each pass alone first meet.
Sources: GitHub: events that trigger workflows (pull_request, GITHUB_REF) · GitHub: managing a merge queue (verified 2026-10-07).
Speaker notes — The PR job tests the merge result
  • Why this page exists: the gate on page 9 is only as good as the commit it tests. Show of hands first: does a PR job test the branch tip or the merge? Rooms usually split.
  • Evidence: for pull_request, GITHUB_REF is refs/pull/N/merge and GITHUB_SHA is the last merge commit; no run happens if the PR has a merge conflict, and if main moves after the last PR event the result is stale until the PR is updated (GitHub events doc above). Merge queues need merge_group in the workflow; the scaffold’s PR workflow has only pull_request. Speaker notes — Choosing a deployment target
  • Why this page exists: the choice is usually made on impressions. Delivery beat: read the top row, then ask the room what they need: a company domain, tasks over an hour, a GPU, no operations work. Each answer points to a column. Sessions get their own page next.
  • Selection guidance: Google’s architecture guide (last reviewed 2026-04-21) recommends Agent Runtime for a “fully managed experience with minimal operational overhead,” Cloud Run for serverless scaling with language flexibility, and GKE for “complex stateful requirements” and fine-grained configuration. It also says that using a platform you already manage can simplify long-term operations. It describes Agent Runtime as a fit for Python agents, but Deploy an agent allows any language through a Dockerfile or image; the deploy page is the more specific source. The same guide says Agent Runtime doesn’t host custom MCP servers, while Cloud Run and GKE can.
  • State: Memory Bank works “in any environment that has permission to read and write memories” (Set up Memory Bank), and Cloud Run needs an Agent Engine instance to use it (Host AI agents on Cloud Run). So the difference is who wires it up, not who can have it.
  • Duration: Use an ADK agent gives a 10-minute maximum for a streamed query and sends longer work to query jobs of up to seven days, with results written to Cloud Storage. Another page, Use a custom agent, says 15 minutes for streaming; check both before delivery. The 7-day figure is in the release notes (2026-04-22). No GKE limit is documented in these sources, so that cell is a statement about your own configuration.
  • Idle and hardware: on Agent Runtime, min_instances runs 0–75 with a default of 1; idle time isn’t billed while this is in Preview, which the docs say is subject to change. Cloud Run’s default minimum is 0, and idle instances are billed under instance-based billing even at 0. CPU options on Agent Runtime are 1, 2, 4, 6, or 8 vCPU, up to 32 GiB. Cloud Run recommends a GPU service for self-hosted models, and ADK names running open models as a reason to choose GKE. If the model is a hosted endpoint, the agent itself needs only CPU, so hardware won’t decide the choice.
  • If asked, these exist on all three, so they rarely decide the choice. Running code the model wrote: Code Execution on Agent Runtime (no Preview banner on 2026-10-07; re-check), Cloud Run sandboxes (Preview), GKE Agent Sandbox (GA 2026-05-20). Private VPC: a PSC interface on Agent Runtime, which you can’t change without recreating the resources (PSC interface); direct VPC egress or a connector on Cloud Run; native on GKE. Agent Gateway governs agents on all three.
  • Per-agent identity does differ: Agent Identity is GA and opt-in on Agent Runtime (IAM release notes, 2026-04-22), Preview on Cloud Run (Agent Platform features; gcloud beta run deploy --functional-type=agent --identity-type=agent-identity), and not listed for GKE (overview), which uses a Kubernetes service account. Pages 17 and 18 cover identity.
  • Agent Runtime custom containers listen on 8080; SDK support needs /api/reasoning_engine and /api/stream_reasoning_engine (runtime contract). For agents that suspend and resume, GKE also has Agent Substrate, for evaluation and non-production use, with production on an allowlist.

Where conversations are stored after a deploy

An agent deployed with adk deploy cloud_run works in testing. Once Cloud Run runs two instances, a follow-up message may fail with 404 Session not found.

A session is the stored conversation history and state that ADK reads on each turn. Each request names its session id, and the server looks it up in its session store.

By default, Cloud Run does not keep a conversation on one instance. It spreads requests across the instances that are running, so a follow-up can reach an instance that never saw the session.

Session affinity is an alternative: gcloud run services update --session-affinity makes Cloud Run send a client’s requests to the same instance, using a cookie the client must send back. It is best effort: when that instance stops or hits its concurrency or CPU limit, the next request goes to another instance and the session is gone.

Example

Input: adk deploy cloud_run … --session_service_uri=agentengine://123

Mechanism: both instances call the same Agent Platform Sessions resource; the engine can exist with no agent code deployed on it.

Result: whichever instance receives turn 2 reads s-7f3 from the shared store, and the conversation survives scale-in and restarts.

Takeaway: check which session store your deploy path writes; once there is more than one instance, use a shared store, or session affinity if losing a conversation when an instance stops is acceptable.

Sizing a deployment

CPU, memory, concurrency, and instance counts are ordinary service settings; what is easy to miss is whose defaults apply.

Two ways to size a Cloud Run service

Supporting services, and stamping the commit

Four services the pipeline uses, and one habit that lets you go from a misbehaving revision or trace back to the commit that built it.

Artifact Registry

Stores the built image. Scans it on push when the Container Scanning API is enabled.

Cloud Build

Runs the pipeline steps from a trigger: push, tag, or pull request.

Cloud Deploy

Versioned credentials. Reads are logged only when Data Access audit logs are on.

ADK’s Gemini client takes its location from that variable (google_llm.py). A live 404 on a deployed service was not run; the chain is tested in parts.
  • Lifecycle: retirement dates “won’t be moved to an earlier date”. The scaffold’s gemini-3.8-flash is GA, released 2026-09-02, retiring 2027-09-02 or later (Gemini 3.8 Flash, checked 2026-10-14); the lifecycle page lists it under “shorter terms,” with that date. Gemini 2.5 models retire 2026-10-20; don’t use them. -latest: the Gemini API models page says the alias “will get hot-swapped with every new release” and may point at a preview or experimental release.
  • Agent Runtime: its deploy doc says not to set GOOGLE_CLOUD_LOCATION, while agents-cli 1.9.0 sets it to global by default and comments that it isn’t reserved (deploy/agent_runtime.py); check after deploy. Model Registry versions models you tune or import, not Gemini ids you call. FallbackModel (ADK 2.9+) can answer from a different model; the gen_ai.request.model span attribute records which (_fallback_model.py).

Tools on a server you don’t deploy

A refund agent’s tools come from an MCP (Model Context Protocol) server, a separate service that lists, describes, and runs tools, that the payments team deploys on their own schedule.

ADK asks the server for its tool list on each use, by default. A new or reworded tool description reaches your model with no commit or deploy on your side; a cache lifetime (tool_list_cache_ttl_seconds) only delays it.

tool_filter limits which tools reach the model. A tool the server adds later stays hidden; the descriptions of the tools you keep still come from the server.

Agent Registry catalogs agents and MCP servers with search, IAM, and audit logs. Connecting through it controls who may call a server; it doesn’t freeze the server’s descriptions.

Run the eval set on a schedule, not only on your own pull requests, so a change on their side shows up as a failed run.

Example

Input: the payments team rewords issue_refund from “Issue a refund” to “Issue a refund or store credit” and deploys on a Wednesday.

Mechanism: the next tool listing carries the new description, and the agent starts offering store credit; nothing runs in your pipeline.

Result: Wednesday night’s scheduled eval run fails the cases that expect a refund; the expected and actual replies show store credit offered illustrative.

Takeaway: a remote tool is a dependency that changes outside your pipeline; schedule an eval run so you see the change.
Sources: mcp_toolset.py (tool_filter, tool_list_cache_ttl_seconds) · Agent Registry overview (verified 2026-10-07).
Speaker notes — Tools on a server you don’t deploy
  • Why this page exists: tool descriptions are what the model decides from. If the tools are in your repo, a description change is a diff and the PR gate covers it; this page is the case where they aren’t. Delivery beat: ask what in their setup would notice the Wednesday change.
  • Evidence: with the default tool_list_cache_ttl_seconds=None, McpToolset calls tools/list on every get_tools(), and ADK doesn’t subscribe to tools/list_changed (mcp_toolset.py above). Consuming through the registry (AgentRegistry.get_mcp_toolset, agent_registry.py) resolves URL and auth but still lists tools live. gcloud agent-registry mcp-servers list --format=json (2026-10-07) shows no owner or version field; a tools snapshot and updateTime exist, but whether the snapshot refreshes on a server deploy is not documented.
  • Registration (automatic registration): automatic for Agent Runtime; Cloud Run opt-in with gcloud beta run deploy --functional-type=agent|mcp-server; GKE by label; otherwise gcloud agent-registry services create. agents-cli publish registers with Gemini Enterprise, not Agent Registry (agents-cli publish --help, 1.9.0). Apigee and MCP Toolbox for Databases can publish servers. Model Armor screening at Agent Gateway is covered in Module 5, Security and Governance; access policy through the gateway is not covered in this course.

Section 3 recap

Pin an explicit model id and the location it is served in, both in the repo; run CI with the production location.

Model ids retire on published dates; upgrade through a pull request so the eval gate runs.

Remote MCP tools are listed live; filter which ones reach the model and run evals on a schedule.
