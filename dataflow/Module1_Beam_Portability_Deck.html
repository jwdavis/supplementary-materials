An abstraction layer between SDKs and runners

The portability framework lets a pipeline written with any SDK run on any runner. Without it, every SDK–runner pair is its own integration:

Before: every runner reimplements every SDK

After: one shared contract — N + M

Every ✗ is an integration someone would have to write and maintain. Python and Go on Flink and Spark simply did not exist before the shared contract.
Speaker notes — An abstraction layer between SDKs and runners
  • The definition really is one sentence — resist adding to it. An abstraction layer between SDKs and runners, so that any pipeline runs on any runner. The N×M → N+M picture is the "little insight" version of why the layer exists; it's the same argument as LLVM, ODBC, or JVM bytecode — reach for whichever analogy your room knows.
  • The concrete historical fact makes it real: before the framework, Python on Flink didn't exist. Not "was limited" — didn't exist.
  • The Beam roadmap's own framing is worth quoting: the goal is that "everybody can run everywhere," and the framework "enables cross-language pipelines (sharing I/O or transformations across SDKs) and user-customized execution environments ('custom containers')" — exactly the capabilities this module walks through (beam.apache.org/roadmap/portability).
  • What Beam itself is — pipelines, PCollections, transforms, the runner list — is covered in other modules. Don't re-teach it here.

How it works: the graph and the harness

  • Build time — your pipeline is serialized to a language-neutral proto (the Runner API); each transform declares the container environment it runs in
  • Run time — an SDK harness container runs your code, in your language, with your dependencies; the runner sends it work over gRPC (the Fn API)
  • The runner never imports your code — it talks to a container over a wire protocol
That one design choice is the whole module: swap the runner (Section 1), swap the container (Section 2), or mix containers in one job (Section 3).
Speaker notes — How it works: the graph and the harness
  • This is the only architecture slide in the module — lower the stakes out loud. Nobody needs to memorize the two API names; they need to recognize "SDK harness," "Runner API," and "Fn API" when they appear in logs and error messages.
  • The mental model that makes everything downstream obvious: your code runs in a container, and the runner talks to that container over gRPC. It does not link against your code. It does not import your modules. It sends work and receives results.
  • Two consequences worth stating explicitly: (1) if your code runs in a container you can specify, you control the entire runtime — Python version, native libraries, model files. That's the custom-containers section, and it should feel inevitable rather than magical. (2) If the boundary is a wire protocol rather than a language binding, nothing requires all the containers in one job to be the same language. That's the cross-language section.
  • Anyone who wants the full architecture — the individual gRPC services, the design docs — gets pointed at beam.apache.org/roadmap/portability. Don't teach it here.

The pipeline

Scenario: count orders per product category. Input: a CSV of orders in Cloud Storage. Output: a text file of counts.

Python — orders.pyimport apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions

def category_of(line):
    return line.split(",")[1]   # order_id,category,amount → "electronics"

with beam.Pipeline(options=PipelineOptions(argv)) as p:
    (p
     | "ReadOrders"  >> beam.io.ReadFromText("gs://my-bucket/orders/*.csv", skip_header_lines=1)
     | "GetCategory" >> beam.Map(category_of)
     | "CountPerCat" >> beam.combiners.Count.PerElement()
     | "Format"      >> beam.Map(lambda kv: f"{kv[0]},{kv[1]}")
     | "WriteCounts" >> beam.io.WriteToText("gs://my-bucket/out/counts"))
Note what is not in this code: no runner, no project, no region, no cluster, no worker count. The pipeline says what, never where.
Speaker notes — The pipeline
  • Walk the PCollection types along the diagram — the same edges will exist on all three runners.
  • The callout is the slide's real content. Have someone read the code and confirm out loud that there's no execution target anywhere in it. That absence is what makes the next slide possible.
  • PipelineOptions(argv) with nothing parsed in code is intentional — every runtime decision arrives from the command line. This is also the pattern the templates material builds on later in the course.
  • beam.combiners.Count.PerElement() rather than a hand-rolled Map + GroupByKey + sum is a deliberate best-practice choice: it's a Combine, so it pre-aggregates before the shuffle. Don't explain combiner lifting here (Module 5 does) — but don't model the bad version either.

Speaker notes — Run it three ways
  • This is the slide the old module was missing entirely. Run it live if you can; a DirectRunner execution on a small CSV takes seconds and makes the point better than any diagram.
  • Flag scope, precisely — students conflate "Beam flags" with "Dataflow flags": only --runner is core Beam. --project, --region, and --temp_location come from the Dataflow runner's GoogleCloudOptions; --flink_master comes from the Flink runner.
  • The honest caveat, again: this works cleanly here because ReadFromText and WriteToText are supported everywhere. A pipeline using a Google-Cloud-specific connector (say, WriteToBigQuery) would still run on Flink, but that connector's behavior and tuning differ. Portability is about the model, not a promise that every connector is equally good everywhere.
  • If someone asks how a Python pipeline runs on a Java engine at all — perfect. Point back at the harness slide from the intro: what crossed the wire was a proto, and a Python SDK harness container on the workers does the Python work.

Python — unit-testable without any clusterfrom apache_beam.testing.util import assert_that, equal_to

with beam.Pipeline() as p:
    result = (p
        | beam.Create(["1,electronics,50",
                       "2,books,20",
                       "3,electronics,15"])
        | beam.Map(category_of)

Speaker notes — Develop locally, deploy remotely
  • This is the practical payoff of portability students will use this week — don't let it get lost among the architecture. Portability isn't only about hedging against engine migrations someday; it's about a tight local test loop today.
  • beam.Create plus assert_that/equal_to from apache_beam.testing.util is the standard testing idiom. A student who leaves this module able to test a transform locally has gotten real value from it.
  • The strictness point is genuinely useful and counterintuitive: the DirectRunner deliberately randomizes bundle boundaries and element order so that code depending on order fails locally rather than mysteriously in production. "Works on DirectRunner but not Dataflow" is common; the reverse is rare, and that asymmetry is by design.
  • Cost angle for the budget-conscious: every DirectRunner iteration is a Dataflow job you didn't pay for.

Speaker notes — Section 2: Custom Containers
  • If students remember one hands-on skill from this module, it should be this. The arc: the failure they'll hit → the Dockerfile → build & push → launch → use what's inside → when to bother.
  • This works because of the harness model from the intro: the SDK harness is a container you can substitute your own image for.

The problem: it worked on my laptop

Scenario: your pipeline classifies product descriptions with a scikit-learn model. It needs scikit-learn==1.5.2, a pinned NumPy, a 40 MB model file, and a native library for text normalization. You submit to Dataflow:

ModuleNotFoundError: No module named 'sklearn'

Why: the default SDK harness container has the Beam SDK and its dependencies. It does not have yours.

ApproachProblem
--requirements_file=requirements.txtInstalls at worker startup — slow, repeated on every autoscale event, depends on PyPI being reachable
--extra_packages (local .tar.gz)Same startup cost; no native-dependency support
Custom containerEverything baked in ahead of time. Workers start ready.
Speaker notes — It worked on my laptop
  • Lead with the error message — it's the one students will actually hit, and recognizing it later is worth more than any abstraction.
  • Be fair to --requirements_file: genuinely fine for a small pure-Python pipeline with two or three lightweight dependencies, and less setup than a container. The failure modes disqualify it at scale: installs run at worker startup, so every autoscale event pays the cost again, and the job now depends on PyPI availability at run time. A large dependency tree can add minutes per worker.
  • The native-library requirement is the hard disqualifier — you cannot pip install a system package. There, a container isn't an optimization; it's the only option.
  • The 40 MB model file is a deliberate detail: baking model artifacts into the image is a real and common pattern for ML pipelines, much better than downloading from GCS in setup() on every worker.

The Dockerfile

Dockerfile# Base image must match your local Python + Beam versions
FROM apache/beam_python3.12_sdk:2.75.0

# Native deps first — they change least often
RUN apt-get update && apt-get install -y \
      --no-install-recommends libicu-dev \
 && rm -rf /var/lib/apt/lists/*

# Then Python dependencies
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt

# Then artifacts that change most often
COPY models/classifier.joblib /opt/models/classifier.joblib
ENV MODEL_PATH=/opt/models/classifier.joblib

# Do NOT override ENTRYPOINT — it starts the SDK harness

Image naming

apache/beam_<lang><ver>_sdk:<beam>
beam_python3.12_sdk:2.75.0
beam_java17_sdk:2.75.0 · beam_go_sdk:2.75.0

Rules that will bite you

  1. Pin the tag. Never :latest
  2. Match versions. Container Python + Beam must match the submitting environment
  3. Don't touch the ENTRYPOINT. It launches the SDK harness
Speaker notes — The Dockerfile
  • The layer ordering isn't cosmetic — Docker caches layers, so putting the slowest-changing things first means a model-file change rebuilds one small layer instead of reinstalling every dependency. Students iterating on a pipeline will feel this immediately.
  • Rule 2 is the error students will actually hit, so make the failure concrete: submit from Python 3.11 with a beam_python3.12_sdk image and you get serialization errors — your DoFns are serialized by the submitting interpreter and deserialized by the container's. Mismatched versions produce confusing failures deep in the job, not a clean error at submission.
  • Rule 3 catches people who treat this like an ordinary application image. The entrypoint is the SDK harness process from the intro diagram — override it and the runner has nothing to talk to.
  • If students have older internal Dockerfiles: FROM apache/beam_python3.8_sdk:2.25.0-era bases are a real migration item — Python 3.8 is long gone and 3.9 was dropped in Beam 2.75.0.

Speaker notes — Build and push to Artifact Registry
  • The registry change is the most concretely actionable correction in this module. Any student following an older tutorial that pushes to gcr.io will fail outright — the service is gone, not deprecated. Existing gcr.io URLs have been served from Artifact Registry since October 2025, so old references may resolve; new pushes do not.
  • gcloud builds submit versus local docker build && docker push is worth thirty seconds: Cloud Build needs no local Docker, produces consistent images, and is architecture-safe. Apple Silicon developers who build locally get an arm64 image Dataflow workers cannot run — a genuinely common and baffling failure. If building locally, --platform linux/amd64 is mandatory.
  • Same-region placement is a real performance item, not a nicety: every worker pulls the image at startup, so a cross-region pull is paid per worker on every autoscale event.

Using what's in the container

Pythonimport os
import joblib
import apache_beam as beam

class ClassifyFn(beam.DoFn):
    def setup(self):
        # Once per DoFn instance — NOT once per element.
        # The model is already in the image.
        self.model = joblib.load(os.environ["MODEL_PATH"])

    def process(self, product):
        label = self.model.predict([product.description])[0]
        yield product._replace(category=label)

classified = products | "Classify" >> beam.ParDo(ClassifyFn())
The pattern: heavy, immutable things (models, clients, lookup files) go in the image and are loaded in setup(). Never in process().
Speaker notes — Using what's in the container
  • Closing the loop matters — building an image is pointless if students don't know how to use what's inside it.
  • setup() versus process() is the performance lesson. setup() runs once per DoFn instance; process() once per element. Loading a 40 MB model in process() means loading it millions of times — the single most common performance bug in ML-adjacent Beam pipelines. The DoFn lifecycle gets full treatment in Module 5; here just plant the rule.
  • The ENV MODEL_PATH from the Dockerfile pays off here: the path lives in the image, not hardcoded in the pipeline, so a new model version is an image rebuild rather than a code change.
  • If asked why joblib: it's the scikit-learn convention and handles large NumPy arrays efficiently. Either way, serialized model files execute code at load time — only load artifacts you built and control; baking them into the image is part of what makes that guarantee hold.
  • Very large or frequently changing models: loading from GCS in setup() is the alternative — slower startup, but decoupled from the image lifecycle. Both are legitimate; the trade is image size and rebuild frequency versus worker startup time.

Speaker notes — When to reach for a custom container
  • The judgment slide. Custom containers add real overhead — a build step, a registry, versioning discipline, and a new way for version mismatches to bite. Don't sell them as universally correct.
  • The heuristic generalizes cleanly and is worth repeating: move work from run time to build time. Every second of per-worker startup is paid again on every autoscale event, and streaming pipelines autoscale continuously.
  • The last row previews the cross-language section — a multi-language pipeline has more than one SDK harness image in play. Not a bolted-on feature; the same environment mechanism doing exactly what it was designed for.

The problem: the connector is in the wrong language

Scenario: your team writes Python. You need to read from Kafka, enrich the events, and write to BigQuery. The mature, battle-tested KafkaIO connector is written in Java.

Speaker notes — The connector is in the wrong language
  • The original module opened this topic with a mesh diagram of every SDK connected to every other SDK — a picture of a capability, with no problem attached. This version leads with the problem, because the capability is unremarkable until you've felt the alternative.
  • Kafka is the canonical example because the asymmetry is real and long-standing: Java's I/O ecosystem is by far the most mature, and Python teams were locked out of it. The same applies to JDBC, Spanner, and Snowflake connectors.
  • Ask the room which of the three "before" options they'd have picked. The two-pipeline hop is the one experienced people choose — name what it costs: an extra Pub/Sub topic, its throughput bill, another deployment to monitor, and end-to-end latency that's now the sum of two pipelines.
  • Don't reveal the mechanism yet — the next slide shows the scenario as ordinary-looking Python code, and the two slides after that explain how the Java gets in and how it runs.

The solution: one Python pipeline, Kafka to BigQuery

Python — kafka_orders.pyimport json
import apache_beam as beam
from apache_beam.io.kafka import ReadFromKafka

def parse_order(kv):
    key, value = kv          # Kafka records arrive as (key, value) bytes
    return json.loads(value)

with beam.Pipeline(options=options) as p:
    (p
     | "ReadOrders" >> ReadFromKafka(       # Java — KafkaIO
           consumer_config={"bootstrap.servers": BOOTSTRAP},
           topics=["orders"])
     | "Parse"     >> beam.Map(parse_order)  # Python
     | "LargeOnly" >> beam.Filter(            # Python
           lambda o: o["amount"] >= 100)
     | "WriteToBQ" >> beam.io.WriteToBigQuery(# Python
           "my_project.analytics.large_orders",
           schema="order_id:STRING,amount:NUMERIC"))
ReadFromKafka is a thin Python wrapper — the code it stands for is Java. Next two slides: how the Java gets into your graph, and how it runs.
Speaker notes — The solution: one Python pipeline, Kafka to BigQuery
  • The punchline: it looks like ordinary Python. No FFI, no bindings, no subprocess management, nothing to install beyond the Beam SDK (and a local JRE — that gotcha gets its own slide). Have the room find anything in the code that looks Java-flavored; there isn't anything except the transform's pedigree.
  • Walk the diagram: one node is red. Recall the intro — every transform in the graph is tagged with the container environment it runs in. This pipeline is simply a graph whose transforms carry two different tags. That sentence is the entire definition of a multi-language pipeline.
  • Small real-world detail worth a sentence: ReadFromKafka emits (key, value) byte pairs, so the first Python step is always a parse/decode — that's why parse_order exists.
  • WriteToBigQuery here is the Python transform — the point of the example is one Java transform at the edge, Python everywhere else.

At build time: expansion

  1. Your script reaches ReadFromKafka — a thin wrapper with no Kafka code inside
  2. The wrapper starts the expansion service, a small local Java helper process, and asks it to expand the transform: "give me the real KafkaIO"
  3. The service returns KafkaIO as language-neutral proto, tagged with the Java container it needs
  4. Those transforms are spliced into your graph beside your Python ones — and you submit as usual
From the intro: every transform in the graph names the container it runs in. "Expansion" just splices in transforms that name the Java container.
Speaker notes — At build time: expansion
  • Define the terms before leaning on them — this slide exists so "expansion service" and "expand" are never used un-introduced. The expansion service is a helper process that knows the Java transform catalog; "expanding" a transform means asking it for the transform's real subgraph, returned as the same language-neutral proto everything else in the graph is made of.
  • Expansion happens once, at build time, on your machine — not per element, and not on the workers. This is also the setup for the next-but-one slide: building a multi-language pipeline needs a local JRE precisely because this Java helper runs on the submitting machine.
  • --experiments=use_portable_job_submission will show up in job details if anyone looks — the Dataflow runner adds it automatically for multi-language pipelines. An artifact to recognize, not a flag to set.

At run time: two harnesses, side by side

  • The runner reads the merged graph and starts one container per environment on each worker — here, one Java and one Python
  • There is no Python-to-Java bridge inside either process: two containers, each running its own transforms, exchanging elements over gRPC
The intro's model, unchanged — the runner talks to containers over a wire, so it doesn't care that one job now has two kinds.
Speaker notes — At run time: two harnesses, side by side
  • The misconception to kill: students assume a live Python-to-Java bridge (JNI, a subprocess, py4j). There isn't one. At run time there are two peer containers; the runner hands Kafka-reading work to the Java harness and Parse/Filter/Write work to the Python harness, and elements flow between them over the Fn API data channel.
  • The element crossing is real work — serialize on one side, deserialize on the other. For a connector at the edge of the pipeline it's paid once per element and is negligible; a cross-language transform in the middle of a hot path pays it twice. This is the setup for the closing advice: cross-language at the edges, native in the middle.
  • Everything else about the job is normal: autoscaling, monitoring, and draining don't care how many harness environments a worker runs.

Error: Java not found. Please install Java or set JAVA_HOME.

You do not write Java. You do not deploy Java. But the machine that builds the pipeline needs a Java runtime, because it starts the expansion service locally.

Speaker notes — The gotcha: you need Java locally
  • The single most common cross-language support question, and it will happen in the lab. Frontloading it converts a confusing failure into a recognized one.
  • The distinction that resolves the confusion: build-time dependency, not a run-time one. Your workers get Java through a container the runner pulls automatically. Only the machine constructing the pipeline needs a JRE, because that's where the expansion service starts.
  • A real CI/CD trap worth naming: a containerized build environment that includes Python but not Java will fail to submit multi-language pipelines, with an error that looks nothing like "your build image is missing a package."
  • Transform Service is the newer, cleaner answer for teams that can't install a JRE. Mention it, point at the Beam programming guide, don't teach it in depth.

Managed I/O: the current best practice

ReadFromKafka is one hand-built wrapper, with its own API shape — and every connector has a different one. Managed I/O is the same cross-language machinery behind one uniform API: name a connector, pass a config map.

        "catalog_name": "my_catalog",
        "catalog_properties": {...},
    })

# Write to BigQuery
rows | managed.Write(
    managed.BIGQUERY,
    config={"table": "my_project.analytics.orders"})

Speaker notes — Managed I/O
  • Land the transition first: nothing new is happening underneath — managed.Read(KAFKA, ...) expands through the same expansion service and runs in the same Java harness the previous slides explained. What changes is the front door: one API shape for every connector, instead of one hand-built wrapper per connector.
  • Managed I/O didn't exist when the original module was written; it's now the recommended entry point for these sources and sinks.
  • The intent bullet is the deepest one. When you call ReadFromKafka directly, the runner sees an opaque transform. With managed.Read(KAFKA, ...), it sees "this pipeline wants to read Kafka" as structured intent — and can substitute a better implementation, tune parallelism, or upgrade the connector without you changing code. That's a materially different relationship between pipeline and runner.
  • Connect it back: Managed I/O is built on cross-language transforms. The Java-versus-Python question disappears into the config map. This is what the portability framework was for — students should see the harness model, cross-language, and Managed I/O as one arc landing here.
  • Also worth noting: the Python-native SpannerIO is deprecated in favor of the cross-language version. The direction of travel is clear.

Cross-language: when and why

Reach for it when

  • The connector you need exists in another SDK (usually Java I/O from Python)
  • A specific library only exists in one language
  • Teams in different languages need to share transforms

Costs to know about

  • A local runtime for the other language at build time
  • More containers at run time — slightly higher worker memory, slower startup
  • Elements cross a process boundary — serialization on both sides
Practical guidance: prefer Managed I/O where it covers your connector. Use direct wrappers (ReadFromKafka, ReadFromJdbc) where it doesn't. Hand-written ExternalTransform only for genuinely custom cases.
Speaker notes — Cross-language: when and why
  • The judgment slide, matching the containers section's shape. Cross-language is not free and shouldn't be presented as such.
  • The serialization cost is the one people underestimate. Elements crossing between a Python and a Java harness get encoded and decoded on both sides. For an I/O connector at the edge of the pipeline this is negligible — it happens once. For a transform in the middle of a hot path, it's real overhead. Cross-language at the edges, native in the middle is the rule of thumb.
  • The three-tier guidance is the actionable takeaway: Managed I/O first, wrappers second, ExternalTransform only when you must. Most students will only ever need the first tier.

Module summary

The portability framework

  • An abstraction layer between SDKs and runners — one shared contract instead of N×M integrations
  • Build time: the pipeline becomes a language-neutral proto (Runner API); each transform declares its container environment
  • Run time: your code runs in an SDK harness container the runner drives over gRPC (Fn API)

What it buys you

  • Different SDKs, different runners — the same pipeline on your laptop, Dataflow, or Flink
  • Custom containers — --sdk_container_image, built to Artifact Registry
  • Cross-language pipelines — Java connectors from Python via the expansion service; prefer Managed I/O
Three flags worth remembering--runner=DataflowRunner        # which engine
--sdk_container_image=$IMAGE  # your runtime
--experiments=enable_portable_runner
                    # only Java streaming
