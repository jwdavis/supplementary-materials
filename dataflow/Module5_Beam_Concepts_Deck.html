Beam Fundamentals

Speaker notes — Section 1: Beam Fundamentals
  • Quick pulse-check before diving in: ask who has written a Beam pipeline before, in any language. The answer calibrates your pace through this section — it's a genuine intro for newcomers and a five-minute recap for veterans.
  • The goal of the section is twofold: the vocabulary (Pipeline, PCollection, PTransform, Runner — words used constantly all week) and the run mechanics (how the same code targets a laptop or Dataflow via options).

What is Apache Beam?

  • Open source, unified programming model for batch and streaming data pipelines
  • Same SDK, same classes, same transforms — whether your data is bounded (a file) or unbounded (a stream)
  • SDKs in Java, Python, and Go (plus Beam SQL)
  • You write your pipeline once; a runner decides how it actually executes
Write once, run anywhere.
Speaker notes — What is Apache Beam?
  • The unified model is the headline. Historically batch and streaming meant two systems, two codebases, two teams (at Google: MapReduce/FlumeJava for batch, MillWheel for streaming). Beam descends from the Dataflow model paper that unified them; Google donated the SDK to Apache in 2016.
  • Map the vocabulary early: bounded data → what people mean by "batch"; unbounded → "streaming." Beam's terms describe the data, not the engine, and the same transforms operate on both.
  • Read the diagram plainly: the three boxes on the right are the runners — there is no separate "runner" component sitting between your code and them. You name exactly one at launch (the --runner flag, two slides ahead) and the pipeline is handed to it. The DirectRunner runs on your machine for development and testing; Dataflow is one of several production runners. Portability is real insurance — teams do move pipelines between runners — but be honest that IO connectors and feature support vary by runner.
  • Beam SQL and the DataFrames API are also entry points; both compile down to the same model and both have a dedicated module later.

The four core concepts

  • Pipeline — the whole job, structured as a DAG: a directed graph of steps, no cycles — data only flows forward
  • PTransform — a node in the graph: consumes PCollections, produces new ones
  • PCollection — an edge: the dataset flowing between transforms
    • distributed — partitioned across many workers; no one machine holds it all
    • immutable — never modified; every transform emits a new one
  • Runner — executes the DAG on a backend
Immutable ≠ copied: a "new PCollection" is a new edge in the graph, not a physical duplicate. Immutability is what makes distributing — and safely retrying — the work possible.
Speaker notes — The four core concepts
  • These four words carry the whole week. The diagram says the quiet part out loud: a pipeline is a DAG — PTransforms are the nodes, PCollections are the edges. Branches and merges are normal (Read feeding two transforms here; Flatten merging later); "acyclic" because data only flows forward. The job graph in the Dataflow console is literally this picture.
  • What "distributed" means, concretely: a PCollection with a billion elements never sits on one machine — it's split into partitions spread across the workers, each holding a slice in memory or on disk. Apply a Map and every worker runs the function over its own slice at the same time. This is also why a PCollection has no index, no "first element," and no random access — it isn't a list; it's a dataset scattered across a cluster.
  • Immutability: the mutate-in-place habit comes from the single-machine world where memory was scarce. Here, transforms never modify their input — so there's no shared state to lock, workers can process their partitions independently, and (Section 5) a failed piece of work can simply be re-run from its unchanged input.
  • "Isn't producing a new PCollection every step wasteful?" No — a new PCollection is a new edge in the graph, a logical handle, not a duplicated dataset. At run time the runner decides what actually gets stored: consecutive per-element steps are typically fused, meaning an element passes from Map straight into Filter as an ordinary function call, and the "intermediate PCollection" never exists as stored data at all. Immutability is a rule about what your code may observe (never a modified input) — not an instruction to copy anything. Fusion is covered properly in Section 5.

Building a pipeline

Scenario: read a text file from Cloud Storage, compute the length of each line, write the results back out.

Pythonimport apache_beam as beam

p = beam.Pipeline()
(
    p
    | "ReadLines"      >> beam.io.ReadFromText("gs://my-bucket/input.txt")
    | "GetLineLengths" >> beam.Map(len)
    | "WriteOut"       >> beam.io.WriteToText("gs://my-bucket/output")
)
p.run()   # nothing executes until here
  • Each | adds a step to the graph and returns the new edge (a PCollection); Java uses .apply(...) chaining — same idea
  • The string before >> is the transform label — unique per step, and it becomes the step name in the Dataflow job graph
Build, then run. Everything above p.run() only constructs the DAG — no data moves. run() hands the finished graph to the runner for execution.
Speaker notes — Building a pipeline
  • Two phases, visible in the code's shape: the pipe expressions only add nodes and edges to the DAG — nothing executes, no data moves. p.run() is the moment the finished graph is handed to the runner. A print statement placed between transforms runs at construction time, before any data exists — the classic first-day confusion, now answerable from the slide.
  • run() returns a PipelineResult and, on Dataflow, does not block — the job is submitted and the script continues; call result.wait_until_finish() to block on completion. The DirectRunner executes locally.
  • Students will meet with beam.Pipeline() as p: in samples and docs — the context manager just calls run() (and waits) on exit. We teach the explicit form because it keeps build-vs-execute visible; the with shorthand is fine once that distinction is solid.
  • Push hard on labels. They must be unique per step, and they're the step names in the Dataflow UI — two anonymous beam.Map(len) steps are indistinguishable in the job graph. Skipping labels is the single most common debugging regret.
  • Java equivalent: p.apply("ReadLines", TextIO.read()...) chained; execute with p.run().waitUntilFinish().

Running a pipeline: PipelineOptions

Runtime behavior — which runner, which project, where to stage files — is set via PipelineOptions, parsed from --flag=value args. A few options are core Beam; each runner contributes its own.

FlagPurpose
Core Beam — every runner
--runnerWhich runner (DirectRunner, DataflowRunner)
Dataflow runner only — GoogleCloudOptions

The pipeline code doesn't change between local and cloud — only the options passed in. That's the payoff of the unified model.
Speaker notes — PipelineOptions
  • Give each flag a sentence: --runner picks the engine; --project/--region say where the job runs; --temp_location and --staging_location are GCS paths where Beam uploads your code, dependencies, and shuffle/temp data so workers can fetch them; --job_name is what you'll see in the console.
  • Scope matters — these are not all "Beam" flags. Only --runner is core Beam. The rest are contributed by the Dataflow runner (Python: GoogleCloudOptions; Java: DataflowPipelineOptions) and mean nothing to other runners — Flink and Spark bring their own flag sets. Switch runners and the core flags survive; the runner-specific ones get swapped out.
  • DirectRunner is also the default when --runner is omitted — so a bare python3 my_pipeline.py runs locally.
  • The green callout is the point of the slide: identical code, different options. Local iteration with DirectRunner on a data sample, then the same script to Dataflow.
  • Java: PipelineOptionsFactory.fromArgs(args).create() does the parsing; flags arrive via mvn ... -Dexec.args="--runner=DataflowRunner ...".

Custom pipeline options

Parameterize your own pipeline the same way — define custom flags instead of hardcoding paths and table names.

Pythonclass MyOptions(PipelineOptions):
    @classmethod
    def _add_argparse_args(cls, parser):
        parser.add_argument("--input_path", required=True)
        parser.add_argument("--output_table", required=True)

opts = MyOptions()  # parsed from the command line
p = beam.Pipeline(options=opts)
(p | beam.io.ReadFromText(opts.input_path) | ...)
p.run()
python3 my_pipeline.py --input_path=gs://... --output_table=proj:ds.table \
  --runner=DataflowRunner --project=$PROJECT_ID --region=$REGION ...
Speaker notes — Custom pipeline options
  • This is the lab's "parameterize the execution of the pipeline" objective — students will write exactly this class. Teaching it before the lab means the pattern won't be a surprise.
  • Custom flags and standard flags ride together on one command line; Beam routes each flag to the options class that declares it. Under the hood it's argparse, so required=, default=, type=, and help= all work.
  • The "why": hardcoded paths mean editing code to rerun against new data or a different environment. Options make the same artifact reusable across dev/test/prod — this is also the foundation the later templates material builds on.
  • The other idiom students will see in samples: a plain argparse.ArgumentParser plus parser.parse_known_args() — the known args become the app's own flags, and the leftover list is handed to PipelineOptions(pipeline_args) for Beam. Google's wordcount example does exactly this. Both idioms are fine; the subclass form keeps everything in one options object and is what template-style pipelines build on.
  • Java: define an interface extending PipelineOptions with getter/setter pairs and @Description/@Validation.Required annotations.

Speaker notes — Section 2: Built-in Transforms
  • The section order is deliberate: the built-ins are what students will actually write most days, so they come first. ParDo appears in the next section as "the thing these are all made of."
  • Arc of the section: per-element transforms (Map, FlatMap, Filter) → key-value plumbing → grouping and aggregating (GroupByKey, CombinePerKey) → combining and splitting whole PCollections (CoGroupByKey, Flatten, Partition).
Map

Map: one element in, one element out

Scenario: normalize a field — uppercase every word.

Pythonuppercased = words | beam.Map(str.upper)
  • Takes a plain function, applies it to every element — strictly 1 : 1
  • Same picture as the DAG: Map is a node; words and uppercased are edges — the boxes just show what's flowing on each edge (Java: MapElements)
Speaker notes — Map
  • Deliberately the simplest possible starting point: a plain function, applied per element, one out for one in. Any callable works — here str.upper itself, no wrapper needed.
  • Tie the diagram back to the DAG picture: the node is the transform, the labeled edges are the PCollections, and the callout boxes just show what's flowing along each edge.
  • The function ships to the workers — it's serialized together with everything it references. Concrete example to give: big_table = load_lookup_csv() at module top (say 500 MB), then def enrich(row): return (row, big_table[row.id]) used in a Map. Because enrich references big_table, the whole 500 MB gets serialized and dragged to every worker along with the function. Keep referenced state small — big lookup data belongs in a side input (Section 4) or loaded once per DoFn instance in setup() (Section 5).
FlatMap

FlatMap: any number out, per element in

Scenario: tokenize lines of text — each line becomes many words.

Pythondef split_into_words(line):
    return line.split()

words = lines | beam.FlatMap(split_into_words)
  • Every element the function returns (or yields) lands in the output PCollection — 0, 1, or many per input
  • This is the general shape of per-element processing; Map is the "always exactly one" case
Speaker notes — FlatMap
  • Walk the counts in the diagram: 2 lines in, 6 words out — the output count per element is whatever the function's returned list contains.
  • "Should it yield instead of return?" Either satisfies FlatMap (the function must return an iterable; lists and generators both qualify). Prefer return when the whole collection already exists — line.split() has built the list, so a generator adds code without saving memory. Prefer yield when outputs are produced incrementally and could be numerous, or when emission is conditional at several points. (The DoFn examples later use yield deliberately: in process() a bare return value is a bug — it must be an iterable — so yielding removes the trap.)
  • The confusion to preempt: "wouldn't this produce 2 elements, each a list?" That's what Map would do — beam.Map(split_into_words) yields 2 list-elements. FlatMap flattens the returned iterable: each item inside it becomes its own element in the output PCollection. That flattening is the "Flat" in FlatMap — worth demonstrating live with both transforms if the question comes up.
  • Returning an empty list drops the element entirely — conditional emission. Plant that now: it's exactly the move the next slide formalizes as Filter.
  • split_into_words is spelled out as a named function for teaching; beam.FlatMap(str.split) would work identically here.
  • Java: FlatMapElements.
Filter

Filter: a specialized FlatMap

Scenario: drop empty lines. FlatMap can already do this — emit the element unchanged, or emit nothing:

Pythondef keep_non_empty(word):
    if len(word) > 0:
        return [word]    # emit the element, unchanged
    return []            # emit nothing

non_empty = words | beam.FlatMap(keep_non_empty)

Filter states the same intent directly — give it a predicate:

Pythondef is_non_empty(word):
    return len(word) > 0

non_empty = words | beam.Filter(is_non_empty)
One machine, three output counts: Map — exactly one · FlatMap — zero or more · Filter — zero or one, the element unchanged.
Speaker notes — Filter
  • The FlatMap version is on the slide to prove a point, not as a recommendation: Filter is a FlatMap constrained to "the unchanged element, or nothing." Showing the general form first makes the specialized one obvious.
  • Be precise about what returns what: the predicate function returns True or False, but the transform's output is 0 or 1 elements into the output PCollection — always the element itself, never a boolean.
  • Named predicate functions (is_non_empty) beat inline lambdas in teaching and in production code alike — they show up by name in stack traces and are testable on their own.

Key-value pairs: the prep for grouping

Grouping, aggregating, and joining (next) all operate on key-value pairs — in Python, plain 2-tuples. A few small transforms handle the plumbing.

Python# Sale: a NamedTuple with fields region, amount
def key_by_region(sale):
    return sale.region

keyed   = sales | beam.WithKeys(key_by_region)
regions = keyed | beam.Keys()
records = keyed | beam.Values()
Per-element recapOut, per element in
Mapexactly 1
FlatMap0, 1, or many
Filter0 or 1, unchanged
No magic: each of these is a one-line Map under the hood — a hand-written Map returning (key, value) tuples is exactly equivalent.
Speaker notes — Key-value pairs
  • Key-value pairs have no special class in Python — a KV is literally a 2-tuple, and any transform that "wants keys" just expects tuples. (Java is typed: KV<K, V>.)
  • "What's a Sale?" PCollection elements can be any serializable Python object — dicts, tuples, NamedTuples, dataclass instances. The examples use a typing.NamedTuple because attribute access (sale.region) reads well, and NamedTuple is what Beam's Python schema support builds on (Schemas module, later). Dicts are equally common in real pipelines — especially from BigQuery or JSON sources — where the same function would read sale['region'].
  • If asked whether WithKeys/Keys/Values are "real" transforms: yes — predefined in both SDKs (Python: apache_beam.transforms.util; Java: org.apache.beam.sdk.transforms) — but they're pure conveniences: in the SDK source, Keys() is a one-line MapTuple returning the first element. Teach the concept (get your data into tuples), not the catalog.
  • The worked example makes WithKeys' key behavior visible: the key is added alongside the element — the whole Sale is still there as the value; Keys and Values just project one side back out (note records round-trips to the original input). Also worth flagging: for aggregation you often don't want the whole element as the value — a plain Map returning (sale.region, sale.amount) is the right prep for a per-key sum.
  • The recap table closes out the per-element family before switching gears: everything so far was element-at-a-time; grouping (next) is the first transform where elements have to meet.
GroupByKey

GroupByKey: collect all values per key

Scenario: from (city, ZIP) records, list every ZIP code for each city.

Python# zip_records — Rec is a NamedTuple(city, zip):
#   Rec(city='Lexington', zip='40513'),
#   Rec(city='Seattle',  zip='98125'), …

def as_city_zip(rec):
    return (rec.city, rec.zip)

city_zips = (
    zip_records
    | beam.Map(as_city_zip)
      # ('Lexington', '40513')
    | beam.GroupByKey()
      # ('Lexington', ['40513', '40502'])
)
What works: every value for a key arrives together — the full iterable, for arbitrary per-group logic (formatting, medians, custom rules).
The concern: the values are re-partitioned by key across the network (the shuffle), and each key lands on one worker. A hot key means one overloaded worker while the rest idle (Section 6).
Speaker notes — GroupByKey
  • The first transform where elements have to meet: input is (key, value) pairs; output is one (key, iterable-of-values) pair per distinct key. Getting there requires a shuffle — values are re-partitioned by key so that all values for a key end up on the same worker.
  • "Does every value really cross the network?" Strictly, no — a value that already sits on the worker its key is assigned to wouldn't need to move, which averages 1/N of the data with N workers. So at any real scale, effectively everything moves. And on Dataflow specifically, shuffled data is written to the Dataflow Shuffle service (batch) or Streaming Engine (streaming) rather than kept on worker disks — decoupling shuffle state from workers is what lets the job autoscale and recover from worker loss without redoing the shuffle. "Every value crosses the network" is the right first-order model to teach.
  • Reach for GroupByKey when you genuinely need the whole group at once. What that means concretely:
    • Formatting a list — this scenario's output is the list of ZIPs; there's nothing to reduce.
    • Median / exact percentiles — the middle value can only be found with every value present at once (and sorted). There is no way to keep a "running median" the way you keep a running sum: absorbing values one at a time throws away information the final answer needs.
    • Order-dependent logic — e.g. turning a user's clicks into sessions: you must sort the group by timestamp before walking it.
    The common thread: the computation cannot be done by looking at values one at a time in arbitrary order. When it can — sum, count, max — the next slide's transform is the better tool.
  • The concern panel plants Section 6: one-worker-per-key is a semantic bound, so a hot key concentrates work no matter how many workers you add. And if all you do with the group is fold it down to a value, the next slide is the better tool.
Combine

CombinePerKey: reduce values per key

Scenario: total sales per salesperson, from ('amara', 120.0) pairs.

Pythontotals = sales | beam.CombinePerKey(sum)
         # ('amara', 342.5)

grand_total = (
    sales
    | beam.Values()
    | beam.CombineGlobally(sum)
)        # one number overall
  • Works with sum, min, max, beam.combiners.MeanCombineFn — or your own CombineFn (next slide)
Because sum is associative & commutative, each worker pre-aggregates before the shuffle — no worker ever owns a giant pile. Section 6 quantifies the win.
Speaker notes — CombinePerKey
  • The decision rule vs. GroupByKey. "Fold the group into a value" means collapsing it to a single result — a sum, a count, a max. The naive version students write: keyed | beam.GroupByKey(), then a Map or DoFn that loops over the list adding things up. Same answer — but GroupByKey must first move every raw value across the network and hand the complete list to one worker (with the hot-key problem from the last slide) before that loop ever runs. Combine states up front what will be done with the group, so the runner can do most of the adding before the data moves — the complete list never has to exist anywhere. Tell-tale sign in code review: if the step after a GroupByKey starts with a for-loop that accumulates, it wanted to be a Combine.
  • Combiner lifting, from the ground up. Two properties of sum make the trick legal:
    • Associative — grouping doesn't matter: (a+b)+c = a+(b+c). You may add in any batches.
    • Commutative — order doesn't matter: a+b = b+a. You may add in any order.
    Together they guarantee: partial sums computed over scattered pieces of the data, in any order and any grouping, merge into the same final answer. So the runner "lifts" part of the aggregation ahead of the shuffle — each worker sums whatever values it happens to hold (the partials in the diagram), ships only its per-key subtotals, and the subtotals merge after the shuffle. The runner cannot prove these properties by reading your code: using Combine is the declaration — that promise is the entire point of expressing the aggregation this way (and if the function secretly depends on order, you get wrong answers, not an error). Counterexample that makes it land: subtraction is not associative — (10−3)−2 ≠ 10−(3−2) — so "reduce by subtraction" cannot be safely lifted.
  • Custom CombineFn: for when the mergeable state differs from the answer — the next slide walks the classic example (mean) in code.
  • CombineGlobally reduces the whole collection to a single element. Its windowed nuances (without_defaults) belong to the windowing module — park them.
CombineFn

Custom CombineFn: when state ≠ answer

Scenario: average sale per salesperson. You can't merge means — mean([1,2])=1.5 and mean([3])=3 don't give you mean([1,2,3])=2 — so the working state must carry (sum, count).

Pythonclass MeanFn(beam.CombineFn):
    def create_accumulator(self):
        return (0.0, 0)          # (sum, count)

    def add_input(self, acc, value):
        s, n = acc
        return (s + value, n + 1)

    def merge_accumulators(self, accs):
        sums, counts = zip(*accs)
        return (sum(sums), sum(counts))

    def extract_output(self, acc):
        s, n = acc
        return s / n if n else 0.0

avg_sale = sales | beam.CombinePerKey(MeanFn())
In practice, reach for built-ins first (beam.combiners.MeanCombineFn, Count, Top) — write your own when no built-in matches your state shape.
Speaker notes — Custom CombineFn
  • The core insight, worth saying twice: the accumulator is the mergeable state, and it is not the answer. For sum they happen to coincide (a partial sum merges by summing), which is why plain sum works as a callable. For mean they differ — and that difference is the entire reason CombineFn exists.
  • Walk the code against the diagram: add_input runs per value on whichever worker holds it (building the pre-shuffle partials); merge_accumulators runs at the lifting boundary, combining partials from different workers — it's the method that makes combiner lifting possible; extract_output runs once per key at the very end. The numbers match the previous slide: 120 + 95 + 127.5 = 342.5 across 3 sales → 114.17.
  • Small production details worth mentioning: guard the empty-accumulator case in extract_output (division by zero), and keep accumulators small and serializable — they travel over the network.
  • Other real examples of "state ≠ answer" if asked: min and max tracked together, a weighted average (sum of products + sum of weights), top-N (a bounded heap).
CoGroupByKey

CoGroupByKey: join by key

Scenario: find orders that haven't shipped. Answering that requires matching each order with its shipments by order ID — CoGroupByKey does the matching.

Pythonjoined = (
    {'orders': orders, 'shipments': shipments}
    | beam.CoGroupByKey())

def is_unshipped(kv):
    order_id, groups = kv
    return len(groups['shipments']) == 0

unshipped = joined | beam.Filter(is_unshipped)
  • Both inputs already keyed by the same key (the order ID)
  • Output per key: both sides' matches as lists, tagged by the dict names — an empty list is an unmatched row, which is exactly what the scenario needs
Speaker notes — CoGroupByKey
  • The scenario has a goal beyond matching — that's deliberate. Matching is the means; the empty-list side is the signal. Walk the diagram: o-1042 matched both sides; o-1043 has shipments: [], and the Filter turns that into the answer.
  • Output shape: one element per key — (key, dict of lists, tagged by the input names you chose). From that, every join flavor is a small per-element step: inner = both lists non-empty; left outer = keep every order, tolerate an empty shipments list (this scenario is left-outer-join thinking); full outer = keep everything.
  • "Why doesn't Beam just have a Join transform?" (it will come up): Beam's core keeps the primitives minimal, and a relational join is "cogroup, then a per-key step" — so Beam exposes the primitive. That buys you n-way joins (three entries in the dict), explicit control over unmatched rows, and a job graph where the one shuffle is visible. Higher-level joins — Beam SQL's JOIN, DataFrames merge, Java's join-library extension — are conveniences built on CoGroupByKey.
  • If the inputs aren't keyed yet, a Map or WithKeys gets them there first (last section's plumbing).
  • Contrast with Flatten (next): CoGroupByKey matches different-typed collections by key; Flatten merges same-typed collections with no matching at all.
Flatten

Flatten: merge same-type PCollections

Scenario: identically formatted click events arrive from three sources, landing in three PCollections. Downstream processing shouldn't care where an event came from — it wants one collection.

Pythonall_events = (
    (us_events, eu_events, apac_events)
    | beam.Flatten()
)
  • A union, not a join — no keys, no matching; the elements are simply merged
  • All inputs must share the same element type
Don't confuse with CoGroupByKey: Flatten merges same-typed collections; CoGroupByKey matches different-typed collections by key.
Speaker notes — Flatten
  • Be precise about what travels: the events arrive from three sources; because they share one format (one element type), the three PCollections can be merged and every downstream step is written once instead of three times.
  • Same shape appears with: regional Pub/Sub topics, monthly files, or parallel branches of your own pipeline converging.
  • The output's element order is arbitrary — but PCollections are unordered anyway, so nothing is lost.
  • Cheap: no shuffle, no matching — the runner just treats the inputs as one logical collection.
Partition

Partition: split one PCollection into several

Scenario: route log records by severity — errors page someone, warnings get reviewed, info goes to cheap archive. One pass over the data, three destinations.

PythonSEVERITIES = ['INFO', 'WARN', 'ERROR']

def by_severity(log, num_partitions):
    return SEVERITIES.index(log.severity)

info, warn, error = (
    logs | beam.Partition(by_severity, 3))

error | beam.io.WriteToBigQuery(alert_table)
warn  | beam.io.WriteToBigQuery(review_table)
info  | beam.io.WriteToText('gs://logs/archive')
  • The function returns a partition index; the number of outputs is fixed when the graph is built
  • The opposite of Flatten — each output is an ordinary PCollection with its own downstream steps
Need one slice → Filter · a top-N ranking → beam.combiners.Top · every slice continuing to different processing → Partition
Speaker notes — Partition
  • The scenario is chosen so every output is used — differently. That's the honest home turf of Partition: severity routing, hot/warm/cold storage tiers, A/B experiment splits, per-customer-tier enrichment. If only one slice would be consumed (e.g. "just the top decile"), Partition is the wrong tool — a Filter or beam.combiners.Top says that directly.
  • Mechanics: the function receives (element, num_partitions) and returns an index; the result unpacks into ordinary PCollections (info, warn, error = ..., as in the official transform catalog), each starting its own branch of the DAG.
  • Why the count is fixed at graph-construction time: the DAG is static — each output is an edge, and edges can't be added while the job runs. (Severity levels known up front fit that constraint naturally.)
  • Related tool to disambiguate: routing decided inside a DoFn (e.g. parse success/failure) → tagged outputs, coming in Section 3. Partition is the declarative version for a fixed, known set of routes.

ParDo + DoFn: who does what

  • ParDo ("parallel do") — the transform: a node in the DAG that says "apply this logic to every element, in parallel"
  • DoFn ("do function") — the object holding the logic: its process() method is called once per element
  • You write the DoFn; ParDo handles the distribution

Speaker notes — ParDo + DoFn: who does what
  • Keep the two names cleanly separated: ParDo is the transform — the node you'll see in the job graph; the DoFn is the object you hand it, holding the per-element logic. An analogy that lands: ParDo is the machine, the DoFn is the die you insert into it.
  • process() is a generator: yield zero, one, or many times per element — the same 0/1/many framing as Map, FlatMap, and Filter from last section.
  • Why a class rather than a function? The class gives the logic a home for lifecycle methods and per-instance resources (clients, buffers) — Section 5. For logic that needs none of that, the wrappers are shorter.
  • Java: extend DoFn<InputT, OutputT>, annotate the method with @ProcessElement, emit via OutputReceiver, apply with ParDo.of(new ComputeWordLengthFn()).

What actually happens when a ParDo runs

  • Your DoFn is serialized and shipped to every worker; each worker builds its own copies
  • Workers process their bundles independently — no coordination between them; that's why adding workers adds speed
  • All the workers' outputs together form the new PCollection — bundles, retries, and the DoFn lifecycle in depth: Section 5
Speaker notes — What actually happens when a ParDo runs
  • This is the mental picture for the rest of the module. Nothing in the DoFn's code says "distributed" — the fan-out is entirely the runner's job. Your contract: correct logic for one element; the runner's contract: run it everywhere the data is.
  • What "copies" means, concretely: when the job starts, every worker deserializes your DoFn class and constructs its own instances of it. One instance works on one bundle at a time; a worker running several bundles in parallel therefore has several instances alive at once, and instances are kept and reused for later bundles rather than rebuilt. The exact reuse rules — and why they matter once a DoFn holds state — are Section 5.
  • Preempt the question this picture raises: "can process() see other elements?" No — one element at a time, on whichever worker holds it. Anything that needs data beyond the element leads either to grouping (already covered) or to side inputs (Section 4) — this slide is the setup for both.

Multiple outputs: the dead-letter pattern

A tagged output is a named output stream of a ParDo: each emitted element is addressed to a tag, and each tag becomes its own PCollection. The classic use: route bad records aside instead of crashing the pipeline.

Pythonclass Transform(beam.DoFn):
    def process(self, element):
        try:
            yield beam.pvalue.TaggedOutput('success', transform_element(element))
        except (ValueError, KeyError):
            yield beam.pvalue.TaggedOutput('failure', element)   # → dead-letter queue

output = input | beam.ParDo(Transform()).with_outputs('success', 'failure')
# output bundles one ordinary PCollection per tag, accessed by name:
clean  = output.success   # a PCollection — continues the pipeline
failed = output.failure   # a PCollection — write to a "failed records" table
Without this, one malformed record either fails the whole job (batch) or retries forever (streaming). Route bad data aside deliberately — Section 5 shows exactly how failures propagate.
Speaker notes — Multiple outputs: the dead-letter pattern
  • Walk the try/except: success path emits the transformed element tagged success; the except path emits the original element tagged failure — you want the raw record in the dead-letter queue, not a half-transformed one.
  • Production hygiene: catch the specific exceptions you expect (here ValueError/KeyError), never bare Exception — a blanket catch quietly dead-letters genuine bugs you'd want to crash on and fix. And enrich the dead-lettered record: attach the error message and a timestamp so triage doesn't require reproducing the failure.
  • "Are clean and failed real PCollections?" Yes. .with_outputs() returns a DoOutputsTuple, and accessing a tag — by attribute (output.success) or by index (output['success']) — hands back an ordinary PCollection (verified against the SDK). Downstream, each is just another edge in the DAG: typically failed goes to a BigQuery table or GCS path for inspection and replay.
  • Sell this as near-mandatory for streaming: one poison message otherwise retries indefinitely and can stall the pipeline. In batch it saves the whole job from one bad row.
  • Forward reference: the "why" behind the warning callout — bundle retries and failure semantics — is Section 5. If questions start there, promise them two sections ahead.

  • The one-sentence framing to repeat throughout: a side input is a broadcast, not a join. Small data copied to every worker, so the big data never shuffles.

Two scenarios, same shape

A — a single computed value

Flag any order above the average order value. The average is one number — computed from the entire dataset.

B — a small lookup table

Convert transaction amounts to USD using a 200-row currency table.

Same shape both times: every element needs a small piece of data that isn't part of the element. And recall from the ParDo section — per-element code sees one element at a time, on whichever worker holds it.
Speaker notes — Two scenarios, same shape
  • The setup slide — name the shape before any API appears. Two flavors of the same need: a value computed from the data itself (the average) and reference data from elsewhere (the currency table).
  • The load-bearing recall from the ParDo runtime slide: per-element code holds exactly one element, on one worker. The rest of the dataset — and anything else the element needs — is not just "somewhere else in memory"; it's on other machines.
  • Ask the room "so how would you do it?" before advancing. The common wrong answers, worth naming as they come up: compute the average inside the per-element function (impossible — the rest of the data isn't reachable, and it would redo a whole-dataset computation per element), or join on a dummy key (works, but shuffles the entire big collection to meet one number). The right way: side inputs

Speaker notes — The right way: side inputs
  • Walk the argument's journey: CombineGlobally produces a one-element PCollection; AsSingleton declares it a side input; passed as an extra argument to beam.Filter, it arrives in above_avg(order, avg) where avg is already a plain float — no unwrapping.
  • Why this beats the naive approaches: the average is computed once, by a real aggregation step in the pipeline (not per element — per-element code couldn't see the dataset anyway); and only the small side moves — the runner materializes it and broadcasts one copy to each worker, where it's cached in memory. The orders never shuffle.
  • The views: AsSingleton (exactly one value), AsDict / AsMultiMap (keyed lookups — the currency table), AsList / AsIter (everything).
  • Side inputs ride along as extra function arguments on any per-element transform — the wrappers shown here, or a DoFn, where the value arrives as an extra process() parameter.
  • For warehouse-fluent audiences: this is a broadcast join by another name.
  • Streaming fine print, flag and defer: side inputs are computed and matched per window — an element in window W sees the side-input value for window W. Full story in the Windows & Triggers module.

Good fit

Small, broadcastable data that fits comfortably in worker memory and changes rarely (per window at most):

Data that is large, or that varies per key — that's a join: use CoGroupByKey.

Broadcast small · join big

How Pipelines Execute on a Cluster

So far, a pipeline is a graph of transforms. Now: what actually happens when Dataflow runs that graph across dozens of machines — how work is split, how it scales, and what happens when something fails.
FundamentalsBuilt-in transformsParDo & DoFnSide inputsExecutionSkew
Speaker notes — Section 5: Execution on a Cluster
  • The arc of the section: bundles (the unit of work) → parallelism (how work spreads and where it can't) → failures (retries and their consequences) → the DoFn lifecycle, which only makes sense once bundles and retries are understood.
  • Motivation to offer: you can write correct pipelines without this section, but you cannot debug slow or failing pipelines without it.

Splitting work: bundles

  • The runner splits each PCollection into bundles and hands bundles to workers — the bundle, not the element, is the unit of work (and of retry)
  • Bundle size is the runner's tradeoff: smaller → less lost work on failure, more overhead (streaming); larger → more efficient (batch)
  • A worker runs several bundles at once (separate threads), each with its own DoFn instance — multiple copies of your DoFn are live in one process
  • Bundles don't align with keys: after a grouping step, one bundle can hold pairs for many different keys
Speaker notes — Splitting work: bundles
  • "The bundle is the unit of work and the unit of retry" is the load-bearing sentence of the whole section — the failure-handling slide and the lifecycle slide both stand on it. Say it twice.
  • Bundle division is arbitrary and chosen by the runner, not by you. The tradeoff it's balancing: persist results after every element (max safety, max overhead) vs. retry everything on failure (min overhead, max lost work). Streaming runners commit small bundles frequently for latency; batch runners use large bundles for throughput.
  • Unpacking the two fine-print bullets:
    • Several DoFn copies per process: a worker executes multiple bundles concurrently on separate threads, each thread with its own DoFn instance. Consequence: module-level globals are shared across those threads — not a safe home for mutable state. Keep state on the instance, managed through the lifecycle methods (coming up).
    • Bundles ≠ keys: a bundle is just a slice of the data stream. After a GroupByKey, one bundle can interleave pairs for many keys — so a DoFn that accumulates per-key state must key its accumulator (a dict by key), never assume "this bundle = one key." The Bigtable example later buffers rows for many keys in one batcher.

  • Narrate the numbers in order. ⓪ the DAG from the code. ① one input PCollection of raw log lines. ② the runner splits it into bundles and spreads them across workers — note that amy's and bo's lines are mixed across both workers; nothing is organized by key yet. ③ each worker runs the fused parse→filter→pair chain over its own bundle, element by element, as plain function calls — the bot /ping line is dropped inside Worker 1 and never touches the network or disk.

  • Because element-wise work is freely re-splittable, this is also where autoscaling and Dynamic Work Rebalancing operate: any worker can take any bundle, and a straggler's remaining work can be re-split mid-job.

Failure handling and retries

  • Bundles are the unit of retry: if your code raises an uncaught exception while processing any element, the runner discards the bundle's work and retries the whole bundle — not just the failing element
  • This is exactly why the DoFn rules matter:
    • Don't mutate external state from process() — a retry would re-apply the mutation
    • Clear per-bundle state in start_bundle() so a reused DoFn instance doesn't leak state from a previous (possibly failed) bundle
  • Repeated bundle failure → job fails (batch) or the element retries indefinitely (streaming) — which is why the dead-letter pattern matters: route bad data aside deliberately, don't let one malformed record poison retries
  • Autohealing is separate: Dataflow detects and replaces unhealthy VMs transparently — infrastructure-level recovery, not bundle-level
Rule of thumb: write process() as if it may run more than once for the same element — because on retry, it will.
Speaker notes — Failure handling and retries
  • Keep the three layers distinct — they're different mechanisms with different owners:
    • Bundle retries — your code's concern: process() must tolerate re-execution.
    • Dead-lettering — your design's concern: bad data routed aside on purpose.
    • Autohealing — Dataflow's concern: unhealthy VMs replaced transparently.
  • Concrete numbers help: batch retries a failing bundle 4 times, then fails the job; streaming retries indefinitely — a poison message can stall a streaming pipeline forever, which is the strongest argument for the dead-letter pattern from Section 3.
  • The idempotency rule of thumb in the callout is the takeaway. Example to give: "increment a counter in an external DB from process()" — on retry the count is wrong. Batch external writes in finish_bundle, or write to idempotent sinks.

Lifecycle in practice: the Bigtable sink

From Beam's own Bigtable connector — batching writes across the bundle lifecycle:

Pythonclass _BigTableWriteFn(beam.DoFn):
    def start_bundle(self):
        if self.table is None:                      # DoFn instances persist across bundles —
            client = Client(project=self.beam_options['project_id'])
            instance = client.instance(self.beam_options['instance_id'])
            self.table = instance.table(self.beam_options['table_id'])

        self.batcher.flush()                          # commit before the next bundle
        self.batcher = None

Speaker notes — Lifecycle in practice: the Bigtable sink
  • Walk the three methods against the lifecycle diagram from the previous slide — this is real Beam source, not a toy.

  • The batcher, by contrast, is per-bundle: fresh in start_bundle, flushed in finish_bundle, nulled after. Flushing before the bundle commits is what keeps a retry from double-writing half a bundle's worth of buffered mutations.
  • Frame it as the template to copy: any DoFn that writes to an external system should look like this — expensive client per instance, buffered writes per bundle, flush in finish_bundle.

Data Skew

Grouping is the one place where parallelism is bounded by your data. When one key is much hotter than the rest, here's what goes wrong — and what to actually do about it.
FundamentalsBuilt-in transformsParDo & DoFnSide inputsExecutionSkew
Speaker notes — Section 6: Data Skew
  • Connect back to the parallelism slide: the shuffle is where parallelism is bounded by keys, and skew is that bound biting. The constraint is semantic (one worker per key in GroupByKey), not scheduling — so Dynamic Work Rebalancing can't fix it, and the remedy has to come from how you aggregate.
  • Shape of the section: the problem, then salting (the hands-on fix for a truly hot key), then the complete what-to-do list — make sure the section ends on the resolution, not the problem.

Why skew hurts at scale

  • GroupByKey sends all values for a key to one worker — with a hot key, one worker grinds through a million values while the other idles after a thousand
  • The stage finishes when the slowest key finishes; wall-clock time and cost are both set by your worst key
Speaker notes — Why skew hurts at scale
  • Walk the numbers: a million values for x, a thousand for y. GroupByKey's contract puts each key on one worker, so Worker 1 does 1000× the work while Worker 2 idles — and both are billed for the whole stage.
  • Both symptoms matter: wall-clock (the stage is as slow as the hottest key) and cost (idle workers you're paying for). In the Dataflow UI this looks like one long-running stage with most workers at low CPU.
  • Real-world hot keys to name, because students will hit them: null or default IDs (the classic — every record missing a customer ID shares one key), "unknown"/catch-all categories, celebrity users, and single-tenant-dominated datasets.
  • Repeat the point from the divider: Dynamic Work Rebalancing cannot help — the work isn't re-splittable because the grouping contract pins the key to a worker.

Salting a hot key, step by step

One key ('x') dominates the data, so one worker gets the whole pile. Salting temporarily turns that one key into several, spreads the pile, then merges the partial results.

Pythondef salt(pair):
    key, value = pair
    shard = random.randint(0, 2)
    return (f'{key}-{shard}', value)   # 'x' → 'x-1'

def unsalt(pair):
    salted, subtotal = pair
    return (salted.rsplit('-', 1)[0], subtotal)

totals = (pairs
    | beam.Map(salt)
    | beam.CombinePerKey(sum)   # 3-way parallel
    | beam.Map(unsalt)          # 'x-1' → 'x'
    | beam.CombinePerKey(sum))  # merge 3 partials
For Combines this ships built-in: beam.CombinePerKey(sum).with_hot_key_fanout(10) — prefer it over hand-rolling. Legal for the same reason lifting is: the partials merge because sum is associative & commutative.
Speaker notes — Salting a hot key
  • Build it up in three sentences: (1) The problem is that one key = one worker, so a hot key's pile can't spread. (2) The trick: append a random shard number to the hot key — 'x' becomes 'x-0', 'x-1', 'x-2' — so the shuffle now sees three keys and spreads the pile across three workers, each producing a subtotal. (3) Strip the suffix and aggregate once more: key 'x' now has only three small partial values to merge — the second stage is trivially cheap.
  • Why it's legal: identical reasoning to combiner lifting — summing in two rounds gives the same answer only because the aggregation is associative & commutative. Salting does not work for whole-group logic (a median can't be computed from sharded sub-medians).
  • Random vs. deterministic salt: random is fine here — if a bundle fails and retries, its outputs are discarded wholesale, so elements landing on a different shard the second time is harmless.
  • Choosing the fanout: enough shards to spread the hot key across your workers — single digits to low tens; more shards only add second-stage work.
  • In real code, prefer the built-in: with_hot_key_fanout(n) (Java: Combine.perKey(fn).withHotKeyFanout(n)) implements exactly this diagram inside the Combine.

What to actually do about skew

  1. Prefer Combine over GroupByKey + custom reduce whenever the aggregation is associative & commutative — this alone fixes most skew-driven slowdowns
  2. Push grouping toward the end of the pipeline. Filter and map before the GroupByKey so the skew-sensitive step sees as little data as possible
  3. Salt hot keys when one key is unavoidably huge — the previous slide's two-round aggregation; for Combines, with_hot_key_fanout(n) does it built-in
  4. Design keys with cardinality in mind — a low-cardinality status field makes a poor key when a higher-cardinality composite key would distribute evenly
  5. Know when to stop. Sometimes skew is a property of the data itself — a truly hot customer or item. Then the honest answer is "this step's runtime is bounded by your worst key," not a magic setting
Speaker notes — What to actually do about skew
  • Salting has its own slide now — here it's item 3 in the toolbox; refer back rather than re-deriving it.
  • Item 4's example: keying by status with five possible values caps parallelism at five workers no matter the cluster size — a composite key like (status, region) may serve the same downstream need and distribute far better.
  • End on item 5's honesty: sometimes the data is skewed and the bound is real. Knowing that saves teams from chasing a setting that doesn't exist.
