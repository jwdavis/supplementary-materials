Speaker notes — Section 1: What Dataflow actually does

  • The section answers, in order: who runs the pipeline (1.1), what submission actually does (1.2), what the cluster is (1.3), how data gets split and moved (1.4), how the graph is rewritten (1.5), how the cluster resizes (1.6), what streaming adds (1.7), and what it all costs (1.8).

You wrote a pipeline. Now who runs it?

Scenario for this module: nightly sales files land in Cloud Storage (~500 GB). Your Beam pipeline computes revenue per product and writes it to BigQuery. Later, the same events arrive continuously on Pub/Sub.

  • A Beam pipeline is a description of a computation — a graph. It does nothing until a runner executes it
  • Running it at this scale needs:
    • machines — enough of them, then none of them
    • splitting the input across those machines
    • regrouping data for the aggregation
    • surviving machine failures mid-job
  • Dataflow is the Google Cloud runner: a fully managed service that does that whole list, per job
Speaker notes — You wrote a pipeline. Now who runs it?
  • Anchor the scenario — it carries the whole module. Batch flavor: nightly files, revenue per product, BigQuery. Streaming flavor (from slide 1.7 on): the same events on Pub/Sub. Every diagram that follows is this pipeline.
  • Be honest about the alternatives rather than dismissive: the DirectRunner is genuinely the right tool for development and unit tests, and a self-managed Flink or Spark cluster is a legitimate choice for teams that already operate one. Dataflow's pitch is specifically no cluster operations: nothing exists before the job, nothing is left after it.
  • The "needs" list is the section's table of contents in disguise: machines (1.2–1.3), splitting and regrouping (1.4), surviving failure (1.4), plus two things the student may not know to ask for yet — graph optimization (1.5) and autoscaling (1.6).

What happens when you run your pipeline

Speaker notes — What happens when you run your pipeline
  • This is the module's anchor diagram — it returns, annotated, on the last slide, and Module 3 hangs the whole IAM story on the same picture (who is allowed to do each arrow).
  • Worth being precise about what "submitting" is, because two different payloads travel: the code (JARs / Python packages) goes to the Cloud Storage staging location for the workers to download at startup; the graph (serialized to JSON) goes to the Dataflow API (projects.locations.jobs.create). The service never runs your code — it runs the graph; your code runs on the workers.
  • Two boxes, two owners: the Dataflow service lives in a Google-managed project; the worker VMs are ordinary Compute Engine instances in your project (visible in the console, billed as Dataflow SKUs). Worker VMs aren't shared across pipelines — resources are allocated per job.
  • The cleanup guarantee is a docs quote worth repeating: "By default, Compute Engine VMs are deleted when the Dataflow job completes, regardless of whether the job succeeds or fails." Nothing to remember to tear down.
  • References: Pipeline lifecycle, Security and permissions.

A cluster per job, managed for you

  • Workers are ordinary Compute Engine VMs — you can see them in the console, but you never create, SSH to, patch, or delete them
  • Per-job and ephemeral: two jobs = two independent worker pools; no shared cluster to size or schedule around, no idle cluster to pay for
  • You set the knobs you care about — the service chooses the rest:
    • --max_num_workers — the ceiling (best practice: set this, not an exact size)
    • --machine_type — only if you must; by default Dataflow selects the machine type, and the disk, for you
  • Contrast: on a self-managed cluster, sizing, upgrades, and bin-packing jobs onto it are your problem
Speaker notes — A cluster per job, managed for you
  • "Serverless with visible servers" is the honest description: the VMs are real and in your project (students will meet them again in Module 3 when they hit CPU and in-use-IP quotas), but their lifecycle is entirely the service's job.
  • Machine-type defaults changed in the docs: don't teach "the default is n1-standard-1" anymore — the fixed per-mode defaults are gone from the quotas page. The teachable sentence is the worker-VM guide's: "By default, Dataflow selects the machine type for the worker VMs that run your job, along with the size and type of Persistent Disk." Override with --machine_type (Python) / --workerMachineType (Java) only when the job's profile demands it; shared-core types (f1-micro, e2-small…) aren't supported under the SLA.
  • If asked for the feature name, the docs are currently inconsistent: the quotas page says "By default, Dataflow uses Auto VM Selection to select machine types… from a flexible range of compatible VM families at runtime," but the right-fitting page describes Instance Flexibility (Auto VM Selection) as something that turns on when you use min_ram/cpu_count resource hints — and notes it isn't supported with Dataflow Prime. Safest classroom line: "you don't pick a machine type unless you need to; Dataflow does" — without leaning on the feature name.
  • Fixing --num_workers to "tune" a job mostly disables the service's best feature (autoscaling, slide 1.6). The knob worth setting is the ceiling — it bounds both cost and quota consumption.
  • References: Configure worker VMs, Auto VM Selection.

The plumbing you don't write: splitting and moving data

500 GB of sales files must be read by many workers at once — and then records for the same product must find each other for the aggregation.

  • Input is split into bundles, handed to workers; a failed bundle is retried automatically — 4 attempts in batch, indefinitely in streaming
  • Where all values for a key must meet, Dataflow runs the shuffle — repartitioning data by key across workers. You write CombinePerKey; the service moves the data
  • Dynamic work rebalancing: a straggler's remaining work is split and given to idle workers — no manual sharding
  • Corollary: hand-rolled sharding (withNumShards) caps the parallelism Dataflow may find — let the service choose
Speaker notes — The plumbing you don't write
  • Connect back to Module 5's GroupByKey slide if students have seen it (course order varies): there the shuffle was a Beam concept — "values for a key must meet." Here it becomes a service responsibility — Dataflow does the repartitioning. Where that shuffled data physically lives is Section 3's entire story; plant the question now: "while the shuffle is in flight, where is that data?"
  • Bundle retry semantics are worth stating precisely (they're exam-favorite facts): batch retries a failing bundle 4 times, then the whole job fails; streaming retries indefinitely — which is why a poison-pill record can stall a streaming pipeline (the dead-letter pattern from Module 5 is the cure).
  • Dynamic work rebalancing triggers on work imbalances and stragglers; the docs' fine print: it can't split finer than a single record, and it needs parallelizable input (a source being read, or a materialized intermediate result). Its documented enemy is fixed sharding — withNumShards limits Dataflow "to parallelizing based on your chosen number of shards." Google's blog name for this is "liquid sharding" — same feature.
  • References: Dynamic work rebalancing, Pipeline lifecycle (error handling), Beam execution model (bundles).

The service rewrites your graph before running it

Python(p
 | beam.io.ReadFromText('gs://sales/*')
 | beam.Map(parse_row)        # ┐
 | beam.Filter(is_valid)      # ├ fused:
 | beam.Map(to_amount)        # ┘ one pass
 | beam.CombinePerKey(sum)    # ← shuffle
 | beam.io.WriteToBigQuery(…))
  • Fusion: consecutive element-wise steps run as one stage, in a single pass — intermediate PCollections are never materialized
  • Combine optimization: aggregations combine locally on each worker before the shuffle — don't hand-roll this
  • Steps run in any order the data dependencies allow
Speaker notes — The service rewrites your graph
  • Why fusion matters to a student: adding more small, well-named steps costs approximately nothing at run time — so write readable pipelines. The expensive seams are the shuffle boundaries, and after this slide the student can read a job graph and point at them.
  • Docs wording worth quoting: fusing steps "prevents the Dataflow service from needing to materialize every intermediate PCollection," and the service "respects data dependencies… but otherwise steps might be executed in any order."
  • Combine optimization (partial / multi-level combining): each worker pre-sums its own records for a key, so what crosses the shuffle is one partial sum per worker per key, not every record. The docs say explicitly: "it is strongly recommended that you do not attempt to make this optimization by hand." This is also the setup for Section 3's cost punchline — shuffle is billed by the GiB.
  • If asked how to prevent fusion (the high-fan-out case: a step that expands each element into thousands, where fusing it with its consumer caps parallelism at the small input's size): the current documented tool is the Redistribute transform (Redistribute.arbitrarily / .byKey). Older material says Reshuffle — Beam now marks it internal-only.
  • Reference: Pipeline lifecycle (fusion optimization, combine optimization, prevent fusion).

Autoscaling: the cluster resizes itself mid-job

  • On by default for all batch jobs, and for streaming jobs on Streaming Engine
  • Batch: worker count re-evaluated about every 30 seconds from progress and estimated remaining work
  • Streaming: tracks source backlog and worker CPU utilization
  • You set the ceiling — --max_num_workers (defaults to 2,000, which is also the per-job quota)
  • Billing follows actual workers, per second — scale-down is money back
  • The one exception: Persistent Disk is billed on the exact value of --max_num_workers, not the average — so a ceiling isn't free when workers carry big disks
Best practice: don't pin --num_workers to "tune" a job. Set a max; let the service move within it.
Speaker notes — Autoscaling
  • Precision on the defaults, per current docs: "Horizontal Autoscaling is enabled by default on all batch pipelines," and it's on by default for streaming jobs that use Streaming Engine. A non-Streaming-Engine streaming job needs --autoscaling_algorithm=THROUGHPUT_BASED plus a max — one more quiet reason Streaming Engine (Section 4) is the recommended path.
  • The batch signal is not CPU alone: the service estimates the pipeline's parallelism (threads needed to process the remaining work efficiently) and re-plans roughly every 30 seconds. Streaming scales on backlog plus utilization.
  • Flags: --max_num_workers (Python/Go) / --maxNumWorkers (Java); a minimum can be pinned with --dataflow_service_options=min_num_workers. The autoscaling page states the default plainly: "The default value is 2,000" — and the quotas page's limit matches: "Each Dataflow job can use a maximum of 2,000 Compute Engine instances," rising to 4,000 for Streaming Engine streaming jobs or service-based Shuffle batch jobs when no worker zone is specified.
  • The Persistent Disk exception is the pricing page verbatim: "Compute Engine usage is based on the average number of workers, whereas Persistent Disk usage is based on the exact value of --maxNumWorkers." A streaming job allocates its disk pool up front (1:1 worker:disk minimum, up to 15 disks per worker as the pool is redistributed). Where it bites: a non-Streaming-Engine streaming job carries 400 GB per disk, so an absurdly generous ceiling is a real line item. With Streaming Engine's 30 GB boot disks (or Shuffle's 25 GB), it's noise. So: a generous ceiling, not an unlimited one.
  • The diagram's second message is the billing model preview: the bill is the area under the step curve. That framing makes slide 1.8's per-second billing bullet obvious instead of novel.
  • Vertical autoscaling (resizing worker memory) exists but is a Dataflow Prime feature — park it unless asked.
  • Reference: Horizontal Autoscaling.

Streaming: correct answers, even out of order

The same sales events now arrive on Pub/Sub. Mobile clients retry uploads — events arrive late, and sometimes twice. You want per-hour revenue, correct.

  • Exactly-once processing (the default): every record gets a unique ID; Dataflow tracks IDs it has processed and discards redeliveries — sums stay correct
  • A watermark: "a threshold that indicates when Dataflow expects all of the data in a window to have arrived" — a high-water mark on event time: everything below the line has arrived, so the 2–3 PM window can close and emit while data keeps flowing
  • Watermarks are Beam semantics, not a Dataflow feature — every runner tracks one, and the data source determines it
  • Dataflow's edge is the estimate: its own Pub/Sub connector reads a private API — the age of the oldest unacknowledged message — for a low-latency, high-accuracy watermark. Beam's reference Pub/Sub connector (other runners) can only estimate from messages it has already seen
  • Late data isn't silently lost — Beam's windowing model (allowed lateness, triggers) decides; details in the streaming modules
Speaker notes — Streaming semantics
  • Altitude control: the goal is that students can say what a watermark is and what Dataflow does about it that a self-configured runner doesn't. Windowing mechanics, triggers, and allowed lateness get their own modules — park the details. The next slide walks one window through in wall-clock time.
  • Why it's called a watermark (students ask): it's the water-level metaphor, a high-water mark. Picture arrived data as water rising up the event-time axis; the watermark is the line it has risen to — everything below the line is submerged (has arrived), everything above may still be coming. The research lineage (Google's MillWheel, the Dataflow model paper — the systems behind this service) calls it the low watermark: the oldest event time that could still be outstanding. Nothing to do with the faint stamp on paper.
  • Why the diagram draws it past 3:00 rather than at 3:00: the watermark is a moving threshold that advances as the backlog drains — the window closes at the moment it passes 3:00, and the drawing shows a moment shortly after. At wall-clock 3:00 the watermark is usually still short of 3:00 (messages in flight, phones retrying); minutes later the oldest unacknowledged message has an event time past 3:00 — say 3:05 — so the watermark stands at ~3:05 and the 2–3 PM window has closed. The gap between wall clock and watermark is exactly the data freshness chart in the monitoring UI.
  • Exactly-once mechanics, one level deeper if the room wants it: every step-to-step output is checkpointed; each worker keeps time-bucketed Bloom filters over seen record IDs so the dedup check rarely touches stable storage. For Pub/Sub, dedup keys on the message ID (or a custom attribute via withIdAttribute).
  • Two honest caveats if probed: (1) exactly-once covers the pipeline's processing, not user-code side effects — an external API call inside a DoFn can still fire twice on retry; (2) there is a cheaper at-least-once streaming mode (--dataflow_service_options=streaming_mode_at_least_once) for ETL-style pipelines that tolerate duplicates — it returns in Section 4.
  • The runner contrast, said carefully — don't claim other runners lack watermarks. Beam's programming guide: "Beam tracks a watermark… In practice, your PCollection's data source determines the watermark, and watermarks can be more precise or complex." What differs is the estimate: the Pub/Sub docs say Beam "provides a reference implementation of the Pub/Sub I/O connector for use by non-Dataflow runners," while Dataflow's custom implementation uses Google-internal APIs "to offer low-latency watermarks, high watermark accuracy, and efficient deduplication." Some connectors do put the estimate in your hands (KafkaIO's configurable watermark policies are the classic example) — but that's per-connector, not "all other runners."
  • Is the "intelligent" part only about Pub/Sub? Essentially yes: the legacy course phrase "intelligent watermarking" maps to Dataflow's source-side estimation for Pub/Sub (the private API above, plus a "tracking subscription" it creates to inspect event times in the backlog). Watermark tracking and propagation through the pipeline graph is standard Beam on every runner.
  • References: Exactly-once processing, Read from Pub/Sub to Dataflow, Streaming pipelines (watermark definition), Beam programming guide §8.4.

Watching one window close

Two clocks matter. The wall clock means nothing to the pipeline — the watermark passing 3:00 is what closes the 2–3 PM window.

Python(p
 | beam.io.ReadFromPubSub(
       subscription=sub)
   # each message stamped with event time
 | beam.WindowInto(
       window.FixedWindows(3600))
   # hourly windows, on event time
 | beam.Map(lambda e: (e.product, e.amount))
 | beam.CombinePerKey(sum)
   # emits when the watermark
   # passes the window's end
 | beam.io.WriteToBigQuery(…))
The gap between the two clocks is the Data freshness chart in the Dataflow monitoring UI.
Speaker notes — Watching one window close
  • This slide exists to separate the two clocks. Students' instinct is "at 3:00 the hourly window closes." Walk the timeline slowly: at wall-clock 3:00 the watermark is still at 2:58, because the service can see that messages with older event times are still unacknowledged — closing now would drop them. Four minutes later nothing older than 3:05 is outstanding, the watermark passes 3:00, and that is the close. The lag is the price of a correct answer — and it's visible as Data freshness in the job's monitoring page.
  • Where Dataflow gets its confidence (this is the "intelligent" part, and it's Pub/Sub-specific): the custom connector reads a private Pub/Sub API for "the age of the oldest unacknowledged message in a subscription," and when the pipeline uses event timestamps, Dataflow also creates a tracking subscription to inspect the event times still in the backlog. That's how it can assert "nothing older than 3:05 is still out there" instead of guessing.
  • On a runner using Beam's reference Pub/Sub connector, the same pipeline still has a watermark — but it's estimated only from messages already seen, so it advances less accurately: either cautiously (results always later than needed) or optimistically (more data lands late).
  • The 3:09 event: it's in the 2–3 PM window by event time but arrived after the result was emitted. Beam's default configuration does not allow late data (it's discarded); allowed lateness and triggers can instead re-emit a corrected pane. That's the streaming course's opening act — here, plant only "the model has a policy for this."
  • References: Read from Pub/Sub to Dataflow (private API, tracking subscription), Dataflow monitoring interface (data freshness).

The theme: get state off the workers

One idea explains the rest of this module — why the service moves job state out of the worker VMs, and what that buys you.
The serviceThe themeShuffle serviceStreaming EngineFlexRSWrap-up
Speaker notes — Section 2: The theme
  • One slide, deliberately: this is the module's original title ("Separating Compute and Storage") distilled into a claim students can test each of the next three features against.

Why "separating compute and storage" is the theme

  • A worker holding data is a worker you can't easily take away:
    • scale-down must first move its data
    • a lost VM loses its data — re-work
    • disks are sized for the peak, paid for always
  • Dataflow's answer: move job state — shuffled data (batch), window state (streaming) — into Google-managed backend services
  • Workers become nearly stateless compute: easy to scale, cheap to run, safe to lose
  • The rest of the module is this idea, three times: Shuffle service · Streaming Engine · FlexRS (its payoff)
Speaker notes — The theme
  • Give the claim in one sentence and let the diagram carry it: state on a worker couples the data's fate to the VM's fate. Decouple them and everything the last section promised (autoscaling, fault tolerance, cheap workers) gets better.
  • Preview the three applications so students know the map: batch shuffle data → Shuffle service (Section 3); streaming window state and streaming shuffle → Streaming Engine (Section 4); and once workers are disposable, running 90% of them on preemptible VMs becomes safe → FlexRS (Section 5).
  • "Nearly stateless" is deliberate wording — workers still hold in-flight bundles and caches; the point is that durable job state lives elsewhere.

Dataflow Shuffle service (batch)

The serviceThe themeShuffle serviceStreaming EngineFlexRSWrap-up
Speaker notes — Section 3: Dataflow Shuffle service
  • Framing matters: this is not an optional add-on students must remember to enable — it's how batch Dataflow works today, by default, everywhere. The section explains the machinery they're already using and the line item it puts on the bill.

Where does the shuffled data live?

Before CombinePerKey can finish, every product's records must be brought together — the shuffle. While the job runs, that regrouped data has to sit somewhere.

  • The worker-based way: shuffle data written to worker CPU, memory, and Persistent Disk — historically a 250 GB disk per batch worker, largely for this
  • Consequences: big disks whether busy or not; a lost worker loses its shuffle data; a worker holding shuffle data can't be released
  • The Shuffle service moves the operation into the Dataflow backend — it "partitions and groups data by key in a scalable, efficient, fault-tolerant manner"
  • It's the base operation behind GroupByKey, CoGroupByKey, and Combine
Speaker notes — Where does the shuffled data live?
  • Open by cashing the check from slide 1.4: "while the shuffle is in flight, where is that data?" Two possible answers — on the workers (the old way, still how most non-Dataflow runners work), or in a purpose-built service (Dataflow's default).
  • The quoted line ("partitions and groups data by key in a scalable, efficient, fault-tolerant manner") and the transform list are verbatim from the docs — shuffle is the base operation behind GroupByKey, CoGroupByKey, and Combine.
  • The diagram deliberately claims only what the current docs claim: the shuffle moves "out of the worker VMs and into the Dataflow service backend"; workers must be in the same region as the job; and you specify a region only — "Dataflow automatically selects the zone in the region you specified." The richer internals story (petabit-bisection network, in-memory tiers with disk spill, multi-zone placement) comes from older Google architecture talks and blog posts, not the current product docs — fine as instructor color if a student pushes, but flag it as such rather than presenting it as documented product fact.
  • Data locality note for security-minded rooms (Module 4 hook): the documented commitment is regional — workers and the shuffle backend are tied to the job's region, with zone selection automatic.
  • Reference: Dataflow shuffle for batch jobs.

What the Shuffle service buys you

  • Faster execution for the majority of batch pipelines — shuffle runs on purpose-built infrastructure, not general-purpose VMs
  • Leaner workers — shuffle no longer consumes worker CPU, memory, or disk: the 250 GB batch worker disk becomes a 25 GB boot disk
  • Better autoscaling — workers hold no shuffle data, so they can be released the moment they're idle
  • Fault tolerance — an unhealthy VM holding shuffle data no longer fails the whole job
All four benefits are the docs' own list — and you get them without doing anything: batch jobs use Dataflow Shuffle by default.
Speaker notes — What the Shuffle service buys you
  • The four bullets are near-verbatim from the shuffle-for-batch page; the disk numbers are from the pricing-page footnote ("250 GB Persistent Disk if not using Dataflow Shuffle, 25 GB Persistent Disk if using Dataflow Shuffle").
  • Tie each benefit back to the theme slide rather than treating them as four separate facts: they're all corollaries of "the VM no longer holds the state." Faster is the only one that isn't — that one comes from shuffle running on specialized infrastructure.
  • The autoscaling benefit is the docs' phrasing too: "VMs don't hold any shuffle data and can therefore be scaled down earlier."
  • If a job is genuinely disk-heavy for other reasons, --disk_size_gb raises the boot disk from the 25 GB default.

Shuffle service: is it on? What does it cost?

  • On by default for every batch job, in all Dataflow regions. Nothing to enable — the feature page itself documents no enable/disable flag anymore
  • One real constraint: specify --region, not a zone — an incompatible region/zone pair blocks the service
  • Billed per GiB of data processed during shuffle — you trade worker CPU/disk cost for a data-volume line item
  • Best practice, now with a price tag: minimize shuffled bytes — CombinePerKey (pre-combines per worker) over GroupByKey-then-sum is a billable difference

Speaker notes — Shuffle: on? cost?
  • Update from older course material: earlier decks said Shuffle was default only "in supported regions" and pointed to docs "to learn how to enable it." Both halves are stale — the current page's first sentence is "Batch jobs use Dataflow shuffle by default," it's available in all Dataflow regions, and the enable/disable instructions are gone from the feature page.
  • Precision if challenged on "no flag": the old opt-in experiment --experiments=shuffle_mode=service hasn't vanished from the doc set — the troubleshooting page still suggests it for shuffle-bound jobs "not using the service-based shuffle," and the FlexRS page uses --additional-experiments=flexible_resource_scheduling,shuffle_mode=service,delayed_launch as a workaround for templates that don't support the FlexRS option. Read those as legacy remnants for edge cases, not as evidence a normal batch job needs the flag.
  • If asked whether you can turn it off: the legacy worker-based mode still exists in the API (ShuffleMode: VM_BASED), but forcing it means workers shuffle peer-to-peer and need a firewall rule allowing traffic on ports 12345–12346 — and a Google KB article ("Error disabling Dataflow Shuffle or Streaming Engine") exists precisely because people break jobs this way. Teach it as "the default, effectively always on."
  • Walk the tier table once with the 1 TiB example: 250 × 0.25 + 774 × 0.5 = 449.5 billable GiB. The discount structure rewards mid-size jobs; past 5 TiB you pay full volume — which is exactly when combiner discipline (Module 5) pays for itself in dollars.
  • References: Dataflow shuffle for batch jobs, Pricing (rates and volume adjustments).

Streaming Engine

The same idea for streaming: window state and the streaming shuffle move off the worker VMs into the service backend — with no changes to your pipeline code.
The serviceThe themeShuffle serviceStreaming EngineFlexRSWrap-up
Speaker notes — Section 4: Streaming Engine
  • Bridge sentence: "Shuffle service is batch-only. Streaming jobs shuffle too — continuously — and they hold window state on top. Same problem, same answer, different service."

The streaming version of the same problem

The Pub/Sub pipeline runs 24/7. Follow one event through CombinePerKey(sum) and two things appear that batch never kept for long.

  • Window state: at 2:41 PM the 2–3 PM window is a table of running sums — one (product, window) → sum entry per product — that must survive until the watermark closes the window
  • Streaming shuffle: no "map finishes, then shuffle" here — each worker owns a slice of the key space, and every arriving event is routed to its key's owner the moment it arrives, so each sum accrues in exactly one place
  • Both are durable, per-key, and live as long as the job runs. The question of this section: where do they live?
Speaker notes — The streaming version of the same problem
  • Make both nouns concrete before any feature talk. Window state: at 2:41 PM the job is holding a running sum for every product sold since 2:00 — real, durable, per-key data with a lifetime (until the watermark closes the window, plus allowed lateness). Batch had nothing like it living that long between stages.
  • "Streaming shuffle" is the docs' own term — the shuffle-for-batch page: "Streaming jobs use a different shuffle mechanism, called streaming shuffle." Same regroup-by-key idea as batch, but continuous and per-event: there is no stage barrier to hide it behind. The routing picture is what makes "events are regrouped by key" meaningful — each worker owns a slice of the key space, and delivering an event is the shuffle.
  • Why one owner per key matters: the sum for "shoes" accrues in exactly one place, so it's correct without cross-worker coordination — and that's also why a hot key pins its worker (Module 5's hot-key discussion connects here).
  • Leave the cliffhanger explicit: everything on this slide must survive a worker dying at 2:59. Where this state physically lives is the next slide — and it's the whole difference between streaming with and without Streaming Engine.
  • Reference: Dataflow shuffle for batch jobs (streaming shuffle naming), Use Streaming Engine.

Where does that state live?

  • Without Streaming Engine: window state and streaming shuffle live on worker Persistent Disks, allocated at job start (400 GB per default worker)
  • Consequences: workers sized for the peak, always; scaling means moving state between VMs — slow and disruptive; the disk allocation caps how far the job can scale
  • Streaming Engine moves window state storage and the streaming shuffle into the Dataflow backend
  • Workers keep running your code, talking to the engine for state — no pipeline changes
Speaker notes — Where does that state live?
  • Open by pointing back at the previous slide's state tables: a worker dies at 2:59 — what happens to its running sums? Without Streaming Engine, they're on that VM's Persistent Disk; with it, they're in the service backend and the replacement worker just picks up where the dead one left off.
  • The docs' framing of the alternative: without Streaming Engine, "the Dataflow runner executes the steps of your streaming pipeline entirely on worker VMs, consuming worker CPU, memory, and Persistent Disk storage." The 400 GB per-worker PD figure is the pricing-page default for non-Streaming-Engine streaming workers; there's also a 15-disks-per-worker service limit with a 1:1 minimum — disk topology is fixed at job creation, which is precisely why scaling stateful workers is painful. (And per the pricing page, that disk pool is billed on the exact value of --maxNumWorkers — the slide-1.6 gotcha.)
  • "No pipeline changes" is the docs' promise: worker nodes keep running user transform code and "transparently communicate with the Streaming Engine to store state."
  • If students ask how the previous slide's key-ownership picture scales: with Streaming Engine, state is sharded by key range and scaling is a reassignment of key ranges to workers — no disks to drag between VMs. Source that carefully: it comes from Google's engineering article "Streaming Engine: Execution Model for Highly-Scalable, Low-Latency Data Processing" (linked from the Streaming Engine doc page), not from the doc page itself.
  • Reference: Use Streaming Engine for streaming jobs.

What Streaming Engine buys you

  • Smaller, cheaper workers — docs recommend a 2-vCPU machine (n4-standard-2) with a 30 GB boot disk, instead of 4 vCPU / 15 GB with a 400 GB Persistent Disk
  • Responsive autoscaling — scaling no longer moves state between VMs: "smoother, more granular scaling" as traffic swings
  • Service improvements without redeploys — the engine is Google-run; streaming internals improve under your running job
  • Lower quota footprint — smaller VMs, tiny disks against your Compute Engine quotas (Module 3)
Speaker notes — What Streaming Engine buys you
  • All four bullets are the docs' benefit list, lightly compressed; "smoother, more granular scaling" is their phrasing. The machine-type guidance changed over the years — older decks say n1-standard-2; the current page's example flags are n4-standard-2 / n4-highmem-2 with a 30 GB disk, and it notes those are the defaults when Streaming Engine is on.
  • The supportability bullet is underrated in practice: streaming pipelines run for months; with state in the engine, Google ships performance and correctness improvements under running jobs, no drain-and-redeploy.
  • The quota bullet pays off in Module 3: fewer vCPUs, no 400 GB PD fleet, fewer in-use IPs per unit of throughput.

Streaming Engine: is it on? What does it cost?

  • Default depends on SDK:
    • Python (2.21.0+, Python 3): on by default — and from SDK 2.45.0 it cannot be disabled
    • Go (2.33.0+): on by default
    • Java: opt-in via flag
  • Two billing models:
    • Resource-based (newer): metered in Streaming Engine Compute Units
    • Data-processed (docs label it legacy): per GiB the engine processes; still the default unless you opt in
  • Net effect: smaller VM bill + an engine line item — typically comparable or lower total, with much better scaling
Java — enable:mvn compile exec:java … \
  --enableStreamingEngine
gcloud (templates) — enable:gcloud dataflow jobs run … \
  --enable-streaming-engine
Opt into resource-based billing (any SDK):--dataflow_service_options=\
  enable_streaming_engine_resource_based_billing
Tie-back to slide 1.7: the cheaper at-least-once mode requires Streaming Engine — and turning it on auto-enables resource-based billing.
Speaker notes — Streaming Engine: on? cost?
  • The honest cost framing: you're trading a VM bill for a service bill, and gaining elasticity. us-central1 anchors: Compute Unit $0.089 (with 1-yr/3-yr CUDs at $0.0712/$0.0534); legacy data-processed $0.018/GiB. The batch shuffle volume tiers do not apply to streaming.
  • Python detail worth precision: enabled by default since SDK 2.21.0 on Python 3 (CMEK jobs excepted historically); --experiments=disable_streaming_engine worked only through 2.44.0. From 2.45.0 the docs say you cannot disable it. So for Python students the right mental model is "Streaming Engine is streaming Dataflow."
  • Two operational constraints to name: a running pipeline can't be switched onto Streaming Engine in place (drain, add the option, resubmit), and there's a 60 GB-per-key limit on buffered input for open windows (buffered elements plus custom state).
  • At-least-once mode (--dataflow_service_options=streaming_mode_at_least_once): duplicates possible, significantly cheaper and lower latency; docs call out map-only ETL, log ingestion, and CDC-with-downstream-dedup as the fits. Enabling it auto-enables Streaming Engine with resource-based billing.
  • References: Streaming Engine, Streaming modes, Pricing.

Flexible Resource Scheduling (FlexRS)

The payoff of stateless workers: give Dataflow scheduling flexibility, get a ~40% discount on batch compute.
The serviceThe themeShuffle serviceStreaming EngineFlexRSWrap-up
Speaker notes — Section 5: FlexRS
  • FlexRS closes the module because it only makes sense on top of Sections 2–3: preemptible workers are only safe because shuffle state lives off-worker.

The nightly job doesn't care when it runs

The daily batch job must finish by 8 AM. It's submitted at midnight and takes about an hour. Nobody cares whether it runs at 12:05 or at 3:00 — and that slack is worth money.

  • FlexRS: you give Dataflow scheduling flexibility; Dataflow gives you ~40% off worker vCPU and memory
  • The job is queued (state: Queued) and launched at a favorable time within 6 hours of submission
  • It runs on a mix of preemptible and regular VMs — 90% preemptible by default
  • Safe because of Section 3: FlexRS uses the Shuffle service, so a reclaimed VM is just replaced — no state lost, no work redistributed; the regular VMs keep the job progressing
Speaker notes — FlexRS scenario
  • Preemptible VMs are spare Compute Engine capacity, deeply discounted, reclaimable by GCE at any time — normally disqualifying for a job whose workers hold shuffle data. The docs' logic, verbatim in spirit: because FlexRS uses service-based Shuffle, "the Dataflow service doesn't have to redistribute data to the remaining workers" when a VM is preempted, and running regular VMs in parallel means the pipeline keeps progressing and prior work isn't lost.
  • The 6-hour window is the service finding capacity: "Dataflow finds the best time to start the job within that time window, based on the available capacity and other factors."
  • Quota fine print for Module 3: FlexRS needs preemptible CPU quota (separate from regular CPU quota), and a queued job occupies a concurrent-job slot while it waits.
  • The decision rule to leave with: "would anyone notice if this started five hours late?" If no — FlexRS.
  • Reference: Use Flexible Resource Scheduling.

Speaker notes — FlexRS: using it
  • The goal-flag subtlety is a favorite trick question: setting --flexrs_goal=SPEED_OPTIMIZED changes nothing — the docs say it "defaults to SPEED_OPTIMIZED, which is the same as omitting this flag." The discount requires COST_OPTIMIZED.
  • The discount is "a uniform discounted rate of about 40% on vCPU and memory cost" regardless of which workers were preemptible — you don't get a different rate for the regular 10%. Shuffle and the (25 GB) PD are explicitly not discounted. The published rates are exactly 60% of batch: $0.0336 = 0.6 × $0.056.
  • Early validation checks environment settings ("such as IAM roles and network configurations"), is unbilled, and runs no user code. Caveat from the docs: the environment can change between validation and delayed launch — a job that validated can still fail at start if someone deletes the bucket at 2 AM.
  • Also unsupported: Compute Engine reservations, and M2/M3/H3 machine series. Requires SDK ≥ 2.12.0 (Java/Python).
  • References: FlexRS guide, Pricing.

Knowledge check

  1. A worker VM dies mid-shuffle on a batch job. What happens to the job — and why is the answer different than it would have been on worker-based shuffle?
  2. You turn on Streaming Engine for a Java streaming pipeline. Which line items on the bill go down, and which new one appears?
  3. Why does FlexRS require the Shuffle service?
  4. Your teammate sets --flexrs_goal=SPEED_OPTIMIZED to "make FlexRS faster." What did that flag actually do?
  5. The console's job graph shows two stages, but your pipeline has six steps. What happened, and where did the boundary come from?
Speaker notes — Knowledge check (answers)
  • 1. The job continues: shuffle data lives in the service backend, so the VM is replaced and its bundles retried (up to 4 attempts per bundle in batch). With worker-based shuffle, the dead VM's shuffle data would be gone — the docs list "an unhealthy VM holding Dataflow shuffle data doesn't cause the entire job to fail" as a headline benefit of the service.
  • 2. Down: worker vCPU-hours and memory (smaller machine type, e.g. n4-standard-2), and Persistent Disk (400 GB → 30 GB). New: the Streaming Engine meter — Compute Units under resource-based billing, or per-GiB data processed under the legacy model.
  • 3. Because 90% of the workers are preemptible and can vanish at any moment. That's only survivable if the shuffle state isn't on them — the service holds it, so a preempted VM is replaced without losing or redistributing work.
  • 4. Nothing. SPEED_OPTIMIZED is the documented default, "the same as omitting this flag." The queued, discounted FlexRS behavior requires COST_OPTIMIZED.
  • 5. Fusion: the service fused consecutive element-wise steps into single stages; the boundary is the shuffle (the aggregation). The Execution details tab shows the optimized stages, and the component steps of each fused stage are listed in the Stage info pane.
