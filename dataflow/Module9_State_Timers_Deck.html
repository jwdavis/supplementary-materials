Why Stateful Processing?

Your toolkit ends at "group and combine." This section shows a problem those tools can't express — and why the fix has to come from the runner, not from cleverer Python.

Speaker notes — Section 1: Why Stateful Processing?
  • The goal of this short section is a felt need: by its end, students should agree that (a) the existing tools can't solve the buffering problem, and (b) the obvious instance-variable hack is broken for three independent reasons. Only then does the API feel inevitable rather than arbitrary.
  • The "why the runner must own the state" argument (workers, bundles, retries) is the whole reason the API exists — it gets its own slide here rather than a footnote.

Scenario: each order event needs data from a customer-profile service. Calling it once per element at Dataflow scale means thousands of requests per second from hundreds of workers — but the service allows batch lookups of up to 100 IDs. Goal: buffer up to 100 orders per customer region, call once per batch.

Speaker notes — The toolkit so far, and the gap
  • Walk the table as a recap, then let students try to solve the scenario with it — each attempt fails instructively:
    • ParDo? Stateless: by the time element 2 arrives, element 1 is gone. There's nothing to accumulate a batch in.
    • GroupByKey / CombinePerKey? They group per window — the runner's boundary. "Every 100 elements" is not a window; count-based batches with a size cap aren't expressible as windowing.
    • Triggers (Module 8)? AfterCount(100) gets close — but triggers control when a grouping emits; they can't run arbitrary code like "issue one RPC per batch, then reset," and trigger firing is a runner hint, not a contract.
  • The two missing capabilities, stated precisely because the two API sections mirror them: memory across elements (→ State API) and custom emit rules (→ Timer API + your own flush logic).
  • Why "customer region" and not "customer" as the key: batch lookups accept up to 100 different IDs, so batching per customer would mostly make batches of one. Key granularity matters and comes back in Section 5 (parallelism).
  • Real-world variants of the same shape: writing to a database in bulk, calling an ML model with a batch of inputs, any rate-limited external service.

Why not just a Python instance variable?

Pythonclass EnrichFn(beam.DoFn):          # DON'T
    def __init__(self):
        self.buffer = []            # looks like it should work

    def process(self, element):
        self.buffer.append(element)
        if len(self.buffer) >= 100:
            yield call_api(self.buffer)
            self.buffer = []
The fix is not cleverer Python. It's asking the runner to own the memory: durable, scoped per key, and rolled back with failed bundles.
  • Many workers: each worker (and each thread) has its own copy — dozens of half-full buffers, none of which sees all elements for a key
  • Retries: module 5 showed bundles are retried on failure; a retry replays elements into a buffer that already holds them — duplicates
  • No durability: autoscaling down or a worker crash simply deletes the list
Speaker notes — Why not an instance variable?
  • Let the code sit on screen for a moment — it looks completely reasonable, and most students have written exactly this somewhere. The three failures are independent: fixing one doesn't fix the others.
  • Many workers: recall Module 5's execution model — the DoFn is serialized and instantiated on every worker, often several instances per worker. "self" is per-instance, so there is no single buffer; there are dozens, each seeing an arbitrary slice of the key's elements.
  • Retries: Module 5's contract is that a failed bundle is retried wholesale and its outputs discarded — but self.buffer isn't an output, so nothing rolls it back. The retried elements append a second time. Exactly-once output requires state the runner can roll back with the bundle.
  • Durability: autoscaling (Module 2) removes workers on purpose; the buffered elements vanish silently. No error, just missing enrichments downstream.
  • If asked "what about setup()/instance caches?" — per-instance state is fine for read-only resources (clients, lookup tables). What's broken here is accumulating input data in it. That distinction is worth stating crisply.
  • The callout is the thesis of the module: durable, per-key, retry-consistent memory can only come from the runner. The next slide names the contract.

Stateful DoFn: the idea

  • A ParDo can declare state cells; the runner stores them durably and hands them to process() alongside each element
  • The contract that makes it safe:
    • Input must be key–value pairs; state is scoped per key and per window — every element for a key is routed to where that key's state lives
    • Reads and writes are consistent with retries: a failed bundle's state writes are discarded with it
    • State is invisible across keys — two customers never share a cell
Mental model: a little durable dictionary the runner keeps for you — one entry per key + window.
Speaker notes — Stateful DoFn: the idea
  • Map each contract line to a failure from the previous slide: per-key routing fixes "many private buffers"; roll-back-with-the-bundle fixes the retry duplicates; durable storage fixes the crash/autoscaling loss. The contract is exactly the three fixes, nothing more.
  • "Per key and per window" — say it twice. With the default global window, "per window" disappears and it reads as plain per-key state. But window a stream into 10-minute fixed windows and each key gets a fresh set of cells per window. This becomes load-bearing for garbage collection in Section 5.
  • Consequence students should predict: because every element for a key must be routed to where that key's state lives, elements for one key are processed serially — state introduces the same key-based parallelism physics as GroupByKey (Section 5 returns to this).
  • Where the state physically lives on Dataflow: in streaming with Streaming Engine (Module 2), state lives in the service, off the workers — which is exactly what makes it survive autoscaling. The mental model "a durable dictionary the runner keeps" is accurate.
  • Java spelling of the same idea, for mixed cohorts: state is declared with @StateId annotations and StateSpecs; the mechanics slide in the next section gives the mapping.

ValueState

First stateful DoFn: a running count per key

Scenario: tag each order with that customer's order number — 1st, 2nd, 3rd… Impossible for a stateless ParDo; overkill for GroupByKey (we want per-element output, immediately).

Pythonfrom apache_beam.coders import VarIntCoder
from apache_beam.transforms.userstate import ReadModifyWriteStateSpec

class OrderNumberFn(beam.DoFn):
    COUNT = ReadModifyWriteStateSpec('count', VarIntCoder())

    def process(self, kv, count=beam.DoFn.StateParam(COUNT)):
        customer, order = kv
        n = (count.read() or 0) + 1
        count.write(n)
        yield customer, order, n

# ('cust-17', 'order-A')  →  ('cust-17', 'order-A', 1)
# ('cust-42', 'order-B')  →  ('cust-42', 'order-B', 1)
# ('cust-17', 'order-C')  →  ('cust-17', 'order-C', 2)
Speaker notes — First stateful DoFn: running count
  • Why this scenario before the buffer: it's the smallest possible stateful problem — one integer per key — so every line of boilerplate is visible and explainable. The next slide dissects the anatomy; this one is just "watch it work."
  • Trace the comments against the state cylinder: cust-17's second order reads 1, writes 2, emits 2. cust-42 is untouched by cust-17's elements — the isolation from the contract slide, now concrete.
  • Contrast with the alternatives from the scenario line: CombinePerKey(Count...) would give final counts per window, not a number on each element as it passes; a GroupByKey would wait for the window boundary. Stateful ParDo emits per element, immediately, with memory.
  • Note the input is already keyed — stateful DoFns require KV input; running this on an unkeyed PCollection is an error. The keying step (Module 5's WithKeys/Map) is assumed done upstream.
  • In batch the same code runs fine — but the numbering within a key depends on processing order, which batch runners don't guarantee. Fine for this teaching example; order-sensitive logic in production wants OrderedListState or explicit sorting.

Speaker notes — Anatomy of a stateful DoFn
  • Why the coder is mandatory here when Beam usually infers coders: state crosses a process boundary on every access — it's written to durable storage between elements, possibly read back on a different worker after autoscaling. The declaration pins down the byte format up front. Compact, deterministic coders matter (Section 5 returns to this).
  • The injection is per-element scoping in disguise: the same process() call signature serves every key, but the handle the runner passes resolves to this element's key+window cell. Students never route anything themselves — routing is the runner's half of the contract.
  • The default-argument idiom (count=beam.DoFn.StateParam(COUNT)) is how Beam Python does dependency injection throughout — same pattern students saw with beam.DoFn.WindowParam in Module 8. The "default value" is a marker the runner replaces, not a real default.
  • Java mapping, one sentence each: @StateId("count") ties a field to the cell name; StateSpecs.value(VarIntCoder.of()) is the declaration; the @ProcessElement method takes a @StateId("count") ValueState<Integer> parameter. Same three parts, different spelling.
  • Naming: the string 'count' identifies the cell in the runner — it must be unique within the DoFn, and it's what you'd see in state-size metrics.
CombiningState

Upgrade the count: Combining state

The read-modify-write round trip is the slow way to add 1. If the update is a combine — sum, min, max: module 5's CombineFn idea again — declare that, and the runner merges blind writes without reading.

Pythonfrom apache_beam.transforms.userstate import CombiningValueStateSpec

class OrderNumberFn(beam.DoFn):
    COUNT = CombiningValueStateSpec('count', combine_fn=sum)

    def process(self, kv, count=beam.DoFn.StateParam(COUNT)):
        customer, order = kv
        count.add(1)            # no read needed to update
        yield customer, order, count.read()
  • add() is cheap; the runner can compact many adds lazily
  • Best practice: if the state is an aggregation, use Combining state — same rule of thumb as module 5's "prefer Combine over GroupByKey"
The combine_fn is the same kind of object as in CombinePerKey — the knowledge transfers.
Speaker notes — Combining state
  • The performance intuition: a value cell makes every update a read-modify-write round trip against durable state. A combining cell accepts add()s blind — the runner queues and merges them when convenient, exactly like combiner lifting in Module 5 merged partial sums before the shuffle. Same legality argument, too: only associative & commutative updates may be reordered and batched.
  • Here the code still calls count.read() to emit the running number — so this particular DoFn doesn't get the full blind-write benefit. The win is real when updates vastly outnumber reads (e.g., add per element, read only at flush time — which is exactly the shape of the next slide's buffer counter).
  • CombiningValueStateSpec('count', combine_fn=sum) infers the accumulator coder from the combine_fn; you can pass a full CombineFn object (like Module 5's MeanFn) for state-≠-answer aggregations.
  • Java: StateSpecs.combining(Sum.ofIntegers()) with a CombiningState<Integer, int[], Integer> parameter.
BagState

BagState: buffering elements

Back to the real problem: buffer orders per key, flush at 100. A value cell holding a list would re-serialize the whole list on every element — BagState is append-only and cheap to add to.

Pythonfrom apache_beam.transforms.userstate import (
    BagStateSpec, CombiningValueStateSpec)

class BatchEnrichFn(beam.DoFn):
    MAX_BATCH = 100
    BUFFER = BagStateSpec('buffer', OrderCoder())
    COUNT = CombiningValueStateSpec('count', combine_fn=sum)

    def process(self, kv,
                buffer=beam.DoFn.StateParam(BUFFER),
                count=beam.DoFn.StateParam(COUNT)):
        _, order = kv
        buffer.add(order)
        count.add(1)
        if count.read() >= self.MAX_BATCH:
            yield from enrich_batch(buffer.read())  # one API call
            buffer.clear()
            count.clear()
  • Why the separate count: reading the bag to check its size would defeat the cheap-append property
  • clear() after flushing — the cell survives forever otherwise
Bug in this code: a key stuck at 37 buffered orders never reaches 100 — those orders are trapped forever. State alone can't say "flush after a while." That's what timers are for.
Speaker notes — BagState: buffering elements
  • Why not a value cell holding a Python list: every element would read the whole list, append one item, and re-serialize the whole list back — O(n²) serialization over a batch. BagState.add() appends without reading; the read happens once, at flush time. Unordered, duplicates allowed — a bag, not a list.
  • The two-cell pattern (bag + combining counter) is idiomatic, not an optimization hack — you'll see it in Beam's own GroupIntoBatches implementation. The counter takes blind add(1)s; its read() at the top of the flush check is the only read per element, and it's against a small compacted value.
  • OrderCoder() stands in for whatever coder fits the element type — a registered custom coder, or commonly beam.coders.registry.get_coder(Order). The point is the same as slide 8: bags serialize their elements to durable storage.
  • Give the bug a beat. Ask "what's wrong with this code?" before revealing the callout — someone will find it. Quiet key at 37: no more elements, no more process() calls, no flush, orders never enriched. Any threshold rule has this failure mode; it's not a corner case, it's guaranteed at 3 a.m. traffic levels.
  • Java: @StateId("buffer") StateSpecs.bag(OrderCoder.of()) with a BagState<Order> parameter.

Speaker notes — Choosing a state type
  • The highlighted rows are the two the module has already used — and honestly the two that cover the large majority of production stateful DoFns. The bottom three are worth knowing exist, not worth designing around by default.
  • Set state: membership testing without reading a whole bag — the natural cell for dedup ("have I seen this ID?"). OrderedList: reads come back sorted by timestamp and support range deletes — the natural cell for sessionization and sort-order logic. Map: random access by sub-key without deserializing everything.
  • The language caveat is real and current: the Python SDK (through 2.70) has no MapStateSpec — Map state is Java-only today. If a design leans on per-sub-key random access from Python, restructure the key instead (make the sub-key part of the element key).
  • "Runner-dependent" is not hand-waving: the capability matrix is the authoritative check, and support genuinely differs across Dataflow, Flink, and the portable runners for the newer cell types. Value/Bag/Combining are the safe core everywhere state is supported at all.
  • If asked "why is Value called ReadModifyWriteStateSpec in Python?" — the Python name describes its access pattern honestly; Java's ValueState is the same cell.

Speaker notes — Section 3: The Timer API
  • The section opens by replaying the stuck-buffer bug as a picture, then introduces the mechanics, then solves the bug twice — once per time domain — and closes with a decision slide and the mechanics worth knowing (overwrite-on-set, looping timers).
  • Module 8 vocabulary (watermark, window end, event vs. processing time) is assumed and reused without re-derivation — if it didn't stick, this section will surface that quickly.

The stuck-buffer problem

  • Two distinct "too long" clocks we might want:
    • "the window is over — the data is complete, flush what's left" (event time, watermark-driven — module 8 vocabulary)
    • "nothing has arrived for 60 real seconds — stop waiting" (processing time, wall clock)
  • A timer is a callback you schedule from process(); the runner calls back with access to the same key's state
Speaker notes — The stuck-buffer problem
  • No code on this slide on purpose — the picture is the argument. The buffer climbs, input stops, and nothing in the State API can ever run again for this key: no elements → no process() calls → no flush check.
  • The two vertical lines preview the section's two solutions, and they are genuinely different policies, not two spellings of one idea: the blue line fires when the data says the window is complete (whenever that turns out to be); the red line fires when the clock says we've waited long enough (regardless of data).
  • The last bullet is the API's key property, easy to miss: a timer callback is not a detached cron job — it runs for a specific key and window, with that key's state cells injected, so flush logic can read and clear the same buffer. Timer + state is one machine, not two features.
  • Ask which clock the class would pick for the enrichment scenario before moving on — the honest answer ("both") is exactly where the capstone lands.
TimerSpec

Timers: the moving parts

Pythonfrom apache_beam.transforms.userstate import TimerSpec, on_timer
from apache_beam.transforms.timeutil import TimeDomain

class BatchEnrichFn(beam.DoFn):
    FLUSH = TimerSpec('flush', TimeDomain.WATERMARK)  # or REAL_TIME

    def process(self, kv, ..., flush=beam.DoFn.TimerParam(FLUSH)):
        flush.set(when)      # schedule (overwrites previous set)

    @on_timer(FLUSH)
    def on_flush(self, ...): # runs when 'when' is reached
        ...
  • TimeDomain.WATERMARK = event time · TimeDomain.REAL_TIME = processing time
  • One timer per spec per key + window: set() overwrites the earlier deadline — re-setting is how you push a deadline back
  • The @on_timer method can take StateParams — and even set timers again (the "looping timer" pattern, later)
Speaker notes — Timers: the moving parts
  • Point out the symmetry with state — the API is deliberately parallel: declare a spec as a class attribute, inject a handle with TimerParam, operate on it. One genuinely new part: the @on_timer(SPEC) decorator marks the callback method.
  • The overwrite semantics deserve emphasis now (and get their own slide later): a spec holds at most one pending deadline per key+window. set() is idempotent-friendly — calling it on every element with the same deadline is harmless, and calling it with a new deadline moves the timer. There is no "list of pending timers" per spec.
  • The diagram's real content is the shared cylinder: process() and on_flush() are two entry points into one per-key machine. That's what makes "flush whatever is buffered" expressible in the callback at all.
  • Java mapping: @TimerId("flush") + TimerSpecs.timer(TimeDomain.EVENT_TIME) (note: Java says EVENT_TIME/PROCESSING_TIME where Python says WATERMARK/REAL_TIME), callback annotated @OnTimer("flush").
  • Timers, like state, require keyed input and fire per key+window — a timer set while processing cust-17 can never invoke logic for cust-42.
WATERMARK

Event-time timer: flush when the window closes

Scenario: the pipeline uses 10-minute fixed windows (module 8). Whatever is still buffered when the watermark passes the end of the window is complete — and must go out.

Pythonclass BatchEnrichFn(beam.DoFn):
    EXPIRY = TimerSpec('expiry', TimeDomain.WATERMARK)

    def process(self, kv,
                w=beam.DoFn.WindowParam,
                buffer=beam.DoFn.StateParam(BUFFER),
                count=beam.DoFn.StateParam(COUNT),
                expiry=beam.DoFn.TimerParam(EXPIRY)):
        expiry.set(w.end)   # idempotent: same deadline every time
        ...                 # buffering logic from the BagState slide

    @on_timer(EXPIRY)
    def on_expiry(self,
                  buffer=beam.DoFn.StateParam(BUFFER),
                  count=beam.DoFn.StateParam(COUNT)):
        if count.read():
            yield from enrich_batch(buffer.read())
        buffer.clear()
        count.clear()
  • Fires when the watermark passes w.end — when the runner believes the window's data is complete
  • Clearing state in the callback is not optional — this is the garbage collection for the window (Section 5 returns to it)
Speaker notes — Event-time timer
  • w.end comes from beam.DoFn.WindowParam — the same injected parameter students met in Module 8. Setting the timer to the window end on every element is deliberately idempotent: same deadline each time, and overwrite-on-set makes the repeats free.
  • Connect to Module 8 precisely: "watermark passes the end of the window" is the same moment the default trigger would fire a windowed aggregation. This DoFn is hand-rolling what triggers gave declaratively — which is the point: state+timers is the general mechanism underneath.
  • The if count.read(): guard: the timer fires even for keys whose buffer flushed at exactly 100 just before window end — an empty flush should not call the API with zero IDs.
  • Late data (Module 8's allowed lateness): elements arriving after the watermark passes the window end land in an expired window's state lifecycle — with default allowed lateness of zero they're dropped. The interplay is subtle; the honest classroom answer is "with defaults, the flush at w.end is final."
  • Java: @OnWindowExpiration is a related-but-different hook — a guaranteed last-callback-before-GC. Worth mentioning to Java cohorts as the belt-and-suspenders companion to an explicit expiry timer.
REAL_TIME

Processing-time timer: flush on inactivity

Scenario: latency matters more than batch fullness — "no order should wait more than 60 real seconds for enrichment, even at 3 a.m. traffic levels."

Pythonfrom apache_beam.utils.timestamp import Duration, Timestamp

class BatchEnrichFn(beam.DoFn):
    STALE = TimerSpec('stale', TimeDomain.REAL_TIME)

    def process(self, kv, ...,
                stale=beam.DoFn.TimerParam(STALE)):
        if not count.read():          # first element of a batch
            stale.set(Timestamp.now() + Duration(seconds=60))
        ...                           # buffering logic

    @on_timer(STALE)
    def on_stale(self, ...):          # same flush-and-clear body
        ...
  • Wall clock: fires 60 s after set(), regardless of watermarks or data flow
  • Setting only on the first element of a batch bounds each element's wait at ~60 s — and avoids re-setting the timer on every element
Alternative semantics — "60 s of silence" — would re-set on every element; both are one-line policies. Deadline-since-first is what GroupIntoBatches(max_buffering_duration_secs=…) implements.
Speaker notes — Processing-time timer
  • The if not count.read(): line is the policy decision, and it's worth slowing down for. Set-on-first gives a hard bound: the first order in a batch waits at most 60 s, later ones less. Set-on-every (sliding deadline) means "flush after 60 s of silence" — under a steady trickle of one order per 59 s, that batch never flushes. Same API, one line apart, very different latency guarantees.
  • Why Timestamp.now() here when the module keeps warning about wall clocks: processing-time timers are defined by the wall clock; this is the one place it belongs. The deadline is absolute, so set = now + duration.
  • Processing-time timers fire on a best-effort schedule — "no earlier than the deadline, as soon after as the runner gets to it." For latency bounds that's exactly the right contract; for correctness bounds (completeness) it's the wrong tool — that's the previous slide's timer.
  • In batch pipelines, processing-time timers are largely meaningless (the job just runs to completion); this pattern is streaming-specific. Section 5's support slide makes that explicit.
  • Java: TimerSpecs.timer(TimeDomain.PROCESSING_TIME), and the offset idiom is timer.offset(Duration.standardSeconds(60)).setRelative().

Event time or processing time?

Event time — WATERMARK

"fire when the data is ready"

  • Completeness-driven: flush / emit when a window's input is complete
  • The final, authoritative per-window result
  • Pace follows the data: a stalled source stalls the timer too

Processing time — REAL_TIME

"fire when the clock says so"

  • Latency-driven: timeouts, "at most N seconds in the buffer"
  • Periodic output regardless of data flow
  • Results may be incomplete by design
They compose. The capstone on the next section's first slide uses both on one DoFn: an event-time timer for completeness, a processing-time timer for latency.
Speaker notes — Event time or processing time?
  • Concrete prompts to run the class through, answers in parentheses:
    • "Flush the session's events once the session window is complete" — (event time: completeness).
    • "Emit a heartbeat per device every minute even if it sent nothing" — (processing time: periodic regardless of data).
    • "Time out a signup flow after 24 h of no activity" — (processing time: a real-world clock promise).
    • "Produce the definitive hourly total" — (event time: the watermark defines 'definitive').
  • The third bullet on each side is the sharp edge: an event-time timer on a stalled source may fire arbitrarily late (the watermark isn't advancing) — correct but not timely. A processing-time timer always fires — timely but possibly incomplete. That's not a flaw in either; it's the definition of the two clocks, and it mirrors Module 8's completeness-vs-latency trade-off exactly.
  • This is also Module 8's watermark material paying rent: if students can't say why "the watermark passed w.end" differs from "10 minutes of wall clock elapsed," revisit that before the capstone.

Timer mechanics worth knowing

  • Overwrite on set: one pending deadline per spec per key + window; set() replaces it. To "extend," just set again
  • Looping timers: an @on_timer callback may set its own timer again — periodic per-key output, e.g. "emit each key's running total every minute even if nothing arrived"
  • Callbacks see state: flush logic lives once, called from both process() and timer callbacks
  • Timers are per key + window, like state: a timer for cust-17 never fires logic for cust-42
Java only: @TimerFamily allows dynamically-tagged timers when a fixed set of TimerSpecs isn't enough.
Speaker notes — Timer mechanics worth knowing
  • Overwrite-on-set is a feature, not a limitation. "One deadline per spec" sounds restrictive until you notice both idioms it enables: idempotent setting (the event-time slide set w.end on every element, free) and deadline extension (a session-timeout timer re-set on each activity is the sliding window). Wanting several concurrent deadlines usually means you want several specs — exactly what the capstone does with EXPIRY + STALE.
  • Looping timers solve "emit even when no data arrives" — something no element-driven code can do, because no elements means no process() calls. Uses: per-key heartbeats, slowly-refreshing caches (slide 20), periodic partial aggregates in the global window. Remember to stop the loop (a condition in the callback), or it runs for every key forever.
  • A pending event-time timer also holds back the output watermark by default — the runner knows output may still be produced at that timestamp. Deep water; flag it only if a student hits "my watermark is stuck" in production.
  • @TimerFamily (Java): dynamically-keyed timers within one declared family, for "one timeout per thing within the key." Python has no equivalent through 2.70 — restructure keys instead.

Speaker notes — Section 4: The Full Pattern

Capstone: the batched-enrichment DoFn, complete

Pythonclass BatchEnrichFn(beam.DoFn):
    MAX_BATCH = 100
    BUFFER = BagStateSpec('buffer', OrderCoder())
    COUNT  = CombiningValueStateSpec('count', combine_fn=sum)
    EXPIRY = TimerSpec('expiry', TimeDomain.WATERMARK)
    STALE  = TimerSpec('stale',  TimeDomain.REAL_TIME)

    def process(self, kv, w=beam.DoFn.WindowParam,
                buffer=..., count=..., expiry=..., stale=...):
        expiry.set(w.end)
        if not count.read():
            stale.set(Timestamp.now() + Duration(seconds=60))
        buffer.add(kv[1]); count.add(1)
        if count.read() >= self.MAX_BATCH:
            yield from self._flush(buffer, count)

    @on_timer(EXPIRY)
    def on_expiry(self, buffer=..., count=...):
        yield from self._flush(buffer, count)

    @on_timer(STALE)
    def on_stale(self, buffer=..., count=...):
        yield from self._flush(buffer, count)

    def _flush(self, buffer, count):
        if count.read():
            yield from enrich_batch(buffer.read())
        buffer.clear(); count.clear()
Speaker notes — Capstone: the complete DoFn
  • Nothing on this slide is new — say that first. Bag + counter is the BagState slide; expiry.set(w.end) is the event-time slide; set-on-first STALE is the processing-time slide. The composition is the only new content: three entry points, one _flush().
  • The elided buffer=... parameter defaults stand for the full beam.DoFn.StateParam(BUFFER) spellings shown on earlier slides — they're compressed here so the structure fits on one slide.
  • Walk the three flush paths and what each guarantees: size (100 reached in process() — throughput), completeness (EXPIRY at window end — correctness), latency (STALE at 60 s — the 3 a.m. guarantee). All three call the same _flush(), which clears both cells — so after any flush, the next element starts a fresh batch and re-arms STALE.
  • Residual sharp edges, worth naming honestly: after a size-triggered flush, STALE still fires on schedule (harmless: the count.read() guard makes it a no-op, and Python through 2.70 has no timer.clear() — guard-in-callback is the idiom). And _flush as a generator called from three methods works because each caller yield froms it.
  • If this feels like a lot of machinery for "batch my API calls" — good. That reaction is the setup for the next slide.
GroupIntoBatches

Now that you can build it: don't. Use GroupIntoBatches

The pattern you just built is common enough that Beam ships it as a transform.

Pythonenriched = (
    orders                                   # ('cust-region-EU', order)
    | beam.GroupIntoBatches(
          batch_size=100,
          max_buffering_duration_secs=60)
    | beam.MapTuple(lambda key, batch: enrich_batch(batch))
)
# ('cust-region-EU', [order, order, …])  ≤100 per batch, ≤60 s wait

  • On Dataflow, prefer GroupIntoBatches.WithShardedKey(...) (Java: withShardedKey()) — lets the runner shard hot keys and autoscale
  • Also built on state & timers: Deduplicate — per-key dedup with a time horizon
State and timers are the mechanism. Built-ins are the product. Learn the mechanism to use the products well — and to build your own when none fits.
Speaker notes — GroupIntoBatches
  • Map the knobs to the capstone line by line: batch_size=100 is the count.read() >= MAX_BATCH check; max_buffering_duration_secs=60 is the STALE timer with set-on-first semantics; the window-end flush comes free with windowing, like EXPIRY. The output is (key, list-of-orders) — the API call itself stays yours, in the MapTuple.
  • GroupIntoBatches.WithShardedKey is the production tip worth underlining on Dataflow: it batches per (key, shard) instead of per key, which legitimizes exactly the "batching per shard is fine" observation from the scenario — and it unlocks autoscaling beyond the key count for this stage. See the "grouping elements for efficient external service calls" pattern page (linked on the final slide).
  • Deduplicate (from apache_beam.transforms.deduplicate; also DeduplicatePerKey) completes the message that this module's mechanism underlies the library: Set/Value state ("seen?") plus an event-time GC timer (the horizon). Students can now read its docs and see the state and timers in it.
  • The decision rule to leave them with: reach for built-ins first; hand-roll a stateful DoFn when the logic is genuinely custom — not when it's a batch, a dedup, or anything else already on the shelf. The full decision ladder closes Section 5.

Best Practices and Pitfalls

Cleanup, key choice, performance habits, and runner support — the difference between a stateful pipeline that works in a demo and one that survives production.
Why stateful?State APITimer APIThe full patternBest practices
Speaker notes — Section 5: Best Practices and Pitfalls
  • Ordering: the two correctness pitfalls first (state leaks, key-choice parallelism), then performance habits, then runner/language support, then the closing decision ladder that ties the whole module together.
  • Everything here generalizes beyond the enrichment scenario — these are review-checklist items for any stateful DoFn a student ever writes.

State must be cleaned up — by you

The runner GCs state when its window expires (end of window + allowed lateness). Two consequences:

  • Windowed pipelines: flush-and-clear at your event-time timer; the runner reclaims the rest at expiry
  • Global window + streaming = state lives forever unless you clear it or set your own GC timer — the classic slow leak: memory and backlog grow for weeks, then the pipeline degrades
  • The pattern: per-key GC timer in the global window = event-time timer set to "last activity + horizon"; the callback clears all cells
If you write to a cell, decide in the same block of code who clears it and when.
Speaker notes — State must be cleaned up
  • The runner's guarantee, stated exactly once more: state (and timers) belong to a key and window, and the runner reclaims them when the window expires — end of window plus allowed lateness. In windowed pipelines your explicit clear() at flush is mostly about not carrying dead weight until expiry.
  • The trap: streaming pipelines commonly run in the global window (Module 8: unbounded, never expires) — precisely where stateful DoFns are most tempting. There, no expiry ever comes. Every key ever seen — every customer, every device, every session ID — holds its cells forever unless your code clears them.
  • Why it's insidious: the leak has no error message. On Dataflow it shows up weeks later as growing state size / memory pressure and rising watermark lag. By then the fix (a GC timer) requires updating a pipeline that's already degraded.
  • The GC-timer pattern in words: on each element, set an event-time timer to "now + horizon" (overwrite-on-set makes this a sliding deadline per key); the callback clears every cell. It's the dedup tile's horizon and the capstone's EXPIRY generalized.
  • The callout is a code-review habit, phrased to be checkable in a diff: any state.write()/add() without a visible clearing path in the same DoFn is a bug until proven otherwise.

Key choice controls parallelism (again)

  • All elements for one key are processed serially wherever that key's state lives — module 5's GroupByKey physics, and it applies to stateful ParDo too
    • Too few keys → capped parallelism: 3 keys = at most 3 busy workers
    • Hot key → one overloaded worker, everyone else idle; upstream backlog
  • Pick keys with enough cardinality and balance — customer-region was fine; "country" with 90% US traffic is not
  • Batching per shard rather than per logical key is often fine — that's exactly what GroupIntoBatches.WithShardedKey legitimizes
Speaker notes — Key choice controls parallelism
  • Same figure as Module 5's hot-key slide, one addition: the state cylinder glued to Worker 1. That's the causal link — the elements can't spread out because they all need the same cells, and the cells live in one place. Serial per key is a semantic bound (state consistency requires it), not a scheduling accident.
  • Worse than GroupByKey in one respect: a GroupByKey hot key hurts once per window at aggregation time; a hot key in a stateful ParDo serializes every element's processing, continuously.
  • Run the scenario's numbers: keying the enrichment by "customer" gives millions of keys (great parallelism, terrible batches of ~1); by "country" gives ~200 keys with 90% of traffic in one (parallelism capped, one giant hot key); "customer region" was chosen as the middle ground. Key design is a real design axis, not plumbing.
  • The sharding observation generalizes: when per-key semantics aren't actually required (batching isn't — any 100 orders from the region make a valid batch), a synthetic shard component in the key buys parallelism. GroupIntoBatches.WithShardedKey is that move, done for you, with Dataflow-side autoscaling awareness.

Performance habits

  1. Aggregation in state → Combining, not read-modify-write — blind writes let the runner compact lazily
  2. Buffers → Bag, with size tracked in a separate Combining cell — never read a bag just to count it
  3. Coders matter twice: state is serialized on every access path — compact, deterministic coders (module 5's coder guidance applies)
  4. Set timers idempotently or conditionally — w.end every time, or "only on first element" — not a new deadline per element when avoidable
  5. Keep per-key state small (KBs, not MBs): it's a working set, not a database — very large per-key data usually means the key is wrong, or the job is a join that belongs in CoGroupByKey / side inputs
Speaker notes — Performance habits
  • Items 1 and 2 are the module's own examples promoted to rules — refer back to the Combining and BagState slides rather than re-deriving.
  • Item 3, "twice": once per write and once per read — and for hot paths the write happens per element. A JSON-ish PickleCoder on a per-element cell is a hidden tax on every single element; a VarIntCoder or a tight custom coder is not. Determinism matters because state bytes are compared/merged by the runner.
  • Item 4's cost model: each set() is a state write. Idempotent sets (same deadline) are cheap for the runner to elide; genuinely moving the deadline per element (sliding timeouts) is fine when it is the semantics — the habit is about not doing it accidentally.
  • Item 5 is the design smell that catches real designs: "load the customer's full history into state" is a join wearing a state costume. Joins have tools (CoGroupByKey, side inputs — Module 5); state is for the compact working set of an ongoing computation.
  • Observability on Dataflow: streaming jobs expose per-stage state metrics; a stage whose state size only ever grows is item 5 or a missing GC (previous slide) — usually the latter.

Support varies: check before you design

  • State and timers require a keyed input, and are supported on Dataflow and most portable runners for the core cells (Value / Bag / Combining) — check the capability matrix for Set / OrderedList / Map and for processing-time timers
  • Language gaps are real: Map state has no Python spec (through 2.70); timer families are Java-only
  • Batch vs streaming: the APIs work in both — but in batch, "processing time" and watermark semantics are less meaningful; event-time timers effectively fire at the end of each window's data
  • Dataflow note: streaming state lives in Streaming Engine when enabled (module 2's compute/state separation) — that's what makes large state autoscale-safe
Design against the runner and SDK you will actually deploy on — and verify the exotic cell types against the matrix before the architecture depends on them.
Speaker notes — Support varies
  • The keyed-input requirement is worth restating as a checklist item because the error only appears at pipeline construction/run time: applying a stateful DoFn to an unkeyed PCollection fails — add the keying Map/WithKeys first.
  • The core trio (Value, Bag, Combining) plus both timer domains is the portable safe set — everything this module built runs on Dataflow today. The moment a design leans on Set/OrderedList/Map or on subtle timer behavior, the capability matrix is the source of truth, not memory — support genuinely shifts between Beam releases.
  • Batch nuance, one level deeper if asked: in batch there's no incremental watermark — the runner processes a window's data and then fires its event-time timers; processing-time timers may fire only at the end or be of limited use. Code using event-time timers ports cleanly between batch and streaming; wall-clock latency logic is streaming-only by nature.
  • The Streaming Engine link back to Module 2 lands the architecture story: state off the workers is why stateful streaming pipelines can autoscale and survive worker loss — the durability half of the Section 1 contract, physically explained.

Summary

  • State = durable per-key + window memory the runner owns: consistent with retries, invisible across keys. Cells: Value, Bag, Combining (+ Set / OrderedList / Map where supported)
  • Timers = scheduled callbacks with access to that state. Event time for completeness, processing time for latency — and they compose
  • Always pair writes with a clearing plan; in the global window, GC is entirely yours
  • Key choice = parallelism; shard hot keys
  • Prefer built-ins (GroupIntoBatches, Deduplicate); hand-roll only truly custom logic
