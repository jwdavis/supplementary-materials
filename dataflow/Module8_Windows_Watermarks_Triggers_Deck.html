Two clocks: event time and processing time

Amy taps "checkout" at 08:00:45 on the subway. Her phone uploads it at 08:07:02. Which time is true?

  • Event time — when it happened; travels with the element as its timestamp
  • Processing time — when the pipeline sees it; just the worker's clock
  • The dashboard question ("views during 08:00") is an event-time question
Grouping by processing time is just micro-batching — fine for "roughly current" stats. Grouping by event time reconstructs what actually happened. Beam lets you choose; this module defaults to event time.
Speaker notes — Two clocks
  • The one fact that generates the whole watermark section: lag is normal, variable, and unbounded in the worst case. Say it now, cash it in later — if lag were constant, you could just wait that long and be done; because it isn't, "how long do we wait?" needs real machinery.
  • "Which time is true?" — both, for different questions. Billing and analytics questions ("views during 08:00") are event-time questions; operational questions ("how far behind is my pipeline right now?") are processing-time questions. Section 3's metrics slide makes that split concrete.
  • Java aside: every element in a Beam PCollection carries an intrinsic timestamp; sources set it, and a DoFn can override it (shown for both languages later in this section). In batch, sources typically stamp everything with the same minimum timestamp — which is why batch windowing needs the TimestampedValue slide.

Streams arrive out of order

Three users tap at 08:00. Amy's event arrives at 08:01. Bo was in the subway: 08:09. Cy was in airplane mode over the Atlantic: 13:42.

  • Arrival order ≠ event order, and the gap has no upper bound
  • Any grouping scheme based on arrival puts these three 08:00 taps in three different groups
  • We need grouping that follows the event-time stamp — and a policy for stragglers
Out-of-order data isn't a failure mode to handle — it's the normal condition of any stream that crosses phones, networks, or retries.
Speaker notes — Streams arrive out of order
  • Tell the story with the people, not the boxes: three taps in the same minute; only where each phone was differs. Amy on wifi (a minute of lag), Bo underground (nine minutes), Cy in airplane mode over the Atlantic (five and a half hours). Nothing failed — every event eventually arrived, intact and truthfully stamped.
  • These same three users and these exact events return in the watermark section (slides "When can we emit the result?" and "On time — or late") — spend the time to make them familiar now.
  • Foreshadow precisely: windows solve where Cy's event belongs (the 08:00 window, always); watermarks + allowed lateness decide whether it still counts by the time it shows up. Belonging and counting are different questions — keeping them apart avoids most confusion in Section 3.

Speaker notes — Section 2: Windows

Windows: finite groups in an infinite stream

A window turns "views per minute" into finite groups — so the aggregation from the batch pipeline can finish, unchanged.

  • A window is a time interval in event time; every element is assigned to one or more windows by its timestamp
  • Aggregations (GroupByKey, Combine) then run per window — each window is a self-contained little batch job
  • Default: everything sits in one global window — which is why an aggregation on an unbounded source without windowing is rejected by Beam
Windowing changes no data and doesn't split the PCollection — elements stay interleaved in one collection, each carrying its window as metadata. The window joins your key at the next grouping; the aggregation you already know does the rest.
Speaker notes — Windows: finite groups
  • Why CombinePerKey is named in the diagram: it's the exact aggregation from the batch slide four slides back — same transform, same sum; the only new line is WindowInto. If asked "does this work with GroupByKey / Mean / any combine?" — yes, all of them; windowing is orthogonal to which aggregation runs.
  • "So is a window a partition of the PCollection?" — close, but no, on two counts. (1) Nothing is physically split: it's one PCollection, elements interleaved, each tagged with its window; the window acts as an extra, implicit part of the grouping key when an aggregation runs. (2) Partitions are disjoint — sliding windows (two slides ahead) put one element in several windows, which no partition does. "Time-based grouping key," not "partition," is the durable mental model.
  • The error message students actually hit, worth showing live if demoing: GroupByKey cannot be applied to an unbounded PCollection with global windowing and a default trigger. Now they can read it: unbounded + one global window + "fire when complete" = never fires, and Beam refuses to build that graph.
  • Windows exist in batch too — the first lab uses them on bounded data. Event time, not "streaming mode," is what makes windows work; the same WindowInto line behaves identically over yesterday's files.
  • Precision worth keeping: elements are assigned to "one or more" windows — exactly one for fixed and session windows, several for sliding (next slides). The window becomes part of the element's implicit grouping key alongside your own key.
  • Aggregating an unbounded stream without windows is possible — either with a trigger on the global window (end of Section 4) or with State and Timers (next module). Park it.
FixedWindows

Fixed windows

Scenario: views per minute — every minute, one non-overlapping bucket.

Pythonfrom apache_beam import window

per_minute = (events
    | "PerMinute" >> beam.WindowInto(
          window.FixedWindows(60))  # seconds
    | "One"   >> beam.Map(
          lambda e: (e["page"], 1))
    | "Count" >> beam.CombinePerKey(sum))
  • Equal, consecutive, non-overlapping intervals; every element lands in exactly one
  • Durations are seconds in Python (60), a Duration in Java
  • The workhorse: hourly rollups, per-minute dashboards, daily aggregates
One element, one window — results are easy to reason about and cheap to compute. Reach for fixed windows first.
Speaker notes — Fixed windows
  • Java: Window.<T>into(FixedWindows.of(Duration.standardSeconds(60))).
  • Connect back to the batch slide: the hand-built minute-string key ('08:00') was a fixed window, done manually and fragile. FixedWindows(60) is the same idea as a first-class concept the runner understands — which is what lets watermarks and triggers attach to it later.
  • The diagram's events (08:00:12, 08:00:41, 08:01:07, 08:01:33, 08:02:05) reappear in the watermark section — spend a moment making them familiar.
  • Anticipated question: "what about a tumbling window?" — same thing, different vendor vocabulary. Fixed = tumbling; sliding (next) = hopping in some ecosystems.
SlidingWindows

Sliding windows

Scenario: ops wants a 5-minute moving average of checkout latency, refreshed every minute.

Python# latencies: ('checkout', 3.2) pairs
avg_latency = (latencies
    | beam.WindowInto(
          window.SlidingWindows(
              size=300, period=60))
    | beam.combiners.Mean.PerKey())
    # -> ('checkout', 2.8) per window
  • size = how much data each window covers; period = how often a new one starts
  • Windows overlap, so one element belongs to size / period windows (here: 5)
  • The mean runs once per key per window — the aggregation itself is nothing new
Overlap multiplies work: SlidingWindows(3600, 60) puts every element in 60 windows. Keep size / period small, or rethink the question.
Speaker notes — Sliding windows
  • Java: SlidingWindows.of(Duration.standardMinutes(5)).every(Duration.standardMinutes(1)), then Mean.perKey().
  • The elements are keyed (('checkout', 3.2) = page, seconds) so the ordinary keyed mean applies. If someone instead reaches for the unkeyed CombineGlobally(MeanCombineFn()) over these windows, they hit the #1 Stack Overflow question for sliding windows in Python: it must be suffixed .without_defaults(). CombineGlobally promises a result even for empty input (an empty sum is 0); with non-global windows there's no sensible way to emit defaults for every possible empty window, so Beam requires you to opt out — otherwise, a pipeline construction error.
  • Anticipated question: "is the element duplicated?" — logically yes, one copy per window it falls in. Combiner lifting (Module 5) keeps the cost manageable: partial aggregates per window, not five copies of raw data shuffling around. Still, the warning callout is real — size/period ratios in the tens multiply state and compute.
  • Walk the highlighted element: an event at 08:04:20 falls in [08:00,08:05), [08:01,08:06), [08:02,08:07), [08:03,08:08), and [08:04,08:09) — five windows, because 300 / 60 = 5.
Sessions

Session windows

Scenario: marketing asks "how long is a shopping session?" A session ends when the user goes quiet for 30 minutes.

Python# clicks: ('amy', click_event) pairs
sessions = (clicks
    | beam.WindowInto(
          window.Sessions(gap_size=30 * 60))
    | beam.GroupByKey())  # one group per user
                          #   per session
  • Data-driven: the window's edges come from the data, not the clock
  • Defined by a gap: elements closer together than the gap merge into one window
  • Computed per key — Amy's silence doesn't end Bo's session
Fixed and sliding windows are known before any data arrives. Session windows are discovered from the data — which is exactly why "when is it complete?" gets interesting in the next section.
Speaker notes — Session windows
  • Java: Sessions.withGapDuration(Duration.standardMinutes(30)).
  • Mechanically, each element opens a proto-window of gap length; overlapping proto-windows merge. That's why sessions are "discovered from the data" — and why a session window can keep growing as long as activity continues (Bo's 80-minute session).
  • Unkeyed sessions are almost never what anyone wants — a busy site would collapse into one giant global session. The GroupByKey-shaped pairing is the natural companion: sessions per user, per device, per whatever the key is.
  • Real uses beyond shopping-session length: gaming sessions (the Beam mobile-gaming examples, linked at the end), reading sessions in media, machine "activity bursts" in IoT.

Where the timestamp comes from: streaming sources

Windows group by the element's timestamp — so who sets it? For Pub/Sub: the publish time, unless you say otherwise.

The recommended override — not what you get by default:

Pythonevents = (p
    | beam.io.ReadFromPubSub(
          subscription=
        "projects/store/subscriptions/page-views",
          timestamp_attribute="event_ts")
          # RFC 3339 or epoch millis
    | beam.Map(json.loads))
  • Default (no timestamp_attribute): event time = publish time — when the message reached Pub/Sub, not when the tap happened on the phone
  • The override: the publisher stamps the true time into a message attribute, and timestamp_attribute tells the source to use it instead
  • With that one argument, Amy's buffered subway events carry 08:00, not 08:07
Publish time is a processing-time stamp wearing an event-time costume. If the true time matters, use timestamp_attribute.
Speaker notes — Timestamps: streaming sources
  • Java: PubsubIO.readStrings().fromSubscription(...).withTimestampAttribute("event_ts").
  • Why publish time is often "good enough, until it isn't": for well-connected publishers the two times differ by milliseconds. The gap opens exactly when it matters most — mobile clients buffering offline, backfills, replays. Amy's subway checkout is the concrete case: with publish time it lands in the 08:07 window; with timestamp_attribute it lands in 08:00 where it belongs.
  • A subtle but important bonus: with timestamp_attribute set, Dataflow estimates the source's watermark from that attribute — so old buffered events also hold the watermark back appropriately. That's exactly the machinery Section 3 needs; plant the phrase "the source tracks how old its unprocessed data is."
  • The attribute value format: RFC 3339 timestamp or epoch milliseconds. The publisher sets it with one extra argument on publish().

Where the timestamp comes from: your own data

Batch files have no publish time — the timestamp is a field in the record. Attach it yourself in a DoFn.

Pythonclass AddTimestamp(beam.DoFn):
    def process(self, element):
        yield beam.window.TimestampedValue(
            element,
            element["event_ts"])  # secs since epoch

stamped = raw | beam.ParDo(AddTimestamp())
  • TimestampedValue(element, ts) re-emits the element with a new event timestamp
  • This is how batch data gets windowed — which the next lab does
  • Same trick fixes streams whose timestamp lives in the payload, not an attribute
Windows don't care whether data is bounded or streaming — only that elements carry meaningful event timestamps.
Speaker notes — Timestamps: your own data
  • Java: context.outputWithTimestamp(element, new Instant(ts)) inside the DoFn's @ProcessElement method.
  • Why the input card says 1970: a batch source like ReadFromText stamps every element with the minimum timestamp — there's nothing meaningful to use. Windowing on that is legal and useless (everything lands in one window). The DoFn swaps in the record's own field.
  • Common question: "can I move a timestamp backward?" — yes, within limits; the old "allowed timestamp skew" escape hatch is deprecated/discouraged. The clean pattern that avoids the question entirely: set timestamps as early as possible, at or immediately after the source, before any windowing.
  • This slide is the setup for Lab 1 — students will write exactly this DoFn against batch web-log data.

Speaker notes — Section 3: Watermarks

When can we emit the result?

It's 08:01:00 on the wall clock. May we emit "views for 08:00"? Bo's 08:00 tap is still in the subway.

  • Emitting at the wall-clock minute boundary — and never looking back — drops every straggler: silently wrong
  • Waiting forever emits nothing — perfectly complete, perfectly useless
  • We need an estimate of "all data up to time T has probably arrived"
This trade-off — latency vs. completeness — has no free lunch. The watermark is Beam's honest, moving estimate of where "complete" currently is.
Speaker notes — When can we emit the result?
  • Let students propose the middle road: "just wait a fixed 5 minutes past the window." That's a static heuristic — and a perfectly reasonable instinct. The watermark is the adaptive version of exactly that instinct: instead of a hard-coded delay, the pipeline continuously measures how delayed its data actually is and moves the "safe to close" line accordingly.
  • Stress the word silently on the first bullet. Dropping Bo doesn't error, doesn't warn by default — the count is just 2 instead of 3, and nobody knows. Silent correctness loss is the villain of this whole section.

The watermark

The watermark is the pipeline's running claim: "I believe I have now seen (nearly) everything with event time earlier than T."

  • Picture a moving line on the event-time axis: the pipeline's current boundary between "probably all here" and "still arriving"
  • A window whose end the watermark has passed is complete as far as the pipeline can tell — the default moment to emit its result
  • It's a heuristic, continuously re-estimated from the data actually in flight — usually right, occasionally passed by a straggler
Nothing about your data changed — the watermark is metadata about progress, the streaming replacement for end-of-file.
Speaker notes — The watermark
  • Say the claim sentence twice; everything in this section is a footnote to it. The watermark is a position in event time that only ever moves forward — not a timer, not a configured delay.
  • The end-of-file connection is worth making explicit: batch always had a watermark too — it just jumps from −∞ to +∞ the instant the file ends, so nobody ever needed to name it. Streaming is what makes the watermark move gradually and become visible.
  • Read the figure left to right: the first window's end (08:01) is behind the watermark (08:01:31) — complete as far as the pipeline can tell, so it emits. The second window straddles the line — still open. The early dot at 08:02 makes the key asymmetry: data ahead of the watermark arriving is normal and harmless; the watermark is held back by the oldest thing believed still missing.

Every stage has a watermark

It isn't one number for the whole job. The watermark starts at the source and flows through the pipeline — and every aggregation consults the watermark at its own stage.

  • The source estimates the first watermark from what it knows about data not yet read (next slide: how Pub/Sub does it)
  • Each transform's output watermark = the older of its input watermark and its oldest buffered, not-yet-emitted work — downstream watermarks trail upstream ones
  • Every GroupByKey / Combine emits a window when its input watermark passes the window's end — not just the one next to the source
  • Multiple inputs (Flatten, joins): the minimum across them; and a watermark only ever moves forward
Batch has all of this too — a file source's watermark simply jumps to +∞ at end-of-file, so every stage's windows become emittable the moment reading finishes.
Speaker notes — Every stage has a watermark
  • This is the slide that stops "the watermark" from sounding like a Pub/Sub feature. The source only starts it; propagation is generic Beam model (Streaming 102's input/output watermark formulation): every transform has an input watermark (what upstream claims complete) and an output watermark (what it can promise downstream), and the output waits on the transform's own buffered work.
  • Concrete reading of the figure: the source believes everything before 08:01:31 has arrived. The Combine, though, is still holding the [08:00, 08:01) window's partial sums it hasn't emitted yet — so it can only promise 08:00:58 downstream. The instant it emits that window, its output watermark jumps forward. Aggregations are where watermarks pause.
  • Why students should care: chained aggregations (e.g. per-minute counts re-windowed into per-hour maxima) each fire off their local watermark, in order — the hourly window can't emit before the minute windows feeding it have. It composes correctly with no extra code; that's the payoff of watermarks being runner metadata rather than user logic.
  • Dataflow's UI shows this per-stage value as "watermark" on each step in the job graph, and the job-level data freshness chart tracks the output end. Deep dive: the Streaming 102 essay (Additional material) — its watermark-propagation section is the canonical treatment.

Where the number comes from: Pub/Sub on Dataflow

Pub/Sub promises delivery — not order, not completeness. So Dataflow estimates the source watermark from the one thing it can see: the backlog.

  • Dataflow polls a Pub/Sub API that reports the age of the oldest unacknowledged message on the subscription — the watermark never claims completeness past work still sitting in the backlog
  • By default that tracks publish time; with timestamp_attribute, Dataflow also creates a hidden tracking subscription to inspect the event times still in the backlog — so old buffered events hold the watermark back too
  • What no estimate can see: an event not yet published (Cy's phone in airplane mode) is in no backlog anywhere — the watermark can pass it, and it arrives late
Every source estimates differently (Kafka: per-partition progress; files: what's left to read), but the contract is identical: a best-effort completeness claim, honest enough to act on — never a guarantee.
Speaker notes — Where the number comes from: Pub/Sub
  • Mechanics, in order: (1) the Pub/Sub connector uses a private Pub/Sub API that exposes the age of the oldest unacknowledged message per subscription — fresher than the public Cloud Monitoring metric; (2) with a custom timestamp_attribute, Dataflow additionally creates a second, tracking subscription and samples the backlog's event-time attribute values to estimate an event-time watermark, since publish order and event order no longer match. Source: the Dataflow docs page "Streaming with Pub/Sub" (linked from Additional material's streaming-pipelines doc).
  • The tracking-subscription detail is also the honest answer to "is this exact?" — it's sampling a backlog that changes constantly. Treat the watermark as a well-informed estimate with engineering behind it, not folklore — and still fallible in exactly one direction: events that were never published in time.
  • Cy is that direction: her 08:00 tap sat on her phone until 13:42. No subscription, no backlog, no API could know it existed. This is why "perfect watermark" requires a source that can bound lateness — and why the late-data policy (two slides ahead) exists at all.
  • If asked about self-hosted runners: same division of labor — the runner owns watermark tracking, the source's UnboundedReader.getWatermark() supplies the estimate. Nothing about the concept is Dataflow-specific; only this estimation machinery is.

On time — or late

One rule sorts every arriving element: compare its event time to the current watermark.

  • Arrives while the watermark is still behind its window's end → on time
  • Arrives after the watermark passed its window's end → late
  • Late is defined by the watermark — without a watermark, "late" is meaningless
amy — arrives 08:01, on time
bo — arrives 08:09, on time (barely)
cy — arrives 13:42, late
Same three taps from Section 1 — now the pipeline can name which one is a problem, and by how much.
Speaker notes — On time — or late
  • Walk the two lanes top to bottom: the top lane is event time — all three taps sit inside [08:00, 08:01), and nothing about the events themselves differs. The bottom lane is arrival — the orange marker is the moment the watermark passed 08:01 (about 08:10 wall clock, held back adaptively by real lag). Amy and Bo arrive before that moment: on time. Cy arrives hours after it (note the axis break): late by definition, not by any property of the event itself.
  • Bo being "barely on time" is a feature of the adaptive watermark: because real lag held the watermark back, the window hadn't emitted at wall-clock 08:01 — the naive emit-at-the-boundary strategy from the start of this section would have dropped him.
  • "Early" firings — results emitted before the watermark — also exist, and arrive with triggers in Section 4. Keep this slide to on-time vs. late to avoid overload; the trigger section names all three panes.

What happens to late data

Default policy: late data is dropped — Cy's tap never reaches the 08:00 count — unless you allow lateness.

Pythonfrom apache_beam.utils.timestamp import (
    Duration)

per_minute = events | beam.WindowInto(
    window.FixedWindows(60),
    allowed_lateness=Duration(seconds=10 * 60))
    # accept data up to 10 min late; on-time
    # result still emits at the watermark
  • Default allowed_lateness is 0: when the watermark passes the window's end, the result emits and the window's state is freed — late arrivals have nowhere to land
  • With lateness: the on-time result still emits at the watermark, nothing is delayed — but the state is retained afterward, and each late arrival emits a correction
  • Once the watermark passes end-of-window + allowed lateness, the window expires: state freed, further stragglers dropped. Lateness is a budget of retained state, not a free setting
Dropping is silent correctness loss. Decide a lateness budget on purpose, and watch Dataflow's droppedDueToLateness counter rather than assuming zero.
Speaker notes — What happens to late data
  • Java: .withAllowedLateness(Duration.standardMinutes(10)).
  • Precision worth insisting on: allowed lateness does not postpone the on-time result — it emits when the watermark passes the window's end, exactly as before. What lateness buys is the window's afterlife: state is retained, and (with the default trigger) each late arrival emits an updated result. When the watermark passes end + lateness, the window expires — state garbage-collected, later stragglers dropped. So yes: state really is lost at the lateness limit; that's the deliberate trade.
  • Vocabulary note: this deck says a window emits at the watermark and expires at end + lateness — avoid the ambiguous "closes," which students hear as either one. What corrections contain (a running total? just the new elements?) is the accumulation-mode question — parked to Section 4, where it belongs.
  • Python's allowed_lateness is fully supported — older course material claimed otherwise; that correction stands.
  • How to pick the budget: look at the actual lag distribution (data freshness chart, next slide) and the business's tolerance. A 10-minute budget catches Bo's subway ride; catching Cy's transatlantic flight would mean holding every window's state for six hours — probably not worth it for a dashboard, possibly worth it for billing. It's a genuine business decision, which is why Beam won't make it for you.
  • Cy's five-hour lateness with a 10-minute budget: still dropped — but now by explicit policy, with a metric counting it, not by silent default.

Watching the watermark: Dataflow's two metrics

You never see "the watermark" as a number — you see its shadow in two Job Metrics charts.

  • Data freshness: how far real time has pulled ahead of the watermark — "how stale is the newest complete result?"
  • System latency: how long an element currently takes to get through — "is the pipeline itself slow?"
  • Dataflow's autoscaler reads the same signals you do
Freshness answers "is my data behind?"; latency answers "is my pipeline behind?" You need both to diagnose which one is the problem.
Speaker notes — Watching the watermark
  • Show a real streaming job's Job Metrics page here if one is available — these two charts are on the job's page in the console, and connecting them to the watermark concept is this slide's entire job.
  • Data freshness is literally the vertical gap from the watermark-as-a-graph plot, charted over wall-clock time. When the freshness line climbs, the watermark is falling behind real time — results for recent windows aren't out yet.
  • Walk the on-slide example as one story: at 08:10 freshness reads 9 min (watermark at 08:01 — the 08:00 window just emitted) while system latency reads 45 s (elements clear the pipeline fast). Conclusion in one breath: the pipeline is healthy; the data is just arriving late — a publisher-side or network problem, and adding workers would change nothing. The contrasting story: freshness 9 min and latency 7 min means elements themselves crawl — now it is the pipeline. Same first number, opposite diagnosis; that's why you need both.
  • The two can move independently, and that independence is diagnostic: a publisher outage raises freshness while latency stays flat (nothing to process, but what arrives moves fast); a slow external call in a DoFn raises latency first. The next slide's 2×2 table turns the combinations into diagnoses.
  • These charts return in the Monitoring & Troubleshooting module; here the goal is just to connect them to the watermark concept — the watermark is not hidden, it's published, as freshness.

Reading the two metrics together

Speaker notes — Reading the two metrics together
  • Walk one story per cell:
    • Top-right (traffic spike): a flash sale doubles the click stream. Each element still processes quickly (latency stable) but the backlog grows, so the watermark — and freshness — falls behind. This is the case autoscaling exists for.
    • Bottom-left (slow external API): a DoFn calls an enrichment service that's degrading. Elements take longer and longer (latency climbs) even though input volume is unchanged. Note: autoscaling won't help if workers are mostly waiting — CPU is idle, so no scale-up signal.

Triggers

When — and how often — to emit results, and how successive results relate. The policy layer on top of windows and watermarks.
Streams & timeWindowsWatermarksTriggers
Speaker notes — Section 4: Triggers
  • Arc: the problem (the dashboard can't wait an hour) → the default trigger made visible → early firings → late firings, which force the accumulation-mode question → the sink-driven decision rule → triggers that ignore the watermark entirely (processing-time and data-driven, closing the GlobalWindows loop) → the consolidated pipeline and best practices.
  • Vocabulary to establish early and use relentlessly: window (the group), firing (the moment), pane (the emitted result). One window can emit many panes.

The dashboard can't wait

Product upgrades the ask: hourly totals — but "don't make me stare at a blank tile for an hour, and do fix the number if stragglers arrive."

  • One window now wants three kinds of output: early estimates while it's open, a best answer at the watermark, corrections for late data
  • The watermark alone gives only the middle one
  • A trigger is the policy for when a window emits a result pane
Four words carry this section — the window is the group; a trigger fires (the moment); each firing emits a pane, one result element for that window; the window expires when its allowed lateness runs out. One window, many panes.
Speaker notes — The dashboard can't wait
  • Vocabulary beat — do not skip: window (the group), firing (the moment a trigger goes off), pane (the result a firing emits). The Java trigger API is unreadable without "pane," and even the Python one talks about panes in its accumulation modes. The original deck never named it; naming it now saves the rest of the section.
  • The three kinds of output map exactly onto the watermark: before it (early panes — speculative), at it (the on-time pane — the watermark's best answer), after it (late panes — corrections, only if lateness is allowed). Triggers are the knob for the before and after; the watermark still anchors the middle.
  • The tile sequence at the bottom is the whole scenario in four numbers: 118 and 253 are honest partials, 347 is the watermark-complete answer, 348 is a straggler correction. Ask which number was "wrong" — none of them; each was the best answer at its moment. That reframing is what makes accumulation modes (two slides ahead) feel natural.

The default trigger: fire once at the watermark

What you've been running all along, written out explicitly:

Pythonfrom apache_beam.transforms.trigger import (
    AfterWatermark, AccumulationMode)

per_minute = events | beam.WindowInto(
    window.FixedWindows(60),
    trigger=AfterWatermark(),
    accumulation_mode=AccumulationMode.DISCARDING)
  • No trigger specified = AfterWatermark(): each window fires once, when the watermark passes its end — one pane, its only result
  • With the defaults (allowed_lateness=0), that pane is also the only pane, and late data is dropped
  • In Python, naming a trigger explicitly also requires naming accumulation_mode — Beam refuses to guess how panes relate
Defaults are a real policy: complete-ish, once, drop the rest. Perfect for many pipelines — now you can change it deliberately.
Speaker notes — The default trigger
  • Java: .triggering(AfterWatermark.pastEndOfWindow()) — and Java likewise requires an explicit accumulation call (.discardingFiredPanes() or .accumulatingFiredPanes()) once you set any trigger.
  • Imports used through this section, so they're stated once: from apache_beam.transforms.trigger import AfterWatermark, AfterProcessingTime, AfterCount, Repeatedly, AfterAny, AccumulationMode.
  • Why Beam refuses to guess the accumulation mode: with one firing per window it doesn't matter — but the only reason to name a trigger is to get more firings, and then it matters enormously (slides ahead). Forcing the choice at the same moment you take control of firing is the API protecting you.
  • Pedagogical point of the slide: nothing changes. This code behaves identically to the bare WindowInto from Section 2 — the defaults were always a policy; now they're visible and editable.

Early firings: estimates before the watermark

Hourly window, but show a number every 30 seconds of wall-clock time while it fills.

Pythonper_hour = events | beam.WindowInto(
    window.FixedWindows(3600),
    trigger=AfterWatermark(
        early=AfterProcessingTime(30)),
        # fire every 30 s until the watermark
    accumulation_mode=AccumulationMode.ACCUMULATING,
    allowed_lateness=Duration(seconds=0))
  • early= decorates the watermark trigger with extra firings before it
  • AfterProcessingTime(30) runs on the worker's clock — the dashboard's refresh rate, independent of event time
  • Each pane is a new element emitted downstream — a new row, a new message. Nothing is updated in place; the consumer keeps the latest
Early firings trade compute for freshness — the aggregation reruns per firing. Combiner-friendly aggregations (Module 5) keep that cheap.
Speaker notes — Early firings
  • Java: AfterWatermark.pastEndOfWindow().withEarlyFirings(AfterProcessingTime.pastFirstElementInPane().plusDelayOf(Duration.standardSeconds(30))).
  • Be precise about what the pipeline actually does — students misread this: every 30 s the trigger fires and the pipeline emits a new element with the revised aggregate — a new BigQuery row, a new Pub/Sub message. The pipeline never reaches out and updates a tile; three firings = three elements downstream. It's the consumer (the dashboard query) that must pick the most recent one — which is why the sink pattern on the accumulation-mode slide matters.
  • Why ACCUMULATING here: since the consumer keeps only the latest pane, each pane must be the full running value — 118, then 253 (not 135), then 347. The decision rule lands formally two slides ahead; this is its first sighting in the wild.
  • Processing time is the right clock for a refresh rate — "every 30 seconds of our time" — precisely because it shouldn't care how event time is distributed inside the window.
  • Note the explicit allowed_lateness=0: early firings and lateness are independent knobs. This slide adds only the "before" panes; the "after" panes come next.

Late firings, and the accumulation question

Pythonper_hour = events | beam.WindowInto(
    window.FixedWindows(3600),
    trigger=AfterWatermark(
        early=AfterProcessingTime(30),
        late=AfterCount(1)),
        # re-fire for each late element
    allowed_lateness=Duration(seconds=2 * 3600),
    accumulation_mode=AccumulationMode.ACCUMULATING)
  • late= adds firings after the watermark, for as long as allowed_lateness keeps the window alive
  • This window now emits many panes — so what's in each pane? That's the accumulation mode
  • ACCUMULATING: every pane = everything so far. DISCARDING: every pane = only what's new since the last pane
Accumulation only matters when a trigger fires more than once — which is exactly why it lives here and not in the windows section.
Speaker notes — Late firings + accumulation
  • Java: .withLateFirings(AfterPane.elementCountAtLeast(1)), then .accumulatingFiredPanes() / .discardingFiredPanes().
  • Walk the numbers once for each mode — they're chosen so the totals differ visibly. Accumulating: 13 → 31 → 40 → 44, each pane the full answer so far. Discarding: 13 → 18 → 9 → 4, non-overlapping increments that sum to 44. Both are correct; they're answers to different consumers — next slide.
  • Cost note, said here and tabled next slide: ACCUMULATING holds all pane input in window state until the window closes — wide windows plus accumulating mode is a real memory cost. Discarding lets state flush at each firing.
  • There is a third mode in the model (RETRACTING — emit a withdrawal of the previous pane, then the new one); it's long-standing model theory but not generally available in the SDKs — mention only if asked.

Choosing an accumulation mode: look at your sink

Your sink / consumerModeWhy
A reader that keeps the latest — dashboard tile; BigQuery rows read through a "newest pane per window" view ACCUMULATING Each pane is the complete current answer; the reader keeps the newest and can ignore the rest
A reader that adds — append-only log, downstream sum, Pub/Sub of deltas; BigQuery view that sums panes per window DISCARDING Panes are non-overlapping increments; consumer adds them up
Ask "what does the reader of my output do with two panes for the same window?" If it keeps the latest — accumulate. If it adds — discard. (Discarding suits associative, commutative aggregations; it also keeps state small on wide windows.)
Streaming writes to BigQuery append — they don't update in place. Write every pane as its own row (window start + pane timestamp), and put the mode's logic in a view: latest-per-window for accumulating, SUM-per-window for discarding.
Speaker notes — Choosing an accumulation mode
  • Wrong pairings are the classic silent bug — walk both failures with the previous slide's numbers:
    • Accumulating panes into a summing consumer: it adds 13 + 31 + 40 + 44 = 128 — massive double counting, and the number even looks plausible.
    • Discarding panes into an overwriting tile: the tile shows 4 (the last pane) where the total is 44 — the dashboard mysteriously "loses" traffic at every refresh.
  • Neither failure raises an error anywhere — pipeline healthy, sink healthy, numbers wrong. That's why the rule is worth memorizing as a sentence: keeps the latest → accumulate; adds → discard.
  • Spell out the BigQuery mechanics, because "the tile replaces its number" hides them: the pipeline appends one row per pane — streaming inserts can't update rows, and an upsert/MERGE per firing would be fighting the tool. Schema: window_start, pane_ts, page, views. Accumulating: the dashboard reads a view like SELECT ... QUALIFY ROW_NUMBER() OVER (PARTITION BY window_start, page ORDER BY pane_ts DESC) = 1. Discarding: the view is SELECT window_start, page, SUM(views) ... GROUP BY .... A Pub/Sub topic of deltas feeding another pipeline is the most common DISCARDING consumer.

Triggers without watermarks

Scenario: a running total of orders since launch — one endless window, results on our schedule: every 100 orders or every 60 seconds, whichever comes first.

Pythonrunning = orders | beam.WindowInto(
    window.GlobalWindows(),
    trigger=Repeatedly(
        AfterAny(
            AfterCount(100),
            AfterProcessingTime(60))),
    accumulation_mode=
        AccumulationMode.ACCUMULATING)
  • AfterCount (data-driven) and AfterProcessingTime ignore event time entirely
  • AfterAny / AfterAll / AfterEach compose them; Repeatedly(...) keeps a trigger re-arming forever
  • This is the legal way to aggregate an unbounded stream in the global window — the trigger supplies what the watermark can't
AfterCount(100) alone strands elements 1–99 of a slow stream forever — nothing fires until the count is met. Compose a time-based trigger alongside it, as here.
Speaker notes — Triggers without watermarks
  • Java: Repeatedly.forever(AfterFirst.of(AfterPane.elementCountAtLeast(100), AfterProcessingTime.pastFirstElementInPane().plusDelayOf(Duration.standardSeconds(60)))).
  • This closes the loop from the window-choosing table: "over everything, on my own schedule" = GlobalWindows + a repeated trigger. The watermark never passes the global window's end (there isn't one), so without a trigger this aggregation would be the illegal construction from Section 2 — the trigger is what makes it legal.
  • Repeatedly matters: most triggers fire once and are done; wrapping in Repeatedly(...) re-arms after every firing. Forgetting it yields exactly one pane, ever — a classic head-scratcher.
  • If a student asks about micro-batching: it's just processing-time windows/triggers — Beam contains it as a special case rather than being built on it.
  • Per-record custom firing logic beyond these (e.g., "fire when I see a FLUSH record") is State and Timers territory — next module. Second plant.

Best practices

  1. Window in event time, stamp early. Use the true event timestamp (timestamp_attribute, or TimestampedValue right after the source), never arrival time — unless micro-batching is genuinely the requirement
  2. Set allowed_lateness on purpose. The default silently drops stragglers; pick a budget from the data (watch data freshness and droppedDueToLateness) and pay the state cost knowingly
  3. Match accumulation to the sink. Reader keeps the latest pane → ACCUMULATING; reader adds panes up → DISCARDING. This is the most common silent-wrong-number bug
  4. Never leave a count trigger alone. Pair AfterCount with a time-based trigger via AfterAny, or quiet periods strand data
  5. Watch freshness and latency together. They're the watermark's public face; the 2×2 table turns them into a diagnosis
