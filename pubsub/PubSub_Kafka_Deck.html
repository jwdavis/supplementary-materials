The model

Why a message broker sits between the programs that send events and the programs that use them, and how Pub/Sub uses topics and subscriptions to hold each message until every consumer has handled it.
Speaker notes — Section 1: The model
  • Ask who has published to Pub/Sub before. If most have, move quickly to page 6.

An ingestion service that forwards has nowhere to keep messages

Cymbal Meet’s media servers carry the audio and video of every call. Every 10 seconds, each media server measures packet loss, jitter, and an audio quality score for each participant it hosts and sends them as one call-quality sample to an ingestion service: 90,000 samples a second at the weekday peak. The ingestion service forwards each sample to three systems: a BigQuery writer, a live dashboard, and an alerting service. At 09:00 on Monday, the alerting service goes down for a 4-minute redeploy.

A producer is a program that sends messages; a consumer is a program that receives them. Here the media servers produce the samples and the three systems consume them. The ingestion service sits between them and only passes samples on.

The ingestion service has nowhere durable to keep alerting’s samples. It can drop them, or hold them in memory and lose them if it restarts.

The ingestion service’s code names every consumer. Adding a fourth, such as an archive, means changing and redeploying it.

Example

Actor: the ingestion service, Monday 09:00–09:04.

Input: alerting’s copy of each sample, about 350 bytes.

Mechanism: 4 min × 90,000/s = 21.6M samples, about 7.6 GB, arrive for alerting with no place to wait.

Result: alerting is back at 09:04, but the 21.6M samples are gone. A spike of poor-quality calls during those 4 minutes never raises an alert illustrative.

Takeaway: a service that only forwards can’t hold messages for a consumer that is down, and it must know every consumer.
Speaker notes — An ingestion service that forwards has nowhere to keep messages
  • Ask the room how many have built a forwarding service like this.
  • Where the samples come from: a media server sees each participant’s packet loss and jitter in the RTCP reception reports that every call exchanges (RFC 3550 §6.4: “fraction lost,” “cumulative number of packets lost,” “interarrival jitter”). What only the app can measure (WebRTC statistics) reaches the media server over the call’s existing connection. The 10-second sample is Cymbal Meet’s design choice.
  • The point of contrast for the next page: a forwarder passes messages on and keeps nothing; a broker stores each message until every consumer has taken it.
  • 21.6M × 350 B ≈ 7.6 GB. Holding that in one service’s memory is possible but fragile: a crash or restart loses it all, and a longer outage outgrows memory.

A broker keeps a copy for each consumer

Replace the ingestion service with a message broker: a service that receives messages from producers and keeps a copy of each message for each consumer until that consumer confirms it has handled it. The media servers now send each sample to the broker once.

A consumer can be down: its messages wait in its queue until it comes back.

A consumer can be slower than the arrival rate for a while: its queue grows, and it catches up when it has spare capacity.

The producer doesn’t need to know who the consumers are: adding a consumer means adding a queue in the broker; the media servers don’t change.

Example

Actor: the alerting service, down for 4 minutes; when running, it can process up to 120,000 samples/s.

Input: 90,000 samples/s keep arriving.

Mechanism: the broker stores alerting’s 21.6M samples. Once alerting is back, it works through 120,000/s while 90,000/s arrive, so its queue shrinks by 30,000/s.

Result: alerting has caught up 12 minutes after it comes back, with no samples lost illustrative.

Takeaway: a broker stores messages for each consumer separately, so a consumer that is down or slow loses nothing and affects no one else.
Speaker notes — A broker keeps a copy for each consumer
  • “Message broker” is the general term: Pub/Sub, Apache Kafka, RabbitMQ, and Amazon SQS/SNS are all brokers. The deck uses it throughout.
  • The broker takes the ingestion service’s place; nothing sits between the media servers and the broker. Media servers can publish directly because they are Cymbal Meet’s own servers and hold Google Cloud credentials (a service account).
  • If asked “why not have the apps publish directly?”: Google’s guidance is not to put service accounts in client apps (IAM best practices for service account keys: “For client-side applications such as tools, desktop programs, or mobile apps, don’t use service accounts”), and the Pub/Sub overview says app events are forwarded to Pub/Sub by a server, with Firebase for app-to-service messaging.
  • Catching up needs spare capacity. If alerting could only process 90,000/s, its queue would never shrink. 21.6M ÷ 30,000/s = 720 s = 12 min.

Topics, subscriptions, and acks

Pub/Sub is Google Cloud’s message broker. In Pub/Sub’s terms, the previous page’s setup is one topic, qos-samples, that the media servers publish each sample to, and one subscription each for the BigQuery writer, the dashboard, and alerting.

Publisher: Pub/Sub’s name for a producer, a program that sends messages to a topic. Here, the media servers.

Topic: a named destination for messages. Pub/Sub copies each message to every subscription on the topic; by default the topic itself stores nothing.

Subscription: one consumer’s queue, attached to one topic. It holds each message published after it was created until a subscriber acks it, which confirms the subscriber has handled it. Then the subscription deletes its copy.

Subscriber: Pub/Sub’s name for a consumer, a program that reads from a subscription. Here, the BigQuery writer, the dashboard, and alerting. Several processes running the same program can share one subscription; each message goes to one of them.

Example

Actor: the archive team, creating a fourth subscription, archive-sub, at 10:00.

Input: samples published at 09:59 and at 10:01.

Mechanism: Pub/Sub copies each message only to the subscriptions that exist when it is published. At 09:59, archive-sub doesn’t exist yet.

Result: the archive receives the 10:01 sample; the 09:59 sample never reaches it. The media servers needed no change.

CaveatA message published to a topic with no subscriptions is lost, with no error. Create subscriptions before publishers start.
Takeaway: a topic hands each message to every subscription on it; each subscription is one consumer’s queue; an ack deletes the message from that one queue.
Sources: Handling message failures, Replay overview (verified 2026-10-01).
Speaker notes — Topics, subscriptions, and acks
  • This is the Pub/Sub version of page 5: point at the same three consumers in the same order. Page 5 is true of any broker; this page is Pub/Sub’s names for it.
  • Handling failures: “messages published to a topic with no subscriptions are lost.” This is the most common “where did my messages go” question, because there is no error.
  • The exception is topic message retention (off by default, 10 minutes to 31 days): it keeps messages on the topic so a later subscription can seek back to them. Page 30 covers it.
  • Warn against “the topic stores messages and subscribers read from it.” That is closer to Kafka; Section 5 makes the contrast.

Create a topic and three subscriptions

The setup from the previous two pages needs one topic and one subscription for each of the three consumers. gcloud is Google Cloud’s command-line tool; Cloud Shell is a browser terminal where it is already installed.

Cloud Shell, project cymbal-meet-prod

One subscription per consumer. Each subscription receives its own copy of every message. If the dashboard and alerting read the same subscription, they would split the samples between them, and neither would see them all.

Pub/Sub returns each resource’s full name, which includes the project. Names are scoped to the project, so another project can have its own qos-samples.

Topic and subscriptions are separate resources with separate access permissions, so the publishing team and each reading team can be granted access separately.

Most settings in this deck belong to the subscription, not the topic, because consumers can need different behavior.

RuleTwo subscription settings, message ordering (page 14) and filtering (page 23), can only be chosen when the subscription is created. Plan the subscription, not just the topic.
Takeaway: one topic for the stream, one subscription for each consumer; each subscription holds that consumer’s queue and settings.

Publish and receive in Python

Cymbal Meet’s billing meter is a Python service that publishes a usage event each time a participant leaves a meeting. A separate invoicing service reads those events and adds up billable minutes.

python · billing meter (publisher)

import json
from google.cloud import pubsub_v1

publisher = pubsub_v1.PublisherClient()
topic = publisher.topic_path(
    "cymbal-meet-prod", "usage-events")

def record_usage(event):
    data = json.dumps(event).encode("utf-8")
    future = publisher.publish(topic, data)
    future.add_done_callback(log_result)

python · invoicing (subscriber)

import json
from google.cloud import pubsub_v1

subscriber = pubsub_v1.SubscriberClient()
sub = subscriber.subscription_path(
    "cymbal-meet-prod", "invoicing-sub")

def callback(message):
    add_billable_minutes(json.loads(message.data))
    message.ack()

stream = subscriber.subscribe(
    sub, callback=callback)
with subscriber:
    stream.result()  # keep running

publish() doesn’t wait for Pub/Sub to answer. It hands the message to a background thread and returns a future: an object that later holds the message ID (a unique ID Pub/Sub assigns to each message), or an error if publishing failed. log_result runs when that answer arrives.

subscribe() doesn’t wait for messages either. It starts background threads that call callback once per message as messages arrive.

The callback acks only after the work is done, so a crash halfway through leaves the message in the subscription to be delivered again.

Takeaway: publishing and receiving both run in background threads; Sections 2 and 3 cover the settings on these two calls and on the subscription.
Sources: python-pubsub samples/snippets; google-cloud-pubsub 2.42.0 (verified 2026-10-01).
Speaker notes — Publish and receive in Python
  • The pattern follows the handwritten samples in googleapis/python-pubsub/samples/snippets/ (archived; the samples were not moved to the google-cloud-python monorepo, whose package has only generated samples). The generated_samples/ directory in the same repo shows raw API calls, one per method; it isn’t how you write a publisher or subscriber.
  • The quickstart calls future.result() right after each publish. That waits for Pub/Sub to answer each message before sending the next, which defeats batching (page 11). Use a done-callback, or collect the futures and wait once.
  • log_result and add_billable_minutes are application functions. Java equivalents: Publisher.newBuilder(topic).build() and Subscriber.newBuilder(subscription, receiver).build().

Batch settings: which limit sends the batch

The Python client library collects published messages into a batch and sends the batch to Pub/Sub as one request when the first of three limits is reached.

python · publisher with the default batch settings

from google.cloud import pubsub_v1

batch = pubsub_v1.types.BatchSettings(
    max_messages=100,     # at most 100 messages per request
    max_bytes=1_000_000,  # at most 1 MB per request
    max_latency=0.01,     # a message waits at most 10 ms
)
publisher = pubsub_v1.PublisherClient(batch_settings=batch)
topic = publisher.topic_path("cymbal-meet-prod", "qos-samples")
for data in messages:
    publisher.publish(topic, data)
If you publish…Limit reached firstWhat each request carries
1,000 messages of 400 B, in one loopmax_messages: 100 messages are waiting long before 10 ms pass, and they total only 40 KBabout 100 messages, about 40 KB; about 10 requests in all
200 messages of 50 KB, in one loopmax_bytes: 20 messages plus the request’s own bytes would pass 1 MB19 messages, about 950 KB; 11 requests in all (the last carries 10)
400 B messages, 1,000 a second, steadilymax_latency: about 10 messages arrive in 10 msabout 10 messages, about 4 KB
one 400 B message every 10 secondsmax_latency: no other message arrives within 10 ms1 message, 400 B, billed as 1 KB

Batching happens inside one publisher process. What fills a batch is how many messages that one process publishes close together, not how many the topic receives from all publishers.

Pub/Sub bills each publish request as at least 1 KB (1,000 bytes), so a request carrying one 400-byte message is billed at 2.5× its size.

Don’t wait on each publish() future before the next call. If you wait for Pub/Sub’s answer to each message, each request carries one message.

Takeaway: with the default batch settings, a batch is sent at 100 messages, 1 MB, or 10 ms, whichever comes first, so it fills only when one process publishes many messages close together.
Sources: google-cloud-pubsub 2.42.0 types.BatchSettings() (test T1), publisher/_batch/thread.py (test T5); Pub/Sub pricing (verified 2026-10-07).
Speaker notes — Batch settings: which limit sends the batch
  • Read the code, then each row as “if you send this, this limit sends the batch, and each request carries this.” Defaults printed from the library (T1): BatchSettings(max_bytes=1000000, max_latency=0.01, max_messages=100). max_messages is “the maximum number of messages to collect before automatically publishing the batch”; max_bytes counts “the maximum total size of the messages … including any byte size overhead of the publish request itself” (types.py). The 10 ms timer starts when a message is published and no timer is running; when it fires, the client sends whatever is waiting (client.py).
  • Exact rule in 2.42.0 (thread.py): overflow = new_size > size_limit or new_count >= self.settings.max_messages. If the next message would overflow a batch that already holds messages, the batch is sent without it and the message starts the next batch. Size is the encoded PublishRequest: the topic name plus each message’s data, attributes, and a few bytes of framing. Two consequences: a full batch carries 99 messages, not 100 (the 100th starts the next batch); and a message that would push the request past 1 MB goes in the next batch.
  • Arithmetic, checked by test T5 (2.42.0, publish request replaced by a local stub that records each request; nothing sent to Google Cloud). Row 1: 100 × 400 B = 40 KB, far below 1 MB; 1,000 messages went as 99-message requests of 40,240 B, 11–12 in all (the 10 ms timer can split the remainder). Row 2: each 50,000 B message counts as 50,005 B; 19 × 50,005 B + the request’s own bytes = 950,198 B, and a 20th would make 1,000,203 B, over 1,000,000; 200 = 10 × 19 + 10 → 11 requests. Row 3: 1,000/s × 0.01 s = 10 messages × 400 B = 4 KB; the test (one publish per 1 ms sleep) gave 8–10 per request. Row 4: 1 message per request every time.
  • Pricing: “A minimum of 1 KB is assessed for each request, independent of the message sizes in the request” (Pub/Sub pricing). 1,000 ÷ 400 = 2.5×. Waiting on each future also costs time: each wait is a full round trip to Pub/Sub. Use a done-callback, or collect the futures and wait once (page 8 notes).
  • A longer max_latency means fuller batches but more delay, and buffered messages are lost if the process dies before sending; call publisher.stop() on shutdown to send them. Publish best practices: batching “creates latency for individual messages because the publisher waits for the batch to be filled up.”

Data and attributes

Cymbal Meet’s alerting team wants only web-client samples. Whether Pub/Sub can filter them depends on where the device type is stored in the message.

data is opaque bytes, up to 10 MB. Pub/Sub delivers it without reading it, unless you attach your own transform code (page 24).

attributes are key-value pairs of strings that Pub/Sub can read: up to 100 per message, keys up to 256 bytes, values up to 1,024 bytes.

Pub/Sub can filter only on attributes, because filters never read the data.

Example

Actor: a media server publishing a web client’s sample.

Input: publisher.publish(topic, data, device="web", sdk_version="4.2.1")

Mechanism: the Python client library sends each extra keyword argument as an attribute; values must be strings. The JSON in data is unchanged.

Result: a filter on attributes.device (page 23) keeps iOS and macOS samples out of alerting’s subscription. With device only in the JSON, alerting receives every sample and must parse each one to discard it.

Takeaway: anything Pub/Sub must filter on goes in an attribute; everything else goes in the data.
Sources: Pub/Sub quotas and limits, Filter messages (verified 2026-10-01).
Speaker notes — Data and attributes
  • Limits from the quotas page. A single publish request is also capped at 10 MB and 1,000 messages, which is why the batch defaults stay well below.
  • Attributes count toward the billed message size, so don’t copy the whole payload into them.
  • Exception: a single message transform you attach is code that can read and change the data (page 24). Built-in filters never can.
  • Example code: publish(topic, data, ordering_key="", retry=…, timeout=…, **attrs); every other keyword argument becomes an attribute. Byte values are decoded as UTF-8, and any other type raises TypeError (client.py, 2.42.0).

When arrival order changes the answer

Cymbal Meet’s session service publishes a joined event when a participant connects to a meeting and a left event when they disconnect. The roster updater, a subscriber process, applies these events to each meeting’s live roster. Amy and Bo joined meeting m_58d1 at about 14:00, so its roster is {amy, bo}. At 14:12:30 Amy’s Wi-Fi drops for a moment: the session service publishes her left, then her joined when she reconnects 300 milliseconds later.

By default Pub/Sub doesn’t promise to deliver messages in the order they were published, even two messages from the same publisher.

Two events published close together can be processed in reverse, for example when processing the first one fails and Pub/Sub delivers it again after the second is done.

Most streams aren’t affected: a call-quality sample carries its own timestamp, so arriving late changes nothing. Code that updates stored state one event at a time, like the roster, is affected.

Example

Actor: the roster updater.

Mechanism: its database write for left times out, so the callback raises an exception and doesn’t ack. Meanwhile the updater applies joined, which changes nothing because Amy is still on the roster. Pub/Sub delivers left again a few seconds later, and this time the write succeeds.

Result: the roster ends {bo}. Amy stays in the meeting but off the roster, and no later event puts her back unless she reconnects again.

Takeaway: out-of-order processing matters only for code that applies events to stored state one at a time, like the roster.
Speaker notes — When arrival order changes the answer
  • Starting state: Amy and Bo joined at about 14:00 (page 14 shows their joined events). Only Amy’s two events at 14:12:30 matter here; Bo is on the roster so the wrong result is visible as “Amy missing,” not “roster empty.”
  • Reordering needs the second event to be processed before the first is finished. That is likely for events a few seconds apart or less, like a reconnect; a join and a leave half an hour apart won’t reorder. “By default, Pub/Sub might not deliver messages in the order they are published” (Subscription properties).
  • When a callback raises an exception, the Python client nacks the message, so Pub/Sub redelivers it; meanwhile the client runs other callbacks on its thread pool (10 threads by default, subscriber/scheduler.py), which is how joined finishes first. Ordering keys (next page) fix this case. They wouldn’t fix events that two separate processes publish in the wrong order: Pub/Sub keeps the order in which it receives messages, so publish one key’s events from one place.
  • Ask the room for fixes before the next page. Good answers: make the consumer order-independent (store each participant’s latest event time and ignore older events), or use ordering keys.

Ordering keys

The roster on page 13 is correct only if each meeting’s events are applied in the order they were published. Events from two different meetings don’t affect each other, so their relative order doesn’t matter.

python · publisher with ordering (not the default)

publisher = pubsub_v1.PublisherClient(
    publisher_options=pubsub_v1.types.PublisherOptions(
        enable_message_ordering=True))
publisher.publish(topic, data, ordering_key="m_58d1")

Messages with the same ordering key are delivered in publish order. Different keys have no order between them.

Enable it on both sides: the publisher, and the subscription when you create it.

Publish every message for one key from the same Google Cloud region (data-center location). Two regions publishing one key get no guarantee between them.

Example

Actor: the session service, publishing with ordering keys, and the roster updater, reading a subscription with ordering enabled.

Input: Amy’s left and joined from page 13, both with ordering key m_58d1.

Mechanism: the client library passes one key’s messages to the callback one at a time. When the write for left fails, Pub/Sub delivers left again and then joined, in that order.

Result: the roster ends {amy, bo}. Other meetings’ events keep flowing while m_58d1 waits.

Takeaway: use as the ordering key the ID of the thing whose events must stay in order, such as a meeting ID.
Sources: Order messages (verified 2026-10-01).
Speaker notes — Ordering keys
  • The top row is page 13’s meeting: Amy and Bo join at about 14:00, then Amy’s reconnect at 14:12:30. In publish order the roster ends {amy, bo}.
  • All three rows come from the Order messages page. The same-region requirement surprises teams with publishers in several regions.
  • Other good keys: an order ID in a shop, an account number in a ledger.
  • For scale, if asked: 6M meetings/day × about 10 events = 60M/day, about 700/s on average.

What ordering costs

A team adding ordering keys to Cymbal Meet’s session events can key each event by its meeting, or put a whole geographic area, such as all of us-east, on one key. Ordering has costs, and the choice of key sets how many meetings each cost affects.

Each key is limited to 1 MB/s of publish throughput.

A redelivery holds up its key: if message 2 is redelivered, message 3 is redelivered after it, even if it was already delivered.

The docs say ordering “decreases publish availability and increases end-to-end message delivery latency.” If one publish for a key fails, the client stops publishing that key until your code tells it to resume.

Example

Actor: the roster updater, reading session events keyed by geographic area.

Input: every us-east event on one key; the database write for one meeting’s left event keeps failing.

Mechanism: Pub/Sub keeps delivering that left again, and every us-east event behind it waits.

Result: the rosters of every us-east meeting stop updating until that one event is acked. Keyed by meeting_id, only that meeting’s roster waits.

Takeaway: key on the smallest unit whose events must stay in order, such as one meeting, and use ordering only on the streams that need it.
Sources: Order messages, Quotas and limits (verified 2026-10-01).
Speaker notes — What ordering costs
  • The availability and latency sentence is quoted from the ordering page; it is on the face as a quote so it doesn’t read as instructor opinion.
  • 1 MB/s per ordering key is on the quotas page. One meeting’s events total about 2 KB over half an hour, far below it.
  • In Python, after a failed publish on a key, call publisher.resume_publish(topic, ordering_key) to publish on that key again (client.py, 2.42.0).
  • Push subscriptions (page 18) deliver only one unacknowledged message per key at a time.
  • With exactly-once delivery as well, acks must be processed in order; out-of-order acks fail with retryable errors.
  • Discussion: which Cymbal Meet streams need ordering? Session events yes; call-quality samples and usage events no.

Recap: publishing

With the default batch settings, a batch is sent at 100 messages, 1 MB, or 10 ms, whichever comes first. Only one process’s messages share a batch, so a process that publishes only now and then sends one message per request and pays the 1 KB minimum.

Put the fields Pub/Sub filters on in attributes. Filters never read the data; only a transform you attach (page 24) can read it.

Use ordering keys only where processing out of order gives a wrong result, keyed on the thing whose events must stay in order.

Ordering limits each key to 1 MB/s, and while a message is redelivered, the messages behind it on the same key wait.

Subscription types

Each subscription has a delivery type, which sets how messages leave Pub/Sub: your program asks for them, Pub/Sub sends them to your program, or Pub/Sub writes them into another Google Cloud service with no program of yours involved.

Speaker notes — Subscription types
  • The “Fits” column follows the docs’ use cases. Pull: “Large volume of messages (GBs per second),” “Environments where it’s not feasible to set up a public HTTPS endpoint.” Push: “Multiple topics that must be processed by the same webhook,” “App Engine Standard or Cloud Run functions subscribers.” Export: “Sending messages directly to a Google Cloud resource without any additional processing” (Choose a subscription type).
  • Cloud Run has both shapes: a Cloud Run service is “a request-driven workload,” a natural push endpoint; a Cloud Run worker pool is “specifically designed for non-request workloads, such as pull queues” (Cloud Run resource model).

The ack deadline

Cymbal Meet’s summarizer reads each finished meeting’s transcript and writes a summary. Most take under a minute; a long meeting takes about 3 minutes. If a summarizer process crashes partway through, another summarizer process should get the transcript; while the first is still working, no other process should.

The ack deadline is how long Pub/Sub waits for an ack before it delivers the message again. Until then, it normally doesn’t give the message to another subscriber.

You set a starting value on the subscription: default 10 s, from 10 to 600 s. On a push subscription, it is how long Pub/Sub waits for your endpoint’s HTTP response, and nothing can extend it.

A Python subscriber that calls subscribe() doesn’t use that value. By default, the client library sets each message’s deadline when it arrives, then keeps extending it until your code acks or nacks the message, or 1 hour passes (max_lease_duration).

Each extension is as long as the time within which 99% of this subscriber’s messages were acked, between 10 and 600 s. If 99% of the summaries so far were acked within 120 s, each extension asks for 120 s, and the next one is sent before 108 s of it (90%) have passed.

Example

Actor: the same summarizer, deployed as a push endpoint on Cloud Run.

Input: a push subscription with the default 10 s ack deadline, and a long meeting whose summary takes about 3 minutes.

Mechanism: after 10 s with no HTTP response, Pub/Sub treats the request as failed and sends the transcript again, while the first request is still running.

Result: the meeting can get more than one summary. Setting the subscription’s ack deadline to 300 s, longer than the slowest summary, prevents this.

Takeaway: a message is delivered again when its ack deadline lapses. On push, the subscription’s deadline is fixed, so set it longer than your slowest request; a Python subscribe() client keeps extending it, so it lapses mainly when the process stops or loses its connection.
Sources: Lease management, Subscription properties, Push subscriptions, Exactly-once delivery; google-cloud-pubsub 2.42.0 source (tests T1, T4; verified 2026-10-06).
Speaker notes — The ack deadline
  • Three values, three places. Subscription ack deadline (default 10 s, 10–600 s; Subscription properties): Pub/Sub uses it for push, where it is also the HTTP request timeout (pubsub.proto), and as the starting deadline for single pull() calls. The Python client sends a 60 s stream deadline when it opens the stream, but immediately overrides each message’s deadline on arrival; its source calls the 60 s “not useful since we’ll modack” (streaming_pull_manager.py L1088–L1095, L1289–L1297). The docs agree: “Supported client libraries don’t use the default subscription acknowledgment deadline” (Exactly-once delivery), and a client “might get [the message] redelivered before the acknowledgment deadline that you set” (Subscription properties).
  • The 99%: the client records, for every message it acks, the seconds from arrival to ack (rounded up, clamped 10–600), for as long as the subscriber runs. Each extension is the 99th percentile of those times (histogram.py, _obtain_ack_deadline). A freshly started subscriber has no history, so it uses 10 s and re-extends every few seconds until the first acks arrive. Lease management: “The high-level client libraries for Python, Go, and Java use the 99th percentile of acknowledgment delay to determine the length of each extension” (Lease management).
  • Timing: a background thread extends every held message (in a callback or waiting for one), then sleeps a random time up to 90% of the deadline (leaser.py). It stops extending a message 1 hour after handing it to your callback (max_lease_duration, T1). With exactly-once on, each extension is at least 60 s.
  • To bound it yourself: FlowControl(min_duration_per_lease_extension=…, max_duration_per_lease_extension=…, max_lease_duration=…), each in seconds (types.py). A lower maximum means a crashed process’s messages come back sooner, at the cost of more extension requests.
  • Push: ack is HTTP 102, 200, 201, 202, or 204; “You can’t modify the acknowledgment deadline of individual messages that you receive from push subscriptions” (Push subscriptions). 300 s in the example is under the 600 s maximum.
  • “Normally” on bullet 1: “Acknowledgment deadlines are not guaranteed to be respected unless you enable exactly-once delivery” (Lease management). nack() asks for redelivery now instead of waiting.

Flow control: how many messages Pub/Sub delivers to one subscriber

When a subscriber process calls subscribe(), Pub/Sub delivers messages to it, and the Python client library passes each message to your callback. Two settings limit how much work one process takes on:

SettingWhat it limitsPython default
Flow control: max_messages, max_byteshow many messages Pub/Sub delivers to the process that it hasn’t yet acked or nacked1,000 messages or 100 MiB, whichever comes first
Thread pool: max_workershow many of those messages the process handles at the same time (one callback per thread)10 threads

python · both settings, at their defaults

flow = pubsub_v1.types.FlowControl(
    max_messages=1000, max_bytes=100 * 1024 * 1024)
threads = ThreadScheduler(
    executor=futures.ThreadPoolExecutor(max_workers=10))
subscriber.subscribe(sub, callback=handle,
                     flow_control=flow, scheduler=threads)

With both defaults, a process can have 1,000 messages delivered and be handling 10 of them. The other 990 wait in the process’s memory for a free thread.

At either flow-control limit, Pub/Sub stops delivering to that process. It sends more once the process is back under 80% of the limit (with the default, fewer than 800 unacked messages). Messages not delivered stay in the subscription.

Messages delivered to one process can’t go to another process reading the same subscription until the first process acks or nacks them, or their ack deadlines lapse. With the default max_messages, one process can receive a whole backlog of up to 1,000 messages while it works on 10, and a process added to help gets none. If the first process crashes, its messages wait until their ack deadlines lapse.

When several processes share a subscription and each message takes a while to handle, set max_messages a little above max_workers. Setting them equal leaves threads idle while the process waits for its next delivery.

Takeaway: flow control sets how many messages one process receives; keep it close to how many the process works on at once, so the rest wait in the subscription where any process can receive them.
Sources: Handle transient spikes with flow control, Troubleshoot pull subscriptions; google-cloud-pubsub 2.42.0 types.FlowControl, scheduler.py; real-service test, 2026-10-07.

Exactly-once delivery

By default, Pub/Sub may occasionally deliver a message again after it has been acked. Exactly-once delivery is a subscription setting that guarantees it won’t: once Pub/Sub has recorded a message’s ack, it never delivers that message again.

gcloud pubsub subscriptions update invoicing-sub --enable-exactly-once-delivery

The guarantee covers only acks that Pub/Sub records, and an ack can fail, for example when it arrives after the message’s deadline has expired. Plain ack() returns nothing, so your code never learns that an ack failed, and the message may be delivered again. ack_with_response() tells you which happened:

python · the invoicing callback from page 8, on a subscription with exactly-once on

def callback(message):
    add_billable_minutes(json.loads(message.data))
    future = message.ack_with_response()
    try:
        future.result()   # returns once Pub/Sub has recorded the ack
    except sub_exceptions.AcknowledgeError as e:
        # not recorded: expect this message to be delivered again
        logging.warning("ack %s failed: %s", message.message_id, e.error_code)

If result() returns, Pub/Sub has recorded the ack and won’t deliver this message again, so the customer’s minutes are counted once.

If it raises AcknowledgeError, the minutes are already added, and you should expect the message to be delivered again. To avoid counting them twice, store each finished message’s ID with its minutes and skip a message whose ID is already stored; a redelivered message keeps its message ID.

Limits: pull subscriptions only; the guarantee applies only to subscribers in the same Google Cloud region; delivery is slower; and it doesn’t cover a publisher that publishes the same event twice (page 21).

Takeaway: exactly-once delivery guarantees no redelivery after a recorded ack; use ack_with_response() so your code knows whether its ack was recorded.
Sources: Exactly-once delivery, Subscription overview, Lease management (verified 2026-10-07); official sample pubsub_subscriber_exactly_once.
Speaker notes — Exactly-once delivery
  • Without exactly-once: “Pub/Sub tries not to deliver an outstanding message to any other subscriber on the same subscription” (Subscription overview); “Acknowledgment deadlines are not guaranteed to be respected unless you enable exactly-once delivery” (Lease management); a duplicate is “a message … re-sent after a successful acknowledgment or before acknowledgment deadline expiration” (Exactly-once delivery). The docs give no rate for duplicates; don’t invent one.
  • With it: “No redelivery occurs after the message is successfully acknowledged. No redelivery occurs while a message is outstanding.” “If the acknowledgment request succeeds, the clients are guaranteed to not receive a re-delivery. If the acknowledgment request fails, the clients can expect a re-delivery.” Plain ack() on such a subscription: “the acknowledgment failures can lead to silent re-deliveries.”
  • The code follows the official Python sample (archived python-pubsub repo, subscriber.py). Without exactly-once, the future from ack_with_response() resolves at once as success (test T2). Imports: json, logging, and google.cloud.pubsub_v1.subscriber.exceptions as sub_exceptions.
  • Storing the message ID: the docs say to “maintain information about the progress of processing a message until it is successfully acknowledged” and use it “to prevent duplicate work when an acknowledgment fails.” Write the ID in the same database write as the minutes. A single message transform (SMT) is a JavaScript function Pub/Sub runs on each message before writing it. It can change the data and attributes, or return null to skip the message.

An SMT sees one message at a time, within 500 ms and without calling other services. It can’t join, count, or average messages.

--use-topic-schema writes each field of the topic’s schema to the table column of the same name. A schema is an Avro or Protobuf definition of the fields every message on the topic must contain; Pub/Sub rejects a message that doesn’t match when it is published.

Pick the subscription type by what reads the messages; exactly-once delivery needs pull.

Reading a backlog

On most weekdays, traffic on Cymbal Meet’s dashboard-sub triples between 04:00 and 10:00 as working-hours calls start, peaking at 90,000 samples/s. Its subscriber runs 6 processes that together handle up to 120,000/s, and each sample takes about 2 s from publish to ack: delivery to a process, then processing. On an unusually busy morning, traffic peaks at 150,000/s instead. Two metrics show which morning is in trouble:

num_unacked_messages_by_region: how many messages in the subscription have no ack yet, including ones a subscriber is working on now.

oldest_unacked_message_age_by_region: how long ago the oldest of those messages was published.

Normal morning: more samples in progress, none waiting longer. With spare capacity, no sample waits for a free process, so each is acked about 2 s after it is published, and the oldest unacked sample is about 2 s old at any volume. Three times the traffic puts three times as many samples in progress at once, so the count triples: 90,000/s × 2 s = 180,000.

Busy morning: from 08:06, more samples arrive than 6 processes handle. Until then, the count reaches 240,000, higher than on any normal morning, yet every sample is still acked in about 2 s. After 08:06, the samples the processes can’t take yet wait for a free process on top of their 2 s, and each new sample waits behind them, so the age climbs. By 10:00 the dashboard shows calls as they were 17 minutes ago illustrative.

Takeaway: the count rises with traffic even when the subscriber keeps up; the oldest age rises only when it falls behind. Alert on the age, with a threshold set by how stale the consumer’s data can be.
Sources: Monitor Pub/Sub (verified 2026-10-07).
Speaker notes — Reading a backlog
  • The idea to land: below capacity, each message’s wait is its own 2 s of delivery and processing, so volume changes how many are in progress (count), not how long each waits (age). Above capacity, messages also wait for a free process, and that wait grows every second.
  • Metric meanings from Monitor Pub/Sub; use the _by_region versions. The same page: “the absolute number of unacknowledged messages is not necessarily meaningful. A backlog of a million messages might be acceptable for a million message-per-second subscription, but unacceptable for a one message-per-second subscription.”
  • Below capacity, count = arrival rate × time from publish to ack (Little’s law): 30,000 × 2 s = 60,000; 90,000 × 2 s = 180,000; on the busy morning 50,000 × 2 s = 100,000 overnight and 120,000 × 2 s = 240,000 at 08:06. The 2 s is illustrative; in practice samples vary, and the oldest is the slowest one in progress. Read your own subscription’s normal age off its dashboard. Simplified: close to capacity, some samples already wait briefly for a process, so the age starts to creep up a little before 08:06.
  • Busy morning (illustrative): 50,000/s until 06:00, rising evenly to 150,000/s at 09:00, flat to 10:00. Simulated second by second with oldest-first handling and the same 2 s per sample: arrivals pass 120,000/s at 08:06; the age passes 60 s at 08:27 with about 8 million waiting; 10:00 has about 157 million waiting and the oldest about 17 min old. Pub/Sub doesn’t promise order, so the oldest can be older. The monitoring page calls count and age growing “in tandem” “Subscribers not keeping up with message volume.”
  • The same picture fits an autoscaled subscriber that can’t scale further (it hits its maximum instances or a quota): the dashed line is then the most it can scale to. Dead-letter topics

Cymbal Meet’s dashboard subscriber reads dashboard-sub (a pull subscription, page 7) and marks a call as poor when its packet loss is above 5%. Samples from web client 6.4.0 carry "packet_loss_pct": null when a call receives no packets in a 10-second interval. Comparing null with 5 raises an exception in the callback, so the Python client nacks the message and Pub/Sub delivers it again.

Retrying can’t fix it: every attempt sends the same sample to the same code. Pub/Sub keeps delivering each null sample until retention runs out (7 days by default), each delivery is billed, and the subscription’s oldest unacked age keeps climbing (page 28).

A dead-letter topic caps the attempts. After the maximum number of delivery attempts (5 with the default; --max-delivery-attempts sets 5–100), Pub/Sub publishes the message to the dead-letter topic and removes it from the source subscription, so the oldest unacked age drops back to normal.

    --member=serviceAccount:$PUBSUB_SA --role=roles/pubsub.subscriber

Part 1: the dead-letter topic needs its own subscription, like any topic; a message published to a topic with no subscription is lost (page 6).

Part 2: Pub/Sub moves the message itself, with its own service account, not your subscriber’s. That account needs publisher on the dead-letter topic and subscriber on the source subscription. Without them, nothing is moved and no error says why.

Then read the moved messages through qos-samples-dlq-sub. Pub/Sub adds attributes naming the source subscription and the attempt count. Here every one comes from web client 6.4.0 with a null loss, so the team changes the callback to treat null as 100% loss and runs the moved samples through the fixed code.

When your code recognizes bad data, ack it and log it. The dead-letter topic is for failures your code doesn’t anticipate.

Takeaway: a dead-letter topic moves a message that fails every time out of the subscription after a set number of attempts, and keeps it where you can read it.
Sources: Handling message failures, Subscription properties (verified 2026-10-07).
Speaker notes — Dead-letter topics
  • Handling failures: subscribers can fail because “a message could be in a format that the subscriber does not expect”; Pub/Sub “can forward them to a dead-letter topic.” Forwarded messages carry CloudPubSubDeadLetterSourceDeliveryCount, CloudPubSubDeadLetterSourceSubscription, and CloudPubSubDeadLetterSourceTopicPublishTime. The attempt count is approximate: Pub/Sub “forwards undeliverable messages on a best-effort basis” (Handling message failures).
  • When a callback raises an exception, the Python client nacks the message (page 13 notes), and Pub/Sub delivers it again right away unless the subscription has a retry policy. Set one with backoff (--min-retry-delay, --max-retry-delay, up to 600 s) so the 5 attempts are spread out. Monitoring page: “You pay for every redelivery.”
  • Permissions: “To forward undeliverable messages to a dead-letter topic, Pub/Sub must have permission to … Publish messages to the topic [and] Acknowledge the messages, which removes them from the subscription.” “Pub/Sub only counts delivery attempts when a dead-letter topic is configured correctly and includes the correct IAM permissions” (Handling message failures). The console’s Dead lettering tab has Grant publisher role and Grant subscriber role buttons; scripted and Terraform setups need both bindings, which is where they are usually missed. PROJECT_NUMBER is the project’s number, not its ID.
  • The topic schema accepts null here because packet_loss_pct is declared nullable (an Avro union of null and double); some intervals can’t be measured. A wrong type, such as the string "four", is rejected at publish and never reaches the subscription.
  • To reprocess dead letters after the fix, have a small job read qos-samples-dlq-sub and call the fixed code, or publish to a separate topic. Republishing to qos-samples would deliver copies to every subscription.

Replay with seek

The dashboard’s subscriber stores a call-health score for each meeting and minute. A build deployed at 14:10 UTC divides packet loss by 100 twice, so 8% loss is scored as 0.08% and every call looks healthy. Support notices at 14:55.

After rolling the subscriber back to the previous build

gcloud pubsub subscriptions seek dashboard-sub --time=2026-10-06T14:05:00Z

Seeking to a time marks every message published before it as acked and every message after it as unacked, so Pub/Sub delivers those again.

Messages already acked can be replayed only if the subscription keeps acked messages (--retain-acked-messages) or the topic keeps messages. Turn one on before you need it. One day of samples is about 2 TB of storage, about $500 a month (page 32).

Seek a few minutes early. Seek times are approximate, and rescoring a correct minute writes the same score again.

Add subscriber processes before you seek. The replayed samples arrive on top of live traffic.

Example

Actor: the dashboard team, after rolling back to the previous build.

Input: dashboard-sub keeps acked messages for 1 day. Live traffic is 90,000 samples/s, and the subscriber’s processes handle up to 120,000/s.

Mechanism: the seek to 14:05 delivers 50 minutes of samples again, about 270 million, mixed in with live traffic. The subscriber writes each score to the row keyed by meeting ID and minute, replacing the wrong score.

Result: with 30,000/s to spare, the replay takes about 2.5 hours, and live scores lag that whole time. More processes shorten it illustrative.

Takeaway: turn on retention before an incident; roll back the bad code before you seek, then let the replay rewrite the results.
Sources: Replay overview, Subscription properties, Pub/Sub pricing (verified 2026-10-06).
Speaker notes — Replay with seek
  • Replay overview: “Seeking to a time marks every message received by Pub/Sub before the time as acknowledged, and all messages received after the time as unacknowledged.” The time is imprecise because of “possible clock skew among Pub/Sub servers” and because Pub/Sub uses the publish request’s arrival time. A seek “might take as long as a minute” to take full effect. To replay acked messages, “you must configure message retention on the topic, or configure the subscription to retain acknowledged messages.”
  • Setup command: gcloud pubsub subscriptions update dashboard-sub --retain-acked-messages --message-retention-duration=1d. Subscription retention defaults to 7 days; either subscription or topic retention can be 10 minutes to 31 days. It keeps only messages acked from then on.
  • Arithmetic: 50 min × 60 s × 90,000/s = 270,000,000 samples. Delivered again: 270M × 400 B = 108 GB = 0.098 TiB × $40 ≈ $4. If the subscriber can handle 120,000/s, it has 30,000/s to spare: 270M ÷ 30,000/s = 9,000 s = 2.5 hours to catch up, and live scores lag during that time, because replayed and live samples are delivered mixed together. More processes shorten it.
  • Retention cost: 1 day × 2.0 TB = 1,863 GiB × $0.27 = $503/month. The default 7 days would store 14 TB = 13,039 GiB, about $3,520/month. Pricing: topic retention is “the least expensive storage mechanism” when several subscriptions need replay, because it is shared.
  • The docs list seek-to-time for problems “not associated with a specific deployment event.” For a planned deploy, a snapshot is the better tool (page 31). Order matters: seeking while the bad build runs rescores everything with the same bug. The rewrite works because the write replaces a keyed row; a subscriber that added to a running total would double-count (page 21).

Snapshots

Before any new build of the subscriber that reads dashboard-sub rolls out, Cymbal Meet’s dashboard team has its release script take a snapshot of the subscription. At 11:00 the team releases a rewritten scorer. At 11:20 the team finds it has been writing wrong scores, rolls it back, and seeks the subscription to the snapshot.

the dashboard team’s release script

# 1. every release: snapshot first, then roll out
gcloud pubsub snapshots create pre-release-1100 --subscription=dashboard-sub
# 2. if the release goes wrong: roll back the build, then
gcloud pubsub subscriptions seek dashboard-sub --snapshot=pre-release-1100
# 3. once the release is good, or the replay is done
gcloud pubsub snapshots delete pre-release-1100

Step 1: a snapshot records which messages the subscription had acked at that moment, and keeps the messages needed to return there: those still unacked, and every message published after it.

Step 2: seeking to the snapshot makes every message acked since then deliverable again. Here that is the 20 minutes of samples the bad scorer handled, now delivered to the rolled-back scorer. The team doesn’t need to know the exact time the release started, and the subscription doesn’t need to keep acked messages.

Step 3: delete the snapshot when you no longer need it. It lasts at most 7 days, and the messages it keeps are billed as storage: under a cent to create here, but about $410 if kept all 7 days, because it keeps every new sample illustrative.

Takeaway: make a snapshot part of every subscriber release, so a bad release can be undone by seeking back to it.
Sources: Replay overview, Pub/Sub pricing, Quotas (verified 2026-10-06).
Speaker notes — Snapshots
  • Replay overview: a snapshot “records the acknowledgment state of all the messages within a subscription at the moment of its creation” and “retains the unacknowledged messages of the source subscription at the time of creation of the snapshot, and any messages published to the topic after the snapshot is created.” Lifetime “equals 7 days minus the age of the oldest unacknowledged message”; you can’t create one that would expire in under 1 hour. Use case: “Incorporating snapshots into your deployment process gives you a way to recover from bugs in new subscriber code.”
  • Pricing: “message storage fees are charged for storing the messages retained by the snapshot,” plus “a one-time fee equivalent to storing that backlog for seven days” (Pub/Sub pricing).
  • Arithmetic: at 11:00, dashboard-sub holds about 180,000 unacked samples (90,000/s × 2 s, page 27), the oldest 2 s old, so the snapshot can live 7 days minus 2 s. One-time fee: 180,000 × 400 B = 72 MB = 0.067 GiB; × $0.27/GiB-month × 7/30 ≈ $0.004. Replay: 20 min × 60 × 90,000/s ≈ 108M samples. Kept 7 days, stored data grows 0 → 14 TB; average 7 TB over 7 days = 49 TB-days = 45,635 GiB-days ÷ 30 = 1,521 GiB-months × $0.27 ≈ $410. The pricing page doesn’t say whether messages also kept by dashboard-sub’s acked retention are billed once or twice; don’t promise either.
  • Quota: 5,000 snapshots per project. A snapshot can be applied to any subscription on the same topic, including a new one, which is useful for testing a new subscriber on real data.

Managed Service for Apache Kafka

A different model: a cluster you size and Google runs. When it is the right choice, and how it connects to Pub/Sub.
Speaker notes — Section 5: Managed Kafka
  • What the service is, how its model differs, when to choose it, and how the two connect. Cluster operations are out of scope.

Why a team already runs Kafka

Apache Kafka is an open-source message broker that keeps messages in a log, an ordered list it stores for a set time. Cymbal Meet runs its dial-in telephony gateways, the servers that connect phone callers to meetings, in its own data centers. Since 2020 the gateways have published call statistics to Kafka, where two Kafka Streams jobs read them. Cymbal Meet’s chat moderation service also reads from Kafka, and from nothing else.

Managed Service for Apache Kafka runs Kafka clusters for you on Google Cloud, so existing Kafka producers, consumers, and Streams jobs work with it.

Kafka Streams is a library for stream processing that reads and writes Kafka topics; rewriting those jobs for Pub/Sub is a project of its own.

Put each workload on the system it already fits; neither system is better in general.

Example

Actor: the telephony team, moving its Kafka topics to Managed Kafka.

Input: the gateways, the two Streams jobs, and the moderation service, all written against Kafka.

Mechanism: each program’s configuration gets the new cluster’s address and new sign-in settings; its code doesn’t change.

Result: these programs stay on Kafka, new cloud streams use Pub/Sub, and page 40 connects the two.

Takeaway: existing Kafka code is a strong reason to run Kafka on Google Cloud.
Speaker notes — Why a team already runs Kafka
  • Keep this page short; it frames the comparison as a question of fit, which is how it comes up in practice.
  • The telephony gateways are a different fleet from the media servers that publish call-quality samples to Pub/Sub (pages 4–7); each stream stays on the broker its team already uses.

What Google manages

The telephony team sizes a Managed Kafka cluster for the call statistics. A cluster is a set of Kafka servers, which Kafka calls brokers. In Kafka, “broker” means one server, not the whole service as on page 5. Unlike with Pub/Sub, the team has a size to choose.

You set total vCPU and memory; Google chooses the broker VMs, creates them, and replaces failed ones.

Disk comes with the cluster: at least 100 GiB per vCPU by default, which you can raise per broker. Older data moves to cheaper long-term storage automatically.

Clusters span three zones (separate data centers within one region) with equal resources; clients sign in with Google credentials or with client certificates.

Topics are split into partitions, ordered slices that consumers read in parallel (page 38). On scale-up, partitions can be rebalanced onto the new brokers.

Example

Actor: the telephony team.

Input: a 12-vCPU cluster.

Mechanism: Google spreads the cluster evenly over three zones, 4 vCPU in each, and provisions disk at 100 GiB per vCPU.

Result: at least 1,200 GiB of disk, 400 GiB in each zone, and no disk for the team to create or attach.

Takeaway: Managed Kafka takes over the operations; you still decide the size.
Sources: Managed Service for Apache Kafka overview, release notes (verified 2026-10-01).
Speaker notes — What Google manages
  • The overview page still says disks aren’t configurable; the release note of 2026-08-27 supersedes it: “You can now configure the disk capacity per broker when you create a Kafka cluster and increase it later.” The docs say Persistent Disk, not SSD.
  • Rebalancing is the cluster setting “Auto rebalance on scale up” (the alternative is “No rebalance”); it balances by partition count, not traffic.
  • Runs Apache Kafka 3.7.1; minor versions aren’t upgraded automatically. Public clusters became an option on 2026-09-10. SASL = credential-based authentication (here, Google credentials); mTLS = both sides present certificates.
  • Pricing is in Data Compute Units (1 vCPU = 0.6 DCU, 1 GiB memory = 0.1 DCU), plus disk, long-term storage, inter-zone transfer ($0.01/GiB), and Private Service Connect. Default quotas per region: 5 clusters, 750 vCPU, 6,000 GiB memory, 200 TiB disk.

A log versus a queue

Cymbal Meet’s ML team wants to retrain a model on the last 30 days of call statistics while the live quality-monitoring consumer keeps running.

Kafka keeps the log of messages (Kafka calls them records); each consumer group (a set of consumers sharing the work of reading a topic) chooses its own position in it.

Pub/Sub keeps one queue per subscription; acked messages are deleted unless retention keeps them.

Example

Actor: the ML team.

Input: Kafka retention set to 35 days.

Mechanism: a new consumer group starts reading at the offset from 30 days ago.

Result: nothing to set up and nothing to republish. On Pub/Sub, the same request needs topic retention turned on in advance, or a copy of the data elsewhere.

Takeaway: Kafka stores history and lets readers move through it; Pub/Sub delivers work and expects history to live elsewhere.
Speaker notes — A log versus a queue
  • If students take one idea from this section, it is this one; the term table and the choice on the next pages follow from it.
  • Kafka’s default retention is 7 days (log.retention.hours=168), so the example assumes the team raised it.
  • Cost shape: Kafka pays to store history (broker disk and tiered storage); Pub/Sub pays per delivery, and its own retention is billed as storage.

Kafka terms and their Pub/Sub counterparts

Cymbal Meet’s Kafka and Pub/Sub teams use some of the same words, such as “topic”, for things that behave differently.

Speaker notes — Kafka terms and their Pub/Sub counterparts
  • Kafka design docs: “The consumer’s position is stored as a message in an internal topic.” Both systems keep the position on the server; the difference is that Kafka lets each group set it freely, and many groups share one copy of the data.
  • “One consumer per partition” holds for consumer groups. Apache Kafka 4.2 made share groups (KIP-932) production-ready, which let several consumers read one partition; Managed Kafka runs 3.7.1, so it doesn’t have them. Mention only if asked.
  • Adding a consumer to a group redistributes partitions; adding a subscription creates a new copy of the stream and a new delivery bill.

Choosing between them

Cymbal Meet runs both: each stream is on the system that fits its requirements.

Choose Managed Kafka when

you have Kafka code, Kafka Connect pipelines (page 40), or Streams jobs you won’t rewrite

you need a fixed set of ordered partitions, each read in full by one consumer

consumers must pick their own position in the log

you need the same Kafka interface on other clouds or in your own data centers

Choose Pub/Sub when

you’re writing new code on Google Cloud

you don’t want to size a cluster

you need push, export subscriptions, or filters

traffic is spiky

CaveatScale is on neither list. Both handle high volume.
Takeaway: choose on the model, the existing code, and whether you want to size a cluster.
Sources: Choose Pub/Sub or Managed Kafka (verified 2026-10-01).
Speaker notes — Choosing between them
  • At Cymbal Meet, Pub/Sub carries the cloud-native streams and Managed Kafka carries the telephony gateways’ call statistics, which the telephony team already owns. Running both is a normal outcome, not a compromise.

Connecting Kafka and Pub/Sub

Cymbal Meet wants the call statistics in its Pub/Sub pipelines, and chat messages delivered to a moderation service that only reads Kafka.

Kafka Connect moves data in and out of Kafka; Managed Kafka runs it for you.

A sink connector takes records out of Kafka into Pub/Sub; a source connector brings Pub/Sub messages into Kafka.

Once in Pub/Sub, the messages are ordinary: the same subscriptions, dead-letter topics, and metrics apply.

Takeaway: connecting the two is a normal steady state; each stream stays on the side that fits it.
Sources: Managed Kafka release notes, Pub/Sub import topics (verified 2026-10-01).

  • Import topics, only if asked: a Pub/Sub topic can ingest directly from Amazon Kinesis Data Streams, Cloud Storage, Azure Event Hubs, Amazon MSK, or Confluent Cloud, with no connector to run. It doesn’t cover on-prem Kafka, which is why it isn’t on the face.
