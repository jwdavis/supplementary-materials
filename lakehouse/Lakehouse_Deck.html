Architecture A: everything reads BigQuery storage

The first architecture needs no new products: leave the data in BigQuery and let the other engines talk to it. This works, today, in both directions.
Python# Spark reads and writes BigQuery directly
df = spark.read.format("bigquery") \
    .load("clearmeet_analytics.qos_events")

df.write.format("bigquery") \
    .option("writeMethod", "direct") \
    .save("clearmeet_analytics.drop_risk")
  • Reads use the Storage Read API: parallel streams, Arrow/Avro, column projection and predicate pushdown
  • Writes use the Storage Write API (writeMethod=direct) or staged GCS load jobs
  • Dataflow does the same through BigQueryIO; both directions are GA and widely used
One copy, in BigQuery-managed storage; engines meet it at an API.
Spark and Dataflow read and write BigQuery tables. Any argument for the lakehouse that starts “because Spark can’t write to BigQuery” is simply wrong — and this is the architecture to beat.
Speaker notes — Architecture A
  • This slide exists to prevent a false premise. The connector is spark-bigquery-connector; direct write goes through the Storage Write API, indirect write stages Parquet/ORC/Avro in GCS and runs a load job.
  • Direct write has real limits worth naming: it cannot set partitioning/clustering options on write, so indirect write is still common for table creation.

Architecture B, and the real question

The second architecture moves the storage layer out: files in Cloud Storage, in a format every engine can open directly. Both architectures work. They fail differently.
The question this deck answers is not “is Iceberg good?” It is: is the API the right boundary, or is the file? Sections 2–4 give you what you need to answer that; Slide 38 answers it.

Recap: two architectures, and the hybrid

First attempt at Architecture B: just put the files in a bucket

Before reaching for Iceberg, try the obvious version of Architecture B. ClearMeet writes qos_events straight to gs://clearmeet-lake/qos_events/ as Parquet — 850 files a day, 180 GB — and points every engine at the directory. This is the naive lake, and it is what Iceberg exists to fix.
  • Nothing defines the table. “The table” is whatever a directory listing returned at that instant. The 14:02 dashboard query lists mid-write and picks up a half-written file — so COUNT(*) twice in a row gives two answers, with no error
  • Nothing defines the schema. Two files can disagree about columns and no component arbitrates between them
  • Nothing knows what is inside. To answer org_id = 4471, a reader must open files to discover what they hold
In Architecture A, BigQuery decided all three of these. Moving the files to a bucket didn’t just relocate the data — it discarded the component that answered these questions, and put nothing in its place.
Speaker notes — First attempt at Architecture B
  • Be explicit about where this slide sits in the argument, because it is easy to mistake for a third architecture. It is not. This is Architecture B built naively — files in a bucket, no table format, no catalog. Slides 8 and 9 establish what breaks; Slides 10–14 add Iceberg to fix the format problems; Section 3 adds the catalog; Section 5 fixes the security problem. Only after all of that is Architecture B a fair comparison against A.
  • Provenance, if asked: the files come from ClearMeet’s existing telemetry pipeline, which previously streamed into BigQuery and is now pointed at a bucket instead. Nothing exotic produced them.
  • The demo question to ask the room: what does SELECT COUNT(*) return twice in a row during a write? Two different numbers, no error. Silent nondeterminism is the worst failure mode there is, and it is the one that makes the naive lake unusable in production rather than merely inelegant.
  • Resist fixing anything yet. Students will propose marker files, manifest text files, or writing to a temp prefix and renaming. Note the proposals and say Iceberg is the industry’s worked answer to exactly these.

The naive lake’s third problem: access control

Same naive lake, now the security question. In Architecture A, ClearMeet granted BigQuery roles and was done. Here three engines open files themselves, so permission has to be granted on the bucket — and a bucket is the wrong shape for the thing being protected.
  • The grant is too coarse. roles/storage.objectViewer is the natural grant, and it covers every object under the bucket — so access to the telemetry table hands over finance/ too
  • The shape is wrong. Bucket IAM is organized by path; the thing you want to authorize is a table. Approximating tables with prefixes is brittle and breaks the moment a table’s files move
  • The controls don’t follow the data. BigQuery’s column-level security and masking are enforced by BigQuery. An engine reading Parquet directly never consults them
Direct file access is Architecture B’s whole point and its central risk, in one sentence. Section 5 solves this with table-level IAM and credential vending — but bank it now as a real cost of B.
Speaker notes — The naive lake’s third problem: access control
  • Naming the problem here, and solving it in Section 5, keeps the honest-accounting frame intact: the deck states B’s costs before its benefits.
  • Common instinct to head off: per-prefix bucket IAM. It is brittle, and it still bypasses whatever the table policy says.

Iceberg answers the first two; the catalog and IAM answer the third

The naive lake failed three ways: no defined table, no schema of record, no usable access control. Iceberg is a metadata layer written beside the data files, and it fixes the first two. Hold the third — it needs the catalog (Section 3) and table IAM (Section 5).
  • An explicit file list replaces the directory listing. A reader is told which 850 files are the table, so a file being written isn’t in it — and all 850 become visible in one step
  • A schema of record, tracked by column id, so two file vintages can’t disagree about what a column means
  • Per-file statistics, so a reader knows which files could hold org_id = 4471 without opening any of them
  • A snapshot history, which is what makes time travel and safe concurrent writes possible
Iceberg does not move or re-encode your data. The Parquet files are untouched; the metadata beside them is what turns a directory into a table with a defined current state.
Speaker notes — What Iceberg adds, and what it doesn’t
  • The sentence to repeat all module: the files are ordinary Parquet; the metadata is the table.
  • Iceberg is one of three open table formats (Delta Lake and Hudi are the others). Google Cloud’s lakehouse is built on Iceberg; that is what this deck teaches.
  • Spec: iceberg.apache.org/spec

The metadata Iceberg writes beside your data

Three tiers of metadata (boxes 1–3 below) describe one tier of data (box 4, your unchanged Parquet). Each tier names the next and adds detail: metadata.json says which snapshot is current, the manifest list names that snapshot’s manifests and the partition each covers, and each manifest lists actual data files with per-column value ranges. Reading left to right narrows from “the whole table” to “these specific files.”
Three tiers, one job: let an engine decide which files it must open before opening any of them.
Speaker notes — The metadata Iceberg writes beside your data
  • The per-file bounds are the payoff and are used on the next slide; make sure the org_id ranges land before advancing.
  • File counts and sizes are illustrative; they depend on writer config and compaction. The shape of the metadata is the teaching point.
  • Manifests are Avro; data files here are Parquet. Lakehouse for Apache Iceberg supports Parquet only for data files.
  • Spec: iceberg.apache.org/spec#table-metadata

Why that structure pays: skipping twice before reading

Because each metadata tier carries the value ranges of the tier below it, a reader can rule out work in two passes: first discard whole manifests whose partition can’t match, then, inside the survivors, discard individual data files whose org_id range can’t contain 4471. Both decisions are made from metadata alone.
SQLSELECT org_id, AVG(audio_mos) AS mos FROM qos_events
WHERE DATE(event_ts) = '2026-07-29' AND org_id = 4471;
Your clustering lesson in an open format: bounds are only tight if the writer sorted on that column. Unsorted writes give every file the full range and pruning quietly does nothing.
Speaker notes — Why that structure pays: skipping twice
  • “Pruning manifests” means step 1 literally: the manifest list has partition ranges per manifest, so whole manifest files are skipped before any file-level work. Say it that way; the two-level structure is the reason Iceberg scales to millions of files.
  • Explicit bridge: BigQuery clustering ↔ Iceberg sort order + per-file bounds. Same physics, different bookkeeping.
  • “1 of 850” is illustrative and assumes a sort on org_id.

The commit: how 850 files appear at once

This is the fix for the half-written file on Slide 8. A writer never edits existing metadata: it writes its data files, then writes a new metadata.json alongside the old one. Neither is visible yet, because “the table” means whichever metadata file the pointer currently names.
  • Committing is moving that one pointer from v3 to v4 — a single atomic step. Before it, readers see none of the new files; after it, they see all 850. There is no moment at which they see some
  • The move is conditional: swap to v4 only if the pointer still says v3. If another writer got there first, this writer’s base has moved, so it retries against the new version rather than overwriting that writer’s work
Readers keep the snapshot they loaded and are unaffected until they refresh. That is how a Dataflow job and a BigQuery query run during the same write and both see a consistent table.
Speaker notes — The commit
  • Provenance question students will ask: the data comes from ClearMeet’s existing telemetry pipeline, the same one from the Ingestion deck — it is now writing Iceberg files instead of streaming into native storage. Nothing mystical produced 850 files.
  • One mechanism, three benefits: atomicity, time travel, safe concurrency.
  • Optimistic concurrency, not locking. Heavy multi-writer contention shows up as commit retries; that is expected behavior, not an error.
  • Spec: “it commits by swapping the table’s metadata file pointer from the base version to the new version.” iceberg.apache.org/spec

Schema evolution: how a column is added without a rewrite

Q3: ClearMeet adds network_type to the QoS payload. In the naive lake, old files lack the column, so you either rewrite all 16 TB or make every query handle both file layouts itself. Iceberg does neither.
  • The mechanism is column ids. The schema assigns every column a permanent numeric id, and each Parquet file records which ids it contains. Names and positions are just labels on top of those ids
  • Adding a column writes a new schema with a new id (here, id 8). No existing file mentions id 8, so when a reader is asked for it and the file doesn’t have it, the answer is defined: NULL
  • Renaming changes the label attached to an id. The id is unchanged, so every existing file still resolves — which is why a rename is a metadata edit and not a 16 TB rewrite
  • Partitioning can change going forward. Old files keep the spec they were written under and still read correctly; the manifest records which spec each file used
One reader, one schema, two file vintages — resolved by id at read time. This is the biggest day-to-day difference from a hand-rolled Parquet lake.
Speaker notes — Schema evolution: adding a column without a rewrite
  • Contrast with Hive-style tables where column position mattered and a rename broke every reader — that is why column ids exist.
  • Partition evolution is useful and confusing: old files keep the old spec, so a query spanning the change reads two layouts. Iceberg handles it; the old data is not reorganized.
  • Docs: iceberg.apache.org/docs/latest/evolution

ArchitecturesFormatCatalogEnginesGovernance
Speaker notes — Section 3: The catalog
  • Section 2 ended on a deliberate gap: the format defines the table, but something must hold the current-metadata pointer and arbitrate changes to it. This section is that something.

What a catalog is for

Iceberg defines the metadata; it doesn’t say who keeps it. A catalog is the service that does three jobs no file in a bucket can do — and every engine must consult the same one.
  • 1 · It resolves names. Engines ask for telemetry.qos_events, not a metadata path. The catalog turns a table name into the location of its current metadata — so nobody hard-codes bucket paths, and tables can move
  • 2 · It arbitrates commits. The pointer swap from Slide 13 must be compare-and-set: move to v4 only if it still reads v3. Object storage gives you atomicity per object but no arbitration between writers, so two writers can each overwrite a pointer file and the second silently erases the first
  • 3 · It is where authorization lives. Because every engine must ask the catalog before reading a table, it is the one place that can decide whether this caller may — the answer to Slide 9, and the subject of Section 5
Skip the catalog and “several engines can write” quietly means “any engine can lose a commit without being told.”
Speaker notes — What a catalog is for
  • Students with on-prem Iceberg will name Hive Metastore or a JDBC catalog — correct, and exactly what they no longer have to operate.
  • This is why a hadoop-type catalog pointing straight at a bucket is unsafe for concurrent writers, which is a common student instinct.

Google’s catalog: the Lakehouse runtime catalog

Traditionally you’d run a Hive Metastore or a JDBC catalog to do those three jobs. Google’s answer, and the core service of Lakehouse for Apache Iceberg, is the runtime catalog: the same role, operated for you. Google calls it “a centralized, serverless metadata service that acts as the single source of truth.”
  • Serverless and regional. You create catalogs, not servers — there is no metastore instance to size, patch, or keep available
  • Hierarchy: catalog → namespace → table. A namespace is Iceberg’s equivalent of a BigQuery dataset
  • It speaks the Apache Iceberg REST Catalog API, the open standard — so Spark, Flink, and Trino connect with their stock Iceberg client and no Google-specific catalog driver
One catalog, two front doors: the open REST endpoint for open-source engines, and native four-part-name access from BigQuery. Same tables, same metadata, same IAM — not two systems to keep in sync.
Speaker notes — Google’s catalog: the Lakehouse runtime catalog
  • Naming: the host is biglake.googleapis.com and roles are roles/biglake.*, while the product is “Lakehouse for Apache Iceberg.” Warn them so the mismatch doesn’t read as an error.
  • Endpoint to write down: https://biglake.googleapis.com/iceberg/v1/restcatalog.
  • Docs: How Lakehouse for Apache Iceberg works

Naming: the four-part name

The same table has two names — one from BigQuery, one from an Iceberg client — and they line up piece for piece.

  • The catalog sits where a dataset would normally sit; the namespace follows it
  • Backticks are required — this is not a dataset reference

Speaker notes — Two Iceberg table types, and who owns the metadata
  • Lead with the organizing fact and let the rest follow from it: whoever owns the metadata is the only one who can safely change it. BigQuery owns a managed table’s metadata, so every write must enter through a BigQuery API. The runtime catalog owns a catalog table’s metadata, so any Iceberg-aware engine may commit to it directly.
  • Row 4 needs the two paths said out loud, because they sound contradictory. An open-source engine writing a managed table sends rows to BigQuery over the Storage Write API and BigQuery writes the files — the docs call this “read/write interoperability with BigQuery Storage API.” The same engine pointing a stock Iceberg library at the bucket gets read-only, because writing files behind BigQuery’s back corrupts the metadata BigQuery owns.
  • Terminology to be strict about all module: Google’s name is Apache Iceberg managed tables (formerly “BigLake tables for Apache Iceberg in BigQuery”). Never say bare “managed table” — students hear “a table Google manages,” which describes native tables too. The other type has no shorter official name than “Lakehouse runtime catalog Iceberg table”; this deck shortens it to “catalog table” after this slide, and says so here.
  • Verified 2026-08 against the table-types page. BigQuery write to catalog tables is Preview, and Google-managed optimization for catalog tables is also Preview. Both are likely to move; re-check both cells before delivery.
  • How the Preview write path actually works, since it is easy to get wrong: it is ordinary BigQuery DDL and DML on the four-part name — CREATE TABLE `project.catalog.namespace.table` (…), then INSERT/UPDATE/DELETE/MERGE. It is gated on table options, and the docs state that a table created from BigQuery has BigQuery DML and automatic table management enabled by default. A table created by Spark, Trino, or the REST API needs those options set before BigQuery can write it.
  • The two CREATE TABLE statements look contradictory side by side; they are not. Both are BigQuery SQL, and the difference is which table type each one makes:
      managed — CREATE TABLE ds.t (…) WITH CONNECTION DEFAULT OPTIONS(file_format='PARQUET', table_format='ICEBERG', storage_uri='gs://…')
      catalog — CREATE TABLE `proj.catalog.namespace.t` (id int, data string);
    The managed statement must name a bucket and a connection because no catalog exists to hold that information — BigQuery reaches Cloud Storage itself, using the connection’s service account. The catalog statement needs neither: the catalog was created with a warehouse location and its own service account, so the table inherits both. Count the name parts to tell which one you are looking at — three means managed, four means catalog.
  • Stale-doc warning for anyone who researches this themselves: the older BigLake-metastore page still lists “you can’t create or modify tables… using BigQuery DDL or DML” as a limitation. That is superseded by the current Lakehouse docs. Expect students who Google it to arrive with the old sentence.

Creating an Apache Iceberg managed table

ClearMeet’s analysts own qos_events and write it with SQL, so BigQuery should own its metadata. That makes it an Apache Iceberg managed table: the BigQuery experience, with the bytes in your own bucket.
SQLCREATE TABLE clearmeet_analytics.qos_events (
  event_ts    TIMESTAMP,
  org_id      INT64,
  meeting_id  STRING,
  audio_mos   FLOAT64)
PARTITION BY DATE(event_ts)
CLUSTER BY org_id
WITH CONNECTION DEFAULT
OPTIONS (
  file_format  = 'PARQUET',
  table_format = 'ICEBERG',
  storage_uri  = 'gs://clearmeet-lake/qos_events');
  • Three options make it Iceberg: file_format, table_format, and storage_uri — the bucket path where BigQuery writes the /data and /metadata folders
  • WITH CONNECTION is required for this table type: it names the service account BigQuery uses to reach that bucket. No catalog is involved here, so BigQuery must be told the bucket and the identity — a runtime catalog table needs neither, because the catalog holds both
  • PARTITION BY and CLUSTER BY behave as in the Storage Optimization deck
  • Full DML and the Storage Write API are supported
The DDL you already know, plus three options and a connection — and the bytes land in a bucket you own, in files other engines can read.
Speaker notes — Creating an Apache Iceberg managed table
  • WITH CONNECTION DEFAULT uses the project’s default cloud resource connection; a named connection works too. Either way its service account needs object access to the bucket — and the docs warn that making the bucket inaccessible to that service account can cause data loss.
  • Only PARQUET is supported for data files; this is Iceberg V2.
  • Limitations worth naming before anyone plans a migration — not supported: JSON, GEOGRAPHY, RANGE, BIGNUMERIC, INTERVAL columns; rename, copy, clone, and table snapshots; materialized views and authorized views; CDC updates; TRUNCATE TABLE; extract jobs; row-level security. Column-level access control is supported — get that pair the right way round, it comes up constantly.
  • Concurrency limit that surprises people: only one mutating DML statement at a time per table; the rest queue.
  • Docs: Apache Iceberg managed tables

Who compacts an Apache Iceberg managed table

ClearMeet streams 5B rows a day in. A streaming writer commits every few seconds and each commit writes its own files, so the table accumulates thousands of small ones — and reading it then means thousands of file opens for the same bytes. Somebody has to rewrite them; for this table type that somebody is Google.
  • Compaction and clustering. Background jobs rewrite the small files into fewer large ones and re-sort rows on the clustering columns, restoring the tight per-file org_id bounds Slide 12 pruned on
  • Garbage collection. When a snapshot expires, the files only it referenced become unreachable — but still sit in your bucket accruing storage charges. GC deletes them
  • What this costs you. Rewriting terabytes is real compute, billed in Data Compute Units (DCUs) per second, separately from your queries. Table maintenance is metered and appears whether or not anyone queried the table
Same bargain as the storage optimizer in the Architecture deck, now on files in your own bucket: you stop scheduling compaction, and a maintenance line appears on the bill.
Speaker notes — Who compacts an Apache Iceberg managed table
  • Tie back hard: they met the vacuum-you-never-run for native tables. Same idea, now on files they can list and watch change.
  • Say the causal chain out loud rather than listing features: streaming commits → many small files → more file opens per query and looser per-file bounds → compaction rewrites and re-sorts → fewer opens, tighter bounds. Every item on this slide is a link in that chain.
  • Verbatim from the docs: “Iceberg managed tables perform automatic table management, including compaction, clustering, garbage collection, and BigQuery metadata generation/refresh… Compute resource usage for table management is billed in Data Compute Units (DCUs) over time, in per second increments.” The docs do not define a DCU further — don’t invent a slot equivalence if asked; point at the pricing page.
  • Second billing gotcha worth naming: load and export operations on these tables (including EXPORT TABLE METADATA, Slide 30) use Enterprise edition pay-as-you-go slots, which standard BigQuery tables are not charged for.
  • This automatic management is the single strongest argument for an Apache Iceberg managed table over a runtime catalog table, and it returns on the Dataflow slide, where a catalog table’s compaction is the customer’s job unless they opt into the Preview.
  • File sizes on the diagram are illustrative; Google doesn’t publish target file sizes and they vary with the writer and the table.
  • Docs: Apache Iceberg managed tables

BigQuery: querying the lake and joining native tables

The original question, answered across both storage layers: which orgs had poor call quality yesterday, and what did the model predict? One query, no copies.
SQLSELECT o.name, AVG(q.audio_mos) AS mos, AVG(r.risk_score) AS predicted_risk
FROM `clearmeet-prod.clearmeet_lake.telemetry.qos_events` AS q
JOIN `clearmeet-prod.clearmeet_lake.features.drop_risk`   AS r USING (meeting_id)
JOIN `clearmeet_analytics.orgs`                           AS o USING (org_id)
WHERE DATE(q.event_ts) = '2026-07-29'
GROUP BY o.name HAVING mos < 3.5;
  • Two catalog tables (four-part names) joined to a native BigQuery table in one query
  • Slots, shuffle, and the execution plan work exactly as the Query Performance deck taught
  • No export and no copy between the lake and the warehouse
The payoff for the analytics team: lake tables are just tables. The four-part name is the only new thing an analyst has to learn.
Speaker notes — BigQuery: querying the lake
  • Read the result row aloud: Acme had poor measured quality and the model flagged it. Result values are illustrative.

Dataflow: three destinations, three different deals

Dataflow already writes BigQuery well through BigQueryIO. Sending the same pipeline to a runtime catalog table changes who owns compaction; sending it to an Apache Iceberg managed table does not.
Python# writing a runtime catalog table
(pipeline
 | beam.io.ReadFromPubSub(subscription=SUB)
 | beam.Map(score)
 | beam.managed.Write(
     beam.managed.ICEBERG,
     config={"table": "features.drop_risk",
       "catalog_name": CATALOG,
       "triggering_frequency_seconds": 60,
       "catalog_properties": {
         "type": "rest", "uri": REST_URI,
         "warehouse": WAREHOUSE,
         "header.Authorization": f"Bearer {token}",

triggering_frequency_seconds is the knob that matters: it sets how often Beam commits, and every commit writes files. Commit every 20 s for freshness and you generate small files all day.
  • What it buys: the output files are an open Iceberg table other engines read directly, without going through BigQuery; the sink is portable across Beam runners
  • What it costs: on a runtime catalog table, compaction is your job — you schedule Iceberg’s rewrite_data_files, or opt into Google-managed table management while it is Preview
  • What doesn’t change: if the destination is an Apache Iceberg managed table, Dataflow writes it through the Storage Write API exactly as it writes a native table — and Google still compacts it. The lakehouse changes nothing about that path
  • The honest verdict: if BigQuery is the only consumer, none of this is an upgrade over BigQueryIO
Speaker notes — Dataflow: does the lakehouse buy it anything?
  • The honest answer to “is there a benefit to the lakehouse for Dataflow?” is: only if something other than BigQuery reads the output, or you need runner/vendor portability. Say that plainly.
  • Head off the contradiction students will raise from Slide 26 — “I thought Google did the compaction.” It depends entirely on who writes the files. Writing an Apache Iceberg managed table, rows enter through the Storage Write API and BigQuery writes and later compacts the files. Writing a runtime catalog table, Dataflow writes the Parquet and commits to the catalog itself, so nothing in BigQuery is watching that table. Google-managed table management for catalog tables exists but is Preview (opt-in via table options).
  • CALL lake.system.rewrite_data_files('features.drop_risk') from Spark is the usual manual compaction answer for runtime catalog tables.
  • Beam’s managed.ICEBERG config keys map onto the Spark settings on the next slide. Note the auth headers are real requirements, and the docs warn the bearer token “expires in 1 hour” — production pipelines need a refreshing credential, not a pasted token.

Reaching an Apache Iceberg managed table from Spark

ClearMeet keeps qos_events as an Apache Iceberg managed table, so BigQuery owns its metadata. The ML team has two ways in, and they are not equivalent.
  • 1 · Through BigQuery’s APIs. The Spark connector reads with the Storage Read API and writes with the Storage Write API. Rows go through BigQuery, so the metadata BigQuery owns stays correct. This path is live and read-write
  • 2 · Straight at the files. BigQuery publishes an Iceberg V2 snapshot into the table’s /metadata folder; a stock Iceberg client reads it as an ordinary Iceberg table. This path is read-only, and shows the table as of the last export
SQL-- publish a snapshot for path 2
EXPORT TABLE METADATA
FROM clearmeet_analytics.qos_events;
Path 2 is read-only and lagging. Never let another engine write these files: the docs are blunt — the table “fails a consistency check and becomes unreadable… There is no self-serve way to recover.”
Speaker notes — Reaching an Apache Iceberg managed table from Spark
  • This slide exists to kill the sentence “open-source engines can only read managed tables.” That is true of one of the two paths. Through BigQuery’s Storage APIs, Spark and Dataflow read and write these tables — the docs call it “read/write interoperability with BigQuery Storage API.” Only the direct-file path is read-only.
  • The rule that generates both answers: BigQuery owns this table’s metadata, so any write must enter through a BigQuery API. Path 1 does; path 2 doesn’t, so path 2 cannot write.
  • Freshness on path 2: schedule the export with a normal scheduled query — bq query --schedule='every 24 hours' 'EXPORT TABLE METADATA FROM …' — or enable per-project metadata auto-refresh, which updates the snapshot on each table mutation. Even then, the docs note metadata “might not contain data that was streamed… within the last 90 minutes.” Treat that as a real freshness budget.
  • Cost footnote: EXPORT TABLE METADATA uses Enterprise edition pay-as-you-go slots, unlike exports on standard BigQuery tables.
  • Third path, worth one sentence if someone asks about Spark reading BigQuery-owned tables through an Iceberg catalog interface: there is a separate custom BigQuery Iceberg catalog (BigQueryMetastoreCatalog) distinct from the REST catalog endpoint. Out of scope here; mention it exists so nobody thinks the REST endpoint serves managed tables.
  • The lag on path 2 is the strongest practical argument for a runtime catalog table when a non-BigQuery engine is a first-class writer.
  • Docs: Apache Iceberg managed tables

Credential vending

Slide 9 left ClearMeet with a bad choice: grant the bucket or grant nothing. With vending on, engines get no bucket grant — they ask the catalog and receive a token scoped to one table.
  • Without vending, every user or engine service account needs a direct bucket grant of its own — roles/storage.objectViewer to read, roles/storage.objectUser to write — which is exactly the too-wide, standing access Slide 9 objected to
  • With vending, the engine sends X-Iceberg-Access-Delegation: vended-credentials; the catalog checks the caller’s IAM on the table and mints a short-lived storage token downscoped to that table’s paths. Callers hold only roles/biglake.viewer or editor — no bucket grant at all
Table-level policy enforced at the storage layer, with nobody holding standing bucket access. This is what makes direct file access governable.
Speaker notes — Credential vending
  • The catalog’s auto-provisioned service account holds roles/storage.objectUser on the bucket; that is the identity vended tokens are downscoped from. It is the only principal with standing bucket access, which is the whole point.
  • Engine service accounts need roles/biglake.editor for a write-scoped credential; roles/biglake.viewer suffices for reads.
  • The exact contrast, verbatim from the setup docs — without vending, reads need roles/biglake.viewer plus roles/storage.objectViewer, and writes need roles/biglake.editor plus roles/storage.objectUser. With vending, the storage roles drop off the user entirely.
  • Credential vending requires the multiple-bucket (bl://) catalog type from Slide 20; the legacy single-bucket (gs://) type is discouraged for new projects.
  • Vending mode is chosen at catalog creation (the option parked on Slide 20).
  • Docs: Credential vending

Finding the table: Knowledge Catalog

ClearMeet now has standard tables, Apache Iceberg managed tables, and runtime catalog tables across three namespaces. A new analyst asks the inevitable question: where is the QoS data?
  • Knowledge Catalog harvests metadata automatically from BigQuery, Cloud Storage, and lakehouse tables — no registration step
  • Entries describe assets; aspects attach your own metadata (owner, sensitivity, domain) from reusable aspect types
  • It also carries lineage and data-quality signals, and supports search across the estate
The runtime catalog answers where are this table’s files. Knowledge Catalog answers what exists, who owns it, where it came from. Different jobs, similar word.
